# 04_SDK_SPEC.md — SDK 规格（设计原则 / API / 状态机 / 移植指南）

> 本文件是"怎么写上位机软件"的**规格书**；`03_INTERFACE.md` 是"设备怎么应答"的**协议书**。
> 两份一起看：`03` 告诉你发什么、收什么；`04` 告诉你代码怎么组织才不会出 bug。
>
> 已经给出**两套可直接运行的实现**，都可以当参考或直接用：
> - `python/arm_sdk.py` + `python/arm_fk.py`（脚本 / 后台服务 / 测试）
> - `web/arm_sdk.js`（浏览器 / Electron，Web Serial）
>
> 两者**行为一致**，且二进制帧与 CRC 已做过**跨语言逐字节对拍**（见 §9）。

## 1. 设计原则（六条，违反必出 bug）

| # | 原则 | 为什么 | 代码落点 |
|---|---|---|---|
| 1 | **行尾由 SDK 强制追加，业务层无从违反** | "下发了没响应"最常见的原因就是漏 `\r\n` | `send_command()` / `sendCommand()` 内 `cmd + "\r\n"`；并**拒绝**传入自带行尾的字符串 |
| 2 | **按"提示符"分帧，不按字节数、不靠超时猜** | 设备每条命令处理完打印 `> `（无换行），是天然结束标记 | 文本累积到 `\r\n> ` 即切一帧 |
| 3 | **异步行必须分流** | `TM `/`  Feedback:`/`  Pose:`/`[RUN]` 是设备随时吐的，混进响应会污染解析 | `is_async_line()` / `isAsyncLine()`；分流到回调 |
| 4 | **"读失败"如实上报，禁止兜底** | 固件读不到位置时**拒绝运动**；上位机若沿用旧值，会掩盖真故障 | `pose()` 返回 `None`/`null`；`pos == -32768` → `None` |
| 5 | **同一时刻只允许一条命令在途**（SDK 内部串行化） | 文本命令的回包**没有请求 ID**，并发会张冠李戴 | 内部锁/ Promise 链 |
| 6 | **不臆造命令与数值** | 命令以 `03_INTERFACE.md` 为准；几何以 `02_MECHANICAL.md` / `arm_fk` 为准 | 不自造 `MOVE`/`SETPID`；不自己估算连杆长度 |

## 2. 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│ 业务层（UI / 业务逻辑）                                       │
│   - 面板、3D 视图、曲线、调参向导                              │
│   - 只调用 ArmSDK 的方法，**不拼命令字符串**、不管行尾/超时     │
└───────────────────────────┬─────────────────────────────────┘
                            │  ArmSDK.status() / moveCart() / ...
┌───────────────────────────▼─────────────────────────────────┐
│ SDK 层（python/arm_sdk.py · web/arm_sdk.js）                 │
│   ├ 命令层  : 一行文本 ⇄ 一个 Response（含 ok/kind/lines）      │
│   │          解析器：status/joint/fk/limits/pid/params/tm      │
│   ├ 分帧层  : 提示符分帧 + 异步行分流 + 二进制帧状态机          │
│   ├ 协议层  : CRC16 / 组帧 / 解帧 / SEQ 配对 / 错误码           │
│   └ 传输层  : SerialTransport（pyserial）/ Web Serial          │
└───────────────────────────┬─────────────────────────────────┘
                            │  字节流
┌───────────────────────────▼─────────────────────────────────┐
│ 设备：STM32 USART6 @115200 8N1 无流控                        │
└─────────────────────────────────────────────────────────────┘

旁路（纯计算，不碰串口）：
  python/arm_fk.py  ·  web/arm_sdk.js 的 FK/IK 部分
    - 与固件逐位一致的 FK/IK
    - 3D 显示用
    - 下发前的本地预校验（ikChecked）
```

**关键**：`arm_fk` 与传输层**完全解耦**。3D 视图可以只用 FK，不需要串口；
UI 拖拽预览可以用 `ikChecked` 先判断可行性，再决定要不要真的下发。

## 3. 响应分帧规格（最重要的一节）

### 3.1 设备输出的真实字节流

发送 `p 0\r\n` 后，串口上实际出现：

```
p 0            ← 固件逐字符回显（在 USART6 RX 中断里，每收 1 字节回 1 字节）
\r\n           ← Console_TryReadLine 收到 '\r' 时打印
  J1: raw=...  ← 命令输出（本行以 \r\n 结束）
>              ← 提示符 "> "，**不带换行**
```

紧接着发下一条命令 `s\r\n`，字节流继续追加：

```
> s\r\n        ← 注意：提示符的 "> " 和下一句的回显 "s" 是**相邻**的
  +----+...    ← s 的输出
> 
```

### 3.2 正确算法

```
缓冲区 buf
收到一个字节 b:
    buf += b
    若 buf 以 "\r\n> " 结尾:      # 提示符 = 一条响应结束
        取出 buf[0 : -4]，清零 buf
        交给 _on_line() 逐行处理
```

### 3.3 为什么**不能**用别的方法

| 错误做法 | 后果 |
|---|---|
| 找第一个 `"> "` | `lk` 诊断输出里有 `-> 线上 0 字节: ...` 这类行，会被误当成提示符 → 提前截断 |
| 读固定字节数 | 输出长度随命令变化（`LP` 上千字节，`p 0` 一行）；注定要么截断要么阻塞 |
| 只用超时（读到静默就认为结束） | 设备有 30 Hz 遥测/日志在吐字节，"静默"永远等不到 → 每次都超时；反过来无遥测时又白等 |
| 用一个正则匹配整段 | 输出格式不统一（表格 / 键值 / 自由文本），正则必然漏 |

### 3.4 行过滤规则（拿到响应后）

| 行 | 处理 |
|---|---|
| 等于本次命令（`strip` 后比较） | **丢弃**（回显） |
| 等于 `>` 或 `> ` | 丢弃（提示符残留） |
| 以 `[RUN]` / `  [RUN]` 开头 | 丢弃（运行日志，已分流） |
| 以 `TM ` 开头 | 丢弃（遥测，已分流） |
| 空行 | 丢弃 |
| 其它 | 保留到 `Response.lines` |

### 3.5 结果判定（关键词，顺序敏感）

判定顺序：**急停 > 安全拦截 > 失败 > 用法错误 > 成功**。

| kind | 关键词 | UI 应表现 |
|---|---|---|
| `estop` | `E-STOP` | 红色告警条 + 禁用所有运动按钮 |
| `safety` | `path check fail`、`path unsafe`、`UNSTABLE`、`Another loop is active`、`read FAILED`、`READ FAIL`、`no reply`、`out of joint limits`、`NOT met`、`too large`、`offline` | 黄色提示 + 原文（说明"为什么没动"） |
| `usage` | `Usage:` | 说明"参数写错了"（通常是 SDK/UI 的 bug） |
| `fail` | `FAIL`/`failed`、`reject`/`Rejected`、`NACK`、`unreachable`、`IK failed`、`cancelled`、`Not `、**`Unknown command`**、**`Unknown pose`**、**`must be`**、**`Cannot `**、**`Error:`**、`Invalid`、`not calibrated` | 红色 toast + 原文 |
| `ok` | `OK`、`Saved`、`Stopped`、`complete`、`set to`、`done`、`started`、`accepted` | 绿色/无提示 |
| `timeout` | （SDK 判断，非关键词） | "设备无响应，检查连接 / 命令是否需要更长超时" |
| `empty` | 无输出且无关键词 | 见 §4.3：可能是"读失败"，不是成功 |

> ⚠ **回归案例（务必保留测试）**：固件未知命令打印
> `Unknown command 'x'. Type 'h' for help.`。若关键词表里没有 `Unknown command`，
> 它会掉进"有输出即成功"的兜底 ⇒ **命令根本没执行，UI 却显示成功**。
> Python/JS 两套 SDK 都已修好并有回归测试（`js_test.mjs` / `example.py`）。
> 移植到别的语言时，这几个串**必须**进失败表：`Unknown command`、`Unknown pose`、
> `must be`、`Cannot `、`Error:`。

> ⚠ **只读命令**（`p`/`f`/`s`/`L`/`LP`）通常没有关键词。有输出即视为 `ok`；
> **没有输出要特别小心**（§4.3）。

## 4. 三类"坑"的规格化处理

### 4.1 异步行的来源与分流

| 前缀 | 来源 | 触发方式 | 分流到 |
|---|---|---|---|
| `TM ` | `TelemetryPrintService` | `tm <ms>` | `on_telemetry(key, values)` |
| `  Feedback:` | `cmdRealtimeFeedback` | `pv <ms>` | `on_async(line)` |
| `  Pose:` | `cmdRealtimePoseFeedback` | `pf <ms>` | `on_async(line)` |
| `[RUN]` | `RLOG_*` 宏 | 任何错误/警告发生时 | `on_log(line)` |

⚠ **`pv`/`pf` 的行没有唯一前缀**（只有两个空格缩进 + `Feedback:`/`Pose:`），
所以分流规则是**前缀匹配整行**，不是"含关键字"。这也意味着：**别用 `pv` 做高频刷新**，
优先用 `tm`（有 `TM ` 前缀，绝对不会和命令输出混淆）。

⚠ 这些行可能在**一条命令的响应中间**插进来（例如 `g` 运动时刚好有 `[RUN]` 警告）。
SDK 已按行独立分流，所以不会破坏响应解析。

### 4.2 命令超时策略

| 命令 | 建议超时 | 说明 |
|---|---|---|
| 绝大多数（`h`/`s`/`p`/`f`/`L`/`LP`/`K`…） | **3 s** | 都是毫秒级返回 |
| `m` / `g` / `P` / `z` / `W` / `B` / `QL` / `QLC` | **30~60 s** | 内部是轨迹执行，UI 应显示"运动中"并可被 `S` 打断 |
| `Y J` / `Y 0` | **20 s** | 写舵机 EEPROM，含失力 ~0.6 s / 轴 |
| `F` | **20 s** | 写 STM32 Flash Sector 11 |
| `i` / `M a` / `R 1` / `compact` | **30 s** | `compact` 期间 CPU 冻结数秒 |
| `c`（校准） | **不适用** | 交互式阻塞，见 §6 |

> **超时不是失败**。UI 必须区分"超时（设备无响应）"与"设备明确拒绝"。
> 建议：超时后**不要自动重发**运动命令（可能已经动了），先让用户确认状态。

### 4.3 ⚠ "静默成功"与"静默改值"陷阱（本设备特有，务必处理）

#### A. 静默无输出（读失败）

固件里有三处**读失败就静默返回、什么都不打印**：

| 命令 | 固件行为 | 上位机必须 |
|---|---|---|
| `f` | `readActualEndPose()` 失败 → **一行都不打** | 输出为空 ⇒ 显示"读取失败"，**不是**"位置(0,0,0)" |
| `pf <ms>` | 同上，这一次不打印 | 曲线**断点**，不要连线插值 |
| `p J` | 单轴读失败时 `SERVO_GetPosition` 返回负值，固件**仍会打印**（raw 可能是 0/垃圾） | 用 `servo < 0` 或 raw 越界判定 |
| `s` | `pos < 0` 时打印 `0.0` | ⚠ **无法区分"真的 0.0°"与"读失败"**；要精确判定请用 `p J` 或二进制 `GET_STATUS`（有 `-32768` 哨兵） |

**规格**：`Response.kind == "empty"` 时，UI 文案为"设备无应答/读取失败"，
**禁止**渲染成 0 值。这是 `AI_BRIEF.md` 铁律 3 的具体落地。

#### B. 静默改值（钳制，命令"成功"但参数变了）

**比 A 更阴**：命令回 "OK"、`kind == "ok"`，但固件把数字改了。若 UI 只看
`ok`，用户会看到"我发了 320，臂停在 300，还提示成功"。

| 命令 | 固件打印 | 说明 |
|---|---|---|
| `a J deg` / `q` / `B` | `  J3: 320 -> 300 deg (raw 4096 -> 4095 limit)` | `clamp_angle()` 按 raw 限位钳制 |
| `m` | **什么都不打印** | 硬钳 0~300 —— SDK 已在本地抛错拦住，不要绕过 SDK 手拼命令 |
| `L J min max` | `  J1 limits set: 80 ~ 220 deg (raw 910 ~ 2503)` | min<0→0、max>360→360（这两种静默）；只有 min>=max 才报错 |

**规格**（SDK 已提供，UI 直接用）：
```python
resp = arm.move_angle(2, 320)
for c in resp.clamps():        # [{'joint':2,'joint_label':'J3','from_deg':320.0,'to_deg':300.0,...}]
    ui.warn(f"{c['joint_label']} 被限位钳制：{c['from_deg']:.0f}° -> {c['to_deg']:.0f}°", level='yellow')
```
> ⚠ `m` 的 0~300 钳制**固件不打印**，SDK 只能在发之前拦。所以 UI 里凡是要发
> `m` 的地方都必须走 `move_joints()`（Python）/ `moveJoints()`（JS），
> **不要**自己拼 `"m " + ...`。

## 5. 命令层 API 规格

### 5.1 通用方法

```
send_command(cmd, timeout=None) -> Response
    Response = { command, raw, lines, async_lines, ok, kind }
    - raw   : 未过滤原文（排错面板显示）
    - lines : 过滤后有效行（解析用）
    - ok/kind: 见 §3.5

write_raw(text)      # ⚠ 危险：不追加行尾、不等响应。仅交互式 `c` 用
send_binary(cmd, payload, timeout) -> (rsp_cmd, rsp_payload, crc_ok)
```

### 5.3 ⚠ 关节号两套约定（**必须体现在 UI 上，或直接隐藏**）

| 命令族 | J 取值 |
|---|---|
| 单轴 `t a r p z w L M T O E U` | **0~5** |
| PID `K I D N Y` | **1~6** |

**规格建议**：SDK 层统一用 **0~5**（程序员直觉），在 PID 方法内部 **+1** 转换，
并在 UI 上只显示 **J1~J6**（用户直觉）。`arm_sdk.py` 已强制校验并在传错时抛异常。

### 5.4 ⚠ 角度两套约定

| 量纲 | 范围 | 出现在 |
|---|---|---|
| **舵机度** | 0~360°（`m` 因硬钳制实际 0~300） | **`m` `a J deg` `B` `q` `L` 的入参**（以及 **二进制 MOVE_JOINTS / GET_STATUS**） |
| **关节角 rel-home** | 可正可负 | 内部 IK、`g`/`BG`/`qg` 的 `pitch`、`P 0~4`（预设位由关节角定义）、`f` 的 relhome 行、`ms`(不在本版范围) |

换算：`关节角 = JOINT_DIR[j] × (舵机度 − SERVO_OFFSET[j])`，`JOINT_DIR = [−1,+1,+1,+1,+1,+1]`。
`arm_fk.servo_deg_to_rad()` / `rad_to_servo_deg()` 就是这对换算。

> **⚠ 输入侧**：`a`/`m`/`B`/`q` 收的全是**舵机度**，不是关节角。看着像执行成功但位置
> 全错，通常就是把关节角填进了这些命令。**输出侧**才是关节角（`f`/`p` 的 relhome 行）。

**规格**：UI 的"关节滑块"和"3D 模型"应当用 **关节角（rel-home）**，
因为现场零点会漂移（可能上百舵机度），写死舵机度就会错位；
而下发 `m` 时由 SDK 换算成舵机度。

## 6. 特殊模式（UI 必须切换状态机）

| 模式 | 进入 | 退出 | UI 要求 |
|---|---|---|---|
| **急停** | 硬件 PE11 拉低 | 硬件恢复 | 全屏红条；只允许 `s`/`h`；其余命令回 `E-STOP active!` |
| **交互式校准 `c`** | `c` 回车 | `q` 退出 / `s` 保存 | ⚠ 期间固件**阻塞在主循环里**读字符，**没有提示符**；SDK 的 `send_command` **会超时**。必须切到 `write_raw()` 逐字节模式，并把回显直接显示在"校准终端"里 |
| **示教 `teach`** | `teach` | `teach exit` | 白名单命令之外的操作会**自动先退出 teach**；UI 应提示"要退出示教吗" |
| **循环中**（`W`/`B`/`BG`/`QL`/`QLC`） | 对应命令 | `S` | 期间其它运动命令会回 `Another loop is active. Use S first.` |
| **主从臂链路** | — | — | **本版上位机不涉及**，不要实现 |

## 7. PID 调参的状态机（上位机核心业务）

### 7.1 生效链（UI 必须如实体现）

```
                     ┌──────────────┐
   K/I/D/N ─────────▶│ STM32 缓存    │  掉电丢失
                     └──────┬───────┘
                            │ Y J（⚠ 该关节失力 ~0.6s，必须提示托臂）
                            ▼
                     ┌──────────────┐
                     │ 舵机 EEPROM   │  掉电保留
                     └──────┬───────┘
                            │ N J 可回读比对
   ────────────────────────────────────────
   F  ─────────────▶ STM32 Flash（存"开机自动下发的缓存值"）
   X  ─────────────▶ 恢复固件默认（只写 RAM）
```

### 7.2 状态机（UI 应显式呈现"未保存"状态）

```
  ┌──────────┐   K/I/D/N    ┌──────────────┐   Y J    ┌──────────────┐
  │ 一致     │─────────────▶│ 缓存已改      │─────────▶│ 舵机已更新    │
  │(N J 一致)│              │(与 EEPROM 不 │          │(N J 一致)     │
  └──────────┘              │  一致)        │          └──────┬───────┘
                            └──────┬───────┘                 │
                                   │ X 恢复默认                │ F 存 Flash
                                   ▼                          ▼
                              ┌──────────┐              ┌──────────────┐
                              │ 回到默认  │              │ 掉电保留 ✓    │
                              └──────────┘              └──────────────┘
```

**强制要求**
1. 每次进入"PID 面板"先 `N J`（一个都不能少）记录基线。
2. 改完值立刻把该轴标黄（"缓存已改，未烧写"），直到 `Y J` 成功。
3. `Y J` 之前弹窗：**"Jx 将失力约 0.6 秒，请托住机械臂后再继续"**，需要用户确认。
4. `X`（恢复默认）也要确认，并提示"这只是 RAM，未持久化"。
5. 面板上给出调参方向提示（见下表）。

### 7.3 调参方向（内置于 UI 提示）

| 增益 | 增大 | 减小 |
|---|---|---|
| **P** | 到点偏软、负重下沉、稳态误差大 | 高频抖动、嗡鸣 |
| **I** | 到位后缓慢下沉、反复微调 | 低频来回晃、超调、积分饱和 |
| **D** | 到点来回荡、过冲 | 高频剧烈抖动（**齿隙大的 J3 尤其敏感**） |

固件默认：`P = [16, 32, 16, 16, 16, 16]`（**肩 J2 = 32**）、`I = [4]×6`、`D = [12]×6`。

⚠ **"到点顿两下"不是 PID 问题** —— 根因是轨迹尾段流式微步，
对应参数 `#42 traj.approach_speed` / `#45 traj.handoff_deg`。UI 提示别指错方向。

## 8. 二进制协议的使用建议

**用文本还是二进制？**

| 场景 | 推荐 | 理由 |
|---|---|---|
| 参数配置、PID、诊断、低频率操作 | **文本命令** | 人类可读、日志友好、解析器现成 |
| **高频状态刷新（>2 Hz）** | **二进制 `GET_STATUS`** | 21 字节定长，无回显、无表格解析；比 `s` 省一个数量级带宽 |
| 需要精确判断"读成功/失败" | **二进制 `GET_STATUS`(bit3 / −32768) 或 `p J`** | `s` 表无法区分读失败与 0.0° |
| 与主从臂链路无关的一切 | 文本 | `0x13` 流帧是主从专用，本版不用 |

**要点**
1. 二进制与文本**共用同一个串口**。解析时必须先判 `0xAA 0x55`；
   固件侧 ISR 也是这么分流的（`0xAA` 开头的字节被协议状态机吃掉，不进文本命令缓冲）。
   ⇒ **不要发以 `0xAA` 开头的文本命令**。
2. 响应按 **SEQ** 配对（文本命令没有这个能力，所以文本必须串行化）。
3. `read_ok == 0` 或任一关节 == `-32768` ⇒ **位姿无意义**，显示"读取失败"。
4. `NACK` 的 `err` 码直接映射 UI 文案（见 `03_INTERFACE.md` §3.5），
   特别是 `5 = ESTOP`（红）、`7 = READ`（查线缆/共地）。
5. **参数读写有两个坑**：`arm_params.h` 注释里写的 `0x30/0x31` 是过时的，
   实际是 `0x40/0x41`。以 `03_INTERFACE.md` 与 `arm_control_protocol.h` 为准。

## 10. 移植到其他语言的清单

若你要用 C# / C++ / Qt / Rust / Go 写上位机，按这个顺序实现：

| 步骤 | 内容 | 验证 |
|---|---|---|
| 1 | 串口打开 115200 8N1 无流控；打开后清缓冲 | 能收到开机横幅 |
| 2 | 读线程 + 提示符分帧（`\r\n> `） | 发 `h`，能拿到完整帮助文本，且不卡 |
| 3 | `send_command` 自动追加 `\r\n`；串行化 | 发 `p 0` 能解析出 3 个字段 |
| 4 | 行过滤（回显/提示符/`[RUN]`）+ 关键词判定 | 用 `03_INTERFACE.md` §1.4 的表格做单测 |
| 5 | 异步行分流（`TM ` / `Feedback:` / `Pose:`） | 开 `tm 100`，确认响应不被污染 |
| 6 | **FK（`02_MECHANICAL.md` §3 公式）** | 零位 `(361.895,0,244.333)`、折叠位 `rho=131.39/z=3.98/pitch=150.03` |
| 7 | IK（解析 + CCD 兜底）+ 闸门 | 300 次往返误差 ≤ 1mm；`ikChecked` 三条用例符合预期 |
| 8 | CRC-16/CCITT-FALSE + 组帧/解帧 | `"123456789" -> 0x29B1`；帧 `aa 55 07 01 00 3d 7a` |
| 9 | 二进制命令（先 PING/GET_STATUS） | 收到 `0x81`/`0x82`，CRC 通过 |
| 10 | PID 三步链 + 危险操作确认 | §9.3 清单 |

⚠ 移植时**最容易错的三处**：
1. CRC 的**反射/非反射**搞反（这个协议是**非反射**、MSB-first、init `0xFFFF`）；
2. 定点编码搞反（角度/位置都是 **i16 小端 ×10**，`-32768` 是读失败哨兵）；
3. 行尾只发了 `\n` 或忘了发。

## 11. 常见问题速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 命令毫无反应 | 没发 `\r\n` | 用 SDK 的 `send_command`；检查是否自己拼了字符串 |
| 每次都要等很久 | 用固定超时而非提示符分帧 | 按 §3.2 重写分帧 |
| 响应里混进一堆 `TM ` 行 | 没做异步行分流 | §4.1 |
| 解析出的数值是 0 / 空 | 命中"静默成功"陷阱 | §4.3，显示"读取失败" |
| 运动命令"卡住"直到超时 | 该命令是长操作，或运动被 `S` 等待 | §4.2 超时表 |
| 明明点了运动但臂没动，也没报错 | 被拒的运动只体现在输出文本里 | §3.5 `safety` 类必须显示 |
| 3D 模型和实机姿态对不上 | 用了舵机度当关节角 / 零点漂移 | §5.4；先 `f` 对比数值 |
| 舵机 PID 改了没效果 | 只改了缓存 | §7.1 三步链 |
| 校准 `c` 模式下命令全部超时 | 交互式模式无提示符 | §6，切 `write_raw` |
