> 复现工具：`tools/link_latency_bench.py`｜原始数据：`outputs/latency_bench/*.json`
> 被测：STM32F407 六轴从站｜网口轮 `ARM-NET-0921A`、CAN 轮 `ARM-CAN-0918H`（同代次，已自检可比）

---

## 一、一句话结论

**按常态（p50）：网口 > CAN > 串口，是清楚的三级台阶。
按最坏情况（max）：顺序反过来 —— 串口 > 网口 > CAN。**

| 判据（ms） | 网口 UDP | CAN @500k | 串口 COM11 |
|---|---|---|---|
| **p50 常态** | **1.61** | 2.72 | 4.78 |
| p90 | **2.22** | 2.94 | 5.16 |
| **p99 尾部** | **3.40** | 6.60 | 6.32 |
| **max 最坏** | 117.66 | 179.94 | **15.26** |
| std 抖动 | 0.82 | 1.48 | **0.56** |
| **吞吐（帧/s）** | **547** | 341 | 202 |
| 600 s 内超时 | **0** | 4（0.002%） | **0** |

> 数据来源：**10 分钟六轴全动长跑**（`stream_joints`，单发单收），样本 33 万 / 20 万 / 12 万，零坏包、零拒帧。

## 二、选哪条（照你的判据对号入座）

| 你的场景 | 选 | 理由 |
|---|---|---|
| 遥操作 / 遥控器（20~50 Hz 流） | **网口** | p50 最快、p99 唯一进 4 ms、吞吐 2.7 倍于串口、零超时、无一项垫底 |
| 绝不允许掉帧 / 力控 / 碰撞敏感 | **串口** | 唯一 `max` < 20 ms（= 50 Hz 一个周期）；抖动最小；但上限只 202 帧/s |
| 长距 / 强干扰 / 车规 / 多从站 | CAN | **物理层优势，本轮桌面短距 + USB 适配器下根本没测到** |
| 两者都要（既快又稳） | 网口 + 上位机实时化 | 尾部瓶颈三条链路共有（见第四节）⇒ **换链路无效** |
| 逐点定位（`MOVE_JOINTS`） | 任意 | 91~157 ms 由**固件轨迹**决定，换链路不提速 |
| 状态轮询 / 画界面（`status`/`fk`） | 网口 | 但差距只有 1.5 倍，被 6~8 ms 读舵机压平（见三·3） |

> **综合最优 = 网口**（6 项判据拿 4 个第一，最差也是第 2）。
> **判据若是"最坏情况也不掉周期" = 串口**。

## 三、三个必须知道的坑

1. **短测的 `max` 是假象。** 150 样本时网口 `max` 只有 3.68 ms；10 分钟 33 万帧的真实 `max` 是 **117.66 ms**，且**每分钟都有一个 36~60 ms 的尖峰**。
   ⇒ 报最坏情况必须用长跑，短测的 `max` 不能拿来用。
2. **只看 p50 会选错。** 按 p50 选 → 网口/CAN；按 max 选 → 串口。选型前必须问清楚"**要常态还是要最坏情况**"。
3. **拿 `status`/`fk` 比链路会被压平。** 这两条命令要先花 **6~8 ms 读六轴舵机**（三条链路都得付、与链路无关），所以看起来"网口只比串口快 1.5 倍"。
   ⇒ 真实链路差距看 `ping`：**网口比串口快 3.5 倍**。

---

## 四、⭐ 真正的瓶颈是上位机，不是链路

- **理论值**：CAN 500 kbit/s 下一帧 8 B 的线上时间仅约 **0.25 ms**；网口 100 Mbit/s 更快。
  实测 117 / 180 ms **比理论值大 2~3 个数量级** ⇒ **不可能是链路造成的**。
- **量级吻合**：三条链路的 `max` 都落在"**若干个 Windows 调度时片（15.6 ms）**"上 ——

  | 链路 | max | ÷ 15.6 ms |
  |---|---|---|
  | 串口 | 15.26 | **≈ 1 个时片** |
  | 网口 | 117.66 | ≈ 7.5 个 |
  | CAN | 179.94 | ≈ 11.5 个 |

- ⇒ **尾部延迟由上位机的调度粒度决定**（Windows 非实时 + USB 适配器）。要真正改善尾部：**换 Linux / 提高通信线程优先级 / 提高定时器精度**，而不是换链路。
  （工具跨平台，换到 Linux 侧重跑同样两轮即可验证。）

---

## 五、两个好消息

1. **臂在动，不拖慢遥操作。** `STREAM_JOINTS` 的 ACK 只表示"这一帧被受理"，与插补/舵机侧解耦。
   六轴大幅摆动跑满 600 s 的 p50 与单轴小幅短测**几乎一样**（网口 1.92 → 1.61，反而更快）
   ⇒ **20~50 Hz 遥操作在臂满负荷运动时依然成立**（网口 547 帧/s，余量巨大）。
2. **链路对逐点定位（`MOVE_JOINTS`）没有影响。** 即使目标就是当前角、臂根本不打算动，固件也要跑完一整条 S 曲线才发 ACK；同一轮内不同链路几乎相等（1.0 倍）。

另外：三条链路 **零坏包**；长跑 **无热漂移**（舵机实测 37~43 ℃，p50 全程平直）。
网口前 3 分钟 p50 从 1.94 降到 1.53 ms —— 这是**向上收敛**（上位机 CPU/网卡/ARP 预热），不是故障。

## 六、复现（一条命令一轮）

```powershell
# 0) 烧对应固件；跑之前必须回中位（⚠ 绝不要用 `M a`，那是标定，会废掉量纲基准）
py -3 tools/flash_arm.py --link net --console-port COM11

# 1) 六轴全动 10 分钟、每 60 s 一桶（把 --link 换成 can / serial 即可跑另两条）
py -3 tools/link_latency_bench.py --link net --cmd stream_joints --motion --allow-move `
   --duration 600 --bucket 60 --motion-axis 1,2,3,4,5,6 --motion-amp 20,20,20,20,70,33 --motion-period 12

# 2) 出总表（含分桶稳定性与残桶自动剔除）
py -3 tools/link_latency_bench.py --report --cmd stream_joints
```

> ⚠ **摆动幅度不是 ±50°**：实测 ±50° 六轴全动时约 **15% 的帧被固件拒收**
> （`pose unsafe` 桌面/立柱禁区 + 单帧跳变 >25° 门限连锁）。
> 收成 **J1~J4 ±20° / J5 ±70° / J6 ±33°（周期 12 s）** 后 **0 拒帧**。
> `pose unsafe` 是**安全功能在正常工作**，不是 bug。

## 七、未测 / 别过度外推

- CAN 的**物理层优势**（差分、抗干扰、远距、多节点）本轮**没测**（桌面短距 + PCAN-USB 适配器）。
  **不要据此判 CAN 出局** —— 它输在上位机侧，不输在协议。
- 全部数据来自 **Windows 非实时 + USB 适配器**。Linux 侧数值预期不同（尾部应变好），**未实测**。
- 网口优势建立在"一帧=一数据报、无分包"上；CAN 要走 8 B 分包 + 重组，这是它常态慢一档的固件侧原因之一。
