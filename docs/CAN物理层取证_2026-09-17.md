# CAN 物理层取证与接线排查（2026-09-17 晚）

> 场景：**PEAK PCAN-USB（=`六叶树`那块，驱动走 PCANBasic）↔ 臂 `CAN PHY V1` 收发器**，
> 两侧都活着、都 500 kbit/s、臂侧 `hw init: ok`。
> 用户判断"物理层没问题（L/H 已对、已共地、以前用同一块卡测 XL320 通）"。
> **本文用与波特率/过滤器/节点号全都无关的"电平判据"把这个前提推翻：链路双向静默，物理层确凿不通。**

---

## 1. 三条硬证据（都是实测原始输出）

### 证据 A — 卡在狂发，臂的 CAN_RX 引脚一动不动（**决定性**）

```
[flood] PCAN_USBBUS1@500000  id=0x7E0 data=0000000000000000  16s ...
[flood] 入队 5188 帧 / 16.0s (约 324 帧/秒)

臂侧 cy 2500（每 1ms 采一次 CAN_RX 引脚电平，共 2500 次）:
  高 2500 次   低 0 次   跳变 0 次
  -> [总线恒定隐性] 总线上一点活动都没有
```

- 载荷刻意用**全 0**（CAN 的显性位=0，占空比最大），对端只要**电气上接在同一对线上**，
  它的 `CAN_RX` 引脚必然出现大量低电平。
- **这个判据与波特率无关**（电平不认波特率）、**与验收过滤器无关**（引脚在滤镜之前）、
  与节点号/协议全都无关 ⇒ 它只回答一件事：**卡的差分信号到底有没有走到臂的收发器。**
- 答案：**没有。**

### 证据 B — 臂在发，没有任何节点应答（指纹精确）

```
cn: test tx : 1040 帧入邮箱    test rx : 0 帧收到   peer rx : 0
    err : tec=200 rec=0 lec=3
    reg : MCR=00010050 MSR=00000C08 ESR=00980053 TSR=1C000009
```

- `lec=3` = **ACK 错**（帧发完但在 ACK 槽没等到显性）；`tec` 每帧 **恰好 +8** = 每帧错一次。
- `rec=0` 且**始终为 0** ⇒ 臂的接收侧**从来没有收到过一个位的可解释波形**（不是"收到但丢了"）。
- `TSR=0x1C000009`：`TME=111`（三个发送邮箱都空，帧确实出去了）+ `TERR0=1`（该帧报错）。
- ⚠ **ACK 是硬件行为，与上位机软件的验收过滤器无关** —— 所以"卡收不到"不能怪过滤器/节点号。

### 证据 C — 臂自己的发侧是好的（模块在驱动它的差分端子）

```
cp  : 探测前总线 MSR.RX=1      RX 脚 内部下拉仍读 11111111（被外部驱高=模块 RXD 空闲为高）
      TX 脚 推挽输出低=00000000 推挽输出高=11111111（驱动级正常）
cn  : hw init : ok    MCR.INRQ=0 / MSR.INAK=0（正常模式，已上总线）
cz  : 入邮箱=ok   tec +8   lec=3
```

- `cz` 报 `lec=3`（而不是 `lec=4/5` 位错误）⇒ **帧的每一位都被自己的位监视认可**，
  说明：模块已上电、`TXD` 确实接到了 MCU 的 `CAN1_TX`（**没有接反**）、模块内部驱动正常。
  （若 `TXD` 没接或与 `RXD` 接反，模块永远保持隐性 ⇒ 会在第一个显性位就报**位错误 `lec=4/5`**。）

## 7. `cw` —— `cp` 的盲区补丁（2026-09-17 19:10 新增）

### 7.1 `cp` 漏掉的那一段

`cp` 报了两条"正常"：**RX 脚被外部驱高**（模块上电）、**TX 脚推挽输出正常**。
但它两次读的都是**引脚自己**：

- TX 那一项是"把 PB9 设成推挽输出，再读回 PB9" —— 只证明 **MCU 的引脚驱动级没坏**，
  跟"这根线到底有没有连到收发器的 TXD"**毫无关系**；
- RX 那一项只证明"外面有个东西在驱动 PB8"，跟"收发器有没有把差分信号传上来"无关。

⇒ **`TX → 收发器 TXD → 收发器驱动总线 → 收发器 RXD → RX` 这条外环，`cp` 从来没碰过。**
而 TXD 那根线断掉时的症状，恰好就是"帧发出去了，谁也收不到"（总线恒定隐性）——
和现在看到的一模一样。UART4 那一轮已经吃过一次同样的亏。

### 7.2 `cw` 怎么做

停掉 bxCAN → 把 TX 脚当**普通 GPIO 持续驱动显性(低)** → **直接读 RX 脚**。

标准 CAN 收发器（TJA1050 / SN65HVD230 / TJA1042 …）在正常模式下，RXD 反映的是
**总线状态**；所以 TXD 拉低会让收发器把 CANH 抬高 / CANL 压低，并把结果透传回 RXD
⇒ **本机 RX 应当跟着变低**。不需要万用表，也不需要总线上有第二个节点。

### 7.3 判据

| `cw` 输出 | 含义 | 下一步 |
|---|---|---|
| 显性→`00000000`  隐性→`11111111` | **外环通** —— MCU 与收发器全部排除 | 断点只剩「卡 ↔ 模块 CANH/CANL」这一段：没接到位 / 接错端子 / 极性 / 共地 |
| 显性→`11111111`（仍是隐性高） | **外环断** —— 收发器没把 TXD 送到总线 | ① TX 那根线没接到模块的 `TX`/`TXD` ② 模块 `TX`/`RX` 丝印与实际相反 → **对调这两根** ③ VCC 跳线错（TJA1050/SIT1050 必须 5V）或器件坏 |
| 显性→`00000000`  隐性→`00000000` | 总线被外部强拉显性 / H–L 短路 | 断电量 H–L 电阻 |
| 两者都出现混合位图 | 总线上还有别的节点在发 | 先停掉对端再测 |

### 7.4 带参数：给万用表用

```
cw 5000      # 先"按住"显性 5 秒, 然后自动做上面的判定
```

万用表只有 ~3 次/秒的刷新率，抓不到 bxCAN 那种每帧 ~190 µs 的间歇发送；
但"按住不放"的显性一定抓得到：

- 在**卡那一端**的 H/L 端子上量到 **CANH≈3.5 V / CANL≈1.5 V** ⇒ 两根线都通；
- 仍是 **≈2.5 V / 2.5 V** ⇒ 卡根本没接到臂的这一对端子上。

## 8. 工具本身的一个坑（2026-09-17 19:05 修）

`tools/can_flood.py` 原来**不检查开卡是否成功**。PCAN 通道会**间歇性**报

```
PcanCanInitializationError: The value of a handle (PCAN-Channel, ...) is invalid
```

（被 PCAN-View / CanAst 占着、或上一次 bus-off 后句柄没释放）。那种情况下脚本
直接 traceback 退出，而对面 `cy` 照样读到"高 N 次 低 0 次" ——
**看起来像"链路不通"，实际是"根本没在发"**。同一晚已因此差点误判一次。

现在：开卡重试 5 次 + 发送期间每 3 秒报一次卡状态 + 结束时报入队帧数与 bus-off。
**看到 `入队 0 帧` 就说明这次 `cy` 的读数无效，不能下结论。**

## 9. `ps` 引脚嗅探 (2026-09-18) —— 回答"卡到底挂在哪只脚上"

### 9.1 为什么要它

用户的疑问是: **"板子有没有解析 CAN2 过来的数据? CAN2 是 PB13/PB14。"**

工程事实(逐条查过):

| 检查 | 结果 |
|---|---|
| 业务代码里有没有 `CAN2` / `hcan2` / `MX_CAN2_Init` | ❌ **一处都没有**(全工程只有 CMSIS 寄存器定义 `stm32f4xx.h`) |
| `.ioc` 里有没有 CAN2 / PB12 / PB13 / PB14 / PB15 | ❌ 一处都没有。CAN1 定的是 PB8=RX / PB9=TX |
| `gpio.c` 里 GPIOB 配了谁 | 只有 **PB5**(GPIO 输出)。PB12~PB15 从未配置 |
| CAN2 的时钟 `__HAL_RCC_CAN2_CLK_ENABLE()` | ❌ 没人调用 |
| F407 上 CAN2 的引脚 | **PB12=CAN2_RX / PB13=CAN2_TX (AF9)**；**PB14 根本没有 CAN 复用功能**(只能是 SPI2_MISO / USART3_RTS / TIM12_CH1 / OTG_HS_DM) |

⇒ **"固件解析 CAN2 的数据"这件事不存在**，CAN2 外设连时钟都没开、引脚都还停在复位态。
⇒ 但用户的问题指向一个**真实可能**: 板子/外接模块上还有第二个 CAN 口，卡接在了那个口上，
  而固件只讲 CAN1(PB8/PB9)。**两种情况的现场症状完全一样**:
  帧发得出去(`TEC` 每帧 +8、`lec=3`)、没人应答、RX 脚一动不动。

### 9.2 `cp` / `cw` 为什么答不了

它们都只认"**当前这一组** CAN 脚"(编译期宏 `ARM_CAN_RX_PIN`)。想知道"是不是还有第二个口"，
必须**横向扫所有与 CAN 有关的候选脚**。

### 9.3 `ps` 怎么做

把 11 只候选脚(`PA11 PA12 PB6 PB8 PB9 PB12 PB13 PB14 PB15 PD0 PD1`)逐个切成 GPIO 输入，
各自在几百微秒内连采 **4096 次**，统计"低电平次数"和"跳变次数"；再用**内部下拉**复采一遍
区分"悬空"与"被外部驱动"。有信号的那只脚会出现大量低电平 + 大量跳变。

⚠ **必须在卡那一端持续灌帧的同时跑**(`tools/can_flood.py`)。没有输入源时悬空脚一律读成
"没东西"，只能证明"没在发"，**不能**证明"接错脚"。

### 9.4 判据

| `ps` 某一行的读数 | 含义 |
|---|---|
| `低=0` 且 `下拉后低=0` | **被外部恒定驱高**(悬空脚会被 40k 内部下拉轻松拉满 ⇒ 有东西在驱) |
| `边沿 ≥ 8` | ⭐ **有活动信号 ⇒ 对端的 CAN 就在这只脚上** |
| `下拉后低 ≈ 满` 且 `边沿=0` | **悬空 / 无外部驱动** |
| 其它 | 被外部恒定驱低 / 该脚被短死 |

典型结论:

- ★ 落在 **PB12/PB13** ⇒ 卡接的是板子的 **CAN2 口**，固件必须改用 CAN2(或把线挪到 CAN1 口)
- ★ 落在 **PB8/PB9** ⇒ 卡确实在 CAN1 口上，问题在收发器或那段线
- 11 行全无 ★ ⇒ 卡的信号**没进到 MCU 任何一只 CAN 脚上**

### 9.6 一条重要的推理修正（本次新增）

之前写过"`lec=3`(ACK 错) 说明位监视通过了 ⇒ 内环是好的 ⇒ 收发器一定接在 PB8/PB9"。
**这条推理只对了一半，必须修正**:

> 收发器**驱动自己那一对端子**时，内部就会把差分电平回馈到 RXD —— 哪怕那对端子
> **根本没接到任何别的节点**。所以 `lec=3` 只能证明 **MCU ↔ 收发器** 这一段是好的，
> **不能**证明"收发器的 CANH/CANL 真的连到了卡那一端"。

于是"`cw` 报外环通、但灌帧时 `cy` 一动不动"**不再自相矛盾**：
外环通 = 收发器在自己那一对端子上能正常工作；灌帧没反应 = 卡不在这对端子上。
⇒ 卡在**另一个 CAN 口**上 这个假设完全站得住，也正是 `ps` 要证的。

## 10. `cx` —— CAN 接口(CAN1/CAN2)运行期切换（2026-09-18 新增）

### 10.1 为什么又把接口做成可切的

§9 的 `ps` 能回答"卡的数据落在哪只脚上"。但**回答完之后呢**?

> 如果 `ps` 说 ★ 落在 **PB12/PB13**（= 卡插在板子的 CAN2 口上），
> 过去的唯一出路是**重编 `CANPIN=...` 再重烧一次固件** ——
> 而这块板子 DTR/RTS 没接 BOOT0/NRST，重烧要**手动拉 BOOT0 + 复位**，
> 一次二十分钟起步；烧错版本还会把结果读成"这个口也不通"，白烧。

2026-09-18 现场确认 **F407 的 CAN2 = PB12(RX)/PB13(TX) (AF9)** 之后，
把"用哪颗 bxCAN + 哪一对脚"从**编译期**改成**运行期**：

```
cx          —— 打印当前接口
cx 1        —— CAN1（PB8/PB9；若编译时给了 CANPIN=pa 则是 PA11/PA12）
cx 2        —— CAN2（PB12/PB13，AF9_CAN2）
cx save     —— 把当前选择写进 Flash 扇区 11 的 CAN 区（重启仍生效）
cx reset    —— 回 CAN1 并落盘
```

⇒ **一次烧录就能两个口都试**，验"卡是不是插在另一个 CAN 口上"不再需要重烧。

### 10.2 实现要点（三个容易踩的坑，都在驱动里处理好了）

| # | 坑 | 处理 |
|---|---|---|
| 1 | **CAN2 的寄存器与过滤器都要经 CAN1(主实例)访问** | `HAL_CAN_MspInit` 里 CAN2 模式**同时** `__HAL_RCC_CAN1_CLK_ENABLE()` + `__HAL_RCC_CAN2_CLK_ENABLE()`。只开 CAN2 直接硬件错误 |
| 2 | **两颗 bxCAN 共享 28 个过滤器银行**，FMR.CAN2SB 是分界 | CAN1 用 bank **0..3**，CAN2 用 bank **14..17**，`SlaveStartFilterBank = 14`。**CAN2 的过滤器配在 0..3 会"配置成功却一帧都收不到"** —— 典型的"看起来全对"坑 |
| 3 | 切接口时**旧那一组银行必须关掉** | `ArmCanDrv_SetInterface()` 先 `can_config_filters_ex(base, DISABLE)`，再 DeInit → 改 `s_iface` → `can_restore_normal()`；同时 Disable 掉两个 RX0 中断向量，挡掉切换瞬间的悬挂中断 |

另外两条设计约束：
- **驱动里任何对引脚/实例/中断号的引用都必须走取值函数**（`can_rx_port()` / `can_regs()` / …），
  再用编译期宏就会"已经切到 CAN2 了却还去读 CAN1"，是最容易骗过自己的那种错。
- `main.c` 里原本直接写 `CAN1->MSR` 的地方全部改成 `ArmCanDrv_RegMSR()` / `ArmCanDrv_BusRxLevel()`。
- 启动顺序：`CanCfg_Load()` → `ArmCanDrv_SetInterface()` → `SetBitrate()` → `CanProto_Init()`。
  `SetInterface` 在**从未上过总线**时只改状态、不碰硬件（`s_ever_inited` 门闩），
  免得启动早期就先按默认 500k 起一次总线，在总线上留一段错误波特率的窗口。

### 10.3 现场怎么用（推荐顺序）

## 11. 「老固件上敲新命令」会真的把臂放倒 —— 白名单闸门 + 固件指纹（2026-09-18 第二轮）

### 11.1 现场事实（这次踩到的）

`tools/can_pin_hunt.py` 还没跑成，先在控制台上试了一下 `cx`：

```
> cx
=== Joint Calibration (2-phase) ===
...
All torques released for hand positioning.
```

`cx` **没有**打印"未知命令"，而是**进了校准向导**。这个向导第一件事是
**松掉全部力矩**（注释里自己写着 `All torques released for hand positioning`）——
也就是整臂当场失去支撑。同一晚这是第二次。

原因在 `ProcessCommand()` 的**首字母兜底 switch**：

```
1) 一堆精确匹配 (teach/save/cx/cn/…) —— 全没命中
2) char cmd = tokens[0][0];
3) switch (cmd) { case 'c': 校准向导; case 'z': 回零点; case 'g': IK 运动; ... }
```

`cx` 在**老固件**里不存在 ⇒ 落到 `case 'c'` ⇒ 校准向导。

⇒ 这条推论比它看起来更值钱：**"板子上跑的是不是新固件"这件事必须先确认，
否则你在控制台上敲的每一个新命令都是对某个单键命令的赌博。**

### 11.2 固件侧修法：多字符命令白名单

`main.c` 里在进 `switch` 之前加一道闸门：

```c
if (tokens[0][0] != '#' && tokens[0][1] != '\0' &&
    !cmd_is_known_multichar(tokens[0])) {
    cprint("  Unknown command '%s'.  'h' = help;\r\n", tokens[0]);
    return;                       /* ← 绝不进 switch */
}
```

`cmd_is_known_multichar()` 是一张**显式白名单**（56 条），列全了所有合法的多字符
命令名：`teach/save/play/del/list/files/compact/rec/tm/lk/ec/sf/mf/sp/ml/mg/mp/mo/ma/ms/
ct/cn/can/cx/cp/cy/cz/cw/ps/zi/zr`，以及靠 `tokens[0][1]` 分发的变体
`pv/qV/qd/qg/QV/QD/QL/QLC/BG/SP/LP/LL` 等。`#P`（PC 中转位置流帧）放行。

> ⚠ **维护约定**：以后新增任何多字符命令，**必须**同步往这张表里加名字。
> 漏了的话新命令会被自己的闸门挡掉，现场表现为"命令没反应"——
> 而这正是最容易浪费半小时的那种故障。

白名单是**用脚本交叉校验过**的：把 `main.c` 里所有 `strcmp(tokens[0], "X")` 的
X（长度 > 1）与白名单求差，结果为空；`tools/*.py` 里默认会敲的命令
（`cx`/`cw`/`ps`/`cn`/`ct`）也全部在白名单里。

`case 'c'` 另有一层单字符守卫（只有**恰好一个 `c`**才进校准向导），双保险。

### 11.3 上位机侧修法：固件指纹前置检查

固件在 `cmdHelp()` 的**首行**印一个指纹（`h` 是任何固件版本都安全的只读命令）：

```
  fw-tag ARM-CAN-0918C  iface=cx-switchable  cmds=cx,cp,cy,cz,cw,ps
```

新增 `tools/arm_preflight.py`：开跑前先敲 `h`，认到指纹才放行；
认不到就**一条命令都不发**直接退出，并且能顺带识别出
"板子现在正卡在校准向导里"（回显里有 `Joint Calibration`）⇒ 提示敲 `q` 退出、**千万别敲 `s`**。

`can_pin_hunt.py` / `can_path_probe.py` 都接上了它，并新增 `--force`：

| 状态 | 行为 |
|---|---|
| 认到指纹 | 全放行 |
| 认不到 + 不加 `--force` | **拒绝执行**（return 3），打印 `h` 的前 8 行原文 + 怎么办 |
| 认不到 + `--force` | 放行 `cw`/`ps`/`cy`/`ct` 这类"上一版固件里真实存在"的命令；**`cx` 仍然拦住**（它只存在于本轮固件，老固件上零收益却会松力矩） |

顺带修掉一个会制造"神秘输出"的小问题：**发命令只发 `\r`，不发 `\r\n`**。
`\r` 结束一行之后，那个多余的 `\n` 会被校准向导的按键读入吃掉，
回显一行 `Unknown key '\n'` —— 看着像随机的怪东西。
（正常模式下 `\n` 当空行被忽略，所以这个坑只在交互模式下露头。）

## §12 引脚组定案：本板 CAN1 在 **PA11/PA12**（2026-09-18）

### 症状组合（看见这个就直接跳到本文）
上位机在发、臂侧 `cn` 报 `hw init ok` + 精确 500k + `tec=0`，但 **`MSR.RX` 恒 = 1、四个收帧计数器全 0**。
⇒ 总线上有电平、而 **MCU 的那只 CAN_RX 脚一次都没看到** ⇒ 收发器不在固件驱动的那对脚上。

### 决定性取证 = `ps` 的对照实验（**两次**，缺一不可）
```bash
python tools/can_pin_hunt.py --port COM11          # ① 灌帧中跑 ps/cx/cw
python - <<'PY'                                    # ② 静默总线再跑一次 ps（对照）
import serial; s=serial.Serial("COM11",115200,timeout=0.3)
s.write(b"ps\r"); print(s.read(9000).decode("utf-8","replace")); s.close()
PY
```
实测读数（同一只脚）：

| 条件 | 「无上拉低/总」 | 边沿 | 「下拉后低/总」 | 判读 |
|---|---|---|---|---|
| **不灌帧** | `0/4096` | **0** | `0/4096` | 被外部驱高，**无活动** |
| **灌帧中** | `2547/4096` | **68** | `2123/4096` | ★**卡的信号在这只脚上** |

⚠ **只跑一次"有没有 ★"不算证据**：`PA11/PA12` 在 F407 上同时是 USB_DM/DP，
不灌帧也可能被别的信号驱出边沿。**只有"边沿随灌帧出现/消失"才是证据。**

### 结论与修复
- ⚠⚠ **本节结论已于同日被推翻，见 §13 —— 请以 §13 为准。**
  当时的误判：把 ★ 读成了 `PA11`，实际是 **`PB12`**（读数与被测脚号没逐字核对），
  于是白跑了一轮"改 CAN1 引脚组"。
- （以下为当时的推断，留档以示教训）`cw` 在 PB8/PB9 报**外环断**，`ps` 的 ★ 被读作 **PA11**；
  PA12 灌帧时仍是"悬空" —— 被解释成与 CAN1 备用脚组（`PA11=CAN1_RX`/`PA12=CAN1_TX`, AF9）吻合。
- ⚠ 这个推理有一个致命漏洞：`ps` 报"被外部驱高"和 ★ 之间**没有做逐字核对**，
  而 **`PB12` 恰好就紧邻 `PB13`**，两行读数极易看串。
- 修复（当时给的）：`cx pa`。**实测无效** —— 见 §13。

## §13 【最终定案】卡在**板子的 CAN2 口**（PB12/PB13）；CAN 从站 API 全通（2026-09-18 下午）

### 一句话
**卡一直插在板子的 CAN2 口上（PB12=RX / PB13=TX），而固件在 CAN1 上找它。**
`cx 2` 一条命令解决，**不用重烧**；配套修掉两个真 bug（见下）后，PC ↔ 臂 的 CAN
从站 API 端到端跑通（PING / GET_STATUS / FK / PARAM_COUNT / 周期状态帧 / 一键冒烟全过）。

### 决定性证据（这次的取证是"单列 + 对照"做的）
```bash
python tools/can_pin_hunt.py --port COM11 --cmds ps      # ① 灌帧中只跑 ps
# ② 再单独跑一次不灌帧的 ps 作对照
```
| 脚 | 不灌帧 | 灌帧中 | 判读 |
|---|---|---|---|
| **PB12** | 边沿 **0**、`0/4096` | 边沿 **66**、低 `2390/4096` | ★ **卡的信号就在这只脚上** |
| PA11 | 边沿 0、下拉也拉不低 | 边沿 **0** | 只是**被外部驱高**，无活动 |
| PB13 | 下拉能拉低 | 悬空 | CAN2 是 TX 脚，此时控制器未驱动它 |

- ⚠ 前一轮把这次 ★ 读成了 `PA11`（`PB12`/`PB13` 两行紧邻，看串了），**教训见红线 34**。
- 交叉验证（全部一致）：
  - `cw` 在 PA11/PA12 报 **[外环断]**、`cz 20` 报 `tec=128 lec=3`（发了但无人 ACK）
    ⇒ 臂的 CAN1 那对脚确实不在卡所在的总线上；
  - `cx 2` 之后灌帧，`test rx` **93 → 309**（灌 216 收 216，零丢零错，`tec/rec/lec` 全 0）
    ⇒ **双向物理层确认打通**。

### 顺带定案的两个真 bug（都不是引脚问题，但都会伪装成"链路坏"）

**① 帧序被 3 个发送邮箱打乱（红线 35）**
4 帧的回包在总线上实际顺序是 **F1, F4, F2, F3**（F4 抢走最先空出的 MB0，硬件按邮箱号调度）。
⇒ 症状"**1 帧的 PING 通，4 帧的 GET_STATUS 永远超时**"。
修复：发送侧每帧之间 `ArmCanDrv_TxDrain(20)`（等 3 个邮箱**全空**）；接收侧重组器改成**按帧号定偏移 + 位图收齐**。

**② 卡关掉 ⇒ 臂爬上 error-passive 并停发状态帧（自锁，红线 36）**
`bus.shutdown()` 后总线上没人 ACK，NART=1 ⇒ 每帧 `TEC += 8`，16 帧到 128；
`CanProto_Service()` 见 `tec>=128` 就停发状态帧，而恢复只能靠"发送成功" ⇒ **自锁**。
⇒ 症状"**臂说'状态帧正常发送、已发 67 帧'，卡这边 0 帧**"。
修复用法：**验状态帧时卡必须全程开着**（同一进程"先 PING 再监听"）；已锁住就 `cx 1` → `cx 2` 重置 TEC。
