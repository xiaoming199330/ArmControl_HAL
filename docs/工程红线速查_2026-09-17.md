16. ⭐ **主从遥操 = PC 中转（正式方案）**：主臂 `sp <Hz>` 按节拍吐 `#P`（关节角 rel-home ×10）→ PC `tools/pc_relay.py` → 从臂认 `#P` 直写关节角
    （复用 `ArmApi_StreamJoints`，门闩/限位/跳变保护照旧）。两臂各一路 USB-TTL。诊断第一手证据**全在【从臂】控制台**（`Stream reject`／`Stream watchdog`）；
    relay 必须**非阻塞**读从臂口（`timeout=0.0`，阻塞读每拍塞 50ms）。**clamp 静默** ⇒ "单轴跟不上" ≠ "舵机慢"，先 `L <J> <min> <max>`（RAM only）试。
    CAN/UART4 直连**降级为备选**：默认 PB8=RX/PB9=TX，收发器 `CAN PHY V1` **直连不交叉**、`CANH↔CANH`、**必须共地**、两端 120Ω。
    `ct` 出 `lec=3`+`rec=0` **别再拆线**：走 `cz`（我方 TX 上没上总线）／`cy`（对面在不在发）／`cn` 的 `MSR.RX`（⚠ 只看总线电平，分不清是谁的帧）。
    新链路先做引脚直流探测：CAN `cp`、UART `mp`/`mg`/`mo`/`ml`；RX 加内部下拉仍读 `11111111` ⇒ 外面低阻强驱动。
    ⚠ `cp` 的 TX 项只测 MCU 驱动级、看不见"两板是否共地"——这两条只能万用表。
17. ⭐ **1 Mbps 半双工总线上"读位置"只有一条安全写法：多数表决 + 节流**（09-17，QL 卡死根因）。硬件事实：USART3/UART5 = 1 Mbps =
    **每字节 10 µs**，F4 的 UART **无 FIFO**（最多留 2 字节），晚 10 µs 就丢字节 ⇒ 整帧作废 ⇒ **任何"每趟主循环都读"都是风暴读**。
    - `f`／`P 0`／`g`／`ms`／起点安全读**一律** `read_pos_vote()`（3 采样多数表决 + 重试 + 采样间隔）；
      **新加任何跑在等待期的读，先问"有没有表决、有没有节流"**（QL 判位漏了这条，卡死 3 周）。
    - 热路径超时用 **10 ms**（`read_pos_retry_to`／`SERVO_GetPositionRawTO`／`ReadTelemetry`），100 ms 会按住主循环。
    - `DXL_ReadDiag` 的 `rx_cap` 前导噪声余量已 **+2 → +8**（半双工 TX 回声只能排掉 DR 里的 1~2 字节，残留 2~3 字节是常态；
      余量不足 ⇒ 真帧尾 CHK 被截 ⇒ 报 `corrupt frame`，**影响全部读**）。
    - **文案会骗人**：`mp_fail_joint` 只记"该趟最后一个失败轴"（别信 "J6 corrupt frame" 里的 J6）；"读不到"分 NO_REPLY／BAD_FRAME／ERROR_BITS，处置完全不同。
18. ⭐ **轨迹通道从不写 `Torque_Enable`** ⇒ 被 `t J 0` 松过力（或旧版 `z` 结束时把六轴 Torque 写 0）的轴**静默不执行**：命令全成功、`f` 能读、位置不动。
    **"段跑完再敲 f，六值 == `From:` 逐位相同" = 该段物理上没动** ⇒ 先查力矩（`SERVO_GetTorqueEnabled(j)`／`torque=OFF`），别算角度差。
    卡死/等待类判定**必须带超时**并打印逐轴真相（目标/实测/误差/读失败次数/力矩），否则现场只有一句误导文案。
19. ⭐ **阻塞操作会连带打断遥操链**：从臂 `save`/`compact` 写内部 Flash **阻塞 1~3 s**（首存或满 80 s 录音最坏 ~5 s，可能带扇区擦除）。
    期间主循环停摆 ⇒ ① `RX_BUF_SIZE=128` 只装 ~3 行位置流（60 Hz × ~40 B）⇒ 全丢；② 恢复后 `cmdStreamService` 判流 > `STREAM_TIMEOUT_MS`(500)
    ⇒ 打 `Stream watchdog: no cmd for 500 ms -> hold` 并 `stream_enter()` **重锚当前位置为跳变基准** ⇒ 那几秒主臂位移被整段跳过，还会撞「每帧 25°」连帧拒 → 自锁。
    ⇒ **遥操中任何阻塞 >500 ms 的操作（存盘/擦除/长打印）前必须先停位置流**（主臂 `sp 0`）。新加"可能要几百毫秒"的路径，先问"会不会把流看门狗/控制台喂不上"。
20. **续行符跟着终端走**：`^` 属 cmd.exe；PowerShell 用反引号（行尾最后一个字符，后面不能有空格），且 PS 里 `--` 是自减运算符 ⇒ 照抄 cmd 多行命令会报
    `一元运算符"--"后面缺少表达式`。**给用户的命令一律写成一行**。例：
    `py -3 tools\pc_relay.py --master COM22 --slave COM11 --start --hz 60 --slave-cmd "ec 0" --slave-cmd "teach rec" --teach-name demo1`
    （`--start` 已自带主臂 `mf 0` + `sp <hz>` 与从臂 `sf 1`，不用重复给）。
21. ⭐ **`--dry-run` 曾经不是"不碰硬件"**（09-17 事故，丢掉用户一条 80 s 未存盘录音）：`dry_run` 只在**转发路径**检查，`send()`（开机命令/热键公共出口）
    没守卫 ⇒ 试跑参数把 `teach rec` 真发到从臂 → `teach_mode_prepare()` 里 `teach_rec_cnt = 0U` **静默清空 RAM 录音**。已修：守卫下沉到 `send()`。
    ⇒ **安全开关放最底层出口，不放调用点**；"只测参数"的路径不许有改变现场状态的副作用；破坏性操作前**先报出将要失去什么**
    （固件已加 `⚠ Discarding UNSAVED recording: N samples`）。
    ▶ 从臂录音**只在 RAM**：Ctrl+C 不停录制；`teach exit` 后 buffer 仍活着 ⇒ 再 `teach rec` 会清空（旧版静默）。
      **判据：`teach list` 的样本数，退了也该还是 4000。** 脚本 `r` 已改发 `rec clear` + `teach rec`。
22. ⭐ **`[rec-integrity] read-fail` 要按总线读，别按轴读**：默认 **J1–J3 = 总线 A（USART3, PB10/PB11）**、**J4–J6 = 总线 B（UART5, PC12/PD2）**。
    现场 80 s 录制：A 9878/12000 ≈ **82%**、B 2664/12000 ≈ **22%** ⇒ **总线级**差异，不是某颗舵机。`lost_ticks` 只 16 ⇒ 失败是**快速返回**
    （BAD_FRAME／`ERROR_BITS`），**不是** 10 ms 超时 ⇒ 别按"线缆松"查。`DXL_ReadDiag` 把 `pkt.error & 0x7F != 0`（过载/过温/过压）也算读失败，
    而**位置数据本身有效** ⇒ 热路径会拿"旧值"（跳变守卫误判 → 假 jump → 自锁），**待评估**是否放开。
23. ⭐ **Flash 扇区 11 现在是"两区共享"，禁止任何模块直接 `HAL_FLASHEx_Erase(FLASH_SECTOR_11)`**（09-17）：
    `0x080E0000+0x0000` = PID/校准/限位（`pid_flash.c`）、`+0x1000` = CAN 配置（`arm_can_config.c`）。Flash 只能整扇区擦 ⇒ 各自直擦会把对方**静默清掉**
    （校准零点一丢就是红线 9 那一串）。统一走 `flash_cfg.c` 的 `CfgFlash_WriteRegion(off, src, n)`（读他区→擦整扇区→回写他区→写本区→双区校验）。
    ⚠ 里面两个 4KB 缓冲**必须 static**（放栈上会打穿主栈）。⚠ `PID_FlashErase()` = 整扇区擦，**CAN 配置一起没**（"恢复出厂"语义）。
24. ⭐ **CAN 从站接口**：`0x100+node` 收命令／`0x180+node` 回响应／`0x280+node` 发周期状态帧(`d[0]=0x53`)与异步事件帧(`d[0]=0x45`)／`0x7E0` 自检。
    分包与串口协议同源（`docs/CAN协议规范_2026-09-17.md`；**DLC 变长，不补 8**）。配置 `can node/baud/hb/save/reset/stat clr`，默认 node=1／500k／hb=1000ms，
    **落盘在红线 23 的 CAN 区**。启动顺序**不可换**：`CanCfg_Load()` → `ArmCanDrv_SetInterface(cfg.iface)` → `ArmCanDrv_SetBitrate(cfg.baud)` → `CanProto_Init(cfg.node)`
    （否则总线先以默认速率起一次再重配 ⇒ 上位机满屏错误帧；接口若晚于 `CanProto_Init` 才定，MspInit 已经按错的脚配过 GPIO/中断了）。波特率固定 14TQ／采样点 85.7%，预分频由 `HAL_RCC_GetPCLK1Freq()` 反算并**要求整除**
    （不整除直接拒绝，不给近似值）。⚠ `AutoRetransmission=DISABLE` ⇒ **上位机必须自己按 SEQ 超时重试**。
    ⚠ 状态帧只读廉价标志（`ArmMain_Flags()`），**绝不在里面读舵机总线**；改过滤段别忘 bank2=0x280。
    ⚠ **心跳/任何自动发送必须"有对端才发"**：`AutoRetransmission=DISABLE` 时每帧无人 ACK 就 TEC+8
    ⇒ 1 Hz 心跳在没插线的台子上 ~16 s 到 error-passive、~32 s 到 bus-off，ABOM 恢复后无限循环，
    看着像收发器坏了。已加三条抑制：① 没收到过发往本节点的帧就不发（PING 一次即解锁，且立刻补发一帧）
    ② TEC≥128 暂停 ③ `can hb 0` 关闭。`can` 命令会直接告诉你现在属于哪种状态。
25. ⭐⭐ **CAN 的"控制器"和"引脚对"都是运行期变量 —— `cx 1|2` / `cx pa|pb`，别再靠重编重烧去验假设**（09-18 两次踩）：
    `CAN1` 的两对候选脚：**`PB8(RX)/PB9(TX)`**（`.ioc` 默认）与 **`PA11(RX)/PA12(TX)`**（F407 上同时是 USB_DM/DP）；
    **`CAN2 = PB12(RX)/PB13(TX)`（AF9）**；⚠ **PB14 在 F407 上没有 CAN 复用**，"CAN2=PB13/PB14" 不成立。
    驱动里任何对引脚/实例/中断号的引用**必须走取值函数**（`can_rx_port()`/`can_regs()`/`can_bus_rx_level()`…），
    用编译期宏 = "已经切到 CAN2 了却还读 CAN1"。
    - `cx 1` / `cx 2` 切**控制器**（可 `cx save` 落盘）；**`cx pa` / `cx pb` 切 CAN1 的引脚对**（不落盘，复位回编译期 `CANPIN` 默认）。
    - 切控制器三个必做：① **CAN2 的寄存器与过滤器都要经 CAN1 访问 ⇒ CAN1 时钟必须同时开**；
      ② 两颗 bxCAN 共享 28 个过滤器银行，`FMR.CAN2SB` 是分界（本工程 = 14）⇒ **CAN1 用 bank 0..3、CAN2 用 14..17**，
      CAN2 配在 0..3 会"配置成功却一帧都收不到"；③ 切之前**关掉旧那一组银行** + Disable 两个 RX0 中断向量。
    - 切**引脚对**时额外一条：**CAN1 的两组候选脚都要先 `HAL_GPIO_DeInit`**。只摘当前那组不够 ——
      另一组会继续挂在 CAN1 的输入上，两个 RXD 同时驱动同一外设输入 ⇒ **偶发位错误**（比"完全收不到"难查得多）。
    - 启动时 `SetInterface`/`SetCan1Pins` 在"从未上过总线"（`s_ever_inited=0`）时**只改状态不碰硬件**，
      免得启动早期先起一次总线。判据见 `docs/CAN物理层取证_2026-09-17.md` §10。
    ⚠ **`lec=3`(ACK 错) 只证明 `MCU↔收发器` 通，不证明 CANH/CANL 连到了卡那端**（收发器驱动自己那对端子时内部就会回馈 RXD）
    ⇒ "`cw` 报外环通"与"灌帧时 `cy` 一动不动"**可同时成立**。
    ⚠⚠ 而且反过来也成立：**`cw` 报"外环断"只说明"当前这组脚上没有收发器"**，不代表板子没有收发器 ——
    它可能在**另一组脚**上。这一条正是红线 34 的入口。

26. ⭐⭐ **控制台命令分发是「首字母兜底」，所以"敲错的多字符命令"= 会执行某个单键命令**（09-18，一晚踩两次）：
    `main.c` 的 `ProcessCommand()` 是「先一堆精确匹配 → 全都失败后 `switch (tokens[0][0])` 按**首字母**落 case」。
    于是**在没这条命令的固件上敲它，不会报"未知命令"，而是掉进首字母那个 case 直接干活**。实测代价：
    | 敲了 | 落到 | 后果 |
    |---|---|---|
    | `cx` / `cw` / `cs` | `case 'c'` → 校准向导 | **松全部力矩**，整臂当场塌下来；再按 `s` 就**固化坏零点** |
    | `ze` | `case 'z'` → 回零点 | **真的动** |
    | `ge` | `case 'g'` → IK 运动 | **真的动** |
    | `tq` | `case 't'` → 力矩开关 | 可能松力矩 |
    **两道闸都要有，缺一不可**：
    ① **固件侧**：`ProcessCommand()` 进 `switch` 前有一张**多字符命令白名单** `cmd_is_known_multichar()` ——
       长度 > 1 且不在表里的 token 一律当未知命令挡掉（`#P` 流帧放行）。`case 'c'` 另有单字符守卫。
       ⚠ **以后新增任何多字符命令（以及 `tokens[0][1]` 变体，如 `qv`）必须同步加进那张表**，否则新命令会被自己的闸门挡掉。
    ② **上位机侧**：`tools/arm_preflight.py` —— 敲任何命令前先敲 `h` 认固件指纹
       **`fw-tag ARM-CAN-<版本>`**（印在 `cmdHelp()` 首行；**期望值写在代码常量 `FW_TAG` 里，
       现役 `ARM-CAN-0918G`** —— 以后升版只改那个常量，别再抄版本号进文档，抄了就会锈）。
       认不到就**一条都不发**并直接退出。
       `--force` 可强行继续，但 `cx`（只存在于本轮固件、老固件上零收益却会松力矩）**仍然拦住**。
    ⚠ 发命令**只发 `\r`**：发 `\r\n` 时那个多余的 `\n` 会掉进校准向导的按键读入，打出 `Unknown key`。
    ⚠ 老固件上**手敲** `cx`/`cw`/`ps` 之前，先敲 `h` 看一眼有没有 `fw-tag` —— 没有就别敲。

28. ⭐ **开工前先判"板子活着没有"，别在"命令没实现"上想**（09-18 现场）：
    `口在` **完全不代表** 板子在跑 —— CH340 靠 USB 供电自带枚举，MCU 侧没电时口照样在。
    于是「**0 字节输出**」至少有三种完全不同的原因，现象一模一样：
    | 现象 | 真实原因 | 怎么分辨 |
    |---|---|---|
    | 敲 `h` 有回显 + `fw-tag` | 本轮固件在跑 | ✔ 可以往下测 |
    | 敲 `h` 有横幅、**没有** `fw-tag` | **旧固件**在跑 | △ 只能跑 `cw/ps/cy/cz/ct`，**`cx` 绝不敲** |
    | 敲 `h` 回的是 `=== Joint Calibration` | 卡在校准向导 | ⚠ 敲 `q` 退出，**千万别敲 `s`** |
    | 敲 `h` **0 字节**，但 `stm32flash <口>` 认到 `Device ID` | **BOOT0 还挂着高** | 拉低 BOOT0 + RESET |
    | 敲 `h` **0 字节**，bootloader 也不应答 | **MCU 没上电** 或 **固件挂死** | 只能现场：查电源 → RESET/断电重上电 |
    ⭐ 一条命令出结论：`python tools/board_alive.py --port COM11`
    ⚠ 本工程**没有 IWDG/WWDG**（`grep` 确认）⇒ 一旦挂死就是**永久静默**，不会自己复位。
      排查时看到"刚才还好好的、现在一个字都没有"，先想这两条，别去改波特率、别再怀疑脚本。
    ⚠ **不要**为了"排除时钟跑飞"对活板子做**波特率扫描**：错误波特率下发的字节会变成
      **随机命令注入命令解析器**（可能误触单键分支）。只试 115200 一档。
    ⚠ 判"挂死"之前的**无害**探测手段（本轮都用过，都没打扰板子）：
      被动监听 60s（抓"反复复位"的启动打印）、`DTR×RTS` 四种组合各发一次 `h`（排除被线性拉死）、
      `stm32flash <口>`（只读 version，区分 bootloader vs 真没跑）。**读 CTS/DSR/CD/RI 没用**——CH340 这几个脚悬空。
29. ⭐⭐ **CAN 取证必须从"低速"起步：高速灌帧会把臂压死，而且灌完不恢复**（09-18 现场）：
    现场事实：`h` 在灌帧**开始前**是好的（认到 `fw-tag ARM-CAN-<版本>`），
    `can_pin_hunt.py` 一开灌帧（≈500 帧/秒），灌帧窗口里的 `cx`/`cw`/`ps` **三条全哑**，
    灌帧结束后 30 s 内连敲 7 次 `h` **全 0 字节** ⇒ 板子永久静默，只能断电重上电。
    **"灌帧即哑、且灌完不恢复"只有一个自洽机理**：
      CAN RX 中断被反复重进（RX FIFO 没被放掉）⇒ CPU 永久卡在 ISR ⇒ 主循环再不执行
      ⇒ 控制台永久静默。本工程**没有看门狗**，所以不会自恢复 —— 灌帧停了也一样。
    ⚠ 这个机理成立的**前提**是"帧真的到了 MCU"。于是高速灌帧制造了一个**二选一、结论相反**的歧义：
      | 解释 | 含义 |
      |---|---|
      | 帧到了 ⇒ 把它压死 | **物理层其实是通的**（推翻 09-17 的"静默"结论） |
      | 帧没到 ⇒ 与灌帧无关 | 它的死是掉电/别的原因，物理层**仍然**不通 |
    ⇒ **不要把"高速灌帧"和"读臂侧计数器"混在一起做**，那是把两个变量绑死。
    ⭐ 正确姿势：`python tools/can_rx_witness.py --port COM11 --gap-ms 200 --secs 45 --poll 5`
      （5 帧/秒，每个 `--poll` 秒读一次 `cn`，把 `test rx / peer / 合法好帧 / rec / MSR.RX / tec`
        做成时间序列；**一旦哑掉立刻停手**并报"死在什么速率、已灌多少帧"）。
      判读表：
      | 现象 | 结论 |
      |---|---|
      | `--no-flood` 基线就哑 | **与 CAN 无关**，先查供电/复位（别在这条路上想 CAN） |
      | 灌帧中计数器不涨 & `MSR.RX` 恒 1 | 帧**没进 MCU**（物理层不通 / 卡在另一个口）← 09-17 结论 |
      | 灌帧中计数器涨 或 `MSR.RX` 变 0 | ★帧**进了 MCU**，断点不在物理层，去查过滤器/协议 |
      | 涨一点就哑 | ★同上 + 固件 RX ISR 有 latch-up（记录阈值，再谈修 ISR） |
    ⚠ 想找"多少速率会哑"：`--ramp`（逐级 2000→1000→500→200→50→2 ms，每级 `--stage-secs`）。
    ⚠ 副作用警告：**取证用的灌帧会打扰臂**（`ps` 期间 bxCAN 停 ~10 ms 对端会记错，
      高速灌帧甚至能压死它）⇒ 取证前先确认臂处于可安全打扰的状态。
30. ⭐⭐⭐ **做任何 CAN 取证之前，先量"这块板开机后自己活多久"**（09-18 三次踩坑后定案）：
    **这是本工程目前最贵的一条教训** —— 我们花了三轮把"灌帧压死板子""`cn` 把板子搞死"
    当成 CAN 问题查，**全部是错的**。
    ⭐ 决定性实测（`--await-boot` 从上电那刻计时，**全程只发 `h`**，一帧 CAN 都不灌、`cn` 一次都不发）：
      ```
      上电后 0.0 s   应答 ✔ (横幅 "6-Axis Arm Controller v2.0")
      t= 6.8 s       只发 h → 还活着
      t=10.3 s       只发 h → 静默 ★
      ```
      ⇒ **板子在上电后约 10 秒死掉，与 CAN / 与命令毫无关系**。全程也没抓到重复的启动横幅
        ⇒ 它是**卡死**（本工程无看门狗 ⇒ 永久静默），不是复位重启。
    ⚠ 这个"约 10 秒"和"`h` 之后正好敲了 `cn`/灌帧"**高度混淆**，会让人得出
      "`cn` 是凶手""灌帧是凶手"这种**看起来有因果、其实只是时序相邻**的结论。
      **先量存活时间，再谈命令** —— 否则后面每个读数都是在一条正在死的板子上取的。
    ⭐ 一条命令量存活时间（先挂后台，再让用户断电重上电）：
      ```bash
      python tools/can_rx_witness.py --port COM11 --await-boot --await-secs 200 \
             --no-flood --poll-cmd h --secs 120 --poll 3
      ```
      `--await-boot` 允许板子还没上电就开始跑（会跳过指纹检查 —— `h` 本来就全版本安全），
      `--poll-cmd h` 保证**除了 `h` 什么都不发**。
    ⇒ 存活时间**每次都≈10 s（很稳）** ⇒ **固件开机后有一条固定致命路径**，
      查定时器/CAN 周期状态帧(TEC 涨到 error-passive/bus-off 时的错误中断)/某种 ~10 s 触发的东西。
    ⇒ 存活时间**忽长忽短** ⇒ **供电/硬件**：12V/5V、共地、插头松动、USB 线接触，
      **舵机保持力矩时把电源拉垮**（典型特征：断电后能撑一会儿）。
    ⚠ 分离实验（快、且一次能答两问）：**撑住机械臂后断掉舵机/电机电源，只留 MCU 供电**，
      再上电看它还死不死 —— 不死 ⇒ 就是舵机电流把电源拉垮；照样 10 s 死 ⇒ 固件问题。
      ⚠⚠ 断电会让力矩消失、**整臂可能当场塌下来** —— 必须先支撑好机械臂再做。
    ⭐ 用 `--poll-cmd cn`（`--poll 1`）可以让最后一行读数正好停在死亡前一刻，
      直接看到临死时的 `tec/rec/lec/RX` —— 如果 `tec` 正爬到 255 附近 ⇒ CAN 错误升级
      (error-passive/bus-off) 的那条中断路径可疑。
    ⚠ **本条的方向对、归因错，已被红线 31 定案**：确实"固件里有一条固定的致命路径"，
      但它不是定时器/周期帧，**就是 `h` 那条打印本身**（越界读栈 → BusFault）。
      "≈10 秒"其实是"开机后**第一次长打印**发生的时间"，不是周期事件。

31. ⭐⭐⭐ **`vsnprintf`/`snprintf` 的返回值是"本该写多少字节"，不是"实际写了多少" —— 拿它当长度用会越界读**（09-18 定案，就是上面那条"上电十几秒静默死亡"的真因）：
    ```c
    /* 出事的写法（main.c 的 cprint，存在了很久，所有人都当它没问题） */
    char buf[256];
    int len = vsnprintf(buf, sizeof(buf), fmt, args);
    if (len > 0) HAL_UART_Transmit(&hconsole, (uint8_t*)buf, len, 100);
    ```
    - C99 / newlib 语义：缓冲不够时返回**截断前的总长度**。`h` 的帮助表 **5406 字节**，
      而 `buf` 只有 256 ⇒ `len = 5406` ⇒ 从这 256 字节的**栈缓冲往外读 5150 字节**当数据发出去。
    - 现场指纹（**一眼可辨，别再当"串口乱码"放过**）：
      · 输出**断在第 255 字节处**，正好把一个词劈成两半（实测断在 `[Z] Full ID sca|n 1..253`）；
      · 乱码里能认出**启动时留在栈上的字符串**（实测夹着 `Limits: J1[63~303]...`）；
      · 随后板子**永久静默** —— 越界读到 SRAM 顶端 `0x20020000` 之外就是 BusFault，
        默认 handler 是 `while(1)`（本工程无看门狗 ⇒ 再也回不来）。
    - ⭐ **规矩**：一次 `cprint` 的**格式化后长度可能超过 255** 的，必须改走 `cprint_long()`
      （按 `\n` 切成 ≤200 字节的块逐块发）。**改帮助表/加长输出前必须重数一遍长度。**
    - ⭐ 自查脚本（把字面量 >200 字节的 cprint 全列出来；09-18 全工程只有 `cmdHelp` 一处）：
      ```bash
      python - <<'EOF'
      import re,glob,io
      pat=re.compile(r'cprint\s*\((.*?)\)\s*;',re.S); lit=re.compile(r'"((?:[^"\\]|\\.)*)"')
      dec=lambda s: re.sub(r'\\(.)', lambda m:{'n':'\n','r':'\r','t':'\t'}.get(m.group(1),m.group(1)), s)
      for f in glob.glob('Core/Src/*.c'):
          t=io.open(f,encoding='utf-8',errors='replace').read()
          for m in pat.finditer(t):
              n=sum(len(dec(x)) for x in lit.findall(m.group(1)))
              if n>200: print("%5d  %s:%d"%(n,f,t[:m.start()].count('\n')+1))
      EOF
      ```
    - ⚠ `cprint_long` 是**阻塞**的（5406 B @115200 ≈ **470 ms**）⇒ **运动/遥操/位置流期间不要敲 `h`**。
    - `cprint` 里同时补了**自愈**：传输前若 `hconsole.gState != READY` 先 `HAL_UART_AbortTransmit`
      —— 防"上一次传输被超时打断、之后每次打印都直接 HAL_BUSY 返回"这种"板子在跑但不再说话"。
    - 固件指纹随之升到 `fw-tag ARM-CAN-0918D ... fix=cprint-overread`；`tools/arm_preflight.py`
      的 `FW_TAG` 已同步（认不到 D 会**拒发**）。

32. ⭐⭐ **"等一个永远不来的硬件标志"的裸自旋 = 静默死亡**（09-18 顺手排掉的两处）：
    - `servo_bus_hal.c`：`while (__HAL_UART_GET_FLAG(huart, UART_FLAG_TC) == RESET);` —— **无超时**。
      TC 只要因为任何原因不来（总线被拉死 / 收发器异常 / 时钟被关），**整个 CPU 永久停在这一行**：
      主循环死、控制台一个字不说、**但 USB 还在枚举**。已改为 5 ms 有界并返回 `HAL_TIMEOUT`
      （正常路径不受影响：`HAL_UART_Transmit` 返回 `HAL_OK` 时 TC 其实已经置位）。
    - `servo_bus_hal.c` 的 `receive_common()`：超时检查原本在 `for(;;)` **末尾**，而上面的 ORE
      分支末尾有 `continue` ⇒ **只要 RX 线持续报 ORE（舵机没上电、开漏总线悬空就是一台
      "字节制造机"），超时检查被整个跳过 ⇒ 死循环**。已挪到循环**最顶上**。
    - ⭐ 通用规矩：**任何 `while (标志位)` 都要带 `HAL_GetTick()` 超时**，且超时检查
      **不能被任何分支绕过**（把 `continue`/`break`/嵌套分支都数一遍）。

33. ⭐⭐ **接手现场第一件事：读开机自报的 `[FAULT]` / `[STALL]` / `[BOOT]` 行**（09-18 新增）：
    - 本工程**没有看门狗** ⇒「CPU 撞异常」「主循环卡在无界等待」「掉电」三者在现场
      **表象完全一样**（口在枚举、0 字节输出、bootloader 也不应答）。这三行把它们分开：

      | 开机打印 | 含义 | 下一步 |
      |---|---|---|
      | `[FAULT] 上次运行死于 **BusFault** … CFSR=… BFAR=…` | CPU 撞异常，`BFAR` 就是出错地址 | 按 `ArmFault_AddrHint()` 的提示查（BFAR 落在 CAN2 寄存器 `0x40006800` = 时钟没开就去读） |
      | `[STALL] 上次运行主循环卡死 至少 N ms: phase=… cmd=…` | 主循环卡在无界等待里，`phase`/`cmd` 指出卡在哪 | 对着 `phase` 找那一段的阻塞调用 |
      | `[BOOT] 上次运行无故障、无卡死记录` | 上次是**掉电**/断电重启 | 查电源，别再查代码 |

    - 实现：故障现场写进 **CCM RAM**（`0x1000F000`，`arm_fault.c`）；主循环停滞由 **TIM2 中断**
      （与主循环完全独立）盯 `g_main_progress_ms`，超 `ARM_STALL_MS` 后写 `0x1000F800`。
    - ⚠⚠ **这两条记录跨「复位」保留，跨「掉电」丢失** ⇒ **出事后必须按 RESET，不要断电**，
      否则记录连同现场一起没了，又只剩"口在、无输出"这三个字。
    - ⭐ 主循环里用 `main_progress(ARM_PHASE_*, cmd)` 打点；新增子系统时顺手加一个 phase 值，
      否则 `[STALL]` 只能告诉你"卡了"，告诉不了"卡在哪"。

35. ⭐⭐⭐ **多帧分包流会被"3 个发送邮箱"打乱顺序 ⇒ 严格递增的重组器必然丢整条流**（09-18 定案，
    症状伪装成"协议/物理层坏"）：
    bxCAN 只有 **3 个发送邮箱**。一条 4 帧的回包若"一口气塞进去"：
    F1→MB0、F2→MB1、F3→MB2 挂着，而主循环一等到邮箱空就为 **F4 抢走刚空出的 MB0**；
    硬件按"ID 相同则**邮箱号小者先发**"调度 ⇒ **总线顺序变成 F1, F4, F2, F3**（实测原始帧可反推）：
    ```
    84 11 82 15 | 01 07 00 03    idx0 首帧(共4帧, LEN=0x15)
    03 | b1 05 08 f5 c9          idx3  ← 第 4 帧先到
    01 | 93 0a c7 09 21 07 bf    idx1
    02 | 05 7d 05 0f 00 ae 00    idx2
    ```
    ⇒ 症状是**"1 帧的 PING 通、4 帧的 GET_STATUS/FK 永远超时"**，而链路与引脚其实全是好的。
    - 修复（两处都做，互为保险）：
      ① **发送侧**：`can_send_packed()` 每帧之间调 `ArmCanDrv_TxDrain(20)`（等到 3 个邮箱**全部**空出，
         即上一帧真发完）⇒ 顺序与代码一致。⚠ 判据必须是 `freeLevel == 3`，"有位置放"不够。
      ② **接收侧**：重组器**按帧号定偏移 + 位图收齐**，不再要求 `d[0] == next` 严格递增 ——
         对端是另一块 bxCAN 板时同样会发生乱序，不能只赌发送侧。
    - ⇒ 推广：**凡是"分片/分包"协议，只要发送端有多个并发发送槽位，就必须显式保证顺序**，
      不能假定"我按顺序调用 send() 就会按顺序上线"。
    - ⚠ 主机侧参考实现 `tools/can_host.py` 的 `Reassembler` 同步改成容忍乱序（否则已烧的旧固件配新主机也不通）。

36. ⭐⭐⭐ **"卡被关掉"会让臂自己爬到 error-passive 并停发状态帧 —— 这是自锁，会把读数变成假阴性**（09-18 定案）：
     PCAN 的 `bus.shutdown()` 之后总线上就没有能 ACK 的节点了。臂的 NART=1（不自动重传）⇒
    每发一帧没人 ACK 就 `TEC += 8`，16 帧后到 **128 = error-passive**；而 `CanProto_Service()`
    见 `tec >= 128` 就**暂停周期状态帧**，恢复又只能靠"发送成功" ⇒ **没人 ACK 就永远不成功 ⇒ 自锁**。
    - ⭐ **版本差异（先看你手里是哪版）**：
      - **≤ `0918F`：仍是永久自锁**，只能靠下面的办法人工恢复。
      - **✅ `0918G` 起已修，并已验收通过**：闸门从"永久闩锁"改成 **每 5 s 放一帧探路**
        （`ARM_CAN_TEC_PAUSE_MS`），收到对端命令帧时**立刻解除**暂停（`s_tec_resume`）。
        ⇒ 判据：`cn` 在 `tec ≥ 128` 时现在会打印"**状态帧降为每 5 s 探一帧**"（旧版打印"暂停直到计数回落"）。
    - ⭐⭐ **`0918G` 的修复机理（09-18 16:3x 用 PASSIVE 旁听实测钉死，别再凭猜）**：
      - **error-passive 下的 ACK 错误不会让 TEC 再涨**（ISO 11898-1 的例外）。
        ⇒ "没对端 ⇒ TEC 涨到 255 ⇒ bus-off ⇒ ABOM 自动清零"这条**是错的**（本文件早先版本及源码注释都写错过）：
        实测 `tec=134` **恒定 25 s 不动**，期间约 5 次无 ACK 发送。
        ⇒ **TEC 就停在 128~135 这个区间**，永远不会到 256、永远不会 bus-off。
        ⛔ 所以**别拿"等它 bus-off 自愈"当恢复手段**——**唯一的自愈路径就是那 5 s 探路帧**。
      - **恢复延迟 = `(TEC − 127) × 5 s`**（TEC > 127 时，每成功发送一帧只 `−1`）。
        实测 `TEC=134` ⇒ **恰好 7 帧 × 5 s ≈ 35 s** 才回到 1 Hz。录到的到达序列是铁证：
        ```
        间隔(s): 5.0 5.0 5.0 5.0 5.0 5.0 5.0 | 1.0 1.0 1.0 1.0 ...
                 ← 7 次"探路帧"逐帧把 TEC 从 134 拉到 127 → 之后恢复 1 Hz →
        ```
        ⇒ **判据是"探路帧一定会到"，不是"对端一回来立刻 1 Hz"**。最坏也就 ~40 s，且期间**命令帧不受闸门限制**，
        随时可应答（回包走另一条路，不走周期状态帧的闸门）。
    - ⭐ `0918G` 验收清单（本次实测全绿）：`--smoke` 六项 PASS；`--order-verify 25` = 25/25 全成功、
      到达顺序恒为 `0,1,2,3`、乱序 0；自锁自愈：`monitor` 退出制造 `tec=128 EPVF=1` → 重开卡后 12 s 收 10 帧（1 Hz）、
      PASSIVE 旁听 20 s 收 4 帧（5 s 节奏，证明探路帧真的上总线）。
    - 现场表现极具误导性：`can` 会说"**已探测到对端, 状态帧正常发送**" + "发: 状态帧 67"，
      而卡这边**一帧都收不到**（实测 `--monitor` 连续两次 0 帧）⇒ 很容易误判成"臂不发了/链路坏了"。
    - ✅ 判读口诀：**"臂说发了 N 帧、卡说 0 帧" 时先看 `cn` 的 `tec`**。`tec ≥ 128` ⇒ 就是这条自锁，不是链路。
    - ✅ 正确用法：**验状态帧时卡必须全程开着**（同一个进程里"先发 PING 再监听"，不要分成两次运行）。
      ⚠ 这条对 ≤ `0918F` 是硬要求（否则自锁）；对 `0918G` 起是"避免踩恢复延迟"——
      卡中途关过，重开后就按 `(TEC−127)×5 s` 等一会儿，别急着判失败。
    - ⛔ **已被锁住时的恢复办法：本文件原来写的 `cx 1` → `cx 2` 是错的**（09-18 15:5x 实测证伪）：
      现场从 CAN2 切到 CAN1 再切回 CAN2，`cn` 读回来 **`tec=131` 一点没降**，状态帧仍然停发。
      根因：本工程**没有实现 `HAL_CAN_MspDeInit`**（走 HAL 的空弱定义），所以 `HAL_CAN_DeInit()`
      既不复位 CAN 寄存器也不关时钟；而"进出 init 模式"在这颗 MCU 上并不会清 TEC。
      ⇒ 正确恢复（两条都实测过）：
      1. **敲 `e`（内部回环自检）** —— 它内部做了一轮真正的重新初始化，**实测把 TEC 从 131 清到 7**。
         ⚠ 但 `e` 会把接口**强制切回 CAN1**（它固定测 CAN1）⇒ 必须紧跟一条 **`cx 2`** 才回到卡所在的口。
         ⚠ 清完不一定是 0（实测 7）—— **只要 < 128 就不再锁**，判据是"小于 128"不是"等于 0"。
         完整恢复序列：**`e` → `cx 2` → 再同一个进程里"先 PING 再监听"**。
      2. **按 RESET / 断电重上电** —— 最稳，开机必然 `tec=0`（但 CAN 配置会回到落盘的那一份，需再 `cx 2`）。
    - ⚠ `--monitor` 单独跑拿不到状态帧还有个前提坑：`s_seen_peer` 只在**收到过一条合法命令帧**后才置位，
      `cx` 重初始化后要**先发一条 PING** 才会解锁状态帧。

37. ⭐⭐⭐ **烧录会抹掉 CAN 配置区 —— ≤`0918G` 烧完必须 `cx 2`；`0918H` 起已从根上解决**（09-18 15:5x 提出 → 17:3x 根治）：
    `tools/flash_arm.py` 走 stm32flash，默认**整片擦除**⇒ 扇区 11 里的 CAN 配置区（红线 23）一并被抹掉
    ⇒ `CanCfg_Load()` 只能取**编译期默认值**。
    - **≤`0918G`：默认 = `CAN1`，而卡插在 `CAN2`** ⇒ "刚烧完、`h` 指纹也对、但 `can_host` 全超时"这个组合
      会**必然**出现，且极易被误判成"新固件没修好/烧坏了"。
    - **✅ `0918H` 起：默认 = `CAN2`（= 本板实际接线）⇒ 烧完直接可用，不需要这一步。**
      判据：`h` 首行有 **`defif=CAN2(PB12/PB13)`** ⇒ 跳过 `cx 2`；没有 ⇒ 照旧先 `cx 2`。
      `tools/flash_arm.py` 的烧前闸门会把这条结论直接印出来（有 `defif=CAN2` 就不会拦）。
    - ✅ 判据链：`h` 认到指纹 ① → `cn` 看 **`接口`** 那一行 ② → 不是 `CAN2 PB12/PB13` 就先 **`cx 2`** ③ → 再跑测试。
    - ⚠ 所以"指纹对"**不等于**"可以开始测了"：指纹只证明烧进去了，**接口是独立的一步**。
    - ⚠ `cx save` 只能让配置**跨 RESET** 存活，**跨不了重烧**（整片擦除必抹掉）⇒ 每次烧完都要重新 `cx 2`。
      想让"复位后还是 CAN2"：`cx 2` → `cx save`（注意 `can save` 的用法是 `can save` 子命令，别混）。
    - ⭐ 与红线 34 合起来是一条完整操作序：**烧一次 → `h` 验指纹 →（≤`0918G` 才要 `cx 2`）切口 → 同一个进程里 PING 再测**。
    - ⭐⭐ **这条红线的通用教训：「默认值」必须等于「硬件实况」**。
      一个配置项如果老是靠人工补一步才能对上现实，说明**默认值定错了**；不改默认值，
      就等于给每一次烧录都埋一个"忘了补那一步、然后去查一个根本不存在的问题"的机会。
      （同理适用于波特率、节点号、引脚组 —— 凡是"开机默认"与"现场接法"不一致的，都该把默认值改过来。）

38. ⭐⭐⭐ **"旁听"的工具可能在 ACK —— 它会亲手把被测对象改掉，于是你测出的是假阳性**（09-18 16:3x 定案）：
    想回答"**没人在 ACK 时，臂到底还在不在发帧**"（i.e. 红线 36 的自锁到底有没有真的解开），
    必须用一台**零影响**的仪器。而 PCAN 卡只要一开卡（默认 ACTIVE）就会**自动 ACK** ⇒ 它每收一帧
    就替臂把 TEC 降一格 ⇒ 臂被"救活" ⇒ 工具报"臂在发"，其实是**工具自己把它拉回来的**。
    - ⛔ **`can.Bus(..., listen_only=True)` 是个静默陷阱**：python-can 4.6.1 的 **PCAN 后端根本不认这个 kwarg**，
      直接被吞掉，你**以为在旁听、其实一直在 ACK**。正确写法是 `state=can.BusState.PASSIVE`。
      （后端实现：`pcan.py` 里只在 `state is BusState.PASSIVE` 时才 `SetValue(PCAN_LISTEN_ONLY, ON)`。）
    - ★ 一眼自检（用同一台臂、同一个 tec≥128 状态）：
      | 打开方式 | 是否 ACK | 20 s 应收 | 说明 |
      |---|---|---|---|
      | `listen_only=True` | ❌ 被忽略 → 实际 ACTIVE | **~18 帧（1 Hz）** | 是卡在 ACK，把臂拉回了 error-active |
      | `state=BusState.PASSIVE` | ✅ 真不 ACK | **4 帧（5 s 间隔）** | 探路帧本身在跑，臂仍处于 error-passive |
    - ⇒ `tools/can_listen_count.py` **已加 `--passive`**（默认仍是 ACTIVE，因为它的判读表依赖"卡在 ACK"这个前提）。
      判"臂在不在发"**一律加 `--passive`**：它会把 5 s 节奏直接判成"error-passive 探路帧"。
    - ⭐ 泛化：**任何"观测"都必须先证明自己不改变被测对象**。判据不能是"工具打印了什么"，
      而要能回答"如果我把工具关掉，结论还成立吗"。本工程里同源的坑还有：
      红线 11（`MSR.RX` 瞬时采样）、红线 36（卡一关就自锁）。
    - ⭐⭐ **再深一层：双节点 CAN 上根本没有"零影响观测"**——两种模式各往一边推：
      - `ACTIVE`（会 ACK）⇒ **向下推** TEC ⇒ 可能**掩盖**自锁（"臂在发"是假阳性）。
      - `PASSIVE`（不 ACK）⇒ **向上推** TEC（每帧 +8）⇒ 一帧就把臂推进 error-passive
        ⇒ 你会一直只看到 5 s 探路帧，**看不到"正常 1 Hz"那面**。
        （实测：臂刚从自锁恢复、再 `--passive 8 s` ⇒ 只收到 2 帧。因为 127+8 = 135 直接越线。）
      ⇒ 唯一真正零扰动的仪器是**臂自己的计数器**（`cn` 的 `tec/rec/lec` + `can` 的收发帧数 + 停发原因文案）。
        这正是本工程"判据只用臂侧计数器"的由来——**总线一定会察觉你在看它**。
      ⇒ 选模式时不只是"选对的"，是"**选你愿意接受哪个方向的扰动**"，并在结论里注明数据是哪种模式来的。

39. ⭐⭐ **LINK=net（网口 UDP）与 CAN 是引脚级互斥；而 CAN 命令在 net 固件里"还在"，必须显式拦掉**（09-20 定案）：
    - **硬件事实（F407 上没有第二选择）**：`ETH_TXD1` 只有 `PB13`，而 `PB13` 正是 `CAN2_TX`；
      `ETH_RXD1 = PC4`（原 LED_G）、`ETH_RXD0 = PC5`（原 LED_R）、`ETH_REF_CLK = PA1`（= `UART4_RX`）。
      ⇒ 一个 `LINK=net` 构建**同时废掉 CAN 从站与主从链路(UART4)**，这是编译期选边，运行期无法兼得。
      ⇒ 反过来：**"想用网口"和"想用 CAN"不能靠一条命令切换，只能重烧**（`02_slave_CANslave.bin` ↔ `02_slave_NET.bin`）。
    - ⛔ **真正的坑**：`arm_can_driver.c` / `arm_proto_can.c` 在 Makefile 里是**无条件**编译的，
      所以 net 构建里 `cx`/`ps`/`can`/`cp`/`cy`/`cz`/`cw` **仍然存在**。其中
      **`cx`（换接口）与 `ps`（引脚扫描）结尾都会调 `HAL_CAN_MspInit`，把 `PB12/PB13` 重配成 `AF9_CAN2`**
      ⇒ **敲一条命令就把网口掐死**；现象是"网口莫名不通"，从网络侧怎么查都查不出来（因为没有网络侧证据）。
    - ⛔ **也不能简单删掉这些分支**：删了就落进**首字母兜底**（`c` → `case 'c'` → 校准向导 → **松全部力矩**，红线 3/4）。
      ⇒ 正确做法是"**接住 + 说清楚**"：`main.c` 的 `ProcessCommand` 开头用 `#if ARM_LINK_NET` 拦成
      `[NET] 'xx' 已停用 …` 再 `return`。已落地，指纹带 `fix=…,nocancmds`。
    - **工具侧配套**：`arm_preflight.FW_TAG` → **`FW_TAGS` 多指纹**（`ARM-CAN-0918H` / `ARM-NET-0920B`）；
      `flash_arm.py --link net [--console-port COM11]` 走 net 专用闸门（不再拿 CAN 的 `defif`/引脚组去卡它）。
    - ⭐ **控制台口 ≠ 烧录口**：控制台恒为 `USART6(PC6/PC7)@115200`（`CONSOLE_UART`）；
      ROM bootloader 只在 `USART1/USART3/CAN2/USB` 上。现场两个 CH340 常是"一个烧录、一个控制台"。
      **便宜且可靠的判据**：`stm32flash <COM>` 只读探测 —— **能进 bootloader 的才是烧录口**；
      敲 `h` 有回显的才是控制台口。⇒ **烧录口敲 `h` 永远 0 字节，这不是故障**，别据此判"板子挂了"。

40. ⭐⭐⭐ **一个外设有**多套**合法复用脚位时，必须用"板上占用"交叉验证来选**（2026-09-20，网口首烧踩的；**正反两次都错过**）：
    - 现象：net 版固件启动后一直 `no PHY on MDIO`，但代码"看起来"把 TX_EN/TXD0/TXD1 都配了。
    - 真相：RMII 的 `TX_EN/TXD0/TXD1` 在 F407 上**有两套合法脚位**（AF11，DS8626 Table 7 两套都在）：
      **A) `PG11/PG13/PG14`** ｜ **B) `PB11/PB12/PB13`**。
      初版抄了 F42x/43x 的表写成 `PG11/PG13 + PB13`（漏了 TXD1）；
      第一次"校正"时又断言"F407 只有 PB11/PB12/PB13、PG11 只是 RXER" —— **两次都不对，而且第二次还把 A 组判死了**。
    - ✅ **定案手法（可复用）**：**把两套都列出来，然后按"板上哪些脚已被别的外设占用"筛掉**。
      本板 `PB11 = USART3_RX（舵机总线 A）`、`PB12/PB13 = CAN2` ⇒ **B 组三个全被占 ⇒ 出局** ⇒ 只有 A 组能自洽。
    - ⛔ 为什么编译器不救你：`GPIO_AF11_ETH` 只是个数字，HAL 会乖乖把 AFR 改成 11 而不报错。
      **"AF 编号对" ≠ "引脚功能对"**，这类错在编译期完全不可见。
    - ⚠ 选错的代价不止"功能不通"：用 B 组会把 **PB11 从舵机总线 A 的 RX 抢走**，
      还让 CAN 收发器的推挽 RXD 顶住 PB12 —— 属于**会顺手弄坏别的东西**的那类错。
    - ✅ 判据：写完引脚表，① 逐脚回查**该型号** RM 的 "Alternate function mapping" 表；
      ② 再和 `.ioc`/板上实际占用**交叉对一遍**；③ 开机信息里把实际用的脚位打进指纹（`txpins=…`），便于事后核对。

41. ⭐⭐ **外设的分频/时钟字段没人设 ≠ 默认值是对的**（2026-09-20，与红线 40 同一个故障的两半）：
    - 现象：MDIO 全地址 0~31 扫不到 PHY（读到 `FFFF`/超时）。
    - 真相：`HAL_ETH_Init()` **不写 `MACMIIAR`**；而 `HAL_ETH_ReadPHYRegister()` /
      `WritePHYRegister()` 每次都 `tmpreg1 &= ~ETH_MACMIIAR_CR_MASK` 之后**不回填 CR**
      ⇒ CR 恒为复位值 0 = `Div42`。本板 **HCLK = 168 MHz** ⇒ **MDC = 4 MHz**，
      超 LAN8720A 的 MIIM 上限 **2.5 MHz** ⇒ PHY 不应答。
    - ✅ 修：Init 之后手动 `MACMIIAR = (MACMIIAR & ~CR_Msk) | ETH_MACMIIAR_CR_Div102`
      （150–168 MHz 段，168/102 = **1.65 MHz**）。
    - ⭐ 通用形态：**复位值只保证"能编译"，不保证"合规格"**。MDC / I2C 时钟 / 定时器 PSC
      这类"按 HCLK 现算"的字段，一律**显式算一遍**，并把**当前实际值打进启动信息**
      （net 版 `np` 会打 `MACMIIAR=… CR=?`）—— 否则这类故障只能靠猜。

42. ⭐ **时间戳做差一律强转 `int32_t` 再比，绝不用无符号比较**（2026-09-20）：
    - 现象：文案写 `rescan every 5s`，日志却**每 64 ms 刷一行**（32 地址 × 2 ms 一轮）。
    - 真相：冷却写成 `s_state_t0 = HAL_GetTick() + 3000;` 然后判
      `(uint32_t)(HAL_GetTick() - s_state_t0) < 2` —— **减数是"未来时刻"**，
      无符号差直接回绕成 ~4.29e9，判据**恒真** ⇒ 冷却形同虚设。
    - ✅ 修：独立的 `next` 变量 + `if ((int32_t)(now - next) < 0) return;`。
    - ⭐ 附带一条**文案纪律**：日志说"5s"就得真是 5s。文案与行为不一致时，
      下一个排查的人会**按错的时间尺度去等、去推算**，比没有日志更坏。

43. ⭐⭐ **含糊的读数必须拆成"能分辨假设"的读数**——观测手段要能证伪，不能只给一个含糊数字（2026-09-20）：
    - 现象：`HAL_ETH_ReadPHYRegister()` 全地址返回 `0xFFFF`。这个值**同时对应三种完全不同的病因**：
      ① PA2 根本没接到 PHY（悬空）；② 线被外部推挽硬拉高（短路/被别的输出占）；③ 接线对但 PHY 没工作（供电/nRST/PHYAD）。
      看一眼 `FFFF` **分不出**该去查哪一头，于是排查变成猜。
    - ✅ 做法：加一条**只读**的取证命令，用 MCU 自己的引脚把含糊量拆开（`nm` 软 MIIM bit-bang）：
      · PA2 改**开漏**输出 → 读 idle 电平 / **主动写 0 看线跟不跟** / 松手用 **DWT CYCCNT** 数"多久回高"
        （回不来或很慢 = **这条线上没有上拉电阻** ⇒ 大概率脚根本没接到 PHY ⇒ 排除①）；
      · PC1 写 0/写 1 读回 → 自检这脚还能不能驱动；
      · **全 32 个 PHY 地址**逐位手工发 MIIM 读帧，每帧记下 **TA+16bit 段里 MDIO 被拉低过几次**
        （**低 0 bit = 18 拍里一次都没被拉低 ⇒ 对端根本没驱动这根线**）。
      · 另外在**状态机扫描**里也放宽判据：不只认 `IDR1==0x0007`，**同时记录任何非 `FFFF`/`0000` 的应答**
        —— 原判据只看 LAN8720A 的 ID，PHY 地址在 8..31 或换了型号时会**一律误报"没有 PHY"**（假阴性）。
    - ⭐ 通用形态：**"设备没反应"这类结论，必须能进一步落到"是线、是电、还是对端"**。
      一个观测手段如果只能给出"不通"，它就没帮你缩小假设空间 —— 等于没测。
    - ⚠ 取证命令的两条纪律：**全程只读**（不改配置、不动状态机），**退出前把引脚还给原外设**（AF11）。
      这与 CAN 侧的 `ps`/`cw`、以及红线 38（观测不得扰动被测对象）是同一套规矩。

44. ⭐⭐ **"在跳"不等于"有时钟"：比例型读数只能证明"电平会变"，证不了"有确定频率"**（2026-09-20）：
    - 现象：`np` 采 PA1 2000 次得"高 1080 / 低 920"，工具就写"在跳 ⇒ REF_CLK 有"。
      可**悬空脚捡到的噪声也"有时高有时低"**，占比同样接近 50% ——
      于是"PHY 在工作"这个结论**从未被证明过**，后面所有排查都建在一个没证的假设上。
    - ✅ 做法：把量测**升级成频率证据**，而且**用硬件外设量，不用主循环数**：
      · PA1 借给 **TIM5_CH2**（PA1 的 AF2；TIM5 是 32bit 且本工程空闲 ——
        **TIM2 被 2kHz 控制环占满，别碰**），定时器置**复位模式**
        （`SMCR = TS=TIM_TS_TI2FP2 | SMS=100`）：**每个上升沿把 CNT 清零**
        ⇒ 读到的 CNT = **距上一个上升沿过了几拍**（1 拍 = 1/168MHz = 5.95 ns）。
        真有 50MHz ⇒ CNT 永远只落在 `0..3`（168/50 = 3.36）；没有边沿 ⇒ CNT 单调涨到成千上万。
        **这条判据与主循环快慢、与中断抢占都无关**，才是"硬件级"证据。
        再放开 `SMS=0` 用**输入捕获**量相邻上升沿间隔：真时钟的间隔**又小又集中**（{3,4} 拍），
        噪声的间隔乱七八糟 —— 这是**第二条独立证据**。
      · ⭐ **必配对照实验**（红线 34 的同一条规矩）：同一量测在 **NOPULL** 与 **PULLDOWN** 下各做一遍。
        PHY 的 REFCLKO 是**推挽**输出，内部 ~40kΩ 上下拉**压不动它** ⇒ 两遍必须**一致**；
        若"NOPULL 下有边沿、PULLDOWN 下边沿消失" ⇒ **那是悬空脚噪声**，当场证伪。
      · 结论判据要求**两条独立证据都过**（[1][2] 对照一致 **且** [3] 间隔又小又集中），
        单条不足以定"PHY 在工作"。
    - ⭐ 通用形态：**"信号存在"要用频率/间隔证明，"电路连通"要用对照实验证明。**
      任何"大约一半时间是高"的读数都排除不了悬空脚 —— 那是最常见的假阳性形态。
    - ⚠ 借引脚做量测的收尾纪律：跑完把引脚**还给原外设**（AF11），并提示使用者
      "量测期间 REF_CLK 断过，建议 RESET 一次再做业务"。

45. ⭐⭐⭐ **观测量绝不能来自"我自己的循环跑多快"——自相矛盾的读数要当场判"尺子坏了"，不许挑一条信**（2026-09-20）：
    - 现象：`nt` v1（红线 44）在实机上**自己打自己**：
      · `[1]` 复位模式报 **CNT 最大 30789 拍**（≈ 整个采样循环的长度 ⇒ 计数器从头到尾**没被清过** ⇒ 一个上升沿都没有）；
      · `[3]` 捕获模式却报 **"64 个相邻沿，间隔又整齐地全是 27 拍"**。
      一个是"没有沿"，一个是"沿很规则地来"——**物理上不可能同时成立** ⇒ **至少有一条路本身是坏的**。
      ⇒ 此时不管写"有"还是写"没"，都是**猜**，而"猜"会把人送去查一个不存在的故障。
    - ⭐ 病根：`[3]` 用**软件 `while` 轮询 `CC2IF`** 去读捕获值。当信号快过轮询、或**干脆一个沿都没有**时，
      它数到的"间隔"其实是**自己的轮询周期**（实测 ≈27 拍，与实际报告的 27 拍**逐字吻合**）。
      这正是红线 11（`MSR.RX` 瞬时采样）的同族错误：**把"我的观测动作"当成了"被测对象的属性"**。
    - ✅ 修法（v2）：换成**两条机理互相独立**的硬件路径，再加一条**已知频率自检**：
      · `[1][2]` **复位模式** `SMS=100 + TS=TIM_TS_TI2FP2`：每个沿清 CNT ⇒ 读 CNT = 距上个沿几拍（无沿 ⇒ 涨到成千上万）；
      · `[3][4]` **外部时钟模式 1** `SMS=111 + TS=TIM_TS_TI2FP2`：每个沿 **CNT+1**，并用 **DWT CYCCNT 卡一个固定时间窗**
        ⇒ **窗口内边沿数 / 窗口时长 = 频率**。这条只读窗口**首尾两次** CNT，**不吃轮询快慢的亏**。
      · `[5]` **自检**：把触发源从引脚换成**已知的 `TIM3_TRGO` @100kHz**，同样量一遍。
        **自检不过 ⇒ 整段输出作废**（改判为"工具不可信"，而不是"被测对象没信号"）。
      · NOPULL / PULLDOWN 对照照旧（红线 34）。
      ⭐ 这就是"**先把尺子校准，再量零件**"：没有自检，前面那个矛盾**根本没法裁决**。
    - ⚠ **时间基必须现算，不能写死**：TIM5 在 **APB1**，本工程 `PCLK1 = 42MHz` ⇒ **定时器时钟 = 84MHz**
      （旁证：`tim.c` 里 TIM2 用 `PSC=83` 得 1MHz、`ARR=499` 得 2kHz）。v1 写死 `168MHz`
      （把 APB1/APB2 混了）⇒ **所有时间换算差 2 倍**，连"50MHz 应给 3 拍"那句参考值都是错的（应为 84/50 = 1.68）。
      ⇒ 用 `HAL_RCC_GetPCLK1Freq()` 现算；手写常数一律当 bug 看。
    - ⚠ **量程**：外部时钟模式要求 `f_in < f_TIM/2`。84MHz 定时器 ⇒ 上限 ≈42MHz，
      **50MHz 的 REF_CLK 正好在量程外**（数得到但不准）⇒ 那种读数只能当 **"有快速信号"** 用，别当频率。
    - ⭐ 通用形态：**两个工具给出互相矛盾的结论时，第一反应必须是"哪个工具坏了"，而不是"选一个更顺眼的相信"。**
      判据：**给工具配一个已知输入的阳性对照** —— 过不了对照，它说的"没有"就不算数（同时"有"也不算数）。

46. ⭐⭐ **"PHY 没在给 REF_CLK" 的硬件短路清单：一颗 LAN8720A 要同时满足 4 个 strap/外围条件才会起振并输出 50MHz**（2026-09-20）：
    - 背景：本板 `nm` 全 32 地址 `FFFF/低0bit`（**PHY 一次都没驱动 MDIO**）+ `nt` v2 两条独立路径都**数不到沿**
      ⇒ 结论一致：**PHY 没在工作**。而"没在工作"最常见的原因不是走线，而是**芯片本身的 strap/外围**：
    - 按"先量电压、再看晶振"的顺序查（全部免烧录、万用表即可）：
      ① **VDDCR ≈ 1.2V ？** LAN8720A 内部 1.2V 稳压器的输出。**若量到 0.56~0.76V ⇒ 芯片根本没跑起来**，
         连 25MHz 晶振也不会起振 —— 症状与"REFCLKO 无输出"完全一致。
         成因通常是 **`RBIAS`(24 脚) 的 12.1kΩ 下拉缺失**（原理图漏画/漏贴，最常见的坑）或 `REGOFF`(3 脚) strap 不对。
      ② **`nINTSEL`(2 脚) 必须是低**（用 25MHz 无源晶振、要芯片出 50MHz 时）。
         **悬空/上拉 ⇒ 芯片按"外部时钟输入 + nINT 中断输出"工作 ⇒ REFCLKO 一个时钟都不输出。**
         很多板把它和 **Speed LED** 复用，LED 不导通时靠内部上拉拉高 ⇒ **每次上电复位都可能锁成错误模式**
         （正点原子用跳线帽隔离 LED 就是这个原因）。⇒ 量这个脚的复位后电平，必要时 10kΩ 硬下拉。
      ③ **25MHz 晶振有没有起振？** 万用表量两端应有 0.5~1.5V 的直流偏置（两端略有差）；
         有示波器就直接看。**不起振 ⇒ REFCLKO 必然没有。**
         附带坑：RJ45 那几颗对地电容应为 **~10pF**，错贴成 0.1µF 会导致**整个晶振不起振**。
      ④ **nRST 有没有被按住？** 有的板把它接到某个 MCU GPIO（甚至接到 MCU 的 NRST）。量它应为高。
      ⑤ 最后才是：芯片贴装/虚焊、这板子到底有没有接 PHY（对原理图）。
    - ⭐ 通用形态：**"外设没反应"要先分"它没上电/没时钟"和"我没接对"。**
      一个 PHY 连 1.2V 内部电源都没起来时，**任何软件侧努力（换引脚、改分频、写驱动）都是白费**；
      先花三分钟量电压，能省掉一整轮固件迭代。
    - ⚠ 与红线 44 的接力关系：`np`（比例）→ `nt`（频率）→ **硬件电压/晶振**，
      是"**逐步把假设空间缩小**"的一条链。哪一步给出含糊结论，就该在那一步原地升级手段，别往下走。

47. ⭐⭐⭐ **"某函数返回失败"必须查到"它死在哪一句"——库函数的注释里常常直接写着失败条件**（2026-09-20）：
    - 现象：日志反复刷 `HAL_ETH_Init failed, retry`，第一反应是"MDIO 读不到 PHY ⇒ PHY 地址不对/走线虚焊"。
      **这个解读是错的**，而且它会把一整个排查方向带偏。
    - ✅ 做法：**打开它的源码，看第一句和最后一句**。`stm32f4xx_hal_eth.c` 的 `HAL_ETH_Init()`
      一上来就是 `SET_BIT(DMABMR, SR)`（DMA 软复位）→ 轮询等硬件自清 → 500 ms 超时 `return HAL_ERROR`。
      **这一段发生在任何 MDIO 操作之前** ⇒ 它跟"PHY 应不应答"**毫无关系**（HAL 全程不读 PHY）。
    - ⭐ 而 ST 自己在那个等待处的注释原文就是答案：
      *"The SWR is not performed if the ETH_RX_CLK or the ETH_TX_CLK are not available,
      please check your external PHY or the IO configuration"*
      ⇒ RMII 下 RX_CLK/TX_CLK 合起来就是那**一根 REF_CLK** ⇒ **这条 log 等价于"REF_CLK 不可用"**，
      与 `nt` 数不到边沿是**同一结论的两种测法**。
    - ⛔ **绝不要用社区偏方绕过检查**（把等待循环里的 `return` 改成 `break`）。**过检查 ≠ 能工作**：
      没有 REF_CLK 时以太网物理上不可能通，绕过它只是把"没时钟"**伪装**成"初始化成功"，
      然后让人去查别的。**报错是资产，不是障碍。**
    - ⚠ 一个函数里可能有好几个 `return ERROR`，**它们的含义各不相同**（时钟/总线/超时/参数/资源）。
      不看源码就给失败"编含义"，等于**把推理当观测**（红线 11 同族）。
    - ⭐ 落地：让失败日志**自解释** —— 打出现场值（返回值 / `ErrorCode` / 关键寄存器位），
      直接写上"这意味着什么"；**只打一次**详细版，之后每 N 次报一行简报，
      别让 500 ms 刷屏把有效日志冲掉。

48. ⭐⭐ **板上的机械可动件（拨码开关/跳线帽/短路块）必须进"变量清单"，而且它自带 A/B 对照**（2026-09-20）：
    - 现象：REF_CLK 路径上串着一只 `B1` 1 位拨码开关（`PA1 ─[B1]─ RMII REF CLK`），
      是这条路上**唯一的可动件**。**在拨通它之前，一直在按"芯片坏了"往下查**。
    - ⚠⚠ **更正（2026-09-20 傍晚）**：本条原先那条"行为反转"**方向是错的，已作废**。
      它当时写"B1 断开 ⇒ Init 成功 / B1 接通 ⇒ Init 失败"，前提是"用户已把 B1 拨通"——
      而用户随后澄清"**这才是真正接通的，上次搞错了**" ⇒ **前提错 ⇒ 结论反向**：
      · B1 **断开**（PA1 悬空）⇒ `HAL_ETH_Init` **一直失败**（`DMABMR.SR` 不自清）
      · B1 **接通** ⇒ `HAL_ETH_Init` **成功**，状态机进到 `PHY-scan`
      且它与**同一份固件**里 `nt`（TIM5 硬件数边沿）报的"没有时钟"**互相矛盾**，
      0920F 上没有工具能裁决 ⇒ 这条在实测层面**目前是悬案**，靠 0920J 的 `nt` v2 自检裁。
    - ⭐⭐ **由此得到的教训比原来那条更重要：一条"看起来恰好支持我假设"的现象，不等于证据。**
      它成立与否取决于前提，而这里的前提是"**用户口述的开关位置**"——一个易错输入。
      ⇒ 纪律：**凡依赖"人说的状态"的推理，引用前必须先用物证确认那个状态**
        （这里是断电蜂鸣档量 B1 通断）；否则它只是**把假设换了个说法**，还会因为"看起来是数据"
        而获得它不配有的可信度。这是红线 51（判据要有鉴别力）的姊妹条：
        51 说"读数要能分辨假设"，这条说"**前提要先被证实**"。
    - ⭐ 仍然成立的部分：**通路上的机械件必须进变量清单**，排查顺序
      ① 通路开关通不通 → ② 供电 → ③ 时钟 → ④ 器件/贴装。⚠ **先断电再拨**；
      判状态**量通断，不看丝印/照片**。
    - ⭐ 副产品：那张图上的网络标号是 `RMII REF CLK`（**不是** `REFCLKO`）——标号名暗示它可能是
      **共享时钟节点**而非单向输出。**读标号不能代替读连接**：它到底接到 PHY 的哪只脚，
      要顺着线走到底，这决定了"拨断这个开关会不会连 PHY 一起断粮"。

49. ⭐⭐⭐ **同一只脚在多处被配置、靠"后者覆盖前者"收敛 = 隐患；"最终值正确" ≠ "全过程正确"**（2026-09-20）：
    - 现象（本轮实查）：`gpio.c` 的 `MX_GPIO_Init()` **无条件**把 **PC4/PC5 配成推挽输出并拉低**
      （那是 LED_G/LED_R 的配置）。可在 `LINK=net` 构建里 **PC4/PC5 是 `ETH_RMII_RXD0/RXD1`
      —— PHY 驱动的输入脚**。调用顺序 `MX_GPIO_Init()`(8125) → … → `HAL_Delay(500)`(8226) →
      `NetProto_Init()`(8345) ⇒ **中间 >500 ms 两个推挽输出对着打**，互相灌电流 + 搅乱上电时序。
    - ⭐ 为什么长期没被发现：`np` 读 AFR 时**已经是 11**（`NetProto_Init` 之后才读的）
      ⇒ **读的时候是对的，掩盖了中间有一段是错的**。这类"瞬时错误"在任何"跑起来之后再看"的
      探针下都是隐形的 —— 与红线 11/45 同族：**探针看到的是你选的那个时刻，不是全过程**。
    - ✅ 修法：**所有配置点都要带构建守卫**，而不是只加在"最后一处"。
      `#if !ARM_LINK_NET` 把 `MX_GPIO_Init` 里这两段整块跳过（`LINK=uart`/`LINK=can` 行为不变）。
      验证方式：**反汇编数 `HAL_GPIO_Init` 调用次数**（net=5 / can=6，差的正好是那一段）——
      比"看源码"更硬。
    - ⚠ **CubeMX 生成文件（`gpio.c`/`usart.c`/`tim.c`…）特别容易这样**：`.ioc` 只描述**一种**配置，
      别的构建变体（uart/can/net）只能靠"事后改"；而**重新生成会静默覆盖你的守卫**。
      ⇒ 在文件里留醒目注释 + 在本文档留一条，生成后回来复查。
    - ⭐ 通用形态：**多构建变体下，"引脚语义"必须有一个唯一权威来源。**
      判据：只要某引脚在不同构建里语义不同，就去 grep 它在**整个工程**里的所有配置点
      （`MX_*_Init` / MspInit / 各自的 gpio init / 任何 `HAL_GPIO_WritePin`），
      而不是只确认"最后那个配对了"。

50. ⭐⭐ **板载手册的"脚位功能表"说的是"这只脚能干什么"，不是"它现在在干什么"**（2026-09-20）：
    - 现象：拿到板厂的引脚表后，看到 `PA1` 那一行同时写着 `U2_RTS / U4_RX / ETH_RMII_REF_CLK / TIM2_CH2`，
      于是很自然地起疑："**REF_CLK 会不会被 TIM2_CH2 或 UART4 抢了？**"
    - ✅ 正确答案只能从固件里读，而且**两条都要查到底**：
      · TIM2 → 本工程走 `HAL_TIM_Base_Init`（纯时基），`HAL_TIM_Base_MspInit` **只使能时钟、不碰 GPIO**，
        没有 PWM/输出通道 ⇒ **不占脚**。
      · UART4 → `main.c` 里 `MX_UART4_Init()` 被 `#if ARM_LINK_NET` 挡掉（net 构建不初始化 UART4）
        ⇒ **不占脚**。
      · 旁证：`np` 读 9 只脚的 AFR 全是 `11`（= `GPIO_AF11_ETH`）。
    - ⭐ 通用形态：**功能表/数据手册的 AF 列表是"候选集"，不是"现状"**。
      与红线 48（"标号名不能代替读连接"）、红线 40（"AF 编号对 ≠ 引脚功能对"）同族：
      **候选 ⇄ 实际的区分，是这类排查里最常被混淆的一对概念。**
      ⇒ 判"某脚现在归谁"的**唯一权威证据是固件里的配置点 + 器件寄存器回读（AFR/IDR）**。

51. ⭐⭐⭐ **探针"打印出来的判读句"必须和它的原始读数分开审 —— 对两个相反假设给出同一个输出的，不叫测量**（2026-09-20）：
    - 现象：`np` 的 PA1 判据是"连采 2000 次看高/低比例：**恒定** ⇒ 没时钟；**在跳** ⇒ REF_CLK 有"。
      实测 `高 1081 低 919` ⇒ 打印"在跳 => REF_CLK 有" ⇒ 人**据此认为时钟存在**。
    - ⭐ 而这个读数**在两种相反情况下完全一样**：
      · 真有 50MHz 方波 ⇒ 采样相位伪随机 ⇒ ~50%
      · **悬空脚捡到邻近走线的耦合噪声** ⇒ 也是 ~50%
      ⇒ **它没有鉴别力**。它不是"尺子坏了"，是**它压根不是尺子**。
      这就是红线 44（"在跳 ≠ 有时钟"）的原始案例，却**一直印在固件输出里**，直接把人引偏。
    - ⚠ 更隐蔽的一层：它还会与另一个探针（`nt` 的硬件边沿计数）**给出相反结论**。
      按红线 45，看到矛盾要先判"哪个工具坏了"；但如果不去审**判读句**，就会一直在
      "两个结论里挑一个信"，而真答案是"其中一个读数根本没资格给结论"。
    - ✅ 修法：**探针只输出原始量，并显式写出"这条能判什么、不能判什么"**。
      真要给结论，必须配**能区分假设**的对照（例：PA1 在 内部不拉/上拉/下拉 三态下的静态电平
      ⇒ 只有这一条能分开"悬空"与"被驱动"，见红线 52 与 `docs/网口PHY_Bringup_诊断_2026-09-20.md` §11）。
    - ⭐ 通用形态：**审工具时，既要审"它量得准不准"，也要审"它下结论下得对不对"。**
      前者是采样精度，后者是**判据的鉴别力**。工程上被后者坑的次数不比前者少。
      自检清单：① 这条读数对哪些假设是相同的？② 相同 ⇒ 立刻降级为"原始量"，不许写结论。

52. ⭐⭐ **"恰好没编进来" ≠ "安全"：判据是"所有开关的笛卡尔积"，不是"我这次构建"**（2026-09-20）：
    - 现象（本轮代码审计）：`mg`/`mp`/`mo` 的收尾**无条件**写 `Alternate = GPIO_AF8_UART4;
      HAL_GPIO_Init(GPIOA, PA0|PA1)`。而在 `LINK=net` 构建里 **PA1 = `ETH_RMII_REF_CLK`**
      ⇒ 敲一次就把 REF_CLK 掐死，**现象与"PHY 坏了"一模一样**，从网络侧怎么查都查不出来。
      之所以一直没爆：这些命令被**另一个**开关 `#if ARM_MASTER_BUILD` 挡着，而 net 构建恰好是
      `ROLE=slave`。⇒ **两个独立开关（`ROLE` × `LINK`）的笛卡尔积里有一格是坏的。**
    - ⚠ 注意这与红线 49 是**同一个病根的两种形态**：49 是"同一根脚在多处被配置"，
      这条是"同一个开关在多个组合里语义不同"。共同点：**没有一个唯一权威来源。**
    - ✅ 两道修法，都要做：
      ① **在功能侧堵** —— 把命令在 `ProcessCommand` 的 `#if ARM_LINK_NET` 块里显式拦掉，
         并**写上原因**（不是"没实现"，而是"它会掐死本构建的关键引脚"）；
      ② **验证用符号表，不用读源码** —— `arm-none-eabi-nm build_net/*.elf | grep master_gpio_loopback`
         （空 = 确实没编进来）。**比"我看源码里有 #if"硬得多**，与红线 49 的反汇编法同族。
    - ⭐ 通用形态：**任何"靠另一个开关恰好挡住"的安全，都是借来的安全。**
      做法：把所有影响行为的编译开关列成表，**逐格想象它编译出来的样子**；
      只要有一格是坏的，就在**离它最近的、和它语义相关的分支**上堵，而不是加固另一个开关。

53. ⭐⭐⭐ **内部触发(ITR)表必须按"从定时器那一行"查 —— 同一个 TS 编码，在不同从定时器上连的是不同的源**(2026-09-20)：
    - 现象：`nt` v2 的 `[5]` 自检在实机上**永远不过**（`0 个沿`），于是按自己定的规则
      打出"整段输出作废"。用户因此认为"板子侧的结论没了"——**可实际上坏的是工具自己**。
    - ⭐ 病根：代码想用 `TIM3_TRGO` 当已知 100kHz 源，写成 `SMCR = (2<<4)|7`（TS=2）。按
      **RM0090 Table 76**（TIM2..TIM5 内部触发连接）：
      ```
        从定时器  ITR0   ITR1   ITR2   ITR3
        TIM2      TIM1   TIM8   TIM3   TIM4
        TIM3      TIM1   TIM2   TIM5   TIM4
        TIM4      TIM1   TIM2   TIM3   TIM8
        TIM5      TIM2   TIM3   TIM4   TIM8      ← 本工程用的是 TIM5
      ```
      ⇒ **TIM5 的 ITR2 是 TIM4_TRGO，不是 TIM3！** 要接 TIM3_TRGO，TIM5 必须用 **TS=1(ITR1)**。
      而 TIM4 在本工程**从没配置过、时钟都没使能** ⇒ TRGO 永不动 ⇒ 一个沿都数不到。
      ⇒ **同一个 TS=2，在 TIM4 上是 TIM3_TRGO（对），在 TIM5 上是 TIM4_TRGO（错）。**
    - ⚠ 这类错误的隐蔽性：`SMS=111`/`CEN=1`/`TS=2` 全都是**合法取值**，编译器、寄存器回读、
      HAL 都不会报错——它只是**静静地听一根安静的线**。与红线 40（`AF 编号对 ≠ 引脚功能对`）
      完全同族：**"编号对"不等于"指向对"**，必须查那张"哪个编号指向谁"的表，而且**要查对行**。
    - ✅ 落地：把这四行表直接抄进代码注释，并在同一处**用第二个从定时器当见证**
      （见红线 55）。判据从"自检 ✔/✗"升级为"**两条独立从定时器数同一个源**"。
    - ⭐ 通用形态：**任何"用编号选源"的机制（ITR/EITR/DMA 请求映射/AF/EXTI 线），
      都要问一句"这个编号在这条路径上指向谁"**；同一个编号在不同宿主上的指向不同的，
      是这类外设最常见的坑。

54. ⭐⭐⭐ **"自检失败"不是证据 —— 自检本身也是被测对象；一个从来没通过过的自检，不能用来否定被测目标**(2026-09-20)：
    - 现象：`nt` 的 `[5]` 自检（阳性对照）**一次都没有跑通过**。按写在固件里的判据，
      它输出"自检不过 ⇒ 整段作废"。于是整个"有没有时钟"的调查被**一次次挡回来**，
      而每次挡回来都被当成"被测对象无法判定"，**没人去审那把尺子**。
    - ⭐ 关键区分：**"自检失败"有两种完全不同的含义**——
      ① 被测对象没信号（自检是对的） ② **自检自己接错了/坏了**（自检是错的）。
      只有 ① 能变成证据。要区分它们，**自检必须自带"我为什么会失败"的信息**，
      而不是只输出 pass/fail。
    - ✅ 落地（0920K）：自检改成**三路互证 + 明确归因**：
      · `[5]` 自检A：**自由跑 + DWT 定窗**（不依赖任何触发源）⇒ 验证"定窗/计数器"本身；
      · `[5]` 自检B：已知 100kHz 的 `TIM3_TRGO` **同时喂 TIM5(ITR1) 和 TIM4(ITR2)**
        ⇒ TIM4 是**独立见证**。四条归因路径：
        `T5≈T4≈期望` ⇒ 链路好；`T4≈期望、T5=0` ⇒ **TIM5 的 ITR 通路坏**；
        `T4=T5=0 且 TIM3 不在跑` ⇒ TIM3 没起振；`T4=T5=0 且 TIM3 在跑` ⇒ TRGO 没出去。
      · `[5]` 还**回读 PA1 的 AFR**（应为 2=AF2_TIM5）⇒ 证明"借脚"这个动作真的生效了。
    - ⭐ 通用形态：**阳性对照的"阳性"也必须被证明。** 一个从未通过过的自检，其失败
      只能说明"这条链路上的某一环不确定"，**不能指向被测对象**；此时正确的动作是
      **给自检加第二条独立见证**，而不是接受它的结论。
      与红线 45（矛盾读数先判尺子坏了）、51（判读句要单独审）是同一条纪律的第三次出现：
      **先用已知答案验证测法，再用测法去测未知。**

55. ⭐⭐ **"对同一个激励，用两条互不依赖的路同时观测" —— 这既是自检，也是最强的定位手段**(2026-09-20)：
    - 背景：`nt` 前面四条测量（`[1]~[4]`）**全都**走 `PA1 → TI2FP2 → TIM5` 这**一条**路。
      而 `[5]` 走的是内部 ITR —— **它校准不到"引脚→TI2"这一段**。于是"0 个沿"始终有两种解释：
      "线上真没信号" / "信号有、进不了定时器"，而两者的处置**完全相反**。
    - ⭐ 手法（0920K `[6]`）：把 PA1 临时配成 `AF2_TIM5` 的**输入型**通道（`CC2S=01`
      ⇒ 输出驱动关闭，只有内部 40k 上下拉在起作用 ⇒ **电气上不可能和外部驱动器对着打**），
      再由软件来回搬动内部上下拉，制造一串**已知的人工方波**；然后**同时**用
      `IDR 软采样`和 `TIM5/TI2` 两条互不依赖的路去观测**同一次激励**：
      · 电平跟着走 + TI2 也数到 ⇒ **通路完好**（这才是真正的阳性对照）；
      · 电平跟着走 + TI2 数到 0 ⇒ **通路坏**（当场定位到"引脚→TI2"，而不是板子）；
      · 电平**不**跟着走 ⇒ 节点有**外部驱动器**（不是悬空）—— 这本身就是结论。
    - ⚠ 三条纪律：
      ① **激励必须是"我造的、我知道它应该长什么样"**，不能拿被测对象自己的信号当激励；
      ② **不要用输出驱动去驱动一个可能有外部驱动器的节点**（两个推挽对着打会灌大电流）
         ⇒ 用内部上下拉这种**只"软拉"不"硬推"**的手段，或者先把串联的机械件断开；
      ③ 观测端至少要两条**机理不同**的路，否则"两条路一起坏"就看不出来。
    - ⭐ 通用形态：**"测一个点"和"测一条链路"是两件事。** 链路里的每一段都要有自己的
      阳性对照；如果某一段只能靠"我相信它"，那它就是这段结论里**唯一**的薄弱环节，
      应该优先去测它，而不是继续在那个结论上加推论。

57. ⭐⭐⭐ **HAL 的 `TIM_TS_*` 宏已经包含 TS 字段移位，函数里不能再 `<<4` —— 否则编码会截断成 ITR0/TIM2**(2026-09-20)：`n    - 现象：0920L 的 `nt [5]B` 输出"TIM4 数到 2000 沿、TIM5 数到 0"，且 `[6]` IDR 跟着走但 TI2=0；
      按当时判读会得出"TIM5 的 ITR1 通路坏 / PA1→TI2 通路坏"。
    - ⭐ 病根：`netclk_tim_extclk_mode(TIM_TS_ITR1)` 函数内部仍写 `(ts << 4) | SMS`。
      查 `stm32f4xx_hal_tim.h`：
      ```c
      TIM_TS_ITR1       = 0x0010   /* TS=001, 已左移 4 位 */
      TIM_TS_ITR2       = 0x0020   /* TS=010, 已左移 4 位 */
      TIM_TS_TI2FP2     = 0x0060   /* TS=110, 已左移 4 位 */
      TIM_TS_ETRF       = 0x0070   /* TS=111, 已左移 4 位 */
      ```
      于是 `(TIM_TS_ITR1 << 4) | 7 = 0x0107`，SMCR 的 TS 字段(bit6:4)只取到 `000` = **ITR0(TIM2)**；
      `(TIM_TS_TI2FP2 << 4) | 7 = 0x0607`，TS 字段同样被截断成 `000` = **ITR0(TIM2)**。
      本工程 TIM2 没配 TRGO，所有"听 ITR1/TI2FP2"的测量实际都在听一个静止的 ITR0 ⇒ 全 0。
    - ✅ 修法（0920M）：`netclk_tim_reset_mode` / `netclk_tim_extclk_mode` 改成
      `TIM5->SMCR = ts | TIM_SLAVEMODE_*`（HAL 宏不再二次移位）；TIM4 旁证因为直接写
      `TIM_TS_ITR2 | TIM_SLAVEMODE_EXTERNAL1`，不受影响，所以它能数到。
    - ⭐ 通用形态：用 HAL 宏还是手写数字都可以，**但整个项目只能统一一种约定**：
      · 若传 HAL 宏（已移位）⇒ 函数内部**禁止**再 `<<4`；
      · 若传裸 TS 编号（未移位）⇒ 函数内部必须 `<<4`，且**所有调用点**都得传裸数字。
      混用是灾难。审查时看见 `TIM_TS_` 和 `<<4` 同框，直接判 bug。

56. ⭐⭐⭐ **定时器 `TS` 触发源不要手写数字 —— `TS=7` 不是 TI2FP2，而是 ETRF**(2026-09-20)：
    - 现象：0920K 的 `nt [6]` 输出"上下拉脉冲 400 次、IDR 跟着走 201 次、TI2 数到 0"，
      按当时判读会得出"PA1→TI2 通路坏"。但 AFR 回读=2、CC2S/CCER 都对，**板子/引脚不该背锅**。
    - ⭐ 病根：`[1]~[4]` 与 `[6]` 都写了 `SMCR = (7<<4)|SMS`，作者以为 `7=TI2FP2`。
      查 `stm32f4xx_hal_tim.h`：
      ```c
      TIM_TS_TI1FP1 = 5   /* 101 */
      TIM_TS_TI2FP2 = 6   /* 110 */
      TIM_TS_ETRF   = 7   /* 111 */
      ```
      ⇒ 0920K 实际一直在数 **ETR 引脚**（本工程没接），不是在数 PA1/TI2。于是
      `[6]` 的"IDR 跟着走但 TI2=0"不是通路坏，而是**触发源选错**。
    - ✅ 修法（0920L）：所有 TI2 路径统一写 `TIM_TS_TI2FP2`；ITR1/ITR2 也写
      `TIM_TS_ITR1` / `TIM_TS_ITR2`，不再出现裸数字。
    - ⭐ 通用形态：外设里凡是"编号选源"的字段（`TS`/ITR/DMA 映射/AF/EXTI），
      **合法值 ≠ 指向对**；手写数字最容易把"相邻编码"写成"另一个输入"。用厂家头文件宏，
      或把编码表抄在注释里并配阳性对照。

58. ⭐⭐ **用定时器"外部时钟模式1"数高频信号时，输入频率不能超过 `fCK_INT/2`**(2026-09-20)：
    - 现象：0920M 的 `nt [3][4]` 对 PA1 只读到 **~34 MHz**，但 LAN8720A 的 REFCLKO 应该是 50 MHz，
      初看会怀疑"时钟不对/不是 REF_CLK"。
    - ⭐ 病根：STM32F4 定时器外部时钟输入经过内部同步，**最大可靠频率约为 `fCK_INT/2`**。
      TIM5 在 APB1 上，fCK_INT = 84 MHz ⇒ 上限 ≈ 42 MHz。50 MHz 已超上限，会**欠采样/漏计**，
      读出来的绝对频率低于真实值，甚至随相位跳动。
    - ✅ 判读：`[3][4]` 的绝对数值不准，但"有高频信号"这个定性结论仍成立；更可靠的证据是
      `[1][2]` 复位模式"CNT 最大 2 拍"（= 连续沿间隔极短）和 `np` 对 PA1 的 2000 次采样比例
      接近 50/50（真方波随机采样）而非悬空噪声。
    - ⭐ 通用形态：**不要让测量工具的量程限制反过来否定被测对象。** 若读数"接近上限但不到"，
      先确认工具上限，再决定是"信号频率错"还是"工具在欠采样"。

59. ⭐⭐⭐ **PHY 的 nRST 是 MCU 的一个 GPIO，初始化前必须主动给复位脉冲 —— 漏了它，PHY 会一直卡在复位：REF_CLK 有、MDIO 死**(2026-09-21)：
    - 现象：板子网口全部诊断呈"**时钟部分活、SMI 部分死**"：`nt` 证明 PA1 有 REF_CLK 且通路完好、
      B1 OFF 后归零(证明时钟来自 PHY)；`nt`/`np` AFR 全 = 11；`nm` 里 MDC 驱动正常、MDIO 上拉在、
      但 **32 个地址读帧中 MDIO 一次都没被拉低**；`nx` 报 `phy NOT found addr 0`；
      `HAL_ETH_Init` 却"能过"（REF_CLK 已满足 MAC）。折腾了一整天，从"板子坏了"到"芯片 defective"。
    - ⭐ 病根：板厂 V6.1 的 LAN8720A **nRST(pin15) 接到 STM32 的 PE2**，官方 UB 例程
      `USER/LAN8720/lan8720.c` 里写着 `#define LAN8720_RST PE2`，并在初始化前主动
      `RST=0; delay_ms(50); RST=1;`。
      本工程 `Core/Src/arm_net.c` 的 `net_gpio_init()` **只配了 PA/PC/PG，从未使能 GPIOE、
      从未碰过 PE2** ⇒ PE2 复位后是**浮空输入**，nRST 被外部电路/漏电拖住 ⇒ PHY 数字核(含 SMI)
      一直不工作，模拟侧时钟缓冲却仍能出 REF_CLK。**所有现象一次解释清楚。**
    - ✅ 修法（0920N）：`net_gpio_init()` 里加 `__HAL_RCC_GPIOE_CLK_ENABLE()`，
      PE2 = 推挽输出，先 `HAL_GPIO_WritePin(GPIOE, GPIO_PIN_2, RESET)` 拉低 ~55 ms，
      再 `SET` 拉高 ~10 ms，**然后才进 `HAL_ETH_Init`**。
      烧后实测：`LAN8720A found at PHY addr 0 (id 0007.C0F1)`、`link up 100M full-duplex`、
      UDP PING/GET_STATUS/PARAM_COUNT 全通。
    - ⭐ 通用形态：**"某外设的复位/使能脚是 MCU 的一个 GPIO"这件事，只能从板厂例程/原理图确认，
      不能从数据手册推。** 用 MCU 去驱动一个"看起来自己在工作"的外设时，先问三句：
      ①它的复位脚是谁？②它有没有 power-down / enable 脚？③地址 strap 脚在哪？
      **"时钟在跳"永远不等于"芯片启动了"** —— 时钟路径和数字核可以独立存活。
    - ⭐ 排查形态（通用）：当证据出现「A 部分活(时钟)、B 部分死(SMI)」的**非对称**时，
      不要在两个结论之间反复横跳，**去找那个"只影响 B、不影响 A"的物理原因** ——
      通常是"某个使能/复位离散信号缺失"，而不是"芯片整体坏"。

60. ⭐⭐ **上位机/工具的"判据"必须回到协议规格书逐字节对，不能凭 ACK 的直觉写**(2026-09-21)：
    - 现象：网口已全通，但 `tools/arm_net_host.py --ping` 打印
      `✅ PING: 回包 cmd=0x81 proto_ver=1 err=7`，看"err=7"像业务错误，
      差点去查舵机总线。
    - ⭐ 病根：协议规定 `0x01 PING → 0x81: u8 proto_ver, u8 run_id`（LEN=2，
      见 `sdk_package/03_INTERFACE §3.4`、`Core/Inc/arm_control_protocol.h`、
      参考实现 `sdk_package/python/example.py`）。
      **PING 是查询类，回的是 `0x81`，不是控制类的 `ACK(0x7F)+{orig_cmd, err}`**。
      工具却按 `rcmd==0x7F and rpl[1]==0` 判，于是把第 2 字节的 **run_id=7 当成 err=7**，
      并且永远判不了"链路全通"。
    - ✅ 修法：`--ping` 改判 `rcmd==0x81 and len(rpl)>=2`，打印 `proto_ver/run_id`；
      失败时打印原始 payload hex 供对照。
    - ⭐ 通用形态：**同一套协议里"查询类"和"控制类"的响应形态本来就不同**
      （查询 = `CMD|0x80` + 数据；控制 = `0x7F`/`0x7E` + {原命令, 错误码}）。
      写任何客户端/测试脚本时，"响应码表 + 每种响应的 payload 布局"要从规格书抄，
      **不要让"我觉得应该回 ACK"决定判据**。判据写错 = 自己造一个假故障
      （与红线 51「判读句必须有鉴别力」同族）。

61. ⭐⭐ **算校验和之前，必须先把"校验和字段本身"清零 —— "复制原报文再改两个字段"是必踩的坑**(2026-09-21)：
    - 现象：`nx` 显示 `icmp(ping)=3`（板子**收到了** 3 个 echo request），但 PC 侧 `ping`
      **100% 超时**。UDP 命令收发却完全正常。
    - ⭐ 病根：`Core/Src/arm_net.c` 的 ICMP 应答路径用了"**复制请求头 + 改两处地址**"的写法，
      而 `udp_send()` 是"**逐字段写**"。两处都漏了清校验和占位：
      ```c
      /* ✗ 旧: 注释写着"清校验和", 实际只清了 type/code */
      ic[0] = 0U; ic[1] = 0U;
      uint16_t c = ip_checksum(ic, ilen);      /* 请求的旧 ICMP 校验和还在 ic[2..3] 里 */

      /* ✗ 旧: 复制 IP 头前 12 字节 ⇒ 旧头校验和也被带进 hdr[24..25] */
      memcpy(&hdr[14], &p[14], 12U);
      uint16_t c2 = ip_checksum(&hdr[14], 20U);
      ```
      `ip_checksum()` 是对整段求和再取反。**被求和的字段里如果还留着别人（或自己上一版）
      的旧校验和，结果必然错**，而错的是校验和本身 —— 于是包被对端协议栈静默丢弃，
      本地计数器却一路正常（收到、回发都 +1），形成"看得见计数、看不见回包"的假死。
      **对照 `udp_send()`：`f[24]=f[25]=0U;` 那一行就是正确做法。**
    - ✅ 修法（0920O）：ICMP 侧 `ic[2]=ic[3]=0`（连同 type/code 一起清）；
      IPv4 头改成**逐字段写**（`Ver/IHL、TOS、TotalLen、ID、flags、TTL、proto、src、dst`），
      校验和字段显式清零后再算。顺带把 IHL 固定成 5（无选项），避免请求带 IP 选项时长度对不上。
    - ✅ 离线自证（不烧板）：用 python 复刻两版算法跑同一个标准请求 ——
      旧版"IP 校验 ✗无效 / ICMP 校验 ✗无效"，新版"两个都 ✔有效"。**改硬件前先做这种离线复刻。**
    - ⭐ 通用形态：**任何"就地改写再重算校验"的地方，都要先问一句"这个字段里的旧值清了吗"**。
      手写网络/协议栈（IPv4、ICMP、TCP、UDP、组帧 CRC）时统一约定：
      **要么全新组装（推荐），要么显式清零所有被重算的字段**；"复制+打补丁"最容易漏。
      同族：红线 60（判据要照规格书）、红线 51（判读句要有鉴别力）——
      **现象和实现之间永远隔着"你确认过的那一步"**。

62. ⭐⭐ **回包/应答缓冲区要按"对端最大能发多少"定，不能按"默认包多大"定**(2026-09-21)：
    - 现象：0920O 修好 ICMP 校验和后，`ping`(默认 32B) 已可用；但把同一段代码拿来
      做边界推演时发现 `ping -l 1000` 会**写穿缓冲区**。
    - ⭐ 病根：ICMP 应答帧缓冲写成 `static uint8_t f2[34 + 74U];` —— 这个 `74`
      是"**默认 ping：20(IP)+8(ICMP)+32(数据)+14(MAC) = 74**"算出来的，
      而 `ilen = len - 14 - ihl` 直接来自**收到的帧长**。对面 `ping -l 1472`
      ⇒ `ilen ≈ 1488` ⇒ `memcpy(&f2[34], ic, 1488)` 越过 `f2` 边界 1400+ 字节，
      踩掉紧随其后的静态变量。**收发两端尺寸不对称，是最隐蔽的一类越界。**
    - ✅ 修法（0920P）：`static uint8_t f2[NET_BUF_SIZE];`（与 RX/TX 池同尺寸 1536），
      并加 `if (34U + ilen > sizeof(f2)) return;` 兜底。BSS 只涨 1424 B（73.5K / 128K）。
    - ✅ 验证方式（不烧板）：**把固件那段逻辑用 python 逐行复刻**，喂 32B / 0B / 56B / 1000B
      四种请求，打印"写了 f2[34:N] 是否越界"。复刻成本极低，却能一口气查出长度域、偏移域、
      校验和域三类问题（红线 61 也是这么抓到的）。
    - ⭐ 通用形态：凡是"**入参长度来自外部**"的缓冲区，一律问三句：
      ① 这个尺寸是按谁算的？② 对端能不能发更大？③ 越界时是拒绝还是截断（必须显式选一个）。
      同族：红线 61（重算前先清字段）、红线 5（`vsnprintf` 返回值陷阱）——
      **长度域 bug 不爱崩溃，爱悄悄改邻居，最难查。**

63. ⭐⭐ **"通没通"要先分成「对端没发」「发了没到」「到了被丢」三态，各用各的观测层；串口静默 ≠ 板子死**(2026-09-21)：
    - 现象：`ping` 100% 超时 + 串口敲 `h` **0 字节** ⇒ 极易下结论「板子死了 / 没烧进去」。
    - ⭐ 真相：板子**在回** ICMP，只是**校验和字段=0x0000**，Windows 在 IP 层**静默丢弃**。
      `ping` 和普通 raw socket **都看不见**这种包（它们只看协议栈已经收下的），
      只有 **NDIS 层（Npcap）**能看到「发了、但坏了」的帧。⇒ **判据必须放在能看见坏包的那一层。**
    - ✅ 工具：`tools/net_capture.py`（需管理员 + Npcap）。逐帧打印 IP/ICMP 校验和的
      **实际存值 vs 正确值**；`--ihl6` 认固件代次、`--ping-payload N` 压回包缓冲、
      `--forge-zero` 把「回包内容坏了」与「只是校验和字段没写」**分离**。
    - ✅ 判活别只看串口：`tools/arm_net_host.py --ping --status`（UDP）能回
      `proto_ver / run_id` 就说明**主循环 + 协议栈都活着**。串口无输出应先查
      **TX 线是否接到板上 PC6(USART6_TX) / 是否共地 / 波特率**，而**不是**判死。
    - ⭐ 通用形态：**"收不到"永远先分三态**（发送端计数器 / NDIS 抓包 / 协议栈），
      每态一个观测层；**用错层 = 用错判据**，会得出完全相反的结论。
      配合：反汇编确认**仓库里的 .bin 真的含修复**（`objdump` 找那条 store），
      才能把锅从"代码"推到"板上跑的不是这个 .bin"。
      同族：红线 51（判读句要有鉴别力）、红线 60（判据照规格书）。

64. ⭐⭐⭐ **改完固件必须让"指纹"能区分新旧；而且指纹的输出本身不能超限**(2026-09-21)：
    - 现象：用户重烧后行为**一字不变**，于是只能在「没烧进去」和「代码没生效」之间空转。
    - ⭐ **根因是"可观测性"塌了，两层**：
      ① **同 tag 的两次构建 = 没有版本号**。板子 `h` 回的字面量就是 `fw-tag ARM-NET-0920P`，
         而"带修复的那份"也是 0920P ⇒ 从板上**根本分不出**烧的是哪一份。
         **⇒ 只要代码有实质改动，就动 tag（或至少加一个 fix token）。**
      ② **指纹所在的输出行被静默截断**。`cprint()` 是 `char buf[256]`+`vsnprintf` 钳位，
         横幅那条拼接到了 **368 B** ⇒ 现场只看到 `...np-text-fix,ne` 就断了，
         而**区分版本的那几个 token 恰好排在 255 字节之后**（被截掉）。
         更坑的是：0920J 的横幅 **343 B 也 >255**，所以 J~Q 各版**前 255 字节完全一样**
         —— 截断之后,"逐版对比横幅"这条路彻底失效。
    - ✅ 修法：**每条 `cprint` 的成品 ≤255 B**（超长拆成多条，或用 `cprint_long()`）；
      横幅拆开后 fix 清单**完整可见**。新增 `tools/check_cprint_len.py` 把这条从
      "靠人记住"变成"跑一下就知道"（会按**真实字节**算，转义也算对）。
    - ⭐ 通用形态：**排查卡住时，先问"我凭什么判它换了"**。判据不够细、或被截断、
      或落在看不见坏包的层（红线 63），都会让人在错误的两个选项间反复横跳。
      同族：红线 5（`vsnprintf` 返回值陷阱）、红线 62（缓冲区按对端最大定尺寸）、
      红线 63（三态分层观测）。

65. ⭐⭐⭐ **"软件自检说对、外部观测说错"时，不要在软件层继续翻代码**(2026-09-21)：
    - 现象：固件自检报「算得 == 帧里 ✔」（软件确实把校验和**算对并写进了缓冲**），
      但线上抓包仍是不带校验和的帧。**两个观测都可信，却互相矛盾**。
    - ✅ 三步定址法（本工程一次烧录即可做完）：
      ① **同一帧内的对照字段**：一帧里天然有**两个**由同一句 `memcpy` 搬运的校验和
         （IP 头 `[24..25]` 与 ICMP `[36..37]`）。一个**能**上网线、一个**不能**
         ⇒ 既证明**搬运/内存没问题**，又把范围缩到**那几个字节**。
      ② **跨协议对照**：再发一条 UDP 回包，看**同一池偏移**（UDP 的 `[34..37]` = 源/目的端口）。
         该处**完好**而 ICMP 的同偏移被清零 ⇒ **不是内存别名/踩踏**（普通写坏做不到"按协议挑字段"）
         ⇒ 只剩**认得出协议的硬件**。
      ③ **沿数据通路逐跳回读**：`f2` → 发送返回后回读池 → 描述符 → 寄存器。
         把"内存被写"与"介质被改写"分开。
    - ⭐ 最好再准备一个**反向利用（reverse-utilisation）开关**：既然怀疑某机制在改数据，
      就用运行期开关把它**显式打开**——让"假设成立的修复"与"假设不成立的反证"
      **共用同一次烧录**（本工程 `nx hwck 1` 让 MAC 自己去算校验和）。
    - ⭐⭐ 判据要能**复现再消灭**：能用开关让 bug 出现、再让它消失，才把"相关"升级成"因果"。
      同族：红线 51（判读句要有鉴别力）、红线 63（三态分层观测）、红线 12（别按结构猜字节）。

66. ⭐⭐⭐ **"我没开" ≠ "它是关的"：HAL 的 TX 描述符默认就开着校验和插入（`CIC`）**(2026-09-21)：
    - 事实（`stm32f4xx_hal_eth.c`）：
      * `ETH_DMATxDescListInit()` **:3050 无条件** `SET_BIT(DESC0, ETH_DMATXDESC_CHECKSUMTCPUDPICMPFULL)`
        ⇒ 初始化后**每个 TX 描述符的 `CIC = 0b11`（TCP/UDP/ICMP 全计算）**。
      * 发送时 `ETH_Prepare_Tx_Descriptors()` **:3152 有守卫**：只有
        `pTxConfig->Attributes & ETH_TX_PACKETS_FEATURES_CSUM` 为真，才执行
        `:3154 MODIFY_REG(DESC0, CIC, ChecksumCtrl)`。
      * ⇒ 我们把 `Attributes = 0`（本意"什么都不用 HAL 管"）时，**HAL 一辈子不会去动 `CIC`**，
        那两位就一直是初始化时设的 `0b11`。**"我没开"变成了"它是开的"**。
    - 现象（非常难认）：**MAC 在发送时按帧内容重算并改写校验和字段**，板子发出去的帧
      **和内存里的不一样**；IP 头校验和看着对（MAC 算得对），**ICMP 却变成 `0x0000`**
      （头文件注释：`FULL` = "**including pseudo header**"，而 ICMP **没有伪首部** ⇒
      "先清零再写回"的清零留下了 `0x0000` 就上网线了）。
    - ✅ 修法：发送前**显式**把 `CIC` 清 0——
      `s_txcfg.Attributes |= ETH_TX_PACKETS_FEATURES_CSUM; s_txcfg.ChecksumCtrl = ETH_CHECKSUM_DISABLE;`
      （`ETH_CHECKSUM_DISABLE == ETH_DMATXDESC_CIC_BYPASS == 0`）⇒ 让 `:3154` 每次发送都清位；
      或初始化后 `CLEAR_BIT(s_dmtx[i].DESC0, ETH_DMATXDESC_CIC)`。
    - ⭐ **通用形态**：凡"外设会自己改数据"的功能（**校验和插入/卸载**、CRC、padding、
      VLAN 插入/剥离、timestamp），都必须**回读描述符/寄存器**确认状态，
      **绝不能读自己的 config 结构体**（红线 40 同族，但更阴：这次被改的是
      **我们自己发出去的数据**，表现为"介质上的帧 ≠ 内存里的帧"）。
      判据：`nx` 读 `DESC0` —— `0x00D00000` = `TCH(0x00100000) | CIC_FULL(0x00C00000)`。

67. ⭐⭐⭐ **共享外设被"诊断命令"重配后，必须能恢复；而且必须留一个"回读判据"兜底**(2026-09-21)：
    - 事实：本工程的 **`nt`（REF_CLK 时钟体检）会把 `TIM4` 拿去当"旁证从计数器"**，
      直接写 `PSC/ARR/CCER/CCMR`。⇒ 任何**拿 TIM4 做正经事**的模块
      （如新加的 RC PWM 输入捕获 `arm_rc.c`）在跑过 `nt` 之后会**静默失效**：
      不报错、不抛异常，只是**永远没有样本**。"接线没问题、代码也没报错，就是没数"
      —— 这类静默失效是最难查的一类。
    - ✅ 三层防护（`Core/Src/arm_rc.c` 就是照这个做的）：
      ① **收尾自动恢复**：`nt` 处理块结束前调 `ArmRc_Reinit()`；
         ⚠ 必须 `HAL_TIM_IC_DeInit()` + **全量重配**，**不能只重开中断** ——
         PSC/ARR/CCER/CCMR 全被改过，只开中断会恢复成一个"看着跑了但数不对"的状态。
      ② **回读判据**：`rc` 打印 `CCER/CCMR1/CCMR2/PSC/ARR` 的**实测值 + 期望值逐项比对**，
         被改掉的那一项后面打 `!`。（这是红线 66 "读寄存器，不读 config 结构体"的直接应用。）
      ③ **手动兜底**：`rc reinit`。
    - 同族（都是"某段代码把共享外设 / AF 改成自己的用法，别人就废了"）：
      * `cx/ps/can` → `HAL_CAN_MspInit` 把 **PB12/PB13 变 AF9_CAN2**，而 net 构建里那是
        ETH_RXD1/TXD1 ⇒ 敲一条命令掐死网口（已在 NET 构建里**显式拦掉并说明**）；
      * `mg/mp/mo` → 收尾**无条件**把 **PA0/PA1 还原成 AF8_UART4**，而 net 构建里
        PA1 = ETH_REF_CLK；
      * CubeMX 重新生成覆盖手写守卫（红线 49）。
    - ⭐ **通用形态**：**"A 模块配的外设，B 模块也会去动"时 —— 谁后动谁负责恢复；
      而且必须留下一个"能一眼看出被改过"的回读判据。** 只做恢复、不留判据 ⇒ 下次仍然查半天。

68. ⭐⭐⭐ **流式直写的限位来自 RAW 数组；该数组未标定时是全 0 ⇒ `clamp_raw()` 把六轴全部推向 raw 0**(2026-09-22)：
    - 事实链（全部代码级，可逐条复核）：
      * `cmdStreamJoints()` 逐轴钳位用 **RAW 限位**：`clamp_raw(want, JOINT_MIN_RAW[j], JOINT_MAX_RAW[j])`（`main.c:1952`）；
      * `JOINT_MIN_RAW / JOINT_MAX_RAW` 的**静态初值是全 0**（`main.c:998 / 999`）；
      * 这两个数组**只在 `apply_calib_limits()` 里被填**（`main.c:1419`），而它遇到
        "未校准哨兵"就跳过：`if (span == 0 || span < 20U) continue;`（`main.c:1418`）；
      * `calib_min_raw` 初值 = `{4095,4095,4095,4095,4095,4095}`、`calib_max_raw` = `{0,…}`
        （`main.c:1005 / 1007`）⇒ `span = raw_dist_fwd(4095, 0) = 1` ⇒ **必被跳过**；
      * `apply_calib_limits()` 的**唯一上电调用点**在 `pid_load_startup()` 内，
        且位于 `PID_FlashLoad(...)` 成功且 `limits_loaded` 的分支里（`main.c:1466`）
        ⇒ **Flash 里没存过标定 ⇒ 上电根本不会被调用**。
    - 后果：`clamp_raw(want, 0, 0)` → `raw_in_range` 失败 → `dm == dx` → **返回 `mn == 0`**
      ⇒ **六个关节的目标全被改写成 raw 0**。
    - ⚠ **唯一的兜底是巧合**：改写成 raw 0 后 `stream_pose_ok()` 用 FK 算末端 z 低于
      `traj_z_floor_mm` ⇒ 拒帧 ⇒ 臂不动。**这是"安全但不工作"，不是设计意图，不能依赖。**
    - ✅ **判据（不改代码就能查）**：启动横幅必须有
      `Joint calibration limits loaded from Flash.` + `Work ranges applied (6 jnt)`；
      缺后一行 ⇒ 数组全 0 ⇒ **绝不能让臂进流模式**。
    - ✅ **凡走 `cmdStreamJoints()` 的新功能，入口必须加硬守卫**：六轴有一个 RAW 限位是 0
      就拒绝启动。首个落实点 = `arm_rc_ctrl.c` 的 `rc ctl 1`
      （见 `RC_cfg_final_2.12_2026-09-22.md` §2.12.5）。
    - ⭐ **通用形态**：**"默认值恰好等于一个合法但危险的值"是最难发现的一类** ——
      这里是 `mn = mx = 0`，恰好被解释成"把所有轴都推到 0"而不是"不生效"。
      凡"数组/结构体未初始化就参与钳位/映射/换算"的地方，都要追问一句：
      **"它没被填的时候，会变成什么？"**（同族：红线 66 的"默认值必须等于硬件实况"）。

69. ⭐⭐⭐ **运行期"当前在用哪条链路"只能用「启动时冻结的生效值」；而"偏好"本身必须默认「全关」**(2026-09-22)：
    - **背景**：CAN 与网口在**引脚**上互斥 —— `PB13 = ETH_TXD1` 同时 = `CAN2_TX`（AF11 / AF9 二选一）；
      `PC4/PC5 = ETH_RMII_RXD0/RXD1` 同时 = 原绿/红 LED。而串口 `USART6(PC6/PC7)` 与两者**都不冲突**
      ⇒ **串口常通**，也是"切换链路"唯一可靠的通道。
      新增 `LINK=both` 单固件 + 控制台命令 `link can|net|off` / `link save`，把"这次开哪条"变成
      Flash 里持久化的偏好（扇区 11 **区 C** `0x080E2000`）。为此 `flash_cfg.c` 由「两区互保」
      泛化为**「三区互保」**，保区缓冲 4KB → 8KB（这是加第三个配置区的必然代价）。
    - ⚠ **坑（本轮自审时发现并已修）**：`LinkCfg_Get()->mode` 是**偏好** —— 用户敲 `link can` 会**立刻**改掉它。
      若主循环按**偏好**判定，后果是双重的：① 停止 `NetProto_Poll()` ⇒ **正在跑的网口当场停摆**；
      ② 转而 `CanProto_Poll()` / `CanProto_Service()` ⇒ **去 poll 一个本次启动压根没初始化的 CAN 外设**。
      **访问一个未使能的外设比"它不工作"更糟**（读野地址 / 抢总线 / 写寄存器被静默丢弃）。
      ⇒ 结论：运行期的**一切**判定（主循环轮询哪条 / LED 去留 / CAN 命令拦截 / `nx` 自我守卫）
      **必须走 `LinkCfg_ActiveMode()`**（启动时从 Flash 读出后就**冻结**，运行期永不改变）。
      ⭐ 通用形态：**"可变的偏好"与"本次已生效的事实"是两回事。凡"读出来就马上拿去控制硬件"的判定，
        都必须锚定后者。**
    - ⚠ **默认语义 = 全关**（2026-09-22 用户定）：`magic` / `CRC` / `version` / `mode` **任一不符**
      （含"从未写过"与"整片擦除后"，读出 `0xFFFFFFFF`）⇒ **两条链路都不启用**，只留串口控制台。
      要开必须**显式** `link can|net` + `link save` + RESET。
      理由与红线 66 同源：**默认值必须等于硬件实况** —— 一个从没被写过的配置区，实况就是"没人配过"，
      不能替用户猜一条链路出来，否则等于"**我以为我没开，其实它开着**"。
    - ⚠ **不做热切换**：`PB13` 的 AF11/AF9、`PC4/PC5` 的 AF/GPIO 模式都是**启动时一次配好**的
      （写进 CR/CRL/AFR 与 GPIO 模式寄存器），运行期改变量**挪不动** ⇒ `link` 只负责
      "**写偏好 + 落盘 + 说清什么时候生效**"，绝不给"已经切过去了"的假象。
      ⚠ 与 `cx 1|2`（CAN 接口 CAN1/CAN2 运行期切换）**不是一回事**：后者只换过滤器/外设实例，不碰引脚冲突。
    - ⚠ **没选中的那条一次都不能 poll**（`NetProto_Poll()` 会驱动 PHY 状态机 + 操作 MAC 描述符；
      `CanProto_Poll()` 会读 CAN 寄存器）；**没开的功能不能读自己的结构体当证据**
      （非网口模式下敲 `nx` ⇒ **明确拒绝**，而不是打出一张"看着正常、其实是未初始化内存"的状态表）。
    - ⭐ **same-tag 陷阱（本轮又新增一例）**：`flash_cfg.c` 的三区化是**所有构建共用**的
      ⇒ 重编后的 `LINK=net` / `LINK=can` 与旧导出版 **md5 不同，但 `fw-tag` 一模一样**
      （仍是 `ARM-NET-0921A` / `ARM-CAN-0918H`）。`flash_arm.py` 的 `compare_build()` 只能报
      "md5 不一致"，**说不清差在哪** ⇒ **靠 tag 判代次永远不够**（同族：0918H 那次要靠
      `rc-tim4-capture` token 才分得出）。要动共享代码，就得同步想清楚"哪一版待在哪"。
