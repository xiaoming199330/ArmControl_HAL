# 三链路响应时间 · 实测报告（2026-09-22）

> 被测设备：STM32F407 六轴臂从站
> 工具：`tools/link_latency_bench.py`（`--selftest` = 58 PASS）
> 原始结果：`outputs/latency_bench/*.json`
> 固件：网口轮 `ARM-NET-0921A`（md5 `93b980329f01c027c2fc40bde0c63831`）；
> 　　　CAN 轮 `ARM-CAN-0918H`（md5 `595af8ca5bc004017debe1d8b77ab70c`，横幅含 `rc-tim4-capture`）

## 0. 一句话结论

**按常态延迟（p50）看：网口最快 → CAN 居中 → 串口最慢，是清楚的 3 级台阶。
但按最坏情况（`max`）排序会反过来 —— 综合裁决见 §0.2。**

| 判据 | 网口 | CAN | 串口 |
|---|---|---|---|
| **纯链路**（`ping` p50） | **0.90 ms** | 1.65 ms | 3.15 ms |
| **真实遥操作**（`stream_joints` 运动中 p50） | **1.92 ms** | 2.74 ms | 4.78 ms |

- 网口比 CAN 快 **约 1.8 倍**，比串口快 **约 3.5 倍**（纯链路口径）
- CAN 比串口快 **约 1.9 倍**
- 三条链路**全部零超时、零坏包**；`max` 都只有 `p50` 的 1.2~2 倍 ⇒ 都很稳
- ⭐ **选网口做遥操作**：p50 1.92 ms、p99 2.62 ms、523 次/秒，余量最大

### 0.1 ⭐⭐ 10 分钟长跑修正了两条结论（见 §7）

把每条链路都跑满 **10 分钟、六轴同时大摆幅**（12 万 / 20 万 / 33 万帧）之后：

| 判据 | 网口 UDP | CAN @500k | 串口 COM11 | 谁赢 |
|---|---|---|---|---|
| **p50**（常态） | **1.61 ms** | 2.72 ms | 4.78 ms | 网口（比串口快 **3.0 倍**） |
| p90 | **2.22** | 2.94 | 5.16 | 网口 |
| **p99** | **3.40** | 6.60 | 6.32 | 网口（比最差者快 1.9 倍） |
| **max**（最坏） | 117.66 | 179.94 | **15.26 ms** | **串口（比 CAN 好 11.8 倍）** |
| std | 0.82 | 1.48 | **0.56** | 串口最可预测 |
| 超时 | **0** | 4（0.002%） | **0** | 网口 / 串口 |
| p50 全程极差 | 0.41 ms（**25%**） | 0.08 ms（3%） | **0.04 ms（0.8%）** | 串口最稳 |

**修正 ①：「网口 max 3.68 ms」是短测的假象。**
150 样本的短测里网口 `max` 只有 3.68 ms，长跑 33 万帧的真实 `max` 是 **117.66 ms**，
而且**每个桶（每分钟）都有 36~60 ms 的尖峰**。⇒ **短测的 `max` 绝对不能当最坏情况用。**

**修正 ②：「CAN 比串口快 1.9 倍」只在常态成立。**
按 `max` 排序，结果**反了**：**串口 15.26 ≪ 网口 117.66 < CAN 179.94**。
⇒ 选型必须问清楚：**要常态还是最坏情况？**

⭐⭐ **三条链路的尖峰，量级都指向"上位机调度时片"，与链路波特率无关**（见 §7.4）：

| 链路 | 长跑 max | ÷ Windows 默认时片 15.6 ms |
|---|---|---|
| 串口 | 15.26 | **≈ 1 个时片** |
| 网口 | 117.66 | ≈ 7.5 个时片 |
| CAN | 179.94 | ≈ 11.5 个时片 |

⇒ 决定尾部延迟的是**上位机的调度粒度**，不是总线带宽。这是三条链路**共同的**瓶颈。

### 0.2 ⭐⭐⭐ 综合裁决：到底选哪条

把 6 个判据全部排名（①最好 / ③最差）：

| 判据 | 网口 UDP | CAN @500k | 串口 COM11 |
|---|---|---|---|
| p50 常态 | **1.61 ①** | 2.72 ② | 4.78 ③ |
| p99 尾部 | **3.40 ①** | 6.60 ③ | 6.32 ② |
| max 最坏 | 117.66 ② | 179.94 ③ | **15.26 ①** |
| std 抖动 | 0.82 ② | 1.48 ③ | **0.56 ①** |
| 吞吐（帧/s） | **547 ①** | 341 ② | 202 ③ |
| 600 s 内超时 | **0 ①** | 4 ③ | **0 ①** |
| **拿到第一的项数** | **4** | **0** | **3** |

**三个结论，一句话一个：**

1. ⭐ **综合最优 = 网口**。它**没有任何一项垫底**（最差也是第 2），拿 4 个第一，
   是唯一 `p99` 进 4 ms 的链路，吞吐 547 帧/s 是串口的 **2.7 倍**、且零超时。
2. ⭐ **最"稳" = 串口**。3 个第一**全部落在最坏情况**（max / std / 超时）。
   `max` 15.26 ms 是三条里**唯一落在 50 Hz 一个周期（20 ms）以内**的
   ⇒ 只有它能在"绝不允许掉帧"的语义下自称硬实时。
3. ⚠ **CAN 在本轮没有胜出的判据**（6 项里 0 项第一、2 项垫底、还贡献了唯一的 4 次超时）。
   ⚠⚠ **但这不是 CAN 协议的错**：500 kbit/s 下一帧 8 B 线上时间仅约 **0.25 ms**，
   实测 180 ms 大了 **2~3 个数量级** ⇒ 坏在上位机侧 **PCAN-USB 的 USB 调度 + Windows 非实时**
   （§7.4）。**CAN 的物理层优势（差分、抗干扰、远距、多节点）本轮桌面短距 + USB 适配器的
   条件下根本没测到**，不能据此判 CAN 出局。

**怎么加权，取决于你的判据：**

| 你的权重压在 | 答案 | 理由 |
|---|---|---|
| 常态体验（遥操作、界面刷新、数据回传） | **网口** | p50 比串口快 3.0 倍；余量与吞吐都最大 |
| 最坏情况（力控、碰撞敏感、不允许掉周期） | **串口** | 唯一 max < 20 ms；抖动最小 |
| 两者都要 | **网口 + 上位机实时化** | 尾部瓶颈是三条链路**共有**的（§7.4）⇒ 换链路无效，要换平台/提线程优先级 |
| 长距 / 强干扰 / 车规 / 多从站 | CAN（**物理层优势，本轮未测**） | 但要先解决上位机侧，别用 USB-CAN 适配器 |

> **一句话：综合最优是网口；若判据是"最坏情况也不掉周期"，答案是串口。**
> **CAN 在本次桌面环境下不存在胜出的判据 —— 它的价值在物理层，不在这次测的东西上。**

## 4. ⭐ 运动模式的结论（回答"臂在动时响应如何"）

**臂确实在动** —— `stream_joints` 运动前有**探针 + 回读自检**，两轮实测回读：

| 轮次 | 回读 Δ（舵机度，J1~J6） | 判定 |
|---|---|---|
| 网口轮 | `0.0  0.2  0.3  0.0  +2.70  0.0` | 摆动轴动 2.70°，其它轴被动 ≤0.30° ✅ |
| CAN 轮 | `0.0  0.0  0.0  0.0  +2.80  0.0` | 摆动轴动 2.80°，其它轴被动 0.00° ✅ |

⇒ 量纲换算（逻辑角↔舵机度）与限位钳位都正确，流帧真的写到了舵机。

**结论：臂在动，几乎不拖慢流模式响应。**

| 链路 | 静止 p50 | 运动 p50 | 变化 |
|---|---|---|---|
| 网口 | 1.75 ms | 1.92 ms | **+10%** |
| CAN | 2.62 ms | 2.74 ms | **+5%** |
| 串口 | 4.74 ms | 4.78 ms | **+1%** |

⇒ **`stream_joints` 的 ACK 与插补/直写解耦**（ACK 只表示"这一帧被受理"），
所以 20~50 Hz 遥操作在**机械臂持续运动时依然成立**：
网口 523 次/秒、CAN 352 次/秒、串口 202 次/秒，都远高于 50 Hz 需求。

⚠ 只有 `move_joints` 真正吃运动开销 —— 即使目标就是当前角、臂根本不打算动，
固件也会启动一整条 S 曲线才发 ACK。

> ⭐ 本节是**小幅短测**（J5 ±5°、各 150 样本）的结论。
> **六轴同时大幅摆动、跑满 600 s 的定论见 §7** —— 结论一致（甚至更快），
> 但 §7 还暴露了短测看不到的尾部尖峰。**以 §7 为准。**

## 5. 选型建议

| 场景 | 首选 | 理由 |
|---|---|---|
| 遥操作 / 遥控器（20~50Hz 流） | **网口** | 长跑 p50 **1.61**、p99 **3.40**、547 帧/s，常态余量最大 |
| 要"绝不缺帧" / 极稳周期 | **串口** | `std` 0.56、p50 极差 0.04 ms、**max 仅 15.26 ms**、零超时；但只 202 帧/s |
| 只有 CAN 可用（抗干扰 / 远距 / 车规） | CAN | p50 2.72 够 50Hz；⚠ 但在 Windows+PCAN-USB 上 **max 180 ms、4 次超时** |
| 逐点定位（`move_joints`） | 任意 | 91~157 ms 由**固件轨迹**决定，换链路不提速 |
| 状态轮询 / 画界面（`status`/`fk`） | 网口 | 但差距只有 1.5 倍（被 6~8 ms 读舵机压平） |
| 实时控制盯什么 | —— | **看 p99 和 max，不要看 mean**。⚠ **要问清楚"常态还是最坏情况"** |

**† `move_joints` 的绝对值不可跨轮比**：网口轮测到 91 ms、CAN 轮两条链路都是 156~157 ms。
原因见 §6 异常 ②——两轮的**臂姿态不同**（`cmdMove` 的工作量随轨迹长度变化），
但**同一轮内两条链路几乎相等（1.0 倍）**，所以"链路对 `move_joints` 无影响"这个结论仍然成立。

**‡ CAN 的"std 最小"是短测结论，已被长跑推翻**：短测（150 样本）里 CAN 的 `std` 最小、
`max` 只有 5 ms；长跑 20 万帧才暴露它 **max 179.94 ms、std 1.48**。
⇒ 用 p50/短测选型会选 CAN，用 max 选型会选串口。详见 §7.4。

## 6. ⚠⚠ 本轮发现的两个异常（需要人工确认）

### ① 舵机读取出现**逐字段、瞬时**的读失败（不是某个轴坏）

同一姿态连读三次 `s`（臂静止，180 s 长跑结束之后）：

```
--- 第1次 ---                      --- 第2次 ---                      --- 第3次 ---
| J1 | 178.9 |   No  | 38C |        | J1 | 178.9 |  Err  | 38C |       | J1 | 178.9 |  No  |  0C |
| J2 | 188.3 |  Err  |  0C |        | J2 | 188.3 |   No  |  0C |       | J2 |   0.0 |  Err  | 44C |
| J3 | 185.3 |  Err  | 43C |        | J3 | 185.3 |   No  | 43C |       | J3 | 185.3 |  No  | 43C |
| J4 | 182.8 |   No  | 38C |        | J4 | 182.8 |  Err  | 38C |       | J4 | 182.8 |  No  |  0C |
| J5 | 178.5 |  Err  | 37C |        | J5 | 178.5 |   No  | 37C |       | J5 | 178.5 |  No  | 37C |
| J6 | 180.5 |   No  | 41C |        | J6 | 180.5 |   No  | 41C |       | J6 | 180.5 |  No  | 41C |
```

三点结论：
1. **`Moving` 列的 `Err` 不是"关节在报错"** —— 同一关节上一次 `Err`、下一次 `No`。
   它是**这一格数据这次没读到**。
2. **`Temp 0C` 是同一回事**（J2 前两次 0C、第三次 44C，而角度读到了）。
3. **角度三次完全一致**（`178.9 / 188.3 / 185.3 / 182.8 / 178.5 / 180.5`）
   ⇒ 臂确实静止；早期看到的 `J2 = 0.0` 是**丢读**，**不是真实位置**（别拿它判姿态！）。

失败率（18 次关节读的样本内）：**温度字段约 20%、角度字段约 5%**，随机分散在各轴。
⇒ 由此在 CAN 轮做全命令谱时，`stream_joints` 曾因
`RuntimeError: 有轴读失败（-32768），拒绝构造目标` **中断过一次**（重跑即通过）；
`GET_STATUS` 整帧 6 轴全读到的比例约 **90%**，单轴约 **98%**。

⇒ 这是**舵机总线（USART3 / UART5 半双工）的响应丢失**，不是某个轴坏。
建议查：接插件 / 线束走线（与动力线并行？）/ 终端匹配 / 总线供电。
✅ 已落地对策：工具加了 `read_pose_retry()`（读失败自动重试 4 次），
巡检时**读失败只算警告**、姿态越界才算硬错 ⇒ 长跑不会因偶发丢读而白跑。

### ② 烧录前的复位让机械臂失去了力矩、下沉到新姿态

| 时刻 | J1 | J2 | J3 | J4 | J5 | J6 |
|---|---|---|---|---|---|---|
| 网口轮起始 | 179.4 | **180.4** | **180.7** | 180.5 | 180.7 | 176.8 |
| CAN 轮起始 | 179.5 | **76.7** | **270.9** | 180.7 | 181.9 | 176.7 |

J2/J3 大幅变化（180→77、181→271），J4/J5/J6 基本没动。
⇒ 断电/复位时力矩消失，重力把大臂/小臂放了下来。
⚠ **J2 = 76.7° 已经贴近它的运行下限 75°**（`L` 命令读到的限位 J2 = 75~284）。
这不影响本次 RTT 测量（摆动轴是 J5、幅度 ±5°、探针与回位都成功），
但**下一次上电前要确认臂没有压在东西上 / 没有顶到限位**。

## 7. ⭐⭐ 10 分钟六轴全动长跑（三链路全跑，本轮主结论）

> 目的**不是多攒样本**，而是**暴露随时间的变化**（热漂移 / 总线退化 / 偶发尖峰）。
> ⇒ 结论**只能看分桶**：把 10 分钟汇总成一个 `p50`，恰好把要查的信息抹掉。

### 7.1 测试设计

  ⇒ 频率都极低（网口 1/33 万、CAN 约 1/2 万），但**对实时控制才是决定性的**。

### 7.4 ⭐⭐ 关键发现：常态快 ≠ 尾巴好；**尾部由上位机调度决定**

| | p50 | p99 | max | std | 超时 |
|---|---|---|---|---|---|
| 网口 | **1.61** | **3.40** | 117.66 | 0.82 | 0 |
| CAN | 2.72 | 6.60 | 179.94 | 1.48 | 4 |
| 串口 | 4.78 | 6.32 | **15.26** | **0.56** | 0 |

**排序会反转**：按 `p50`/`p99` 是 **网口 > CAN > 串口**；
按 `max`/`std` 是 **串口 > 网口 > CAN**。⇒ 只报 p50 会误导选型。

⭐ **三条链路的尖峰都指向"上位机调度时片"，与链路波特率无关**：

- 先算**理论下限**：CAN 500 kbit/s 下 8 字节数据帧的**线上时间只有约 0.25 ms**；
  网口 100 Mbit/s 更快。6 关节报文即使分包+重组也在个位数 ms。
  ⇒ 实测 117 / 180 ms 比理论值大 **2~3 个数量级** ⇒ **不可能是链路造成的**。
- 再看量级：Windows 默认调度时片 **≈ 15.6 ms**。
  | 链路 | max | ÷ 15.6 ms |
  |---|---|---|
  | 串口 | 15.26 | **1.0** |
  | 网口 | 117.66 | 7.5 |
  | CAN | 179.94 | 11.5 |

  ⇒ 三条链路的尖峰都落在"**若干个操作系统时片**"的量级上，
  其中串口最幸运：它的单帧小、USB-UART 缓冲平滑，**恰好能被一个时片服务完**。
- ⇒ **结论：当前尾部延迟的真正瓶颈是上位机（Windows + 非实时线程 + USB 适配器），
  不是 CAN / 以太网 / 串口本身。**

**对实时控制的意义**（盯 p99 / max，不盯 mean）：
- 50 Hz 遥操作周期 = 20 ms。最坏情况下：网口掉 **5** 个周期、CAN 掉 **9** 个、串口掉 **0** 个。
- ⇒ 想要"绝不缺帧"，串口反而是最稳的（但只有 202 Hz 上限）。
- ⇒ 想真正改善尾部：**换 Linux（或至少提高 Windows 定时器精度 + 给通信线程高优先级）**，
  而不是换链路。这条要验证的话，换到 Linux 侧重跑同样两轮即可 —— 工具是跨平台的。

### 7.5 幅度为什么不是 ±50°（用户原始要求的偏离说明）

用户原始要求"各轴 ±50°"。实测 ±50° 六轴全动时 **约 15% 的帧被固件拒收**，
固件日志给出两个原因：

```
Stream reject: pose unsafe            ← 主因：桌面 z + 立柱圆柱禁区
J1/J2 jump 33~47 deg (>25)            ← 次生：单帧跳变门限，被拒后 prev 不更新 ⇒ 连锁
```

`pose unsafe` 是**安全功能在正常工作**（末端真的扫进了禁区），不是 bug。
收幅度到 **J1~J4 ±20° / J5 ±70° / J6 ±33°（周期 12 s）** 后 **0 拒帧**，
且幅度排序遵守"先加转了不改变末端位置的轴（J6 夹爪→J5 腕转），最后加会改变末端位置且向下的轴"。

⇒ **包线是量出来的**：试一版 → 数拒帧 → 读固件自己的日志（错误码只说"被拒"，日志才说"哪一轴、差几度、还是禁区"）→ 收幅度。

### 7.6 六轴大摆幅 vs 单轴小幅：RTT 几乎不变

| 场景 | 网口 p50 | CAN p50 | 串口 p50 | 样本 |
|---|---|---|---|---|
| 单轴 J5 ±5° / T2s | 1.92 | 2.74 | 4.78 | 150 |
| **六轴 ±20/70/33° / T12s、600 s** | **1.61** | **2.72** | **4.78** | 33 万 / 20 万 / 12 万 |

⇒ **运动幅度、轴数、持续时间对 `stream_joints` 的 RTT 没有任何影响**（网口反而更快，
因为它在这 10 分钟里稳定到 1.53~1.59）。
流模式的 ACK 与插补/舵机侧解耦 ⇒ **20~50 Hz 遥操作在"臂满负荷在动"时依然成立**。
