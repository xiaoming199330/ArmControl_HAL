## 阶段 3 · 接线（**物理层，最容易翻车的一步**）

| 项 | 要求 |
|---|---|
| 收发器丝印 | `CAN PHY V1` |
| MCU ↔ 收发器 | 模块 `TX`→MCU `PB9`(CAN1_TX)、`RX`→MCU `PB8`(CAN1_RX)，**直连不交叉** |
| 跳线电压 | 先 3.3V；不通再试 5V |
| 总线 | `CANH↔CANH`、`CANL↔CANL` |
| **共地** | **必须**（少共地 = 现场最常见的"偶发错误帧"元凶） |
| 终端电阻 | **总线两端各 120Ω**（臂端 + 卡端；只有一端会读到 ACK 错） |
| 上位机侧 | ⭐ **已确认 = PEAK PCAN-USB**：PCAN 侧用 DB9 的 **2=CAN_L / 3=GND / 7=CAN_H** 引出来接，软件填 `--interface pcan --channel PCAN_USBBUS1`。⚠ **PCAN-USB 的 120Ω 是「可选」的**：`IPEH-002021` 在 `S/N < 199999` 上**根本没有**终端电阻，`S/N ≥ 200000` 才有 120Ω 焊桥且**出厂默认不激活** ⇒ 先量 DB9 的 2–7 脚电阻，≈120Ω 才算卡内有 |

> ⚠ **波特率必须一致**。臂侧默认 **500 kbit/s**，卡侧也要 500k。这是 PING 不通的第一位原因。

### DB9 怎么接到臂的收发器（**接线错了会一直 ACK 错**）

PCAN-USB 的 DB9 公头（**只用到 3 根**）：

| DB9 脚 | 信号 | 接到臂侧收发器（丝印 `CAN PHY V1`） |
|---|---|---|
| **2** | **CAN_L** | 收发器 `CANL` |
| **3** | **GND** | 收发器 `GND` —— **必须共地**，只接两根信号线是最常见的"偶发 ACK 错"来源 |
| **7** | **CAN_H** | 收发器 `CANH` |

- 收发器侧 `TX→MCU CAN1_TX`、`RX→MCU CAN1_RX`（**直连不交叉**），跳线先 3.3 V，不通再试 5 V。
- **两端各 120 Ω 终端**：卡侧先在 **DB9 的 2–7 脚**量一次（≈120Ω 说明卡内那对焊桥已激活；开路就是没有）；
  臂侧收发器模块上的 120Ω 跳线要短接。只有两个节点时，两端就是全部终端；
  缺一端会出现随机 CRC/ACK 错，看起来像“协议不稳”。
- ⭐ **卡上的红色 LED 是最省事的“到底发了没有”指示**（PEAK 官方手册）：**常亮**=驱动已装上；
  **慢闪**=有软件连上了它；**快闪**=正在往总线发数据。
  ⇒ 跑 `--linktest` 时若 LED 根本不快闪，那就不是接线问题，是卡/程序没在发。
- **波特率必须与固件一致**：臂侧默认 500 kbit/s（控制台 `can` 看得到），脚本 `--bitrate 500000`。
- 万用表量 **CAN_H–CAN_L 静态约 0（隐性）**，上电后显性帧才拉到 2 V 左右 —— 静态就短路说明线接错。

### 阶段 3.55 · `cw` 外环测试（**不接线、不用万用表，2026-09-17 19:10 新增**）

⭐ **`cp` 的盲区补丁，也是"我方到底发得出去吗"最干净的判据。**

`cp` 报"TX 驱动级正常"时，它读的是 **PB9 自己**（只证明 MCU 引脚没坏），
跟"这根线有没有连到收发器的 TXD"**毫无关系**。TXD 那根线断掉时 `cp` 依然全绿，
而症状恰恰就是现在这种"帧发出去了、谁也收不到"。UART4 那一轮吃过同样的亏。

`cw` 停掉 bxCAN，把 TX 脚当普通 GPIO **持续驱动显性(低)** 再**直接读 RX** ——
标准 CAN 收发器（TJA1050 / SN65HVD230 / TJA1042）会把**总线状态**透传到 RXD，
所以这一刻本机 RX 必须跟着变低。**不需要万用表，也不需要总线上有第二个节点。**

| 臂侧敲 | 判读 |
|---|---|
| `cw` | 显性→`00000000` 且 隐性→`11111111` = **外环通**（MCU 与收发器全排除，断点只剩「卡↔模块 CANH/CANL」）；<br>显性时仍 `11111111` = **外环断**（TXD 没接 / 模块 TX-RX 丝印反 / VCC 跳线错 / 器件坏）；<br>两者都 `00000000` = 总线被外部强拉显性；混合位图 = 总线上还有别的节点在发 |
| `cw 5000` | 先**按住显性 5 秒** —— 此时拿万用表量**卡那一端**的 H/L：<br>**CANH≈3.5V / CANL≈1.5V ⇒ 两根线都通**；仍 ≈2.5V/2.5V ⇒ 卡没接到这对端子上 |

`cw` 结束会自动把 CAN 恢复成正常模式；敲 `cn` 看到 `hw init: ok` 即已恢复。

### 阶段 3.6 · 判定"线到底通没通"的唯一可信方法（**2026-09-17 晚实测新增**）

⭐ **先说结论：不要用 CAN 卡"报不报总线错"来判断线通没通。**
本次实测把 PCAN 设成与臂**必然不匹配**的位速率（250k vs 臂的 500k，等于"对端必然应答不了"），
`CAN_GetStatus` 照样返回 `0x00000000 正常`。⇒ **这个读数不敏感，不作判据**。
（同一实验也说明：`bus.send()` 不抛异常 ≠ 帧被应答，它只代表"已入卡队列"。）

唯一可信的是**两侧帧计数对拍**，用不过协议层的 `0x7E0` 自检帧：

```bash
# ① PC 侧: 发 200 帧 + 开 3 秒反向监听窗口
"$PY" tools/can_host.py --interface pcan --channel PCAN_USBBUS1 --bitrate 500000 \
      --linktest 200 --link-listen 3

# ② 臂侧: 读计数（现在脚本化了，不用手敲 —— 见 tools/arm_console.py）
"$PY" tools/arm_console.py --port COM11 --cmd cn --cmd ct

# ③ 反向验：臂侧发 200 帧，同时 ① 的监听窗口开着
"$PY" tools/arm_console.py --port COM11 --cmd "ct 200"
```

| 观察 | 结论 |
|---|---|
| 臂侧 `ct` 的"已收"涨了 ≈200 | **卡→臂 通** ✅ |
| 臂侧 `ct` 打印 `lec=3` 且 `tec` 以 8/帧快速涨 | 臂发出的帧**没有任何节点应答** ⇒ 对面不在同一对线上 |
| 臂侧 `cn` 的 `bus pin: MSR.RX` | `1`=隐性(收发器在输出高，上了电)；`0` 恒低=总线被拉死 |
| PC 侧 `--linktest` 的"反向收到"刷出 ≈200 帧 | **臂→卡 通** ✅ |

⚠ **最大的陷阱**：臂侧 `ct` 报 `lec=3` **只在"对面卡已经被打开(初始化)"时才说明接线有问题**。
CAN 卡的程序没在跑 / 卡没插稳时，PCAN-USB 的收发器**是不接总线的**，此时臂看到"无人应答"
完全正常，**说明不了接线对错**。所以必须让**两边同时活着**再判 —— 别单看一边就下结论。

### 实测结论（2026-09-17 19:00，PEAK PCAN-USB ↔ 臂 `CAN PHY V1`，两侧同时活着，都 500 kbit/s）

用 `tools/can_link_pair.py` 一条命令跑出来的：

| 方向 | 观察 | 判定 |
|---|---|---|
| 卡 → 臂 | 卡发 200 帧 `0x7E0`，臂侧 `cn` 的 `test rx` 由 **0 → 0** | **不通** |
| 臂 → 卡 | 臂 `ct 200`，卡侧监听窗口收到 **0 帧** | **不通** |
| 应答探测 | 臂发 10 帧：`tec 160 → 240`（**Δ=+80 = 10×8**）、`lec=3` | **无人应答** |
| 臂自身 | `hw init: ok`、`bus pin: MSR.RX=1`、`MCR.INR=0 INAK=0` | 臂侧 MCU 与收发器供电正常 |

⇒ **物理层确确实实不通（双向全静默）**，与协议层/过滤器/节点号无关。
在这种"**双向同归于尽**"的形态下，按可能性排序查：

1. ⭐ **收发器模块的 `TX`(输入脚) 那根是否真接到了 MCU 的 `CAN1_TX`(PB9)**。
   `cp` 只证明了 `RX` 那根（PB8）被外部驱高 ⇒ 收发器上了电且在输出；
   **`TX` 那根 `cp` 测不到**（它只验 MCU 自己的驱动级，跟外面接没接无关）。
   若 TX 那根没接，收发器永不驱动显性 ⇒ **两边一起静默**，与本次现象完全一致。
2. **两端都缺 120Ω**（卡侧见上：`S/N<199999` 根本没有，`≥200000` 默认不激活；臂侧模块的 120Ω 跳线要短接）。
3. **卡那端 DB9 的 H/L 接反**（自制 2/7 引出最容易反）或 DB9 用了 5 脚(屏蔽)当 GND。
4. **共地没真通**（量卡 GND ↔ 臂板 GND 必须 ≈0V）。

⚠ `--probe` 第 3 步里 `channel_condition` 的含义：`1=可用` / `2=**已被占用**` / `0=不在`。
读到 **2** 说明有别的进程（如 PCAN-View、CanAst.exe）或上次异常退出的残留句柄占着卡，
此时打开会报 `A PCAN Channel has not been initialized yet...` —— 看着像"卡坏了"，
其实只是被占：**关掉那两个 GUI，或把 PCAN-USB 拔掉重插**。

```

输出是一张 PASS/FAIL 表，7 项：

| # | 项 | 判据 |
|---|---|---|
| 1 | PING | 收到 `0x81`，打印 `proto_ver` / `run_id` |
| 2 | GET_STATUS | 六轴**全部读到**（不是 `FAIL`），且 `estop=False` |
| 3 | PARAM_COUNT == 24 | 参数表完整（**项数固定 24，红线**） |
| 4 | FK_QUERY | `read_ok=1`，末端 XYZ/pitch 是合理值 |

| 7 | TRAJ_DONE 事件 | （需 `--allow-move`）25s 内收到事件帧 |

**PING 不通时脚本会直接把下面这套排查清单打出来**，按顺序走：

```
ⓐ 臂侧 `cn`  → hw init 必须 ok；不是就 `e` 排除 MCU 侧
ⓑ 臂侧 `cp`  → RX 脚加下拉仍读 11111111 = 收发器上电且线接上了
ⓒ 臂侧 `can` → node/baud 是否与脚本 --node/--bitrate 一致
ⓓ 波特率不一致是第一原因；第二是 ID 段 0x100+node
ⓔ 若 `cn` 里 rec>0 说明臂确实收到了 ⇒ 是过滤/波特率问题，不是硬件
```

> ★ **`ⓔ` 是分水岭**：臂侧 `cn` 的**收帧计数 > 0** ⇒ 帧已经进 MCU 了，问题在上层
> （波特率对不上会表现为 rec 一直 0 或 lec=6 错误帧；node 不匹配则帧被硬件过滤器丢掉、rec 也是 0）。

| 项 | 结论 |

## 阶段 6 · 配置持久化（**唯一有 Flash 风险的一步，先记基线**）

**做之前先记下这两屏**（万一写入中途掉电，用来核对没被改坏）：

```
zi        ← 抄下 calib_zero_raw 与 raw limits
can       ← 抄下当前 node/baud/hb

```bash

can                   ;  # 确认显示 node=2

# 落盘
can node 2
can save
# 断电重启 → can       ; 应仍是 node=2 且不带 (defaults)
```

| 判据 | 通过 = |
|---|---|
| 不 `save` 重启 → 回默认 | 非易失写入是**显式**的，不存在"改了不知道什么时候生效" |
| `save` 后重启 → 配置保留 | Flash 持久化工作 |
| **重启后 `zi` 的 `calib_zero_raw` 与写入前逐位相同** | **保区机制正确**（存 CAN 配置**没有**擦掉校准记录） |
| `can hb 0` 后上位机 `--monitor` 收不到状态帧，`hb 1000` 恢复 | 心跳开关生效 |

> ⚠ 这一条是**本功能最容易被忽略的坑**：扇区 11 同时住着 PID/校准记录，Flash 只能整扇区擦。
> 各擦各的会把对方**静默清掉**；零点一丢就会复现 `g` 报 `tool pitch NOT met`。新增的
> `flash_cfg.c` 走"读他区→擦整扇区→回写他区→写本区→双区校验"来避免这件事。
> **所以这一阶段的 `zi` 前后对照不能省。**

## 阶段 3.7 ·（2026-09-18 新增）`ps` 引脚嗅探 —— 卡到底挂在哪只 MCU 脚上

### 什么时候需要它

这两个现场**症状完全一样**，但修法完全不同:

| 情形 | `cn` | 灌帧时 `cy` | 修法 |
|---|---|---|---|
| 卡接对了口，但线/终端/收发器有问题 | `lec=3`、`TEC` 每帧 +8 | 一动不动 | 查那一段线 |
| **卡接在板子的另一个 CAN 口上** | `lec=3`、`TEC` 每帧 +8 | 一动不动 | 改用对应外设(CAN2)或把线挪过来 |

`cp` / `cw` 都只认**当前这一组** CAN 脚(编译期宏)，答不了第二种。`ps` 横向扫
11 只与 CAN 有关的候选脚，看**哪只脚上真的出现了活动信号**。

### 关于 CAN2 的事实（2026-09-18 逐条查证）

- 业务代码 / `.ioc` / `gpio.c` 里 **`CAN2`、`PB12`、`PB13`、`PB14`、`PB15` 一处都没有**；
  `__HAL_RCC_CAN2_CLK_ENABLE()` 也没人调用 ⇒ **"固件解析 CAN2 的数据"这件事不存在**。
- F407 的 CAN2 引脚是 **PB12=CAN2_RX / PB13=CAN2_TX (AF9)**；
  **PB14 没有 CAN 复用功能**(只能是 SPI2_MISO / USART3_RTS / TIM12_CH1 / OTG_HS_DM)。
- 所以"CAN2 是 PB13 和 PB14"这个组合在 F407 上不成立 —— 若板子真这么引，
  那第二只脚不是 CAN，需要按实际走线重新确认。

### 操作（一条命令）

```bash
PY="C:/Users/Administrator/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
cd "C:/Users/Administrator/Desktop/ArmControl_HAL（1）"
"$PY" tools/can_pin_hunt.py --port COM11 --channel PCAN_USBBUS1
```

前提: ① 臂板已上电、串口没被别的程序占着 ② 已烧 `ps` 版固件(见 §9.7 两个 md5)。

### `ps` 的输出怎么读

| 行 | 读数 | 含义 |
|---|---|---|
| `PB8` / `PB9` | 边沿 ≥ 8 | ⭐ 对端 CAN 在 **CAN1 口**上 ⇒ 查收发器与那段线 |
| `PB12` / `PB13` | 边沿 ≥ 8 | ⭐ 对端 CAN 在 **CAN2 口**上 ⇒ **不用重烧**: 直接 `cx 2` 切过去再验(见 §3.8) |
| `PB14` / `PB15` | 边沿 ≥ 8 | 这两只在 F407 上没有 CAN 复用 ⇒ 那两根线串了别的信号 |
| 全部 11 行 | 无 ★ | 卡的信号**没进到 MCU 任何一只 CAN 脚上** ⇒ 线/DB9/适配器的问题 |

### 一条必须纠正的旧推理（写进红线级）

以前记过"`lec=3` ⇒ 位监视通过 ⇒ 收发器一定接在这组脚上"。**错了一半**:

> 收发器驱动**自己那一对端子**时，其内部就会把差分电平回馈到 RXD —— 哪怕那对端子
> **一个别的节点都没接**。所以 `lec=3` 只证明 **MCU ↔ 收发器** 通，
> **不证明**"收发器的 CANH/CANL 真连到了卡那一端"。

⇒ 「`cw` 报外环通」与「灌帧时 `cy` 一动不动」**并不矛盾**，可以同时成立。

## 阶段 3.8 ·（2026-09-18 新增）`cx` —— 接口切到 CAN2，**不用重烧**

### 什么时候需要它

阶段 3.7 的 `ps` 如果给出 ★ 落在 **PB12/PB13**，那结论就是"卡插在板子的 CAN2 口上"。
过去这一步之后要重编 `CANPIN=...` 再烧一次；这块板 DTR/RTS 没接 BOOT0/NRST，
重烧要手动拉 BOOT0 + 复位，一次二十分钟，而且烧错版本还会白读一次结果。

**2026-09-18 起不需要了** —— 接口是运行期变量，一条 `cx` 就能切。

### 操作

```bash
PY="C:/Users/Administrator/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
cd "C:/Users/Administrator/Desktop/ArmControl_HAL（1）"

# ★ 落在 PB12/PB13 时: 灌帧 + 自动 cx 2 + cw + ps，一条命令出结论
"$PY" tools/can_pin_hunt.py --port COM11 --channel PCAN_USBBUS1 --cx 2

# 或者手动在控制台上
#   cx           看当前是 CAN1 还是 CAN2
#   cx 2         切到 CAN2 (PB12/PB13, AF9)
#   cn           确认 "接口 : CAN2 PB12(RX)/PB13(TX)" + hw init ok
#   cp / cw      量脚 / 验外环（都针对新那一组脚）
#   cz 100       发侧通路
#   cy 2500      卡灌帧时看 RX 有没有电平
#   ct           两侧帧计数对拍
#   cx save      确认好用之后落盘
```

### 结果怎么读（`cx 2` 之后）

| `cw` 结果 | `cy`(卡灌帧时) | 结论 |
|---|---|---|
| 外环通(显性→全0 / 隐性→全1) | 有跳变 | ✅ 卡在 CAN2 口上，**问题已解决** ⇒ `cx save` 固化 ⇒ 回阶段 4 冒烟 |
| 外环通 | 全高无跳变 | 收发器正常但卡不在这对端子 ⇒ 查 CANH/CANL 那两根线与 DB9 极性 |
| **外环断**(显性时 RX 仍全 1) | 任意 | PB12/PB13 这对脚**后面没有收发器**（或收发器没供电）⇒ 只能把线挪回 CAN1 口，或给板子补收发器 |
| `cn` 报 hw init FAILED | — | 切换本身失败 ⇒ 看 `cn`；可 `cx 1` 切回去 |

⚠ 切接口会停一下总线并重配过滤器，卡那边可能记一个错误帧，属正常。
⚠ `cx` 默认**不落盘**，重启回 Flash 里存的接口；要固化就 `cx save`。

### 为什么以前想切也切不了（原理，出问题时回看这一段）

| # | 事实 | 不处理会怎样 |
|---|---|---|
| 1 | CAN2 的**寄存器与过滤器**都要经 CAN1(主实例)访问 | 只开 CAN2 时钟 ⇒ 直接硬件错误 |
| 2 | 两颗 bxCAN 共享 28 个过滤器银行，FMR.CAN2SB 是分界(本工程 = 14) | **CAN2 的过滤器配在 bank 0..3 ⇒ 配置成功却一帧都收不到** |
| 3 | 32 位 HAL 里 `HAL_CAN_ConfigFilter` 恒以 CAN1 为主实例、CAN2SB 只在这里被写 | 手工改 FA1R 会漏掉 CAN2SB |

这三条都已在 `arm_can_driver.c` 里处理；`cx` 命令、`it.c` 的 `CAN2_RX0_IRQHandler`、
以及 `main.c` 里把 `CAN1->MSR` 换成 `ArmCanDrv_RegMSR()` 是本轮的配套改动。

## 阶段 3.9 ·（2026-09-18）**先认固件指纹，再敲任何 c 开头的命令**

### 为什么这一步排在最前面

现场实测：新固件还没烧，就有人在控制台上敲了 `cx`，结果**进了校准向导** ——
那个向导第一件事是 **松掉全部力矩**（`All torques released for hand positioning`），
整臂当场失去支撑。

原因不是 `cx` 写错了，而是**命令分发是首字母兜底**：

```
精确匹配全失败 → switch (tokens[0][0]) → case 'c' → 校准向导
```

⇒ **"这块板跑的是哪版固件"必须先确认，否则敲的每个新命令都是对某个单键命令的赌博。**

### 一步做完（脚本已内置这个检查）

```bash
PY="C:/Users/Administrator/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
cd "C:/Users/Administrator/Desktop/ArmControl_HAL（1）"

# 只看指纹
"$PY" tools/arm_console.py --port COM11 --cmd h
```

**期望**：`h` 的**第一行**是

```
  fw-tag ARM-CAN-0918H  pins=CAN1 PA11(RX)/PA12(TX)  iface=cx-switchable+cxpa  defif=CAN2(PB12/PB13)  fix=cprint-overread,frameseq,tec-latch,defcan2,tecwin500  cmds=cx,cp,cy,cz,cw,ps
```

| `h` 的输出 | 含义 | 动作 |
|---|---|---|
| 有 `fw-tag ARM-CAN-0918H`（`fix` 含 **`defcan2`**） | 当前固件 ✔ | **直接跑阶段 4 冒烟**（默认已在 CAN2，不用 `cx 2`） |
| 有 `fw-tag` 但 `fix` **不含** `defcan2`（`0918G` 及更早） | 上一版 | **先 `cx 2`**（红线 37）→ 再跑阶段 4 冒烟 |
| 有 `fw-tag` 但 `fix` 里**没有** `tec-latch`（`0918E`/`0918F`） | 上一版 | 可用，但 `tec ≥ 128` 后**永久自锁**，恢复靠 `e` → `cx 2`（红线 36） |
| 老固件的 help（**没有** `fw-tag`，CAN 段只到 `cw`/`ps`） | 上一版固件 | 可以跑 `cw`/`ps`/`cy`/`cz`/`ct`（它们在那版里真实存在），但 **`cx` 绝不要敲** ⇒ 要 `cx` 就先烧 |
| 出现 `=== Joint Calibration` | **正卡在校准向导里** | 敲 `q` 退出。⚠⚠ **千万别敲 `s`**（会把当前姿态固化成零点，见红线 4） |
| 只有一个 `>` / 什么都没有 | 口在、无输出 | 板子没上电或线没接 |

### 脚本会自动拦（`tools/arm_preflight.py`）

`can_pin_hunt.py` / `can_path_probe.py` 开跑前都会先自动敲 `h` 认指纹：

- 认到 → 正常跑；
- 认不到 → **一条命令都不发**，退出码 3，并把 `h` 的前 8 行原文打出来；
- `--force` → 放行 `cw`/`ps`/`cy`/`ct`，但 **`cx` 仍然拦住**（它只存在于本轮固件，
  在老固件上零收益却会松力矩）。

### 顺手记住的两条

- **发命令只发 `\r`**，不要发 `\r\n`。`\r` 结束一行后，多余的 `\n` 会被校准向导
  的按键读入吃掉，回显一行 `Unknown key '\n'` —— 看着像随机的怪东西。
- 固件侧已加**多字符命令白名单闸门**（红线 26）：长度 > 1 又不认识的 token 一律
  当未知命令挡掉，不再落进首字母 case。**以后新增多字符命令必须同步更新那张白名单**，
  否则新命令会被自己的闸门挡掉。

### ⚠ 三个坑（现场都踩过）

**① 烧错了文件 —— 最常见，而且烧完"看着像烧进去了"**

`build/` 那份 **不是** CAN 版。`BUILD_DIR` 是按开关拼的：

| 目录 | 是什么 |
|---|---|
| `build/` | **默认构建**（`LINK=uart`，UART4 主从链路） |
| `build_can/` | CAN 从站版（从臂） |
| `build_master_can/` | CAN 从站版（主臂） |

现场实测 `build/ArmControl_HAL.bin`（182860 B，09-17 17:43）：`grep -qF` 查
`fw-tag` / `cx CAN interface` / `ps CAN pin sniffer` / `cw CAN wire-loop` **全是 NO**
⇒ 烧上去之后敲 `cx` 照样掉进 `case 'c'` 校准向导、**松全部力矩**，你会以为"新命令没用"。

⇒ **烧之前一律**：`grep -qF "fw-tag ARM-CAN-" <bin> && echo 可以烧`
（格式串直接进 `.bin`，比看构建目录时间戳硬 —— 时间戳只说明文件何时写的）。

**② 认错串口**

Windows 的 COM 号**随插拔、换 USB 口会变**：本机从 `COM11 / COM22` 变成了 `COM8 / COM11`
（两个都是 CH340）。烧错板子比烧错文件更难发现。⇒ 列口自己认一遍：

```bash
"$PY" -c "import serial.tools.list_ports as l;[print(p) for p in l.comports()]"
```

**③ `Caught signal 0` —— 不是 STM32 回的错，板子没坏**

```
Write to memory
Erasing memory
Caught signal 0        ← 是 stm32flash 自己的信号处理器打的(它按 %lu 打信号号)
```

含义是**进程被中断**（最常见：擦除握手超时；也可能手动 Ctrl+C）。
只要 BOOT0 还高着，**重跑一次就行**。阶梯：

1. 再跑一遍（擦除时序是边缘性的，重跑常能过）
2. `--erase-first`（`-o` 只擦，把擦除与写入分开，看清是哪一步不行）
3. 换速率：`--baud 115200` / `--baud 9600`
4. BOOT0 在整个擦写过程中**稳定为高**（别用悬空的线夹着）；擦除期间别碰 RESET；
   USB 口换直连（别走 hub）、线换短的
5. **机械臂板用独立电源供电**，USB 只做串口 —— 擦除电流大，CH340 的 3V3 带不动整臂时
   会在擦除瞬间掉压

### 烧完必须做的一步

```bash

# ✅ 0918H 起默认接口 = CAN2，**不用再敲 cx 2**；判据就是首行有没有 defif=CAN2。

```

**这一步不过就别敲 `cx`/`ps`**（阶段 3.9）。过了才继续阶段 3.6–3.8。

一条命令给结论：

| 结论 | 含义 | 下一步 |
|---|---|---|
| ✔ `NEW_FW` | 认到 `fw-tag` ⇒ 本轮固件在跑 | 直接进阶段 3.9 → 3.6/3.7/3.8 |
| △ `OLD_FW` | 有控制器横幅但**没指纹** ⇒ 旧固件 | 只能 `cw/ps/cy/cz/ct`；**`cx` 绝不敲** ⇒ 先烧（阶段 3.10） |

| ✗ `SILENT` + bootloader **也不应答** | **MCU 没上电** 或 **固件挂死** | 现场：查电源 → RESET / 断电重上电 |
| ✗ `PORT_BUSY` | 串口助手占着口 | 先关掉它 |

### 为什么"口在"完全不代表"板子在跑"

CH340 靠 **USB** 供电自带枚举 —— MCU 侧没电、被按在复位上、或者程序挂死，
**口都照样在设备管理器里**。所以「口在 + 0 字节」= 去看板子，不是去看脚本。

### 本工程没有看门狗

`grep` 确认**没有 IWDG/WWDG** ⇒ 一旦挂死就是**永久静默**，不会自己复位。
所以"刚才还好好的、现在一个字都没有"这种现象，稳定态就是"静默"，
必须有**人工复位**才能恢复 —— 脚本无法替代。

### 判"挂死"之前的无害探测（本轮都用过）

| 手段 | 排除什么 |
|---|---|
| 被动监听 **60 s**（不发任何字节） | 排除"在反复复位"（那样会周期性打出启动横幅） |
| `DTR×RTS` 四种组合各发一次 `h` | 排除"被调制解调器线按在复位上" |
| `stm32flash <口>`（**只读** version，不写） | 区分"在 ROM bootloader" vs "真的没在跑" |

**没用**的：读 `CTS/DSR/CD/RI` —— CH340 这几个脚悬空，两个口读出来全是 False，没有区分度。

⚠ **不要**为了"排除时钟跑飞"对活板子做**波特率扫描**（115200/9600/230400/… 各发一遍）：
错误波特率下发的字节会变成**随机命令注入命令解析器**，理论上可能误触单键分支
（`Z` 全 ID 扫描 1..253 是长阻塞操作）。只试 115200 一档就够。
