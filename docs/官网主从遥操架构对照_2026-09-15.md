## 1. 一句话结论

**官网方案里，主臂和从臂之间没有任何电气连接。PC 是唯一的中转站。**

```
SO-101 主臂 ──USB串口──► PC（LeRobot 主循环）──USB串口──► SO-101 从臂
   力矩关                                                     力矩开
```

每条臂各自带一块 USB 总线舵机驱动板，各自占一个串口（`/dev/ttyACM0` / `/dev/ttyACM1`）。
主循环把主臂的**当前角度**读出来，直接写进从臂的**目标角度**。

## 2. 控制律（源码级）

### 2.1 主循环：`lerobot_teleoperate.py`

```python
def teleop_loop(teleop, robot, fps, display_data=False, duration=None):
    while True:
        loop_start = time.perf_counter()
        action = teleop.get_action()        # ① 读主臂 6 关节当前角度
        ...
        robot.send_action(action)           # ② 写从臂 6 关节目标角度
        dt_s = time.perf_counter() - loop_start
        busy_wait(1 / fps - dt_s)           # ③ 节拍对齐，默认 fps = 60
```

**没有握手、没有回包、没有重传** —— 单向位置流，掉了就掉了，下一拍（16.7 ms 后）自然会补上。
这是纯"位置镜像"（position mirroring）遥控，**不有力反馈**。

### 2.2 主臂 = 纯输入设备

```python
class SOLeader(Teleoperator):
    def configure(self):
        self.bus.disable_torque()                    # ★ 主臂力矩常关
        for motor in self.bus.motors:
            self.bus.write("Operating_Mode", motor, OperatingMode.POSITION.value)
        # 注意: 没有使能力矩

    def get_action(self):
        action = self.bus.sync_read("Present_Position")   # ★ 一次总线事务读 6 个舵机
        return {f"{motor}.pos": val for motor, val in action.items()}
```

**主臂全程力矩关断**——人拖着走，6 个舵机退化成一排"带读数的编码器"。
所以主臂不会反抗、不会抖、也不消耗保持力矩。这是"主从遥操"而不是"力反馈遥操"。

### 2.3 从臂 = 位置伺服

```python
class SOFollower(Robot):
    def send_action(self, action):
        goal_pos = {k.removesuffix(".pos"): v for k, v in action.items() if k.endswith(".pos")}
        if self.config.max_relative_target is not None:          # 安全裁剪（可选）
            present_pos = self.bus.sync_read("Present_Position")
            goal_pos = ensure_safe_goal_position(...)             # ★ 限制单步跳变
        self.bus.sync_write("Goal_Position", goal_pos)            # ★ 一次写 6 个舵机
        return goal_pos
```

`configure()` 里还给从臂舵机写了位置环 PID（`P/I/D_Coefficient`），并给夹爪限功率：

```python
if motor == "gripper":
    self.bus.write("Max_Torque_Limit", motor, 500)    # 50% 防止烧毁
    self.bus.write("Protection_Current", motor, 250)
    self.bus.write("Overload_Torque", motor, 25)
```

### 2.4 安全裁剪：`ensure_safe_goal_position()`

```python
diff = goal_pos - present_pos
safe_diff = min(diff, max_diff); safe_diff = max(safe_diff, -max_diff)
safe_goal_pos = present_pos + safe_diff
```

即**按 `max_relative_target` 限制单拍跳变**。主臂被人猛地一甩时，从臂只走"被允许的那一小步"，
而不是瞬间追过去。这是我们工程里"跳变基准 / `read_start_pose_checked`"的同一件事。

### 2.5 物理层

| 项 | 值 |
|---|---|
| 舵机 | Feetech **STS3215**（SO-101 标准版 5 V，型号 777） |
| 总线 | **半双工单线 TTL**，6 舵机菊花链，一条线串到底 |
| 波特率 | **1 Mbps**（`DEFAULT_BAUDRATE = 1_000_000`） |
| 访问方式 | `sync_read` / `sync_write` —— **一次事务操作全部 6 个舵机** |
| 上行 | 主臂：USB 总线舵机驱动板 → PC |
| 下行 | 从臂：USB 驱动板 → PC（或 Seeed 无线版：XIAO ESP32-C3 + micro-ROS over Wi-Fi UDP） |

**`sync_read`/`sync_write` 是效率关键**：6 个舵机合成一帧总线事务，而不是 6 次单独读。
否则 1 Mbps 总线 + 60 Hz 根本撑不住。

## 3. 标定：主从能互换的真正原因

官网标定**分两步、按臂各做一份**，落盘在 JSON 文件里（按 `--robot.id` 命名）：

### 步骤 1：半转对中（`set_half_turn_homings`）

```python
input("Move {self} to the middle of its range of motion and press ENTER....")
homing_offsets = self.bus.set_half_turn_homings()
# Present_Position = Actual_Position - Homing_Offset
# half_turn_homings[motor] = pos - int(max_res / 2)      # max_res = 4095 → 减 2047
```

把臂摆到**行程中间**，让中点读数 = 2048（半圈）。这一步把"每个舵机的绝对零位"归一化掉。

### 步骤 2：扫行程取极限（`record_ranges_of_motion`）

```python
print("Move all joints except 'wrist_roll' sequentially through their entire ranges of motion.")
range_mins, range_maxes = self.bus.record_ranges_of_motion(unknown_range_motors)
range_mins["wrist_roll"] = 0        # wrist_roll 是整圈关节，固定 0..4095
range_maxes["wrist_roll"] = 4095
```

人**手动**把每个关节从头推到尾，固件记录每关节的 `range_min` / `range_max`。

### 步骤 3：写进舵机本身

```python
def write_calibration(self, calibration_dict):
    for motor, calibration in calibration_dict.items():
        self.write("Homing_Offset", motor, calibration.homing_offset)      # 协议 0 时
        self.write("Min_Position_Limit", motor, calibration.range_min)     # 舵机限位
        self.write("Max_Position_Limit", motor, calibration.range_max)
```

**`Min/Max_Position_Limit` 写进舵机 EEPROM**——于是舵机自己就会拒绝越界的 `Goal_Position`，
**硬件级限位**，不依赖上位机。

### 关键点：归一化才是"主从共用的语言"

```python
norm_mode_body = MotorNormMode.DEGREES if config.use_degrees else MotorNormMode.RANGE_M100_100
# 本体 5 关节：-100..100    夹爪：0..100
```

主臂 raw 位置 →（主臂标定）→ **-100..100** →（从臂标定）→ 从臂 raw 目标。

**只要两臂各自标定准确，主臂的 "-50" 和从臂的 "-50" 就是同一个物理角度** ——
哪怕两颗舵机型号、装配角度、零位全都不一样。这就是"主从可互换"的全部秘密。

## 4. 与我们 ArmControl_HAL 的对照

| 维度 | 官网 LeRobot | 我们 ArmControl_HAL |
|---|---|---|
| 主从之间 | ❌ **无直连线**，PC 中转 | ✅ **直连**（UART4 PA0/PA1 → CAN1 PB8/PB9） |
| 主臂角色 | 纯输入设备，力矩常关，读 `Present_Position` | 同（`ma 0` READ-ONLY，`ms` 显示 torque OFF） |
| 从臂控制 | `Goal_Position` 直写，舵机内置位置环 | `sf 1` 跟随 + `ArmApi_StreamJoints()` 直写关节角 |
| **控制律** | **位置镜像（无回包）** | **位置镜像（无回包）** ← 同一个东西 |
| 频率 | 60 fps（`busy_wait` 节拍） | 30 Hz（`MASTER_TX_PERIOD_MS = 33`） |
| 帧内容 | 归一化 -100..100 | 关节角（度）×10，12 字节 payload |
| 安全 | `ensure_safe_goal_position`（限单步跳变） | `read_start_pose_checked` 跳变基准 + 限位判定 |
| 丢帧策略 | 直接丢，下一拍补 | 从臂拒帧回 NACK |
| 标定落盘 | **写进舵机 EEPROM** + 每臂一份 JSON | MCU Flash（`calib_zero_raw` 等） |
| 力反馈 | 无 | 无 |
| 链路带宽需求 | 每臂 1 Mbps 内部总线；PC⇄臂 为 USB CDC | 链路 576 B/s（19 B × 30 Hz） |

**结论：控制律完全一样，唯一差别是"谁当中转"。**
官网用 PC，我们用一条直连线。我们这几轮卡的全部痛苦，都来自那条直连线。

## 5. 对我们的三点意义

### 5.1 我们卡的那条线，官网压根不需要

官网设计里不存在"两臂互连"这个东西。它连的是**两条独立的 USB 串口**。
所以我们这一串 UART4 金属层 → CAN `lec=3` 的排查，本质上是在解决一个**自选题目**。

### 5.2 "PC 中转"可以立刻绕开全部链路问题（零新硬件）

我们两块板**已经在用 USB-TTL 接电脑**（控制台 = `USART6` → `hconsole`，就是你现在敲命令的 COM11）。
所以只要：

- 主臂：把当前 6 关节角按 ~30–60 Hz **从控制台吐出来**
- PC：一个小脚本，开两个串口，A 收到就写给 B
- 从臂：新增一条 ASCII 命令**接收目标角**（内部直接调现成的 `ArmApi_StreamJoints()`）

主从之间**一根线都不用接**，PA0/PA1 与 CAN 的金属层问题全部消失。

### 5.3 它还能当 CAN 的"标尺"

如果 PC 中转能跑通，就意味着：舵机总线、跟随模式、安全判定、控制律、标定**全部正确**，
剩下的唯一变量就是 CAN 那几根线。那时再回头调 CAN，故障域已经被压到最小
（而且可以用 PC 同时抓两端的角度，直接看出谁没动）。

## 6. 三条路线（含代价）

| | A. PC 中转（官网路线） | B. 继续调 CAN（PB8/PB9） | C. 回退 UART4 |
|---|---|---|---|
| 新硬件 | **不需要** | 已有收发器，需接线正确 | 不需要 |
| 固件改动 | 小（主臂加"吐位置"、从臂加"收目标"各一条命令） | 无（固件已就绪） | 无 |
| 现场工作 | 无接线工作，直接跑 | 万用表 9 点 + 跳线电平 + 120Ω | 已止损，不建议 |
| 结果 | **今天就能看到两臂跟动** | 取决于那几根线 | — |
| 缺点 | 成品必须带一台 PC | 仍可能再耗轮次 | 金属层未解决 |
| 定位 | **过渡 / 验证 / 调试标尺** | **成品终态**（两臂自走） | 备胎 |

**推荐：A 与 B 并行。**
先用 A 把"两臂跟动"这件事**确认下来**（证明除链路外全对），再回头用 A 当标尺去钉死 B。
这样即使 B 还要几轮，项目也不再是"什么都动不了"的状态。

> **2026-09-15 决策结果**：用户选定 **A（PC 中转）为正式方案**，且**成品允许常驻一台 PC**
> ⇒ B（两臂直连）降级为备选，不再是必做项。A 已当天实现完毕，见第 7 节。

## 7. ✅ 已实施：PC 中转（2026-09-15 当天落地）

**决策**：采用官网架构为**正式方案**（成品允许常驻一台 PC）⇒ 两臂直连（UART4 / CAN）**不再是必做项**。

### 7.1 固件改动（协议层 `arm_control_protocol.c` 一行未动）

| 端 | 命令 | 作用 |
|---|---|---|
| **主臂** | **`sp <Hz>`**（1~100，`0` 停） | 按节拍往控制台吐一行 `#P a1 a2 a3 a4 a5 a6`；`ms` 里能看到 `Console stream` 的 lines / skipped 计数 |
| **从臂** | **`#P a1..a6`** | 收到即解码 → 直写关节角；**成功时完全静默**（30~60 Hz 下任何打印都会淹掉控制台），只在字段不足/被拒时按 64 次限流报错 |

**关键设计点**

1. `aN = 关节角(rel-home)×10`，用与 0x13 流帧**同一个** `Aproto_EncDeg10` / `Aproto_DecDeg10`
   ⇒ 两端语义严格同一，不可能像"传舵机度"那样错位。
2. 从臂侧复用的是**同一条** `ArmApi_StreamJoints()` 通路 ⇒ `sf` 门闩、限位 clamp、
   跳变基准（首帧以从臂当前实际位置为基准，之后限单步跳变）**全部照旧生效**，
   安全行为与直连链路 100% 一致。
3. 主臂的 `mf`（0x13 直连转发）与 `sp`（控制台流）**相互独立**；`master_service()`
   已重构成"两路共用同一拍读法"——两路都开时**只读一次**舵机，不会让 6 轴被读两遍。
4. `#P` 行从串口到达时若控制台正在示教模式，会被既有的"自动退出示教"逻辑接管
   （只触发一次，不会刷屏）。


### 7.2b 排障：状态行一直「转发 0 行」

**先看「主臂收到 N B」**，两种故障完全不同：

| 现象 | 含义 | 处理 |
|---|---|---|
| `主臂收到 0 B`（其余也是 0） | **端口选错** —— 控制台不在你给的 `--master` 上 | 用下面的嗅探器找真身 |
| `主臂收到 >0 B`，`其它` 在涨，但无 `#P` | 主臂没敲 `sp <Hz>`（或被示教/单键模式吃掉输入） | 主臂敲 `mf 0` → `sp 30` |

脚本会在开跑 3 s 后自动打这条告警（之后每 10 s 复述，主臂口一有数据就停）：

```
⚠ 主臂串口 COM12 已 3 s **一个字节都没收到**（其它输出也是 0）。
```

#### `tools/serial_sniff.py` —— 只读嗅探器（找不到口就用它）

一个字节都不写，纯监听，不会碰舵机。把候选口同时监听几秒，直接下判决：

```powershell
py tools/serial_sniff.py --list
py tools/serial_sniff.py COM8 COM11 COM12 COM22 --secs 6
```

判决表：

| 输出 | 含义 |
|---|---|
| `✅ 这是【主臂位置流】口` | 拿它当 `--master` |
| `❗ 一个字节都没收到` | 不是控制台：RX 没接 / RX-TX 接反 / 插到别的 UART |
| `❌ 打不开：PermissionError 拒绝访问` | 被别的程序占着（串口助手 / 另一个脚本 / 上次没退干净） |
| `⚠ #P 前缀但字段数不对` | 波特率不匹配或半行截断 |
| `○ 有输出但没有 #P` | 可能是从臂口，或主臂还没 `sp` |

> ⚠ **本脚本从不打印 `#P` 行本身**（会刷屏）。所以在终端里看见 `#P ...`
> 而脚本计数却是 0 时，那串 `#P` **一定来自另一条串口路径**
> （板载 USB 串口 / 串口助手窗口）—— 拿它当依据会彻底跑偏。这是 09-15 现场踩到的坑。

### 7.3 带宽核算（为什么 115200 够用）

单行 ≈ 3 + 6×6 + 5 + 2 ≈ **46 B**（含 CRLF）；控制台 115200 8N1 ⇒ ≈ 4.0 ms/行。
- 30 Hz（33 ms 周期）⇒ 占用 **≈ 12%**
- 60 Hz（16.7 ms）⇒ 占用 **≈ 24%**

⇒ 60 fps 对齐官网仍有充裕余量。上限受"每行 4 ms"约束，理论上限 ≈ 250 Hz。

### 7.5 双串口前提

PC 中转需要**两个 USB-TTL 适配器**（一块板一个口）。本机已识别到
`COM8 / COM11 / COM22`（CH340）与 `COM12`（**CP210x**）—— 硬件现成。
⚠ 一块 USB-TTL 拔插切换在两块板之间**不行** —— 必须两个口同时在线。
⚠ `--master` 与 `--slave` 传同一个口会被脚本直接拒绝。

> 适配器**型号**在这里不是无关细节：CP210x / FTDI 的驱动带一个默认 **16 ms** 的
> Latency Timer（见 7.6 ②），CH340 多数不暴露该项。所以"哪个口接主臂"会影响延迟。

### 7.6 延迟调优（2026-09-15 补；15:5x 按实测定标）

整条链路的延迟 = **主臂采样量化 + 采样跨度 + 线路传输/阻塞发送 + 驱动批处理 + 从臂下发**。
逐项量化（`sp 60` + 115200 下）：

| # | 环节 | 量级 | 怎么降 | 要改固件? | 状态 |
|---|---|---|---|---|---|
| ① | 主臂采样周期 `sp <Hz>` | **16.7 ms**（`sp 60`） | 主臂敲 `sp 100` → 10 ms（范围 1~100，周期下限 5 ms） | 否 | 可做 |
| ② | **主臂口 USB Latency Timer** | **0~16 ms（常数偏移）** | 设备管理器 → 端口 → 高级 → Latency Timer：16 → **1 ms** | 否 | **未做** |
| ③ | `cprint` 阻塞发送 35 B | 3.0 ms @115200 | 控制台波特率 115200 → 460800（`make CBAUD=460800`） | **是** | 固件已备 |
| ④ | 主臂主循环占用（决定 ① 上限） | ~10 ms/帧 | 先 `mf 0`（否则两路各读一遍舵机，开销翻倍）；③ 也能腾余量 | 部分是 | — |
| ⑤ | 从臂下发（2 次 SyncWrite @1 Mbps） | ~1-2 ms | 已最优（`stream_enter` 已把 GOAL_SPEED 写 0=max） | 否 | 已最优 |
| ⑥ | **从臂逐字符回显 `#P`** | **~3.5 ms/帧 + 18% 发送带宽** | 流模式关闭控制台 echo（见下） | **是** | **新发现** |

**① 和 ② 是最大的两块，且都不用改固件** —— 先做这两条。
③ 和 ⑥ 各值 ~3 ms，但要重编重烧，属于第二梯队。

> **② 的实测底数**（2026-09-15 用 `winreg` 直读注册表，PowerShell 输出通道在本机是坏的）：
> 本机全部 14 个串口 `Device Parameters\LatencyTimer` **都是 `<unset>`** ⇒
> **从未设置过，全走驱动默认（CP210x/CH340 均 16 ms）**。所以这一项**一分钱都还没省**。

#### ⑥ 从臂逐字符回显（`#P` 流模式下白烧 18% 带宽）

`Core/Src/main.c:196-200`（`Console_TryReadLine()`）：

```c
if (console_rx_len < sizeof(console_rx) - 1) {
    console_rx[console_rx_len++] = ch;
    /* Echo */
    HAL_UART_Transmit(&hconsole, &ch, 1, 10);   // ← 每字符一次阻塞发送
}
```

而且 `Console_TryReadLine()` **每次调用只处理一个字符**（读一个字节就 return）。
一行 `#P a1..a6\r\n` ≈ 35 字符 ⇒ **35 次阻塞发送 + 35 轮主循环**，约 **3.5 ms/帧**；
从臂 TX 上还白占 `35 B × 60 Hz ≈ 2.1 kB/s`（115200 下 18%）。

**副作用（比延迟更值得修）**：与从臂自己的诊断打印（reject / watchdog / `pv`）争抢 TX，
实测出现 `Stream watchdog: no cmd for 500 ms`（×5）；断流期间主臂走过 160°，
恢复后首帧 `stream_prev` 是旧值 ⇒ 必然判 `Stream reject: J5 jump 160 deg` 整帧拒，
且**拒绝时不更新 `stream_prev`**（main.c:1778-1784）⇒ 连续多帧被拒，累计 `rc=4` 拒帧 **3457/9133**。

**✅ 已实施（2026-09-15 16:1x）**：`ec 0|1` 已加（默认 ON），
`pc_relay.py` 侧**没有**自动发 `ec 0` —— 由现场决定，用 `--slave-cmd "ec 0"` 更可控
（否则脚本一启动就静默从臂控制台，现场看不到 `Stream reject` 诊断）。
另外主循环已改成"按需吸干"（一次最多 64 个字符），把"每拍只吃 1 字符"的
吞吐天花板拆掉；`lk` 里可读 `ring drop` / `reject streak max` / `watchdog`。
完整机理与判据见 `docs/从臂偶发冻结_自锁与收帧瓶颈_2026-09-15.md`。

⚠ 仅关回显**不能**根治：真正的"停几秒再猛冲"来自**拒帧不更新 `stream_prev`
⇒ 自锁 + 500 ms 看门狗**。根治要把 ② 跳变判据从"整帧拒绝"改成"限速跟随"，
属判定语义变更，**待确认**（同文档 §3 给了完整方案与理由）。

#### 抖动诊断：新增自动判据（`tools/pc_relay.py`）

光看「当前 Hz」查不出 ② —— 因为它是**常数偏移**，帧率完全正常。所以脚本加了
**帧到达间隔的 σ** 与峰值，并在异常时自动给出结论：

```
转发 1242 行 | 当前 61.0 Hz | 坏行 0 | 其它 9 | 主臂收到 39835 B | 积压 0 B | 从臂 45647 B | 抖动 2.3 ms | 用时 22 s
```

| 现象 | 结论 |
|---|---|
| σ 小（< 3 ms）、峰值接近帧周期 | 链路平滑，延迟来自上游（① / ④） |
| **σ 大 + 峰值 ≈ 16/32 ms** | **② Latency Timer 在攒批交付** |
| σ 大 + 峰值不定 + `当前 Hz` 到不了设定值 | ④ 主循环占满，或 ⑥ 从臂侧停顿 |

⚠ **判据为什么用 σ 而不是"峰值/中位"**：帧成簇时**中位数自己也被拉到长间隔那一侧**
（0 与 33 ms 交替 ⇒ 中位 = 33），比值恒为 1、反而检不出来。σ 才单调。
已用 5 组构造数据回归：平滑/理想→不告警；攒批(sp60)、攒批(sp100)、偶发卡顿→告警，**ALL PASS**。

⚠ 在 `sp 60`（16.7 ms）下 LT = 16 ms 恰好"一周期一帧"、簇不明显 ⇒
**要看簇，得先把主臂提到 `sp 100`（10 ms）**。

#### ① `sp` 提频

```
主臂> sp 60
```
改完**用转发脚本状态行的「当前 Hz」验真**：到不了 60 就说明主臂主循环被占满（④），
此时提 ③ 的波特率或退回 50。

> ⚠ **坑（2026-09-15 现场踩到，浪费一轮）**：`py tool/pc_relay.py --start` 会**无条件重发
> `sp 30`**，把你在主臂控制台手敲的 `sp 60` 顶回去 —— 现象是"主臂怎么设都是固定 30 Hz，
> `sp 60` 没用"。`sp` 命令本身**没有 30 的上限**（范围 1~100，`sp 60`→16 ms 周期，已核源码）。
>
> 两种正确做法（**二选一，别混用**）：
> - 开机命令交给脚本：`--start --hz 60`
> - 保留手敲档位：`--start --hz 0`（`--hz 0` = 脚本不发 `sp`，只发 `mf 0` / `sf 1`）
>
> 已给 `--start` 加了显式警告行，避免下次再当成固件问题去查。

#### ② Latency Timer（最隐蔽的一项）

CP210x / FTDI 的驱动默认 **16 ms**：它不是"有数据就交给应用"，而是"**攒够 16 ms 或缓冲满**才交"。
所以每一帧都被整体压后最多 16 ms —— 而且它是**常数偏移**，看帧间隔、看 Hz 全都发现不了。

- 路径：设备管理器 → 端口 (COM & LPT) → 对应适配器 → 属性 → **端口设置** → **高级** → Latency Timer
- 数值：`16` → **`1`**（毫秒）
- ⚠ 与波特率**无关**，改 baud 不会顺带解决。

**只有「主臂口」这一侧重要**：LT 管的是**接收方向**（攒够才交给应用）。
主臂口是 PC 在读它 ⇒ 受影响；从臂口是 PC 在写 ⇒ 写方向基本不受 LT 约束。

**本机适配器实测对照**（`winreg` 直读 `Enum\USB\...\Device Parameters`）：

| VID/PID | 型号 | 端口 | 能否改 LT |
|---|---|---|---|
| `10C4:EA60` | CP210x (Silicon Labs) | COM12 | ✅ **高级页有 Latency Timer** |
| `1A86:7523` | CH340 | COM8/11/13/18/19/20/22 | ❌ 高级页通常无此项 |

⇒ **把主臂接到 COM12（CP210x）并把 LT 改 1 ms**，从臂用 CH340 即可。
（CH340 可尝试在注册表 `Device Parameters` 下**新建 DWORD `LatencyTimer` = 1**，
再禁用/启用设备；但 CH341SER 是否采纳该值未经证实，属实验手段。）

> md5 逐字节一致）。要用请按上面两条 `make` 重编 —— 但源码已变，重编不会得到同样的 md5。

> ⚠ `BAUD=` 与 `CBAUD=` **不是一回事**：`BAUD` 改的是 UART4 主从链路（PC 中转根本不走），
> `CBAUD` 改的才是控制台 USART6。降延迟要动的是 `CBAUD`。

#### 明确**不要**动的（都是安全机制）

| 参数 | 值 | 为什么不动 |
|---|---|---|
| `STREAM_MAX_JUMP_DEG` | 25°/帧 | 30 Hz 下 = 750°/s，远超臂能力，根本不是瓶颈；调大只是丢保护 |
| `read_pos_vote` 的 1 ms 采样间隔 | 1 ms × 6 轴 | 它**就是** ④ 里 6 ms 的来源，但同时是抗总线噪声/帧跳变的判据 |
| `STREAM_TIMEOUT_MS` | 500 ms | 断流看门狗，与延迟无关 |

#### 分诊顺序（按状态行读数走）

```
「当前 Hz」到不了 sp 设的值  → ④ 主臂主循环占满：先 mf 0，再提 CBAUD(③) 或降 sp
「积压」持续 > 0 B           → PC/从臂侧跟不上，位置在排队
「抖动」大 + 峰值≈16/32 ms   → ② Latency Timer 在攒批（改 1 ms；主臂走 CP210x）
「抖动」大但峰值不等距       → ④ 或 ⑥（从臂回显/诊断占 TX）造成周期性停顿
以上都好、仍"手感慢"         → ① 提 sp 到 100；仍不够就上 ③ 460800
```

## 9. 诚实的边界：官网和我们还不一样的地方

| 项 | 官网 LeRobot | 我们（现状） |
|---|---|---|
| 位置语义 | 归一化 -100..100（按各自标定） | 关节角 rel-home（度）×10 |
| 标定落盘 | 写进**舵机 EEPROM** | MCU Flash（`calib_zero_raw`） |
| 单步跳变保护 | `ensure_safe_goal_position` | 从臂 `stream_prev` + 限位 clamp |
| 丢帧 | 直接丢，下一拍补 | 同（位置流本就不需要重传） |
| 循环节拍 | `busy_wait(1/fps)` 60 fps | 主臂 `sp` 周期（建议 30~60 Hz） |

差异都在"表示层"，不在控制律。**位置镜像 + 无回包 + 无力反馈** 这一核心是一致的。
