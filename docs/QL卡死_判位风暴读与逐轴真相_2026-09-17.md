# QL 卡死在一点不前进 —— 判位"风暴裸读" + 逐轴真相报告

日期：2026-09-17　　现场：从臂（COM11）手动发 `q` / `QL`，两臂固件 `05/06_PCrelay_ec`

## 0. 现场现象（用户原始日志）

```
QL 2 5 60
  Multi-point loop: 2 points, rounds=finite, speed=60 deg/s
  PRE-CLAMP target: 178.37 76.04 270.24 250.29 181.80 140.22
  POST-CLAMP target: 178.37 76.04 270.24 250.29 181.80 140.22
  Move started: v=30 deg/s a=60 deg/s2
  From: 178.73 76.40 270.07 250.29 182.51 143.74
  To:   178.37 76.04 270.24 250.29 181.80 140.22
>   approach ramp ON (tick=132/137, 1000->1000)  [#42=0: ramp disabled, keeping normal speed]
...
>   QL: J6 feedback blocked - corrupt frame (bus noise / dropped byte)
```

之后：`f` 六轴**全部能正常读到**（`178.73 76.40 270.07 250.29 182.51 143.74`），
`LP` / `SP 42 30` / `SP 43 0.1` 全部正常，但 **QL 再也不前进**，也没有
`Point 1 reached` / `Multi-point loop done`。

## 1. 两个必须先读懂的地方

### 1.1 "J6 corrupt frame" 里的 J6 是假的（至少是不完整的）

`cmdMultiPointTargetReached()` 逐轴 `j=0..5`，每遇一轴读不到就覆盖一次
`mp_fail_joint`。所以**打印出来的轴 = 那一趟里最后一个失败轴**，不是"只有它坏"。
25 次计数里其它轴的失败全被这一句吞掉了。

### 1.2 "六轴一个都没动"——这是判断"命令有没有被执行"的最快指纹

`From:` 的六个值 = 段开始时的实测位置；段跑完后再敲 `f`，如果六轴读数与
`From:` **逐位相同**（本次就是：`178.73 76.40 270.07 250.29 182.51 143.74`），
说明这一段**物理上没有发生任何运动**。别去算"J6 差 3.52°"，先确认臂到底动没动。

## 2. 根因（三条，互相叠加）

### ① 判位是"风暴式裸读"——1 Mbps 半双工总线上最脆的一种读法

- 判位在每个主循环趟里读**六轴**；而且 `cmdMultiPointService()` 在同一趟里被
  调用**两次**（`main.c` 轨迹结束链 + 主循环尾部）⇒ 最多 **12 次总线事务/趟**。
  主循环空转时这就是对总线的**连续读、没有一微秒空闲**。
- 总线（USART3/USART5）跑 **1 Mbps = 每字节 10 µs**。STM32F4 的 UART **没有 FIFO**
  （DR + 移位寄存器最多留 2 字节），接收必须在这 10 µs 内把 DR 取走，否则丢字节。
  被任何中断抢占一下（TIM2 优先级 0 / USART6/UART4 优先级 1）就丢。
- 判位要求"**六轴一次全过**"，于是读得越密 → 丢字节越多 → 越判不出来。

固件里其实**早就写过这个结论** —— `readActualEndPose()` 的注释：

> 2026-09-11: 改用 read_pos_vote() …… 此前这里是**裸读 SERVO_GetPosition** ——
> 6 次事务里任何一次丢字节就让整条 f 命令失败，而总线 A（J1/J2/J3）在 1Mbps 下
> 偶发丢帧是已知事实，表现为"连发 3 次 f 才成功一次"。

`f` / `P 0` / `g` / `ms` / 起点安全读取**全部**已改成 `read_pos_vote()`
（3 采样多数表决 + 原地重试 + 采样间隔）。**只有 QL 判位这一处没改。**

### ② 判位永不放弃 —— 卡死时只给一句误导性文案

只要有一轴够不到 `MULTI_POINT_REACHED_TOL_DEG = 2.0 deg`，或某轴一直读不到，
循环就永久停在这一个点上；而文案只说"corrupt frame（总线噪声/丢字节）"，
**既不说哪一轴差多少，也不说是不是"读不到"**。

### ③ 轨迹通道从不动 `Torque_Enable` —— 松过力的轴会"静默不执行"

轨迹（含 QL 段）只写 `GOAL_POSITION` / `GOAL_SPEED`，**从不碰力矩开关**。
于是：

| 情形 | 结果 |
|---|---|
| 用过 `t J 0` 松力手摆姿态，之后忘了上力 | 那一轴**永远不动**，所有命令都返回成功，QL 卡死 |
| 旧版 `z J` / `z a` | 结束时把**六轴** `Torque_Enable` 写 0（注释写 "safe state"，2026-09-17 已删）⇒ 归位完整臂掉力 |

这正是"六轴一个都没动"最可能的解释，也是本次必须让固件**自己报出来**的东西。

## 3. 已实施改动

### main.c

1. **判位改用多数表决读**：`read_pos_vote_to(j, &v, 10ms)`（新拆出的带超时版本；
   `read_pos_vote()` 变成它的 100 ms 薄壳，老调用点行为不变）。原来的 100 ms
   裸读 `read_pos_retry()` 已无调用者，删除。
2. **判位节流 60 ms**（`MULTI_POINT_POLL_PERIOD_MS`）：总线占用降到约 1/50，
   稳定窗口本来就是 500 ms，判位精度不受影响。
3. **逐轴"最近有效值"兜底 400 ms**（`MULTI_POINT_LASTGOOD_MS`）：偶发丢一帧
   不再把整个点判废。
4. **单点确认超时 8 s**（`MULTI_POINT_CONFIRM_TIMEOUT_MS`）：超时 → 打印逐轴
   真相 → **放行进入下一点**（循环能自己跑完），不再无限等。
5. **逐轴真相报告** `cmdMultiPointReportTruth()`，每轴一行：
   `目标 / 实测 / 误差 / ok|OUT OF TOL|READ FAIL`，够不到的那轴**额外读它的
   力矩开关**（`torque=OFF <<< 用 t J 1 上力` / `torque=ON（被负载卡住/限位挡块）`），
   再汇总**各轴读失败次数**与**每轴的失败原因**（NO_REPLY / BAD_FRAME / ERROR_BITS）。
   原来只打"最后一个失败轴"的 25 次计数，也改成打这份表。
6. `multi_point_leg_reset()`：每段开始/结束时清空逐轴计数、缓存、判位节流。

### scs_protocol.c（影响全部读，不只 QL）

`DXL_ReadDiag()` 的接收缓冲**前导噪声余量 +2 → +8**。
半双工下自己的 TX 回声只能排掉"此刻已在 DR 里"的那 1~2 字节，残留 2~3 字节是
常态；旧余量=2 时只要残留 3 字节，真应答帧尾（CHK）就落在 `rx_cap` 之外 ⇒
帧被截断 ⇒ 校验失败 ⇒ 报成"corrupt frame"。这就是那条文案的真正来源之一。

### servo_driver.c/.h

新增 `SERVO_GetTorqueEnabled(joint)`：1=ON / 0=OFF / 0xFF=读不到（只给报错路径用）。

## 4. 现场三步（先分清"不动"还是"读不到"）

1. **上电/接手臂先确认力矩**
   `t 0 1` … `t 5 1`（六轴依次），或直接敲 `i`（初始化，结束会自动抱闸）。
   看到 `Jx Torque ON: OK` 才算数。**手摆过姿态的那一轴必须补这一下。**
2. **重跑 `QL 2 5 60`**，两种结果都好用：
   - 正常跑完 → 说明就是①风暴裸读 + ②卡死逻辑；已修好。
   - 仍卡 → 8 秒后会自己打出这张表（这是新固件最要紧的产出）：
     ```
     ===== QL point 1: NOT confirmed in 8000 ms =====
       tol=2.0 deg   read-fail counts: J1=0 J2=0 ... J6=3
       J1  tgt=+178.4  act=+178.7  err=+0.4  ok
       ...
       J6  tgt=+140.2  act=+143.7  err=+3.5  OUT OF TOL  torque=OFF <<< 该轴没发力矩
             read-fail reason: corrupt frame (bus noise/dropped byte)  err=0x00 []
     ===== continuing to next point =====
     ```
     看两件事：**哪一轴 `OUT OF TOL` 且 `torque=OFF`**（→ `t J 1` 上力就完事）；
   **哪一轴 `read-fail` 次数远高于其它**（→ 那一轴/bus 的接插与线缆，J4~J6 在
   bus B = UART5 PC12/PD2）。
3. **单轴对照**：`a 5 140.2`（单关节直达，0-based，5 = J6）。它动 → 轨迹通道的事；
   它也不动 → 力矩/机械挡块/负载，与总线无关。

## 6. 未动但记一笔

- `cmdMultiPointService()` 在一趟主循环里仍被调用两次（`main.c` 轨迹结束链 +
  主循环尾部）。判位节流已经把它变成一次空转调用，功能无影响；要彻底清理需把
  轨迹结束链那一处删掉（涉及 `else if` 链语义，单独改）。
- `MULTI_POINT_REACHED_TOL_DEG = 2.0 deg` 保持不变：放宽它只会把"某一轴根本到不了"
  这件事实掩盖掉。到位与否由第 4 节的表说话。
