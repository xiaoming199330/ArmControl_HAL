## 0. 一句话

**分两轮测，最后合并出一张表。**

因为 **CAN 和网口在本板上硬件互斥**（`CAN2 = PB12/PB13` 与 RMII 的 `ETH_RXD1/TXD1` 是同一对引脚），
一次运行里两者不可能都通 —— 脚本检测到会警告，但不会替你烧固件。

## 1. 前提检查（先做，别跳过）

| 项 | 怎么查 | 期望 |
|---|---|---|
| 串口口名 | 设备管理器，或 `mode` | 控制台口（默认 `COM11`，**会变**） |
| 控制台没被占用 | 关掉所有串口助手 / 终端窗口 | ⚠ **同时开着会抢字节流，数据全废** |
| 板子活着 | `py -3 tools/board_alive.py --port COM11` | 有响应 |
| 固件版本 | 敲 `h` | 见下表（`fw-tag` + fix 清单） |
| CAN 卡 | 设备管理器能看到 PEAK | PCAN-USB |
| 臂停着 | 串口敲 `stop` | 采样期间臂不动 |

固件版本对应：

| 轮次 | 固件 | 横幅要求 |
|---|---|---|
| 第 1 轮 | `LINK=net` | `fw-tag ARM-NET-0921A` |
| 第 2 轮 | `LINK=can` | `fw-tag ARM-CAN-0918H` **且同一行含 `rc-tim4-capture`** ← 见 §1.1 |

> ⚠ **红线 64**：判"新固件进没进"**只看 `fw-tag` + fix 清单是否齐全**，别看出不出得来别的。

## 5. 读数怎么理解

### 5.1 列的含义

| 列 | 含义 | 该看哪个 |
|---|---|---|
| `样本` | 有效样本数 | 应等于 `--n` |
| `成功` | 收到且校验通过 | **不是 100% 就说明有丢包/坏包** |
| `超时` | 超过 `--timeout` 没回 | >0 要查 |
| `坏包` | 帧能拼齐但 CRC/命令码不对 | >0 说明串扰或解析有问题 |
| `min` | 最快 | 看链路"底噪" |
| **`p50`** | **中位数** | ⭐ **主指标，抗抖动** |
| `p90` / `p99` | 长尾 | **实时控制看这个**，p99 才是卡顿体验 |
| `max` | 最坏 | 偶发一个大的可能只是调度抖动 |
| `mean` / `std` | 均值 / 标准差 | `std` 大 = 抖动大 |
| `次/秒` | 吞吐 | 决定能不能上 50Hz 流 |
| `场景` | `static`（臂不动）/ `motion-J5-5deg-T2s`（臂在摆动） | **两个场景的数不可直接比**（见 §7） |

### 5.2 预期量级（先心里有数，数据回来好判断真假）

| 链路 | 物理下限 | 主要开销 | 预期 p50 |
|---|---|---|---|
| 串口 115200 | **~3.9 ms**（45 字节 × 86.8 µs/字节） | **线速**，不是固件 | **~2~5 ms** |
| 网口 100M | ~5 µs（帧在线上的时间可忽略） | **固件处理** | **~0.5~1 ms** |
| CAN 500k | ~0.3 ms（多帧） | 分包重组 + 固件处理 | **~0.3~0.8 ms** |

> ⭐ **关键理解**：串口慢是**物理必然**（115200 每字节约 87 µs），不是实现问题。
> 所以"哪条快"这个问题的答案很可能是 **网口 / CAN 远快于串口**，
> 真正有信息量的是 **网口 vs CAN 谁更快**，以及 **p99 谁更稳**。

### 5.3 公平性是怎么保证的（不用你操心，但要知道）

- 三条链路**共用 `can_host.py` 的同一套编解码**（帧格式/CRC/字节序/字段全同）
  ⇒ 差异只来自链路本身。自检里有断言："串口帧去掉 `AA 55` 头 == 网口报文"。
- **单发单收**：绝不复用 `arm_net_host.py` 的 `NetHost.request()` —— 它内部**重试 3 次**，
  会把超时等待算进 RTT，统计直接废掉。
- **默认只读**：`--cmd status` 时臂完全不动。

### 5.4 ⭐⭐ 最容易判错的地方：RTT 里有多少是「命令本身」的

> 2026-09-22 实测补入（net 固件 / `ARM-NET-0921A` / 用忙等绕开 `settimeout`，排除 PC 侧干扰）。

同一条链路、同一套探测代码，**只换命令**：

| 命令 | p50 | 分类 | 说明 |
|---|---|---|---|
| `ping` | **0.29 ms** | 纯链路 | 只回 2 字节，不碰硬件 |
| `param_count` | **0.32 ms** | 纯链路 | 只读内存 |
| `status` | **6.6 ms** | 读硬件 | 含「读六轴舵机实际位置」≈ 6.1 ms |
| `fk` | **6.7 ms** | 读硬件 | 同上（正解要拿当前角） |
| `move_joints` | **153 ms** | 控制通路 | 读起点 + 规划 S 曲线 + 上力矩 |

**三条结论，缺一条都会判错：**

1. **纯链路只有 0.3 ms** —— 网口真实的往返开销就这么大。
2. **`status` / `fk` 的 6.6 ms 里有 6.1 ms 是固件读舵机**，三条链路都得付这笔钱。
   ⚠ 拿它比「哪条链路快」会被压平：网口 6.41 vs 串口 11.14 ⇒ 只差 **1.7 倍**（假象）；
   换成 `ping`：网口 0.29 vs 串口 3.21 ⇒ 差 **11.3 倍**（真值）。
3. **`move_joints` 是 153 ms** —— 即使目标 = 当前角（原地不动），`cmdMove` 也会启动完整轨迹
   （固件日志可见 `Move started: v=35 deg/s`、`approach ramp ON tick=4/11`）。
   ⇒ **153 ms ⇒ 上限 6.5 Hz，遥操作绝不能用它，必须走 `stream_joints`。**

**怎么用这张谱：**

| 你的问题 | 用哪个命令 |
|---|---|
| 哪条链路快？ | `--cmd ping`（可加 `param_count` 交叉验证） |
| 真实控制响应里，用户会感觉到多少延迟？ | `--cmd status`（读硬件的钱按真实场景付） |
| 能不能上 50 Hz 流模式？ | `--cmd stream_joints --motion`（见 §7） |

⭐ 脚本已内置判读：跑 `--cmd status` / `--cmd move_joints` 时会在表下**自动打出对应的警告**。

⭐ `--cmd` 支持逗号分隔 —— 一次跑多个命令会**自动追加一张「命令耗时谱」**，一眼看出
哪部分是链路的、哪部分是固件读硬件的：

```powershell
py -3 tools/link_latency_bench.py --link serial,net --cmd ping,param_count,status --n 150
```

> ⚠ 顺带一条排查纪律：**验证「工作范围有没有装载」不要搜 `h` 的输出**。
> `Work ranges applied (6 jnt)` 只在**上电时**打印一次（`main.c:1426`），敲 `h` 只回帮助菜单。
> 可靠的判据是敲 **`L`** 看限位表 —— 若显示的是 `J1=63~303 / J5=12~351`
> 这类**非代码初值**（`main.c:990` 是 `J5=180~340`），就说明 `apply_calib_limits()` 跑过、限位有效。

### 5.5 ⭐ 实测基线（2026-09-22，三链路全测完，可直接拿来对照）

完整报告 → `docs/三链路延迟基准_实测报告_2026-09-22.md`

**p50（ms）：**

| 命令 | 串口 115200 | CAN 500k | 网口 UDP |
|---|---|---|---|
| `ping`（纯链路） | 3.15 | 1.65 | **0.90** |
| `param_count` | 3.10 | 1.63 | **0.96** |
| `stream_joints`（静止） | 4.74 | 2.62 | **1.75** |
| `stream_joints`（运动中） | 4.78 | 2.74 | **1.92** |
| `fk` | 11.32 | 9.14 | **7.50** |
| `status` | 11.07 | 8.71 | **7.55** |
| `move_joints` | 157.08 | 155.81 | 91.00 † |

**网口 > CAN > 串口，是清楚的 3 级台阶**：网口比 CAN 快 ~1.8×，比串口快 ~3.5×；
CAN 比串口快 ~1.9×。三条链路全程**零超时、零坏包**。

⭐ **两轮可比性自检（必做）**：串口是两轮共有对照 —— 网口轮 3.22 / CAN 轮 3.15 ms（差 2%）
⇒ 表有效。

必须记住的结论：

1. **`status` 比 `ping` 多出来的约 6~8 ms 是固件读六轴舵机的固定开销**，与链路无关
   ⇒ 用 `status` 比链路只会得到 1.5 倍的假象，真值看 `ping` 的 3.5 倍。
2. **臂在动几乎不拖慢流模式**：`stream_joints` 静止→运动 p50
   网口 1.75→1.92（+10%）、CAN 2.62→2.74（+5%）、串口 4.74→4.78（+1%）
   ⇒ 流模式 ACK 与插补解耦，20~50Hz 遥操作在运动时依然成立
   （网口 523、CAN 352、串口 202 次/秒）。
3. ~~**CAN 的抖动最小**（`ping` std 0.06 ms、max 仅比 p50 高 9%）~~
   **⚠ 2026-09-22 被 10 分钟长跑推翻，见 §5.5.1**：短测里 CAN 的 std 确实最小，
   但长跑（20 万帧）暴露它**每分钟约 1 次 40~180 ms 尖峰** ⇒ std 1.48、`max` 179.94 ms，
   反而比串口（std 0.56、max 15.26）差一个数量级。
   ⇒ **教训：短测的 max/std 不能代表最坏情况。**
4. **`move_joints` 与链路无关**（同轮内两条链路 1.0 倍），绝对值由固件轨迹决定
   （91~157 ms），且**不可跨轮比** —— 它随臂姿态变化。遥操作绝不能用它。
   ⚠ 早期笔记把它记成 "p50 ≈ 153 ms" 是错的：153 是 p99/max，p50 是 91 ms。

#### 5.5.1 ⭐⭐ 10 分钟六轴全动长跑（最终基线，最该信的一组）

条件：**600 s/链路 × 3 条、六轴同时摆（J1~J4 ±20°、J5 ±70°、J6 ±33°、周期 12 s）、零拒帧、10 桶巡检全过**。

| 指标 | 网口 UDP | CAN @500k | 串口 COM11 |
|---|---|---|---|
| 样本 | **328,131** | 204,517 | 121,478 |
| 成功 | 100% | 204,513 | 100% |
| **超时** | **0** | **4（0.002%）** | **0** |
| **p50** | **1.61** | 2.72 | 4.78 |
| p90 | **2.22** | 2.94 | 5.16 |
| **p99** | **3.40** | 6.60 | 6.32 |
| **max** | 117.66 | 179.94 | **15.26** |
| mean | **1.78** | 2.88 | 4.88 |
| std | 0.82 | 1.48 | **0.56** |
| 吞吐 | **547 帧/s** | 341 帧/s | 202 帧/s |
| p50 全程极差 | 0.41（25%） | 0.08（3%） | **0.04（0.8%）** |

- ✅ **三条链路都没有热漂移**：CAN 桶间 p50 极差 **0.08 ms**、串口 **0.04 ms**；
  网口 0.41 ms 但方向**向下**（前 3 分钟 1.94 → 1.53 ms 后锁定，属**收敛**不是漂移，
  最可能是上位机 CPU/网卡预热）。舵机温度实测 37~43 ℃（跑完回落 33~38 ℃）
  ⇒ **确有 3~5 ℃ 温升，但延迟完全不动**。
- ⭐⭐ **常态快 ≠ 尾巴好**：按 p50 是网口 > CAN > 串口，按 max 是**串口 > 网口 > CAN**。
  50 Hz 下最坏掉周期数：网口 5、CAN 9、串口 **0**。
- ⭐ **六轴大摆幅 vs 单轴小幅，RTT 几乎不变**（网口 1.92→1.61、CAN 2.74→2.72、串口 4.78 不变）
  ⇒ 轴数/幅度/持续时间对流模式 RTT 无影响，进一步证实"ACK 与插补解耦"。
- ⚠ **短测的 `max` 不能当最坏情况用**：网口短测 max 3.68 ms，长跑真实 max **117.66 ms**；
  CAN 短测 max 5 ms，长跑 **179.94 ms**。**这就是"要测 10 分钟"的真正理由。**

## 7. ⭐ 让机械臂「一直在动」的同时测 RTT（`--motion`）

> 2026-09-22 用户提问新增：**要的是臂持续运动时收到的响应时间**。

**为什么这个数才是关键。** 臂静止时测出的 RTT 只有「链路 + 协议解析」的开销；
真实遥操作时，固件主循环同时在跑 S 曲线插补 / 流模式直写 + 舵机总线同步写，
控制类命令的 RTT 会明显变差。**决定能不能上 50Hz 流模式的，是运动中的那些数。**

### 7.1 一条命令

```powershell
# 臂持续摆动 J5 ±5°，同时测 move_joints 的 RTT（先烧好 net 固件）
py -3 tools/link_latency_bench.py --link serial,net --cmd move_joints --motion `
    --allow-move --n 300 --csv

# CAN 轮同理（先烧 can 固件）
py -3 tools/link_latency_bench.py --link serial,can --cmd move_joints --motion --allow-move --n 300
```

### 7.2 摆动是怎么设计的（为什么安全）

| 设计 | 说明 |
|---|---|
| **围绕起始位姿摆动** | 脚本先读一次当前位姿 `base`，之后每帧目标 = `base` 在**摆动轴**上正弦摆动 |
| **有界** | 永远不超出 `base ± amp` ⇒ **不可能**跑出去撞桌面/基座 |
| **连续** | 正弦连续变化 ⇒ 臂一直在动，不是走走停停 |
| **多轴（可逗号多选）** | `--motion-axis 5,6` 可多轴同时摆；默认 `5` |
| **默认 J5 最安全** | J5 只改夹爪朝向、**不改变末端 XYZ** ⇒ 风险最低 |
| **绝不拿 Z 摆动** | Z 是唯一能把末端砸向桌面的方向（这条和 RC 那边的排序原则一致） |
| **⭐ 摆幅被真实限位自动夹** | 用 `L` 实测的限位表把摆幅夹到区间内侧 5° ⇒ **撞不到限位** |
| **⭐ 启动包络（0→1 一个周期）** | 保证 `t=0` 时目标 = base，否则第一帧就吃固件的跳变门限（见 §7.6） |
| **结束自动回位** | 测完自动 `MOVE_JOINTS` 送回起始位姿（`--no-motion-restore` 可关） |

幅度**硬上限 90°**（`--motion-amp` 超过直接被拒，不给"先跑跑看"的机会）；
超过 15° 会按【大跨度】多打一遍安全提示；选 J2/J3 会额外警告（会明显改变末端位置与高度）。

### 7.3 ⭐⭐ 流模式运动前的「回读自检」（不许跳过）

`--cmd stream_joints --motion` 在开跑前会先做一次**探针 + 回读**：
把目标只挪 `3°`、连发 4 帧、等 0.6 s，再读回实际位姿，判定

| 判据 | 不通过意味着 |
|---|---|
| 摆动轴**真的动了**（≥1°） | 流帧没写到舵机 —— 查 `Stream reject`（跳变/姿态被拒）或 `sf 0` 关了跟随 |
| **其它轴被动 < 6°** | 量纲换算错，或**红线 68**（`JOINT_MIN_RAW/MAX_RAW` 未装载 ⇒ 六轴被推向 raw 0） |

任一条不通过 ⇒ **脚本一帧摆动都不发就中止**，并打印下一步该查什么。
这是红线 67 家族的「回读守卫」：绝不做"我发的是对的"这种假设。

### 7.4 ⚠⚠ 量纲：`stream_joints` 与其它命令**不是同一套角度**

| 命令 | 量纲 |
|---|---|
| `GET_STATUS`(0x82) / `FK_QUERY`(0xA1) / `MOVE_JOINTS`(0x10) | **舵机度 0~360** |
| `STREAM_JOINTS`(0x13) | **逻辑角 (-180,180]** |

```
舵机度 = (SERVO_OFFSET[j] + JOINT_DIR[j] × 逻辑角) mod 360
JOINT_DIR    = {-1,+1,+1,+1,+1,+1}
SERVO_OFFSET = {180×6} 出厂默认，**但会被 Home 校零改写**
```

**2026-09-22 修正的一个真 bug**：脚本原先把 `GET_STATUS` 的角度**直接**喂给
`STREAM_JOINTS`，厂值下 J2~J6 会整体偏 180° —— 臂会甩一大下，而不是"原地不动"。
现已按上式换算。**若你的臂做过 Home 校零（`zi` / 零点标定），必须传真实值：**

```powershell
--stream-offset 180,180,180,180,180,180    # 换成固件里 `zi` 打印的 SERVO_OFFSET
```

### 7.5 静止 vs 运动要对比，就各跑一轮

```powershell
# 静止轮（默认）
py -3 tools/link_latency_bench.py --link serial,net --cmd move_joints --allow-move --n 300
# 运动轮
py -3 tools/link_latency_bench.py --link serial,net --cmd move_joints --motion --allow-move --n 300

# 只看运动轮的
py -3 tools/link_latency_bench.py --report --cmd move_joints --report-scenario motion
```

结果的 JSON 文件名和表格都带 **场景** 列（`static` / `motion-J5-5deg-T2s`），
不会互相覆盖而误读；`--report` 混到多场景时会**主动告警**。

### 7.6 ⭐⭐ 长时间 + 大跨度 + 循环往复（`--duration`）

> 2026-09-22 新增：用户要求 **摆幅要大、要循环往复、至少测 10 分钟**才认对比结果。
> 十几秒的小幅测试样本量不够（p99 站不住），也测不出**跑久了的漂移**。

```powershell
# 单链路 10 分钟：J5 ±90° + J6 ±30°，周期 10s，每 60s 一桶
py -3 tools/link_latency_bench.py --link can --cmd stream_joints --motion --allow-move `
    --duration 600 --bucket 60 --motion-axis 5,6 --motion-amp 90,30 --motion-period 10
```

| 参数 | 作用 |
|---|---|
| `--duration 600` | 跑满 600 秒。给了它就**按时长结束**，`--n` 只当安全上限 |
| `--bucket 60` | 每 60 秒切一桶 ⇒ 出一张**稳定性表**，看「有没有越跑越差」 |
| `--motion-axis 5,6` | 多轴同时摆（各轴相位错开 90°，但起步都从 base 出发） |
| `--motion-amp 90,30` | 每个轴各给一个幅度；**会被真实限位再夹一次** |
| `--joint-limits` | 换臂/重新标定过就传真实限位，例如 `12-351,138-266` |

跑完会多两张东西：

```
  ⏱ CAN PCAN_USBBUS1@500k 长时间稳定性（每桶 60 秒）
  桶(分钟)     样本     min     p50     p90     p99     max
  0.0~1.0     19329   2.52    2.77    3.03    8.76   48.28
  1.0~2.0     20307   2.50    2.73    3.02    6.93   78.13
  ...
  9.0~10.0    21026   2.50    2.70    2.88    4.72   80.99
  ⚠ 忽略 1 个「残桶」(样本数 < 正常桶的一半)：10~11min(n=1)
  首桶→末桶(不计残桶): p50 2.77 → 2.70 ms (-3%)   p99 8.76 → 4.72 ms (-46%)
  全程 p50 波动范围: 2.69 ~ 2.77 ms (极差 0.08 ms)；p99 最大 8.76 ms
  ✓ 全程稳定（末桶 p50 未超首桶 1.3 倍）
```

末桶 p50 比首桶高 30%+ 会**主动告警**（热漂移 / 总线退化嫌疑）。

#### ⚠⚠ 残桶：不剔除会得出**方向都反了**的结论

时长不整除分桶粒度时（600 s 被 601 s 的末尾样本挤出第 11 个桶），**末桶可能只有 1 个样本**。
本工具早期版本就因此打印过：

```
  首桶→末桶: p50 2.77 → 2.78 ms (+0%)   p99 8.76 → 2.78 ms (-68%)   ← ⚠ 假的
```

p99 "降了 68%" 完全是那一个样本造成的。现在脚本会**自动剔除**（判据：桶内样本 < 中位数一半），
显式标注 `(+1残)`，并以「**极差**」为主指标 —— 极差比"首末差"稳健得多。

> ⭐ 这也是"要测 10 分钟"的真正理由：**长跑是用来暴露稀有事件的，不是用来攒样本的**。
> 10 分钟汇总成一个 p50，恰好把要查的东西抹掉；长跑同时暴露了
> ① 无热漂移（温度确实升了 3~5℃ 但 p50 不动）② CAN 每分钟约 1 次 40~180 ms 尖峰
> —— 后者用 150 样本的短测**根本看不见**（短测里 CAN max 只有 5 ms）。

**⭐ 运行中位姿巡检**：每个桶边界读一次实际位姿，核对
「摆动轴还在 `base±amp` 内、其它轴没被拖走」。越界会**立即中止并回位**；
单轴读失败只算警告（本机舵机总线有约 5%/20% 的**逐字段瞬时丢读**，不该让它废掉 10 分钟）。
⇒ 反过来，**跑之前必须先回中位**：复位/掉电会让臂下沉贴限位（实测 J2→76.3、J3→270.9），
而脚本是**按实测姿态算限位余量**的 ⇒ 带着下沉姿态跑，摆幅会被夹成 0，那一轮数据作废。

**⚠⚠ 大跨度必须知道的一条固件门限**：固件对每个流帧检查
「单轴变化 > `STREAM_MAX_JUMP_DEG`(25°, 逻辑角) ⇒ 拒帧 `err=4`」，
而且**被拒时 `stream_prev` 不更新** ⇒ 一帧超限会**连锁拒绝**。

⇒ 所以静止状态下第一帧目标**必须等于当前位姿**。脚本用「启动包络」保证这点：
早期版本给每轴加 90° 相位偏移，`t=0` 时 J6 直接 = `base+30°` ⇒ 实测 **11.4% 的帧被拒**。
修好后 `坏响应 = 0`。跑完脚本还会打印：

```
  相邻帧目标最大变化 ≈ 0.13°（实测帧间隔 2.9ms；固件单帧门限 25°）
```

超过门限的一半就会警告「目标是跳变而不是跟随」。

### 7.7 ⭐ NACK 不要只看"被拒"，要解出 `err`

NACK(0x7E) 的负载是 `{orig_cmd, err}`（`arm_control_protocol.h:72`）。脚本会自动统计：

| err | 含义 | 该查什么 |
|---|---|---|
| 1 | PARAM 参数非法 | 负载长度/范围/轴号 |
| 2 | **CRC 错** | **传输层丢字节** ⇒ 查线、终端电阻、干扰，不是姿态问题 |
| 4 | **LIMIT 超限位/桌面/立柱/单帧跳变** | 摆幅撞限位，或**起步跳变**（见 §7.6） |
| 5 | ESTOP 急停激活 | 松开急停（不自锁） |
| 7 | READ 舵机总线读失败 | 舵机线/供电 |

跑完会打一张「被拒原因直方图」。**只有把 err 解出来，才可能知道下一步查什么。**

### 7.8 ⭐⭐ 让**六个轴一起动**：先回中位，再按包线取幅度

> 2026-09-22 用户提问：「为什么只有 5 和 6 轴在动，其他轴不也要一起动吗？」

**为什么默认只用 J5/J6**：J5（腕自转）与 J6（夹爪）是**唯二不改变末端 XYZ 位置**的轴。
让臂"一直在动"却不改变末端位置 ⇒ 不可能把末端扫到桌面/基座上，是最安全的做法。

**但真正卡住 J1~J4 的往往是"没有余量"**。实测：烧固件掉电丢力矩后臂下沉停在
`J2 = 76.7°`（限位 75~284，距下限 **1.7°**）、`J3 = 270.9°`（限位 76~271，距上限 **0.1°**）
⇒ 按"离限位留 5°"算，可动余量是 **−3.3° / −5°**，摆幅被夹成 **0**。
**所以要让其他轴动，必须先把臂抬回中位。**

#### ⚠⚠ 回中位不要用 `M a`

| 命令 | 实际语义 | 能不能用 |
|---|---|---|
| **`M a`** / `M 1` | `cmdCenterCalib()` —— **"set current pose as servo middle (2048)"**，即**把当前姿态标定成中点**（改零点/`SERVO_OFFSET`） | ❌ **绝对不要** |
| **`m 180 180 180 180 180 180 15`** | 普通六关节运动命令，15°/s 走到 180° | ✅ 用这个 |

`M a` 会把零点改掉 ⇒ 流模式的量纲基准（`SERVO_OFFSET`）随之失效，
后面所有"目标=当前角"的计算全错位。**这是本工程最容易误用的一条命令。**

```powershell
# 回中位（先确认上方有净空、周围无人）——控制台命令，走 COM11
m 180 180 180 180 180 180 15
# 固件会回显 From / To / POST-CLAMP，并用 S 曲线走完
```

#### ⭐ 可用包线是量出来的，不是猜的

固件流模式有**三道**校验（`main.c` 的流处理段）：

| 校验 | 行为 |
|---|---|
| ① 限位钳位 | 不拒帧，只把目标夹到限位内（`lk` 能看到 `clamp(limit)` 计数） |
| ② 单帧跳变 > `STREAM_MAX_JUMP_DEG`(25°) | **拒帧 err=4**，且 `stream_prev` **不更新** ⇒ 会**连锁** |
| ③ `stream_pose_ok()`：**桌面 z + 立柱圆柱** | **拒帧 err=4**，日志打 `Stream reject: pose unsafe` |

实测 `±50°` 六轴全动 ⇒ **约 15% 的帧被拒**，固件日志里
`pose unsafe` 与 `J1/J2 jump 33~47 deg (>25)` 同时出现 —— 前者是**安全功能在正常工作**
（末端真的扫进了禁区），后者是它的**次生连锁**。

| 幅度方案 | 结果 |
|---|---|
| J1~J6 各 ±50°，周期 12s | ❌ 约 15% 帧被拒（`pose unsafe` + 连锁跳变） |
| **J1~J4 ±20°、J5 ±70°、J6 ±33°，周期 12s** | ✅ **0 拒帧、0 超时**，10690 样本 p50 2.69ms |

⇒ **能用的"六轴全动"包线（中位姿态、周期 12s）**：
`J1 ±20 / J2 ±20 / J3 ±20 / J4 ±20 / J5 ±70 / J6 ±33`

```powershell
# 六轴全动 + 零拒帧的长跑（板子已在中位、固件为 can/net 对应版本）
py -3 tools/link_latency_bench.py --link can --cmd stream_joints --motion --allow-move `
    --duration 600 --bucket 60 --motion-axis 1,2,3,4,5,6 --motion-amp 20,20,20,20,70,33 --motion-period 12
```

⭐ **怎么确认"拒帧原因"**：`--link can` / `--link net` 时 **COM11 是空闲的**，
可以一边跑一边用串口助手读固件日志，直接看到 `Stream reject: ...` 那一行的原文
（脚本自己的直方图只给 err 码，日志给的是"哪一轴、差多少度、还是 pose"）。
**两条证据一起看，才能分清"不该拒的 bug"和"该拒的安全保护"。**

## 8. 常见故障与处置

| 现象 | 原因 | 处置 |
|---|---|---|
| 某链路 **0 样本** | net/can 同测 = 硬件互斥 | 分两轮烧固件 |
| 全是超时 | 固件没烧对 / 网线没插 / CAN 卡没上电 | 先 `ping`、先敲 `h` 看 `fw-tag` |
| `串口打开失败` | 端口被串口助手占用，或 COM 号变了 | 关掉终端窗口，重列口 |
| `坏包 > 0` | 控制台文本和二进制帧混流 | 加 `--quiet-log` 静音固件日志 |
| CAN 轮横幅**没有** `rc-tim4-capture` | 烧的是 09-18 老包 | 重烧（见 §1.1），否则两轮不同代次 |
| 两轮串口 `p50` 差很多 | 两份固件不同代 ⇒ 对比无效 | 别下结论，先回去核对代次 |
| CAN 打不开 | `pcan` 后端需要 PCAN-Basic 驱动 | 装驱动，或换 `--can-interface usbcan` |
| `次/秒` 明显偏低但 p50 很小 | 分母口径错（已在 v1 修掉） | 本轮自检有交叉检查，报异常就别信这张表 |
| `--report` 说没有 json | `--cmd` 不一致，或没跑过测试 | 两轮都用同一个 `--cmd` |
| `--motion` 报「只对 move/stream 有意义」 | 配了 `--cmd status` 之类 | 查询类命令测不出"运动中的开销"，用 `move_joints` |
| **流模式自检：摆动轴没动** | 流帧被拒 / `sf 0` 关了跟随 / 未进流模式 | 看固件日志有没有 `Stream reject`；确认 `sf 1` |
| **坏响应 > 0 且全是 0x7E** | 被拒，但原因要解 `err` | 看「被拒原因直方图」：err=4 见 §7.6；err=2 是链路丢字节 |
| 大跨度第一秒就大量 err=4 | **起步跳变**超 25° | 已由启动包络修掉；若自建工具要自己保证首帧 = 当前位姿 |
| `--duration` 跑完样本很少 | `--n` 太小把长跑截断了 | 给了 `--duration` 就会自动把 `--n` 抬到安全上限，别手动传小 `--n` |
| **流模式自检：其它轴被动 > 6°** | `SERVO_OFFSET` 不是 180（Home 校零改过），或红线 68（RAW 限位未装载） | 先用 `--stream-offset` 传真实值；再查启动横幅有没有 `Work ranges applied (6 jnt)` |
| 表里出现两个「场景」且混在一起 | 静止轮 + 运动轮都跑了 | 看「场景」列区分，或 `--report-scenario motion` 过滤 |
| **`--report` 里有多组运动场景，看着乱** | 多轮（不同摆幅/周期）都合并进来了 | 现在会提示「同一类场景，可横向比」；要严格比链路请用**同一轮**的两条链路 |
| **分桶表末行样本数是 1** | **残桶**（时长不整除分桶粒度） | 已被自动剔除并标注 `(+1残)`；**别拿它算趋势**（会把结论方向弄反，见 §7.6） |
| **某链路 p50 很小但 max 很大** | 不是链路带宽问题，是**上位机 I/O 路径**抖动 | 先算理论下限（CAN 500k 一帧 ≈0.25ms）；实测 180ms ⇒ 查 USB-CAN 适配器/Windows 调度，别换线 |
| 某链路 `超时` 是个位数但非 0 | 长跑里的稀有尖峰 | 看分桶表的 `max` 列是哪个桶；对照 p99 是否被拉高 |

## 9. 结果怎么用

这张表直接决定 R1 之后 RC 流模式的**下发频率**：

| 结论 | 动作 |
|---|---|
| 网口/CAN 的 `次/秒` ≥ 50 且 p99 < 20ms | **可以上 50Hz 流模式**（`0x13`） |
| 只有 10~20Hz | 流模式降频，或退回"分段下发 + `Trajectory_IsActive()` 才发下一段" |
| 串口 p99 很大 | 串口只做**调试/取证**，绝不做实时控制通路 |

⭐ **上表要用「运动轮」（`--motion`）的数来判，不要用静止轮的。** 静止轮的 p99 好看得多，
但它不代表遥操作时的体验 —— 固件只在臂真的在动时才会去做插补/直写/总线同步写。

### 9.1 ⚠⚠ 频率够 ≠ 体验好：一定要看 `max`

10 分钟长跑（§5.5.1 / 报告 §7）实测的对照：

| | p50 | p99 | max | std | 50Hz 下最坏掉几个周期 |
|---|---|---|---|---|---|
| 网口 | **1.61** | **3.40** | 117.66 | 0.82 | 5 |
| CAN | 2.72 | 6.60 | **179.94** | 1.48 | **9** |
| 串口 | 4.78 | 6.32 | **15.26** | **0.56** | **0** |

⇒ **排序会反转**：按 `p50`/`p99` 是 **网口 > CAN > 串口**；
按 `max`/`std` 是 **串口 > 网口 > CAN**。**只报 p50 会误导选型。**

⭐ **三条链路的尖峰都指向"上位机调度时片"，与链路波特率无关**：
- 理论下限：CAN 500 kbit/s 下一帧 8 B 仅约 **0.25 ms**、网口更快 ⇒ 实测 117/180 ms 大了 **2~3 个数量级**
  ⇒ **不可能是链路造成的**。
- 量级对照（Windows 默认时片 ≈ **15.6 ms**）：串口 15.26 ≈ **1 个时片**、网口 117.66 ≈ 7.5 个、CAN 179.94 ≈ 11.5 个。
  ⇒ 尾部延迟的瓶颈是**上位机（Windows + 非实时线程 + USB 适配器）**，不是链路本身。
- ⇒ **想真正改善尾部：换 Linux / 提高 Windows 定时器精度 / 给通信线程高优先级**，
  而不是换链路。工具是跨平台的，换到 Linux 侧重跑同样两轮即可验证。

⇒ 流模式上线后建议加一条**上位机侧看门狗**：连续 N 个周期没收到 ACK 时，
要么保持上一帧目标（等价于"冻结"），要么送到位安全位 —— **不要**因为一个尖峰就发"急停"。

> ⚠ 别忘了：`nt` 会运行期重配 TIM3/4/5 并可能掐掉网口，**测完要 RESET**。
