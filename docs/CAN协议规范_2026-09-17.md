# CAN 协议规范 — 六轴机械臂（从站）

> 版本 v1.0 · 2026-09-17 · 固件 `outputs/can_api/01_master_CANslave.bin` / `02_slave_CANslave.bin`
> 适用：上位机（PC + USBCAN 卡 / 工控机 / 另一块 MCU）通过 **CAN 总线**调用机械臂全部控制接口。
> 本文件是**给实现对面那一端的人看的**，不需要读 C 源码即可完成对接。

---

## 0. 一句话架构

机械臂扮演 **CAN 从站**，把原本走串口的二进制协议原样搬到了 CAN 上：

```
上位机 ── 0x100+node ──► 机械臂   拆包重组 → 执行 ArmApi_* → 回应答
上位机 ◄─ 0x180+node ─── 机械臂   应答(ACK/NACK/数据)
上位机 ◄─ 0x280+node ─── 机械臂   周期状态帧 / 异步事件帧(主动上报)
```

**协议核心与串口完全一致**（同一套 `SEQ/CMD/LEN/PAYLOAD/CRC16`、同一批命令码、同一套错误码）。
所以：串口 SDK 的编码/解码代码**可以直接复用**，只需把"字节流"换成"8 字节 CAN 帧的分包/重组"这一层。

## 1. 物理层与链路层

| 项目 | 值 | 说明 |
|---|---|---|
| 控制器 | STM32F407 bxCAN1 | 标准帧 CAN 2.0A，**11 位 ID** |
| 引脚 | **PB8 = CAN1_RX，PB9 = CAN1_TX** | 与 `.ioc` 一致。另有 PA11/PA12 备选（需重编译 `make CANPIN=pa`） |
| 波特率 | **500 kbit/s（默认）** | 可用 `can baud` 改：100 / 125 / 250 / 500 / 1000 kbit/s |
| 采样点 | 固定 85.7%（14 TQ：BS1=11, BS2=2） | 改波特率只改预分频，**采样点不变** |
| 收发器 | 3.3V CAN 收发器（丝印 `CAN PHY V1`） | 模块 `TX→PB9`、`RX→PB8`，**直连不交叉** |
| 总线 | `CANH↔CANH`、`CANL↔CANL`，**两端各 120 Ω，必须共地** | 少共地是现场最常见的"偶发错误帧"原因 |
| 帧类型 | 只处理**数据帧**（`RTR=0`），**标准帧**（`IDE=0`） | 扩展帧 / 远程帧被硬件过滤丢弃 |

**接收过滤器**（机械臂侧只认这 4 个 ID 段，其它 ID 一律硬件层丢弃）：

| 段 | ID 范围 | 方向 |
|---|---|---|
| 命令 | `0x100 ~ 0x10F` | 上位机 → 机械臂 |
| 响应 | `0x180 ~ 0x18F` | 机械臂 → 上位机 |
| 状态/事件 | `0x280 ~ 0x28F` | 机械臂 → 上位机 |
| 链路自检 | `0x7E0 ~ 0x7EF` | 双向（`ct` 命令用，与协议无关） |

> ⚠ **ID 段带 node**：`0x100+node`。默认 `node=1`，所以默认收发 ID 是 `0x101 / 0x181 / 0x281`。
> 现场改过 `can node N` 的话，两边都要跟着换。

## 2. 分包格式（**对接的核心，务必逐字节读**）

### 2.1 逻辑流定义

一条"逻辑帧"= 串口上的一整帧，去掉帧头 `0xAA 0x55`：

```
逻辑流 = [SEQ][CMD][LEN][PAYLOAD × LEN][CRC_lo][CRC_hi]
          ↑ 3 字节固定头              ↑ LEN 字节     ↑ CRC-16/CCITT-FALSE
```

- **CRC 计算范围**：`SEQ..PAYLOAD`（即不含帧头、不含 CRC 自身）
- 算法：CRC-16/CCITT-FALSE，多项式 `0x1021`，初值 `0xFFFF`，**非反射**
- 所有多字节整数：**小端**

### 2.2 切成 CAN 帧

| 帧 | d[0] | d[1] | d[2] | d[3] | d[4..7] |
|---|---|---|---|---|---|
| **首帧** | 总帧数 \| 0x80 | SEQ | CMD | LEN | 逻辑流第 4~7 字节（= `PAYLOAD[0..3]`，不足时接着放 CRC） |
| **续帧** | 帧序号 1..14 | — | — | — | 逻辑流后续 7 字节（`d[1..7]`） |

公式：

```
tail_total = LEN + 2                        # PAYLOAD + CRC
first_n    = min(tail_total, 4)             # 首帧在 d[4..7] 里装几字节
rest       = max(tail_total - 4, 0)
总帧数     = 1 + (rest + 6) / 7             # 整除
```

**要点**：
1. **DLC 不补齐到 8**。首帧 DLC = `4 + first_n`，续帧 DLC = `1 + n`。解析时必须用 DLC，不能假设恒为 8。
2. **没有帧间握手**。一整包由发送方连续发完，中间不插别的帧 —— 所以状态帧/事件帧不会嵌进分包中间。
3. 续帧序号必须**连续且不重复**，**但到达顺序不保证** —— 见下方 ⚠。
   丢帧、或者等了 200 ms 还没收齐 ⇒ 整包丢弃，重新等首帧。
4. 重组超时 200 ms（机械臂侧）；上位机侧建议同量级。

> ⚠⚠ **上位机重组器必须"按帧号定偏移 + 位图收齐"，不许要求"严格递增到达"**
>
> 这是最容易写错、且症状最容易被误判成"硬件/固件坏了"的一条。
>
> - **原因**：STM32 bxCAN 有 **3 个发送邮箱**并行发送，**第 4 帧会抢先于第 2/3 帧上线**。
>   实测 4 帧回包在总线上的实际到达顺序是 **`F1, F4, F2, F3`**。
> - **招牌症状**：**"1 帧的 `PING` 能通，4 帧的 `GET_STATUS` 永远超时"**。
>   看到这个组合，**先怀疑重组器，别怀疑硬件**（它同时也排除了接线/波特率/过滤器问题 ——
>   1 帧能通说明物理层和 ID 全对）。
> - **固件侧已处理**：`0918F` 起发送侧每帧之间等邮箱排空（`ArmCanDrv_TxDrain`），
>   实测 `--order-verify 25` 25/25 按序到达、乱序 0。
> - **但上位机不要依赖这一点**：按帧号定偏移 + 位图收齐，是**唯一在两种固件下都正确**的写法，
>   而且天然容忍丢帧重传与重复帧（重复帧号只收一次）。
> - **泛化**：任何"发送端有 N 个并行缓冲"的传输（CAN 邮箱、DMA 通道、多队列网卡），
>   "按发送顺序到达"这个假设都作废。**协议里必须只承诺"帧号可乱序到达，收齐即可"。**
> - 自测：`tools/can_host.py --order-verify 25`（**严格按序**视角，等同客户自己写的上位机）。
>   ⚠ 默认的 `--smoke` 用的是**容忍乱序**的重组器 ⇒ **它证明不了这一条**。

### 2.3 逐字节示例

**① `PING`（0x01，LEN=0）→ 1 帧**

```
发送: 0x101  DLC=6  [81][SEQ][01][00][CRC_lo][CRC_hi]
       d[0]=0x80|1=0x81          d[2]=CMD=0x01  d[3]=LEN=0
存放次序: d[4..7] 装 tail_total=2 字节 → PAYLOAD(0 字节) + CRC(2 字节) = CRC
```
响应 `0x181` DLC=8：`[81][SEQ][81][02][proto_ver][run_id][CRC_lo][CRC_hi]`

**② `GET_STATUS`（0x02，LEN=0）→ 1 帧请求**

```
0x101  DLC=6  [81][SEQ][02][00][CRC_lo][CRC_hi]
```
响应 `0x82` LEN=21 → `tail_total=23`，`rest=19`，总帧数 `1+(19+6)/7 = 4`：

```
0x181  DLC=8  [84][SEQ][82][15][p0 p1 p2 p3]
0x181  DLC=8  [01][p4..p10]
0x181  DLC=8  [02][p11..p17]
0x181  DLC=6  [03][p18 p19 p20 CRC_lo CRC_hi]
```
（`0x15 = 21`）

**③ `MOVE_JOINTS`（0x10，LEN=16）→ 3 帧**

```
tail_total = 18, rest = 14, 总帧数 = 1 + 20/7 = 3

0x101  DLC=8   [83][SEQ][10][10][deg0_lo deg0_hi deg1_lo deg1_hi]
0x101  DLC=8   [01][deg2_lo .. deg3_hi]                  # 7 字节
0x101  DLC=8   [02][deg4_lo deg4_hi deg5_lo deg5_hi CRC_lo CRC_hi 0xFF]
```
响应是 ACK：`0x181 DLC=8 [81][SEQ][7F][02][10][00][CRC_lo][CRC_hi]`

## 3. 命令码总表

> 角度一律 **舵机度（0~300）**；位置 mm；速度 deg/s；加速度 deg/s²。
> ⚠ `MOVE_JOINTS` 用的是**舵机度**，而 `STREAM_JOINTS` 用的是**逻辑关节角（相对本臂 Home）** —— 两者不通用，见 §3.2。

### 3.1 请求 → 响应

| CMD | 名称 | 请求负载 | 响应 | 说明 |
|---|---|---|---|---|
| `0x01` | PING | 无 | `0x81`: `u8 proto_ver, u8 run_id` | 探活；`run_id` 每次上电变，可判"臂是否重启过" |
| `0x02` | GET_STATUS | 无 | `0x82`: 21 字节（见下） | **会读 6 轴舵机总线**，是重操作，别高频调 |
| `0x03` | LOG_SET_LEVEL | `u8 level(0~3)` | ACK | 运行日志等级 |
| `0x10` | MOVE_JOINTS | `6×i16 角度×10, u16 v×10, u16 a×10` = 16B | ACK | 七段 S 曲线；返回 OK 只代表**运动已启动** |
| `0x11` | STOP | 无 | ACK | 立即停轨迹 |
| `0x12` | SET_TORQUE | `u8 joint(0~5, 0xFF=全部), u8 en` | ACK | |
| `0x13` | STREAM_JOINTS | `6×i16 逻辑角×10` = 12B | ACK | 主从直写；**建议 20~50 Hz**，500 ms 无调用自动退出 |
| `0x20` | MOVE_CART | `i16 x,y,z, i16 pitch, u16 v, u16 a` = 12B | ACK | IK-CCD + FK 回代验证后执行 |
| `0x21` | FK_QUERY | 无 | `0xA1`: 21 字节 | 与 `0x82` 布局不同，见下 |
| `0x30` | SET_GRAVITY | `i16 K×1000 (deg/mm)` | ACK | J2 重力前馈增益 |
| `0x31` | SET_CORRECTION | `u8 en, u16 thr×100(0.01°), u8 rounds` | ACK | 自适应修正 |
| `0x40` | PARAM_READ | `u8 id` | `0xC0`: `u8 id, i32 val×1000` | 参数表，见 `LP` / SDK 03 |
| `0x41` | PARAM_WRITE | `u8 id, i32 val×1000` | ACK | |
| `0x42` | PARAM_COUNT | 无 | `0xC2`: `u8 count` | |

**响应码**：`0x7F` = ACK，`0x7E` = NACK。两者负载都是 `u8 orig_cmd, u8 err`。
**数据类响应**：`CMD | 0x80`（`0x01→0x81`、`0x02→0x82`、`0x21→0xA1`、`0x40→0xC0`）。

### 3.2 ⚠ 量纲陷阱（**上位机最容易搞错的地方**）

| | `0x10` MOVE_JOINTS | `0x13` STREAM_JOINTS |
|---|---|---|
| 角度含义 | **舵机度**（0~300，绝对量） | **逻辑关节角**（相对本臂 Home，可为负） |
| 用途 | 单次规划运动 | 主从实时跟随（主臂角度直灌从臂） |
| 编码 | `i16 ×10` | `i16 ×10` |

同一个数值在两条命令里代表**不同的物理角度**。遥操作必须用 `0x13`（两端零点各自校准，只有逻辑角能对齐）。

### 3.3 响应负载布局

**`0x82` GET_STATUS（21 字节）**

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0..11 | 6×i16 | 六关节实际角度 ×10（舵机度）；`-32768` = 该轴读失败 |
| 12 | i16 | X (mm ×10) |
| 14 | i16 | Y (mm ×10) |
| 16 | i16 | Z (mm ×10) |
| 18 | i16 | pitch (deg ×10) |
| 20 | u8 | 位图：bit0 E-Stop / bit1 轨迹中 / bit2 修正中 / bit3 读取成功 |

**`0xA1` FK_QUERY（21 字节）**

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | i16 | X (mm ×10) |
| 2 | i16 | Y (mm ×10) |
| 4 | i16 | Z (mm ×10) |
| 6 | i16 | pitch (deg ×10) |
| 8..19 | 6×i16 | 六关节角 ×10 |
| 20 | u8 | read_ok |

### 3.4 错误码（ACK/NACK 的 `err` 字节）

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | `ARM_API_OK` | 成功 |
| 1 | `ERR_PARAM` | 参数非法（长度/范围/ID） |
| 2 | `ERR_CRC` | 帧 CRC 校验失败 |
| 3 | `ERR_UNREACH` | IK-CCD 不可达 / 不收敛 |
| 4 | `ERR_LIMIT` | 解算结果超关节限位（或被安全层拒绝） |
| 5 | `ERR_ESTOP` | E-Stop 激活，禁止运动 |
| 6 | `ERR_FK_VERIFY` | IK 解 FK 回代验证超差 |
| 7 | `ERR_READ` | 舵机总线读取失败 |

## 4. 状态帧与事件帧（`0x280+node`）

**8 字节定长，不分包，不参与重组**。`d[0]` 区分类型。

### 4.1 周期状态帧（`d[0] = 0x53` 'S'）

默认 **1000 ms** 发一次（`can hb <ms>` 改，0=关）。

| 字节 | 含义 |
|---|---|
| 0 | `0x53` 固定标识 |
| 1 | node_id |
| 2 | **flags 位图**：bit0 E-Stop / bit1 轨迹中 / bit2 流模式 / bit3 修正中 / bit4 示教录制 / bit5 示教回放 / bit6 CAN hw ok / bit7 协议就绪 |
| 3 | **最近一次命令的返回码**（`ARM_API_ERR_*`，0=OK） |
| 4..5 | 已执行命令计数低 16 位（看它是否在推进） |
| 6..7 | 运行秒数低 16 位（约 18 h 回绕） |

**用途**：主机一眼看清臂在干什么、有没有 E-Stop、上一条命令到底成没成 —— **不必轮询 `GET_STATUS`**。

### 4.1.1 ⚠ 状态帧什么时候**不发**（三条抑制条件，必须知道）

机械臂**不会向空气发帧**。下面三种情况状态帧会暂停，主机不要误判成"臂死了"：

| 条件 | 现象 | 为什么这么设计 |
|---|---|---|
| **从未收到过任何发往本节点的帧** | 上电后一直收不到状态帧 | CAN 每发一帧若无人 ACK，发送错误计数 **TEC +8**（本机 `AutoRetransmission=DISABLE`，发一次就放弃）。1 Hz 下发 16 s 就到 **128 = error-passive** ⇒ 台子上没插 CAN 线时会每秒自伤一次。**只要主机 PING 一次，状态帧立刻开始**（且会补发一帧，不用再等一个周期） |
| **TEC ≥ 128（已 error-passive）** | 状态帧**降为每 5 s 一帧"探路"**（`can` / `cn` 会提示） | ⚠ 见下方专门说明 |
| `can hb 0` | 一直不发 | 人为关闭 |

#### ⚠ 关于 `TEC ≥ 128` 的确切行为（**≤0918F 与 ≥0918G 不同，务必看清**）

- **为什么不能永久停发**：TEC 只能靠"**发送成功**"递减（每成功一帧 −1）。一旦永久停发，
  就永远赚不到那次递减 ⇒ **永久自锁**，对端回来了也醒不过来，只能人工复位。
- **`0918G` 起的行为**：闸门改成"**每 5 s 放一帧探路**"。
  - 有对端 ⇒ 那一帧被 ACK ⇒ TEC 逐格回落（**每帧 −1**）⇒ 自动恢复 1 Hz。
  - 无对端 ⇒ TEC 停在 128~135 不动（**实测：error-passive 下 ACK 错误不增 TEC，所以永远不会
    涨到 256 触发 bus-off 自恢复**）⇒ 保持 5 s 一帧，总线负载可忽略。
  - 恢复延迟 ≈ **`(TEC − 127) × 5 s`**，最坏约 35 s。判据是"**探路帧一定会到**"，不是"立刻回到 1 Hz"。
  - **收到任何发往本节点的帧（含 PING）⇒ 立即解除**暂停，不用等定时器。
- **`≤0918F` 的行为**：`if (tec >= 128) return;` 是**永久**闸门 ⇒ 一旦进入就再也发不出来。
  症状极具误导性：臂侧 `can` 说"已探测到对端, 状态帧正常发送"、状态帧计数也停在某个数，
  而主机**一帧都收不到**。**上位机侧特别容易误判成"臂死了"或"链路坏了"。**
- ⭐ **上位机自查口诀**：读臂侧 `cn` 的 `tec`。`tec ≥ 128` ⇒ 就是这条，**不是链路问题**。
  ⚠ 最常见的触发者就是**上位机自己**：你的程序正常退出 ⇒ CAN 适配器关闭 ⇒ 总线上没人 ACK ⇒
  臂 16 s 后自我闸停。**这不是故障，是设计使然**；按上面描述 ≥0918G 会在对端回来后自愈。
- ⚠ **命令帧（`0x100+node`）不受此闸门限制**，任何时候都能被应答 ⇒ **主机侧不需要做任何特殊处理**。

现场排查："为什么收不到状态帧？" → **先在臂侧敲 `can`**，它会直接告诉你
`⚠ 状态帧停发中: 还没收到过任何发往本节点的帧(0x101)` 还是 `(已探测到对端, 状态帧正常发送)`。
`cn` 命令可看 `tec/rec/lec` 原始错误计数。

### 4.2 异步事件帧（`d[0] = 0x45` 'E'）

| 字节 | 含义 |
|---|---|
| 0 | `0x45` 固定标识 |
| 1 | node_id |
| 2 | 事件码 |
| 3 | 事件参数 |
| 4..7 | 事件时刻 `u32` ms（低 32 位） |

| 事件码 | 名称 | 参数 |
|---|---|---|
| 1 | `ESTOP` | 0 |
| 2 | `TRAJ_DONE` | 1=正常走完，0=被中止（含 E-Stop） |
| 3 | `STREAM_EXIT` | 1=流模式看门狗超时退出 |
| 4 | `TEACH_FULL` | 0 |
| 5 | `CFG_SAVED` | node_id |

**只有边沿才发**（E-Stop 按下那一次、轨迹 1→0 那一次），不刷屏。

## 5. 机械臂侧配置（`can` 控制台命令）

配置存 Flash **扇区 11 的 CAN 区**（与 PID/校准记录同扇区、互不覆盖）。

| 命令 | 作用 |
|---|---|
| `can` | 打印全量：node/波特率/三段 ID/心跳/收发与错误计数/最近返回码/是否已保存 |
| `can node <1~15>` | 改节点号（立即生效，**上位机也要换 ID**） |
| `can baud <100\|125\|250\|500\|1000>` | 改波特率（立即重配 CAN，**另一端必须同步改**） |
| `can hb <ms>` | 周期状态帧周期，0=关，100~10000 |
| `can save` | **落盘**（不 save 则重启回默认 node=1 / 500k / hb=1000） |
| `can reset` | 恢复默认并落盘 |
| `can stat clr` | 清统计 |

出厂默认：**node = 1，500 kbit/s，心跳 1000 ms**。

### 5.1 ⚠ CAN 控制器接口（`cx` 命令）—— **接线接在哪个口，必须由它决定**

CAN 配置里**不包含**"用哪一路控制器的引脚"。那是另一套运行期开关（`cx`）：

| 命令 | 作用 |
|---|---|
| `cx` | 打印当前接口与引脚 |
| `cx 1` / `cx 2` | 切到 **CAN1**（默认 PA11/PA12）/ **CAN2**（固定 PB12/PB13），立即生效 |
| `cx pa` / `cx pb` | 切 **CAN1** 的引脚组（PA11/PA12 ↔ PB8/PB9）；对 CAN2 无意义 |
| `cx save` | 把当前接口**落盘**（跨 RESET 存活） |

- **本板卡的 CAN 卡实际插在 `CAN2` 口**（PB12/PB13）。
  - **✅ `0918H` 起开机默认 = `CAN2`**（= 硬件实况）⇒ **通常不需要手动切**。
    判据：`h` 首行有 `defif=CAN2(PB12/PB13)`。
  - **≤`0918G`：默认是 `CAN1`** ⇒ 必须先 `cx 2`，否则"硬件全对、就是不通信"。
- ⭐⭐ **烧录固件会抹掉 CAN 配置区**：烧录工具默认**整片擦除** ⇒ 扇区 11 的 CAN 配置
  （连同 `cx save` 存下的接口选择）一并被抹掉 ⇒ 回落到**编译期默认值**。
  - ⇒ 所以**"默认值"必须等于"现场接线"** —— 否则每次烧完都要人工补一步。
    `0918H` 之前就是这个问题：默认 CAN1、实际 CAN2，于是"指纹对、`h` 正常、但上位机全超时"
    必然出现，且极易被误判成"新固件没修好/烧坏了"（红线 37）。
  - ⇒ `cx save` **只能跨 RESET，跨不了重烧**。
- `cx` 属于**机械臂侧调试命令**，上位机不需要发（也不在 CAN 协议里）。

## 6. 上位机实现要点（**这些坑会真的踩到**）

1. **必须用标准帧（11 位）发到 `0x100+node`**。发到别的 ID 会被机械臂硬件过滤丢弃，表现为"完全没反应"。
2. **DLC 是变长的**。首帧 DLC ∈ [5,8]，续帧 DLC ∈ [2,8]。按 8 字节读会把续帧后面的脏数据当数据。
3. **不要依赖自动重传**。机械臂侧 `AutoRetransmission = DISABLE`（防止对端不在时把主循环拖死）。
   丢帧就丢帧 ⇒ **上位机必须自己按 SEQ 做超时重试**（建议超时 50~100 ms，重试 3 次）。
4. **`GET_STATUS` / `FK_QUERY` 会读舵机总线**（6 轴，几百 µs~ms 级）。别把它当 10 Hz 轮询用 —— 那正是状态帧存在的理由。
5. **`MOVE_JOINTS` 的 ACK ≠ 运动完成**。运动是异步的：等 `TRAJ_DONE` 事件帧，或轮询状态帧的 bit1。
6. **限位是静默钳制的**。目标超限不会报错，会被就地夹到限位内（`ACK` 仍是 OK）。要确认实际到位，读 `GET_STATUS` 或 `FK_QUERY`。
7. **总线两端必须有 120 Ω 且共地**。CAN 收发器的 RXD 浮空会产生随机错误帧，典型症状是"偶尔丢一包"。
8. **`STREAM_JOINTS` 有看门狗**：连续 500 ms 没有新帧，机械臂自动退出流模式并冻结（位置保持，不会失力砸臂）。遥操作发不出帧时是安全的，但会静默停住。
9. **改波特率/节点号的顺序**：先把上位机侧配好，再敲 `can baud/ node`（或反过来），中间会有一段时间通信中断，这是正常的。

## 7. 联调步骤（从零到跑通）

```
① 接线: 上位机CAN卡 CANH↔臂 CANH, CANL↔臂 CANL, GND↔GND, 总线两端各 120Ω
② 机械臂上电, 控制台看到:  CAN slave: node=1 @500 kbit/s, ids cmd=0x101 rsp=0x181 evt=0x281, hb=1000ms
   若显示 "(defaults)" ⇒ 说明从未配置过, 用的出厂默认值(这是正常状态)
   ⚠ 紧接着必须核对接口: 敲 cx → 应为 CAN2 PB12/PB13; 若显示 CAN1 就先敲 cx 2 (§5.1)。
     刚烧过固件的话它**必然**是 CAN1 —— 这步漏了, 后面全部白测。
③ 控制台敲 cn    → hw init 应为 ok; 若 FAILED, 先敲 e (内部回环自检) 排除 MCU 侧
④ 控制台敲 cp    → RX 脚加内部下拉仍读 11111111 ⇒ 收发器已上电且接上了
⑤ 上位机侧: PING(0x01) → 应收到 0x181 上的 0x81 响应(带 proto_ver / run_id)
   ⚠ 收不到 PING 响应时: 先确认波特率一致(500k), 再确认发的是标准帧到 0x101
⑥ 上位机侧: GET_STATUS(0x02) → 4 帧响应, 解析出六轴角度
⑦ 观察 0x281 上的周期状态帧 → 每秒 1 帧, d[0]=0x53
   ⚠ 必须先发过 PING 才会出现（见 §4.1.1：臂不向空气发帧）。工具已自动处理：
     `--monitor` 会先替你发一次 PING（除非加 `--no-ping`）。
⑧ 发一条 MOVE_JOINTS(0x10) → 收 ACK → 等 0x281 上的 TRAJ_DONE 事件帧
⑨ 控制台敲 can   → 看"命令帧/响应帧/CRC错/事件丢"计数是否与上位机侧对得上
```

**参考实现**：`tools/can_host.py`（基于 python-can）已实现上述全部步骤，可直接跑通：
```bash
pip install python-can
python tools/can_host.py --list                       # 看可用 CAN 通道
python tools/can_host.py --selftest                   # ★ 离线自检, 不需要 CAN 卡
python tools/can_host.py --smoke                      # ★ 一键冒烟(只读, 逐项 PASS/FAIL 表)
python tools/can_host.py --order-verify 25            # ★ 多帧回包帧序验收(严格按序视角, 见 §2 要点 3)
python tools/can_host.py --smoke --allow-move         # 加上运动往返(只动 J1/J6 ±3°)
python tools/can_host.py --channel can0 --ping --status --monitor 20
```

> ★ **现场按 `docs/CAN联调测试单_2026-09-17.md` 走**（分 8 阶段、每步带判据与失败去向）。
> `--smoke` 就是那张测试单的阶段 4+5 的自动化版本。

### 7.0 ⚠ 量纲与角色（源码核实，两个会真正踩到的坑）

| 项 | 结论 |
|---|---|
| `0x02 GET_STATUS` 读出的六轴 | `SERVO_GetPosition()` = **舵机度（0~300 绝对量）**，与 `0x10 MOVE_JOINTS` **同一量纲** |
| `0x13 STREAM_JOINTS` 的六轴 | **逻辑关节角**（相对本臂 Home，可为负）—— 与上面**不能混用**；遥操必须用它 |
| 对**主臂**固件发 `0x10` | `cmdMove()` 在主臂里默认只读（`MASTER role: read-only (ma 0)`），必须先 `ma 1`；否则 **ACK 照回 OK 但不动、也没有 TRAJ_DONE** |
| `-32768` | 该轴**读失败**的哨兵值，不是角度。看到它应报错而不是当 -3276.8° 用 |

### 7.1 上线前先跑离线自检

**没有 CAN 卡也能验证编解码是否正确**，避免"把协议实现的 bug 当成硬件问题查"：

```
python tools/can_host.py --selftest
  == 1) CRC-16/CCITT-FALSE 标准校验值 ==
    PASS crc16('123456789') == 0x29B1
  == 2) 分包帧数(LEN -> 帧数), 与固件公式一致 ==
    PASS LEN=0->1  LEN=2->1  LEN=5->2  LEN=12->3  LEN=16->3  LEN=21->4  LEN=64->10
  == 3) 往返: 造帧 -> 拆帧 -> 重组, 内容(含 CRC)必须完全一致 ==
  == 4) 首帧/续帧 d[0] 取值 ==
  == 5) 注入错误: 篡改一字节后 CRC 必须报错 ==
  == 6) 乱序/丢帧后必须放弃整包 ==
  == 7) 状态帧/事件帧解码 ==
```

其中 **`crc16(b"123456789") == 0x29B1`** 是 CRC-16/CCITT-FALSE 的国际标准校验值，
用它保证主机侧实现与固件 `Aproto_Crc16()` 是**同一个算法**（多项式 `0x1021`、初值 `0xFFFF`、
非反射、无输出异或），而不是"看起来差不多"的自造 CRC。

## 8. 固件与版本

**现役（`0918H`，2026-09-18 17:3x）**：

| 文件 | 说明 | md5 | 大小 |
|---|---|---|---|
| `outputs/can_api/01_master_CANslave.bin` | 主臂固件 | `5b0e6000f278523cd0d3c624c620df3e` | 209028 B |
| `outputs/can_api/02_slave_CANslave.bin` | 从臂固件 | `1305367872645bdfb21380f978d7a51e` | 201100 B |

> 历史版本轮转保留：`*.bin.prev` = `0918G`、`*.bin.prev2` = `0918F`。
> `0918H` 相对 `0918G` 两处变化：**① 开机默认接口改成 `CAN2`**（本板实际接线，烧完不用再 `cx 2`）；
> **② error-passive 探路窗口 5000 ms → 500 ms**（最坏恢复 ~35 s → ~3.5 s）。

- **版本指纹（⭐ 判"手里是哪版"唯一便宜手段）**：控制台敲 `h`，首行应含
  `fw-tag ARM-CAN-0918H  pins=CAN1 <引脚>  iface=cx-switchable+cxpa  defif=CAN2(PB12/PB13)  fix=cprint-overread,frameseq,tec-latch,defcan2,tecwin500  cmds=…`
  - `fix=` 字段直接说明修了什么：`cprint-overread`（上电静默死机）、`frameseq`（多帧回包乱序）、
    `tec-latch`（§4.1.1 的错误计数自锁）、`defcan2`（默认接口改 CAN2）、`tecwin500`（探路窗口 500 ms）。
  - `defif=` 告诉你**开机默认落在哪个口** —— 决定"要不要先 `cx 2`"。
  - ⚠ **`≤0918G` 没有 `defcan2`** ⇒ 默认是 CAN1，烧完必须先 `cx 2`（红线 37）。
  - ⚠ **`≤0918F` 没有 `tec-latch`** ⇒ 遇到 `tec ≥ 128` 就是永久自锁，只能 `e` → `cx 2` 人工恢复。
  - ⚠ 老固件上敲新命令**不报错**，而是按首字母执行某个单键命令（`cx` → 校准向导 → **松全部力矩**），
    误入向导后**千万别按 `s`**。所以**先认指纹，再敲别的**。
  - 离线核查不用上电：`grep -qF "fw-tag ARM-CAN-0918H" <bin>`（`cprint` 的格式串直接进镜像）。
- 编译：
  ```bash
  PATH="/c/STM32Tools/arm-gcc-full/bin:/c/STM32Tools/make:$PATH" make -j4 LINK=can CANPIN=pa                    # 从臂
  PATH="/c/STM32Tools/arm-gcc-full/bin:/c/STM32Tools/make:$PATH" make -j4 ROLE=master LINK=can CANPIN=pa        # 主臂
  ```
  产物在 `build_can_pa/`（从）/ `build_master_can_pa/`（主）。
  - `CANPIN=pa|pb` 只管 **CAN1** 的引脚组（默认 `pb` = PB8/PB9，本板实际用 `pa` = PA11/PA12）。
  - `CANIF=c2|c1` 决定**开机默认接口**（默认 `c2` = CAN2，= 本板实际接线）。
  - ⚠ **别用 `make … | grep -c error` 串 `&&`**：计数为 0 时 `grep` 退出码是 1，会把后续步骤短路。
- ⚠ **烧录 = 整片擦除** ⇒ CAN 配置区（扇区 11）与 `cx` 接口设置全被抹掉 ⇒ 回落到**编译期默认值**。
  `0918H` 起默认已是 `CAN2`，所以**不需要**再手工 `cx 2`；`≤0918G` 需要（§5.1）。
- CAN 从站接口在**两种角色固件里都存在**，与 `LINK=uart/can` 那个开关无关（后者只管"主从臂之间"那条链路）。
- 协议版本：`APROTO_VERSION = 0x01`（PING 响应携带）。
- 本规范对应固件新增：可变波特率、`can` 配置命令、状态/事件帧、Flash 保区持久化、`cx` 接口切换。

## 9. 与串口协议的关系（一句话）

```
              ┌──────────── 同一套 ────────────┐
串口:  0xAA 0x55 [SEQ][CMD][LEN][PAYLOAD][CRC16]      ← 直接过字节流
CAN :  [SEQ][CMD][LEN][PAYLOAD][CRC16] 切进 1~N 个 CAN 帧   ← 本节 §2 的分包
              └─────────────────────────────────┘
```
命令码、负载布局、错误码、响应规则**逐字节相同**。串口 SDK 的 codec 可直接复用，只需替换承载层。
