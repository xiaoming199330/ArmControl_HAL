## 3. P0 缺口（写 R1 之前必须定死）

### P0-1 笛卡尔虚拟目标：方案里没有"积分器"这一层

定稿页 §2.12.3 的伪代码是：

```c
ik_ok = IK_Solve(&tgt, rad);   ...
```

**问题：`tgt` 从哪来、什么时候更新、被拒帧时算不算更新 —— 一个字都没写。**
而这恰恰是"末端遥控"的唯一状态所在。必须补上：

| 项 | 必须定死的内容 | 不这么做的后果 |
|---|---|---|
| **基准** | 进 ACTIVE 的那一刻，用 `ArmApi_GetStatus()` 实测 FK 位姿 `(x,y,z,pitch)` + 实测 J5 角当基准；**绝不许假设 0 / 假设 1500µs 的中位** | 第一拍就 25°/帧 跳变被拒 ⇒ "没反应"，或直接猛跳 |
| **维度** | 虚拟目标 = 4 维 `(x,y,z,pitch)` + J5 + 夹爪量，共 6 个量，**pitch 固定为入口实测值** | 平移时末端朝向会自己漂（IK 会把 pitch 当自由量解） |
| **累加语义** | 增量累加到"**上次被接受的目标**"；本拍被拒（`IK 不收敛 / 超限位 / FK 超差 / raw 跳变 / 桌面立柱`）⇒ **本拍增量丢弃**，目标不动 | 被拒期间攒了一张"存单"，松手后臂还在慢慢往存单上爬 —— 且现场看起来像"漂移" |
| **重同步** | `StreamJoints` 是**开环**（不读起点、不看实际到没到）。实际位置会滞后：`clamp_raw` 静默夹住（`main.c:1983-1997` 有计数但不报错）、25°/帧 拒帧、丢读重试都会让实际落后。必须给一个重同步策略（建议：连续拒帧 ≥ N 拍 ⇒ disarm + 报文案，比"每拍读位姿"便宜得多） | 虚拟目标与实际越差越远；rm 时"看起来一切正常" |
| **松手即停** | = 增量为 0（速度=0 ⇒ 目标不变），**不是**"停止下发" | （方案已写明，复核确认 —— 看门狗 500ms 兜的是"控制拍死了"，不是"松手"） |

> ⚠ 顺带纠一个容易搞反的点：`IK_Solve` 解出的是 **J1~J4**，J5 是 Roll（不影响位置，`kinematics.h:103`）
> ⇒ **J5 可以完全独立地用速度积分**，不必进 IK。这正是"平移 + J5 + 夹爪同帧下发"能成立的原因。

### P0-2 RC 拍 vs 网口 `STREAM_JOINTS`：两套控制源今天就会打架

复核到的事实（09-23 新增的部分）：

| 事实 | 位置 |
|---|---|
| 网口二进制协议里**已有** `STREAM_JOINTS`（就是 `ArmApi_StreamJoints`） | `arm_control_protocol.c:214-218` |
| 它**没有** magic 校验（不像危险命令那套 `ARM_API_ERR_MAGIC`） | 同上，直接进 `ArmApi_StreamJoints(deg)` |
| 流模式**默认就是开的**，不需要任何 enable 命令 | `main.c:1852` `stream_follow_en = 1U` |
| 上电后 UDP 5000 收到 12 字节就能驱臂（前提：限位已标定） | 综合以上 |

⇒ **"网口遥操作"其实今天就能做，不必等 R1。** 但这直接带来冲突：

- RC 拍 与 PC 流 **各有一个虚拟目标**，交替 `SyncWrite` ⇒ 目标互相覆盖，**表现是抖动/爬行，而两边都显示"成功"**；
- 更隐蔽的一条：`cmdMove()` 走的是 `cmdStreamExit("trajectory move")`（`main.c:1604`），
  它**只清 `stream_active`，不清 `stream_follow_en`** ⇒ 文本/网口发一条 `m`/`MOVE_JOINTS` 之后，
  **RC 拍下一拍就 `stream_enter()` 把流模式抢回来**（`main.c:1947-1970`），
  而 `stream_enter()` 会**给六轴开力矩 + 把 GOAL_SPEED 写 0**（`main.c:1921-1928`）
  ⇒ 两条通路会**乒乓互踢**，谁都没意识到。

**建议（择一，推荐 A）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 显式归属（推荐）** | `main.c` 加 `stream_owner`（0=none / 1=host / 2=rc）：协议层在 owner==rc 且 RC 在 armed 时，对 `STREAM_JOINTS` 返回 `ARM_API_ERR_BUSY`；RC 层发现 owner==host 时自动 disarm | 改 main.c + 协议层各一处（但 R1 本来就要改 main.c 挂拍） |
| **B. 零改动兜底** | RC 层每拍记"自己上次成功下发的时刻"；若 `ArmMain_Flags()` 的 `FLAG_STREAM`（`main.c:1863`）为 1、而自己已 >200ms 没成功下发 ⇒ 判定被外部抢占 ⇒ 自动 disarm + 报文案 | 只能**事后**发现，抢占瞬间仍会抖一下 |
| C. 不做 | —— | 不可接受：`rc ctl 1` 期间 PC 一发包就把臂接管了 |

### P0-3 "关发射机必须停"在 R9DS 上**验证不了**，而且 `rc` 的文案在误导

方案 §1.4 判断得完全正确（R9DS 丢控是"保持行程"，不是"脉宽消失"）——
**但代码和文案还停留在旧机（HotRC F-04A）时代**，这会让 R5 演练得出假的"通过"：

| 位置 | 现在的内容 | 对新机是否正确 |
|---|---|---|
| `arm_rc.h:4` | "硬件: HotRC F-04A 接收机, 4 路标准 RC PWM" | ❌ 硬件已换 AT9S Pro + R9DS |
| `arm_rc.h:22-24` | "② 不自复位的杆只能驱动绝对量 …… 左杆(实测不自复位, 只有前后 1 轴)" | ❌ 新机 4 轴全自复位，映射已全改 |
| `arm_rc.h:41` | `ARM_RC_NCH 4U /* F-04A 是 4 通道 */` | ⚠ 数字对，理由过期 |
| `main.c:6401` | "失控计数 : N 次 (**关发射机应当 +1**)" | ❌ 新机丢控**不涨** |
| `main.c:6345` | "只有自复位的杆才有稳定中位。不自复位的杆(**你的左杆前后**)" | ❌ 左杆已自复位 |
| `main.c:6471-6475` | 引导"若脉宽归 0 且新鲜变 ✗ ⇒ 理想情况，判据可以直接用新鲜度" | ❌ 新机两者都不发生 |
| `main.c:6480` | "③ 关发射机 → 看失控计数是否 +1、脉宽是否冻结" | ❌ 新机永远是 `live=✔` 那支分支 ⇒ 显示"一切正常" |

⇒ **在 R9DS 上，`rc` 的"新鲜度 / 失控计数"两个判据永远不动**，
`rc` 会一直走 `main.c:6476` 的"✔ 至少一路有信号"分支。现场看起来**完全正常**。

**R5 可用的判据只剩三条**（复核建议写进 R1 的 arm 前置）：

1. **结构性保证（必做，人查）**：X/Y/Z/J5 四个通道的 **F/S 必须设成中位**（丢控 ⇒ 映射速度 0 ⇒ 停）；
   夹爪 F/S **不得设成闭合**。这条只能由人确认，软件查不到。
2. **外挂心跳通道（你已确认要做 ⇒ 09-23 定案，完整设计见 §7.4）**：拿一路闲置通道，
   正常时固定在一端，把它的 **F/S 写成一端的"另一端"** ⇒ RC 层每拍比对，
   读值跳到 F/S 特征值即判丢控。
   ⭐ **09-23 三次更新**：夹爪最终走 **`TIM1_CH4`=`PE14` 硬件捕获**（用户确认引出，§7.1）；
   心跳走 **`PG10`/`EXTI` 软测宽**（任何 GPIO 都可以，与 4 路硬件捕获**同一个解码函数、同一把时基**）。
   原先"两路 TIM1 给不了 ⇒ 只能上 SBUS"的结论**作废**；TIM1 剩余的 CH1/CH3（`PE9/PE13`）留作二期扩容。
3. SBUS 第 23 字节 failsafe 位（协议级，最好，但需反相器 + 待实测乐迪是否真填）。

### 7.3 `TIM1` 启用清单（R0.5 必读 —— TIM1 从未被本工程初始化过）与心跳的 `EXTI` 代价

**夹爪（`PE14`/`TIM1_CH4`）**：误差回到硬件捕获级别（时间戳记在 `CCR4`，与 ISR 何时进来无关）⇒
**§7.3 旧版的"多帧平均抵抖动"要求取消**。但 TIM1 是**从零启用**，有 3 条新账：

1. ⚠⚠ **`PSC` 不是 83，是 167**：`TIM4` 在 APB1（定时器时钟 84 MHz ⇒ `PSC=83` 得 1µs），
   **`TIM1` 在 APB2（定时器时钟 168 MHz）** ⇒ 必须写 `PSC=167` 才是 1 tick = 1µs。
   照抄 TIM4 的 83 会让夹爪读数**统一差一倍**——且量纲与 CH1~CH4 不一致，解码函数直接误判段长。
2. ⚠ **`HAL_TIM_IC_CaptureCallback()` 现在有两个 Instance 进来**（`TIM4` + `TIM1`）
   ⇒ 必须按 `htim->Instance` 分派（红线 40 家族的既有纪律，第一次就要写对）。
3. ⚠ `TIM1` 是高级定时器，但**只做输入捕获不需要碰输出**：`MOE`/`BDTR`/各 `CCxE` 保持默认（输出关）即可，
   `CR1 CEN` 置 1 起计数；NVIC 用 `TIM1_CC_IRQn`，优先级与 TIM4 同级（**5**）。
   `gpio.c` 需加 `PE14 = AF1` 上拉/下拉与 RC 其余四路一致（`PULLDOWN`，双边沿由 IC 配置）。

**心跳（`PG10`/`EXTI`）**：它的任务只是**区分两个值**（≈1000 vs ≈2000µs，§7.4），
不是测连续量 ⇒ ISR 入口抖动 2~10µs 在 1000µs 的量程差面前**无关紧要**，不需要平均。
旧版 §7.3 对"连续量夹爪"算的抖动账不再适用；对心跳只需记住两条：

1. ⚠ **`HAL_GPIO_EXTI_Callback()` 全工程只有一个符号**（已核：当前工程**零处**使用 EXTI，
   所以我们可以独占）。它内部**必须按 `GPIO_Pin` 分派**（现在只有 `PG10` 一个使用者，但要按"可扩展"写），
   且文件头要写明"新增 EXTI 使用者必须回到这里登记"——与 `HAL_TIM_IC_CaptureCallback` 同族纪律。
2. ⚠⚠ **`EXTI10` 线与 `PA10/PB10/PC10/PD10/PE10/PF10` 共号**（一根线号跨七个端口，同一时刻只能一个端口启用）。
   本工程有两个"现役邻居"必须点名保护：
   **`PB10` = `USART3_TX`（总线 A，舵机半双工方向）**、**`PE10` = `DIR_B`（74HC126D 总线 B 方向控制，推挽输出，
   `gpio.c:148`）** —— 它们都**不用 EXTI、现状不冲突**，但**从此"谁都不能把 `PB10`/`PE10` 改成 EXTI"**
   （否则心跳线 10 被抢，RC 心跳静默失效）。中断向量 `EXTI15_10_IRQn`（IRQ 40）不变；
   `PD12~PD15` 已被 `TIM4` 占为 AF2、`EXTI11` 的 `PE11`(急停) 也继续禁用 EXTI（既有纪律照旧）。
   优先级建议仍是 **2**（与 CAN 同级）；`nt` 期间时基 `TIM4` 被 `nt` 借走 ⇒ 那几秒读数是垃圾（收尾已复位统计）。

### 7.4 心跳通道设计（`F/S` 反极性设值法）

**硬件**：R9DS 的 **PWM 模式（红 LED）有 9 路 PWM**（SBUS 模式才是 10 路）⇒ 夹爪 + 心跳之外还有富余。
接收机仍**独立供电**、只与板子**共地**（不变）。

**发射机侧配置（人做，一次性）**：
1. 把心跳那一路绑到**一个两档开关**（或一个平时不动用的旋钮），确认它在**正常位**的输出（记作 `W_ok`，
   通常 ≈1000 或 ≈2000µs，**以实测为准**）；
2. 把开关拨到**另一端**，长按接收机 `ID SET` 3~5s 写入 F/S ⇒ 接收机就把"另一端"记成失控值（记作 `W_fs`）；
3. 松手、把开关拨回正常位 ⇒ 在线时读 `W_ok`，丢控时读 `W_fs`。

**RC 层判据（每拍，`|w - W| ≤ 40µs` 视为命中）**：

| 读数 | 判定 | R1 动作 |
|---|---|---|
| ≈ `W_ok` | **link_ok** | 正常跟随 RC |
| ≈ `W_fs` | **link_lost** | **立刻 disarm**（清积分器）＋**冻结夹爪**（见下） |
| 其它 / 无样本 | 未知 | 不动（保持上一状态，别拿未知当"丢控"） |

**为什么只有"值判据"能看见丢控**：R9DS 丢控是**继续发帧、把值改成 F/S 预设**（P0-3）。
⇒ 新鲜度 `fresh`、边沿计数 `edges`、`lost_events` **结构性失效**，永远不会动。

⭐ **这条通道的第二个用途比"检测"更值钱**：判到 `link_lost` 时，R1 应**冻结夹爪**
（保持最后一次 J6 目标，而不是去追 R9DS 的 F/S）。
因为你已把**夹爪 F/S 也设成中位** ⇒ 若不冻结，丢控瞬间夹爪会**从"正夹着工件"跑到半开**，
工件会掉。**"X/Y/Z/J5 的 F/S = 中位"是安全的（速度归 0 ⇒ 停）；"夹爪 F/S = 中位"不是安全的**。

**备选（不占引脚，二期 / 万一 `PG10` 没引出）**：**"冻结检测"** —— 4 个杆通道若连续 ≥25 帧
（0.5s）**逐帧完全不变**，就有极高概率是丢控（R9DS 的 F/S 是晶振量化值，真在线时人手不可能
把 4 路都压成逐帧 bit 相同）。它的代价是**只能事后 0.5s 发现**，且理论上会被"人手极稳"骗到；
所以它只配当**冗余**，不替代 §7.1 的心跳通道。

### 7.5 你已确认的设置 ⇒ 记进"人查清单"（软件查不到，只能人确认）

1. X / Y / Z / J5 四路 F/S = **中位** ⇒ 丢控 ⇒ 映射速度 0 ⇒ 停 ✔（P0-3 的结构性保证）
2. 夹爪 F/S = 中位 ⇒ ⚠ **必须靠 §7.4 的"冻结"兜住**，否则丢控时爪子自己跑到半开
3. 心跳通道 F/S = **与正常位相反的一端**（§7.4）

### 7.6 R0.5 落地清单（✅ 2026-09-23 16:5x 已落地并编译通过）

核心重构：`arm_rc.c` 里的 `s_channel[]` 从"**TIM4 通道号数组**"升级为"**数据源描述表**"，
让 CH1~CH4（`CCR`）与 CH5/CH6（`EXTI`）走**同一个解码函数**：

```c
/* arm_rc.c —— R0.5 关键形态（示意，未编译） */
typedef enum { RC_SRC_CC = 0, RC_SRC_EXTI } rc_src_kind;

static const struct { rc_src_kind kind; TIM_TypeDef *tim; uint32_t ch; uint16_t pin; } s_src[ARM_RC_NCH] = {
    { RC_SRC_CC,   TIM4, TIM_CHANNEL_1, 0        },   /* PD12 CH1 X   */
    { RC_SRC_CC,   TIM4, TIM_CHANNEL_2, 0        },   /* PD13 CH2 Y   */
    { RC_SRC_CC,   TIM4, TIM_CHANNEL_3, 0        },   /* PD14 CH3 Z   */
    { RC_SRC_CC,   TIM4, TIM_CHANNEL_4, 0        },   /* PD15 CH4 J5  */
    { RC_SRC_CC,   TIM1, TIM_CHANNEL_4, 0        },   /* PE14 CH5 夹爪 (TIM1_CH4, PSC=167!) */
    { RC_SRC_EXTI, 0,    0,             GPIO_PIN_10 },/* PG10 CH6 心跳 */
};

/* 两条通路都收敛到这一个函数: 传"当前 CNT 值"进来, 其余逻辑与 R0 完全一致 */
static void rc_accept_edge(uint32_t i, uint16_t cnt);   /* ← 原 HAL_TIM_IC_CaptureCallback 的函数体 */

/* 硬件捕获: 值来自 CCR (硬件时间戳, 无 ISR 抖动) */
/* EXTI:     值来自 TIM4->CNT (同一个 1µs 时基) */
static uint16_t rc_stamp(uint32_t i)
{
    if (s_src[i].kind == RC_SRC_CC) {
        if (s_src[i].tim == TIM1) {
            return (uint16_t)TIM1->CCR4;     /* ⚠ TIM1 PSC=167 才是 1µs, 见 §7.3 */
        }
        switch (i) { case 0: return (uint16_t)TIM4->CCR1; case 1: return (uint16_t)TIM4->CCR2;
                     case 2: return (uint16_t)TIM4->CCR3; default: return (uint16_t)TIM4->CCR4; }
    }
    return (uint16_t)TIM4->CNT;          /* ⚠ EXTI 通路(心跳): 两档判据, 抖动无关紧要, 见 §7.3 */
}

/* ⚠ 全工程唯一的 EXTI 回调 —— 新增使用者必须回到这里按 pin 分派 */
void HAL_GPIO_EXTI_Callback(uint16_t pin)
{
    for (uint32_t i = 0U; i < ARM_RC_NCH; i++) {
        if (s_src[i].kind == RC_SRC_EXTI && s_src[i].pin == pin) { rc_accept_edge(i, rc_stamp(i)); return; }
    }
}

/* ⚠ 现在有两个 Instance 进来 —— 必须按 Instance 分派(红线 40 家族) */
void HAL_TIM_IC_CaptureCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM4) { /* CH1~CH4: 按 Channel 分派, 走 rc_accept_edge */ }
    else if (htim->Instance == TIM1) { /* CH5 夹爪: rc_accept_edge(4, TIM1->CCR4) */ }
}
```

`HAL_NVIC_SetPriority(TIM1_CC_IRQn, 5, 0)` + `EnableIRQ`；
`ArmRc_Reinit()` 里把 `PG10` 的 `EXTI` 与 `TIM1` 一起重置（`nt` 后统计已复位）。

## 8. 事故复盘：R1 首飞"乱走"（0923D，09-23 19:3x 定案 ⇒ 修复于 0923E）

### 8.1 现象与根因

`rc go on` 后推杆，臂乱走。取证链条（全部对源码）：

| # | 事实 | 出处 |
|---|---|---|
| 1 | 本工程**两层角度域**：**L1** = servo 度 0~360（`cmdSolveIKPoint` 输出、`ArmApi_IkQuery` 输出、`GetStatus.joint_deg`、校准限位、`L` 全是它）；**L2** = 关节度 (-180,180]（IK/FK 工作空间、**`ArmApi_StreamJoints` 输入**、跳变守卫） | `main.c:1756-1774`、`kinematics.c:140` |
| 2 | `SERVO_OFFSET≈180`（Home 锚定）⇒ L1 直喂 L2 入口 = **双重映射**：实际下发 = `offset + dir·L1`，每轴错 ~180° | `kinematics.c:119` |
| 3 | 旧 R1 把 IK 的 L1 输出直接喂 `ArmApi_StreamJoints`（期望 L2） ⇒ 坐标系错位 | 0923D `arm_rc_ctrl.c` |
| 4 | 跳变守卫本应拦住首帧（Δ≈180°>25°），但**基准建立失败**（`base=none`，6 轴投票读在总线丢读下并不罕见）时守卫不使能 ⇒ 错位帧全部放行 | `main.c:cmdStreamJoints` |
| 5 | 且小步目标(0.1mm/帧)时 `cmdSolveIKPoint` 的"已在其位"捷径恒命中，返回的 `cur[]` 也是 L1 ⇒ 错位更隐蔽 | `main.c:3650-3672` |

### 8.2 修复（0923E）

1. **域铁律**：新增导出 `ArmMain_ServoToJoint1()`（main.c，与 `servo_to_joint_deg` 同式）——
   域转换只许走这一个口；R1 在喂 `StreamJoints` 前逐轴 L1→L2。
2. **IK 换口**：`cmdSolveIKPoint` → **`ArmApi_IkQuery`**（无控制台 cprint 副作用、无捷径、
   限位检查用 RAM 的 `JOINT_MIN/MAX`，与限位闸同源）。
3. **J5 卡区保护**：RC 的 J5 目标 clamp 到 **180~340**（L1，固件保护区）∩ 校准限位，
   杜绝杆扫过 77~174 机械卡区堵转；会话启动若 J5 在窗外，RLOG 警告。
4. **底座随动系**（开源遥操作通行做法，参考 so_arm_ros2 的 teleop_ik_node：
   以实时位姿为目标、拒帧不追旧目标）：X/Y 速度按 **J1 当前朝向**旋转（杆上=沿臂朝向前移），
   j1_est 会话起点实测 + 每个被接受帧刷新；`RC_BASE_REL=0` 可退回世界系。

### 8.3 教训

- **两层角度域并存是这个工程最大的静默陷阱**：任何新运动代码过"IK 输出 → 流输入"
  必须显式回答"这一段是 L1 还是 L2"。已写进 `arm_rc_ctrl.h` 头注。
- 跳变守卫依赖基准成功建立 ⇒ **基准失败 + 错位输入**会组合成"守卫失效"。
  安全不能只压在一层守卫上。

## 9. 顿挫根治 + 速度可配置存 flash（09-24，ARM-NET-0923F）

### 9.1 "又慢又一顿一顿"的机理（对源码取证）

| # | 事实 | 出处 |

| 1 | `stream_enter()` 把六轴 **GOAL_SPEED 写 0(全速)**（本意是防轨迹收尾低速拖跟随） | `main.c` stream_enter |

### 9.2 修复（0923F）

1. **自适应 GoalSpeed（根治顿挫）**：会话开始把六轴压到低速软启动(reg=2≈8.8°/s)，

   并在 ≥150ms 节流下写入（写失败不记 ⇒ 自动重试）。舵机连续匀速追赶目标 = 滑行。
2. **杆量一阶滤波**（τ≈125ms）：消 PWM 抖动 + 起停自带斜坡；<2% 残量归零（松手即停）。
3. **速度可配置**：`rc spd` 查看 / `rc spd <vxy> <vz> <vj5> [j6]` 运行时设 /
   `rc spd save` 存 **扇区 11 区 D**（0x3000，magic+ver+FNV 校验，出界拒绝）。
   默认 X/Y 12、Z 8、J5 30、夹爪 90（首版 5/4/15/60 太慢）。
4. **flash_cfg 加区 D**：`CFG_REGION_COUNT` 3→4（保区缓冲 8→12KB RAM）；
   区 D 与 A/B/C 互保 —— 存速度不会动校准零点。
5. **动作范围 = `L` 表**（用户 09-24 指定）：限位源本来就是 `L` 同源的 RAM 校准限位
   （`ArmMain_GetJointLimitsDeg`）；⚠ J5 额外钳 180~340 —— `L` 的 J5 12~351 **含 77~174 机械卡区**，
   这扇窗必须保（卡区堵转本身就是"乱走/卡死"贡献源）。

## 10. 超限位自锁根治：顶到包线软停（09-24，ARM-NET-0924A）

### 10.1 现象与根因

- 现象：杆把臂往桌面/立柱方向推到底 → `Stream reject: pose unsafe` 刷屏 →
  `[RCCTL] DISARM: 流层连续拒帧 (E-STOP/跳变/越界)` → 舵机保持力矩**锁死**，
  `rc go off/on` 之前一直不动。
- 根因链：`stream_pose_ok()`（main.c，桌面 z 下限 + 立柱圆柱包线，判据与
  `fk_path_z_ok` 一致）判不过 ⇒ cmdStreamJoints **整帧拒** ⇒ arm_rc_ctrl 的
  `rej_run` 计到 15（300ms）⇒ DISARM 自锁。包线越界和真异常（跳变/E-STOP）
  混在同一条熔断通道里，是设计缺口。

### 10.2 修法（用户定案："不能锁，就是不让他越过限位那个方向"）

1. **发帧前预检**：main.c 新增只读导出 `ArmMain_StreamPoseOk(q[6])`（与流层
   完全同一判据，输入 L2 关节度），arm_rc_ctrl 发帧前先过它。
2. **五档缩步长试探**（"顶墙软停"）：步长按 `{1, 1/2, 1/4, 1/8, 0}` 试帧，
   取第一个 `ArmMain_StreamPoseOk` 通过的档。朝包线推 ⇒ 自动减速停在包线上；
   0 档 = 本拍笛卡尔不动，**J5/夹爪照常走**（两者已各自钳在安全窗/限位内）⇒
   其他方向不受影响。
3. **抗积分器 windup**：`tgt_x/y/z` 只在帧真被接受时提交（0 档被接受时提交
   原值 = 不前进）。顶死时目标停在包线上，松杆或反向杆**立即**恢复，无回弹迟滞。
4. **熔断通道收窄**：`rej_run` 只计 `ArmApi_StreamJoints` 返回非 OK
   （真异常：跳变/E-STOP）；IK 不可达与包线预检失败**不计数**，只限 2s 一条
   `已到包线/可达边界: 该方向软停`。
5. J5 维持安全窗钳制（180~340，避 77~174 卡区）、J6 维持 `L` 限位钳制——
   这两轴本来就软停，本次是补齐笛卡尔三轴。

### 10.5 0924B 二轮翻车：跳变拒帧风暴 + 拖尾 3-4s（0924C 修复，09-24 实机）

- 现象：`Stream reject: J6 jump 38/102 deg`、J2/J3 jump 25~90° 连刷 →
  `DISARM: 流层连续拒帧 (跳变)`；且松杆后臂还"拖尾"动 3-4 秒、整体不灵敏、
  J6 响应慢。比 0923F 还差。
- 根因（一条链）：
  1. **指令-实际脱节**：session_start 软启动把 GoalSpeed 写 2(≈8.8°/s)，而夹爪
     指令速率 90°/s ⇒ 指令目标以 90°/s 跑、舵机以 8.8°/s 追，差距 150ms 内
     ~12° 并继续滚雪球，直到撞 25° 跳变闸（`stream_prev`=上一**被接受帧**，
     与实际/指令的差距都会爆）。
  2. **拒帧死锁**：跳变拒帧 → rej_run++；600ms 无接受帧触发 resync（重测
     actual），但流的跳变基准 stream_prev 还是旧的远目标 ⇒ 重测后的帧照样
     撞闸 ⇒ 永远拒。15 帧 → DISARM 锁死。
  3. **拖尾 3-4s = 舵机在关差**：目标冻结在前面，舵机以 GoalSpeed=2 慢慢爬
     向旧目标 —— 用户看到"没动摇杆还在动 3-4 秒"。
  4. **不灵敏**：resync 每次又把 GoalSpeed 压回 2 ⇒ 一顿一爬。
  5. J2/J3 一帧跳 25~90° = **近奇异 IK 枝翻转**（中位全伸展姿态，微小目标
     变化让解析解/CCD 在两枝间跳）。
- 修复（0924C，`rc-fb-pace`）：
  1. **反馈钳制（核心）**：每拍轮询 1 轴实际位置（10ms 超时，120ms 一圈），

     ⇒ 指令-实际差距从机理上不可能积累，舵机追不上=天然软停。
  2. **去软启动**：session_start 不再写 GoalSpeed=2；首个被接受帧立即自适应

  4. **拒帧自愈**：流层拒帧(非 E-STOP) → 会话作废 + 全轴 GoalSpeed 提到
     100(≈440°/s) 快速关差 + 下拍重测基准；rej_run 不再被 resync 清零，
     真堵转 15 帧仍熔断。被反馈钳制截断时笛卡尔 tgt 不前进（防 windup）。

### 10.6 0924C 三轮翻车：自锁低速 + 拖尾（0924D 根治，09-24 实机）

- 现象：`rc spd ... 200` 后夹爪仍 ~80°/s 慢爬；松杆后臂拖尾数秒；整体不灵敏。
- 根因（0924C 自己埋的，一条链）：
  1. **EMA 估速正反馈自锁**：`inst = |l1−prev_l1|/dt` 里的 l1 已被反馈钳制锚在
     实际位置 ±LEAD 上 ⇒ "被接受帧的位移" = 舵机实际位移 ⇒ EMA 估出的 = 舵机
     当前速度，写回去 = 速度永远锁在起步值附近（~80°/s），`rc spd` 直通失效。
  2. **积分器欠账**：提交 `j6_t = j6n`（未钳制值）—— 杆按住时目标以 200°/s 跑、

### 10.7 0924E 定案：删"欠账机理"，开环指令速率直通 + 夹爪实时跟随（09-24 实机反馈）

- 用户反馈（0924D）：①全速设满仍"超级好慢" ②"走的时候太晃了" ③要求
  "摇杆停 = 机械臂就停"，质疑"欠账/关账"机理存在的必要性 ④夹爪不要限速。
- 根因承认（用户判断正确）：
  1. **差距×K 关账是反馈环**：GoalSpeed=|目标−实际|×K，实际位置每次轮询
     回来差距跳变 ⇒ 速度寄存器跟着抖 ⇒ **"晃"**；松杆后还要还账 ⇒ 违背
     "摇杆停=立即停"。它的原始目的（0923F）只是防"满速+小步长"的顿挫，
     但代价是反馈环滞后与抖动，得不偿失。
  2. **杆量低通滤波 τ≈125ms**：本地硬件直连延迟≈0，这个滤波就是纯迟滞
     = "不灵敏"的一半来源。
  3. "全速设满仍慢"：夹爪受 j6r 速率限 + 笛卡尔/自调速度机制层层打折。
- 0924E 修法定案（`rc-openloop`）：
  1. **节奏器改开环**：GoalSpeed_j = 指令速率（被接受帧的**指令步长**/dt 的
     EMA 0.5），与舵机实际位置**无关** ⇒ 无反馈环=不晃；目标推进速率 =
     舵机速率 ⇒ 匀速连续不顿挫；松杆 → 指令速率→0 → 只剩最后一小步 ⇒
     **立即停**（不再有关账拖尾）。J5 保底 max(cmd_rate, |w5|)。

     保证 < 25° 跳变闸，快扫滑杆不拒帧；j6_t 提交钳制值，舵机 >18° 落后
     时帧流不断直到真正到位。`rc spd` 第 4 参数 (j6) 废弃（字段兼容保留）。
  3. **删杆量低通滤波**：f_s = stick_norm 直连（死区 60µs + 平方特性保留）。
  4. **速度上限放宽**：vxy 1~120 mm/s、vz 1~80 mm/s、vj5 5~300 deg/s；
     帮助文本同步（save/set 显示去掉夹爪项）。

### 10.8 0924F 根因定案：Goal Speed 单位换算错 50 倍 + 刹车帧（09-24 实机）

- 用户反馈（0924E）：①松杆仍有拖尾、不立即停 ②舵量拉满还是好慢。
- **真根因（50 倍单位错，0923F 起一直错）**：STS3215 Goal Speed(46-47) 寄存器
  单位 = **1 step/s**（1 step = 360/4096°），量程 0~3400 step/s ≈ 0~299°/s ≈
  舵机空载极速。代码一直按"1 单位 ≈ 4.39°/s"换算（=50 step/s）⇒ 写出的值
  全部比意图慢 ~50×：`rc spd` 设 J5=150°/s 实际只拿到 ~3°/s —— "拉满还是慢"；
  舵机以龟速滑向 ≤15°（LEAD）外的最后一个目标 —— "拖尾好几秒"。
  0924E 里只有夹爪跳过 pace 吃到全速，所以只有杆轴慢/拖尾。
- 裁决依据：①寄存器量程 3400 与物理极速 ~300°/s 对上（若 50 step/s/单位，
  量程对应 15000°/s，荒谬）；②项目内"尾段交接写 GOAL_SPEED=42 是小值拖慢
  跟随"——42 step/s=3.7°/s 才叫小值；③首版（无 pace 写入，GoalSpeed 保持
  stream_enter 的 0=全速）用户评价"跟随很快"。
- 修复（0924F，fix 链 +`rc-spd-unit50x`+`rc-brake`）：
  1. `RC_STEPS_PER_DEGS` 1/4.3945 → **4096/360**（°/s→step/s），pace 上限
     300→3400；拒帧自愈关差改写 0（全速）。
  2. **刹车帧**：松杆当拍（intent 下降沿）发一帧目标=实际位置（钳 L 限位+
     包线预检），舵机到达即停 —— 拖尾从 ~0.1~数秒 → 1~2 个控制周期。
  3. 0924E 其余机制（开环指令速率、反馈钳制、包线五档、J6 全速实时跟随）
     不动 —— 单位修正后它们第一次按设计值工作。

  fw-tag **ARM-NET-0924F**，零新告警，cprint 守卫 ✔。⚠ 待上板复测。
- 教训：**外设寄存器单位必须以"量程×物理极限"自洽校验**（3400×假设单位若
  超过舵机物理极速即为单位错）；"看起来能跑"的换算可能错了 50 倍而不自知。

## 11. 输入源换装：R9DS → PS2 手柄（09-24，ARM-NET-0924G）

### 11.1 硬件接线（用户定案，对应手册 V1.5）

| 接收器 | F407ZGT6 | 说明 |
|---|---|---|
| DI/DAT | PB1 | 输入 + 上拉（手柄→主机，时钟下降沿移出） |
| DO/CMD | PB3 | 输出推挽（主机→手柄） |
| CS/SEL | PB4 | 输出推挽（通信期间保持低） |
| CLK | PB5 | 输出推挽（本实现 100kHz，手册推荐 250kHz，取保守） |
| VDD / GND | 3.3V / GND | ACK 悬空 |

- ⚠ **PB3/PB4 复位默认 = JTAG(JTDO/NJTRST)**：本工程只用 SWD(PA13/14)，
  配成 GPIO 输出即可，F4 无需任何 remap。烧录走串口 stm32flash 不受影响。
- ⚠ PB5 = CAN2_RX(AF9)：net 构建 CAN2 已弃用（PB13 被 ETH_TXD1 占），
  编译期已拦 `cx/can`，不会有人把 CAN2 配回来抢脚。
- 工程红线与 .ioc 核对过：PB1/PB3/PB4/PB5 均无其他占用。

### 11.2 协议实现（手册 V1.5 §4 原样，位序 LSB-first）

- 一帧 9 字节（CS 低电平期间一次传完）：DO=0x01 0x42 + 7×0x00；
  DI= idle / ID / 0x5A / 按键1 / 按键2 / RX / RY / LX / LY。
- ID：0x73=红灯(模拟)模式，0x41=绿灯(数字，摇杆无效)。
- 配置序列 `PS2_SetInit` 原样照搬：ShortPoll×3 → EnterConfing(0x43) →
  TurnOnAnalogMode(0x44, analog=0x01, **锁存 0x03**) → VibrationMode(0x4D) →
  ExitConfing(0x43,0x00,0x5A...)。锁存后 MODE 键切不走模式。
- 时序（手册 PS2_Cmd 原样）：DO 设好 → CLK_H → 5µs → CLK_L → 5µs → CLK_H → 读 DI；
  字节间 16µs；半周期 5µs=100kHz（全帧 ~0.9ms，50Hz 拍上占 4.5%）。
- 微秒延时用 **DWT CYCCNT**（168MHz 精确），DWT 不可用时退化 NOP 环。

### 11.3 对上层契约不变（arm_rc_ctrl.c 零改动）

| PS2 | → 通道 | 合成脉宽 |
|---|---|---|
| 右杆 RX | CH1 X | 右=+（>1500） |
| 右杆 RY | CH2 Y | 上=+ |
| 左杆 LY | CH3 Z | 上=+ |
| 左杆 LX | CH4 J5 | 右=+ |
| R1/L1 | CH5 夹爪 | R1=张开→2000，L1=闭合→1000，**按住扫描**（全程 1.2s），松开保持 |
| 链路状态 | CH6 心跳 | 通信正常=1000 |

- 摇杆 0~255 → 1000~2000µs：中心死区 ±3 count，中位恒 1500 开机自动标
  ⇒ **`rc mid` 不再必需**（命令保留兼容）。
- **方向吸收在采集层**（上/右=+，与 AT9S 杆感一致）⇒ ctrl 层实测确认过的
  `RC_SIGN_*` 不动；实测方向反了改 `RC_SIGN_*`，不改采集层映射。
- ⭐ R9DS 三条结构性缺陷在 PS2 上**天然消失**：
  ①R9DS 丢控=继续发帧只改值 ⇒ fresh/lost 失效 —— PS2 是主动轮询，
  没响应=没帧，fresh/lost_events 恢复本义；②心跳 F/S 反极性判丢控 ——
  链路状态本身就是心跳；③中位标定 —— 恒 1500。
- 运行中若连续 50 帧失败且距上次配置 >2s ⇒ 自动重跑 SetInit
  （覆盖"手柄待机后 START 唤醒""被拨到绿灯模式"两种场景）。

## 12. PS2 按键体系：键位映射存盘 + 示教录制/回放手柄化（09-24，ARM-NET-0924H）

### 12.1 用户需求定案

1. 夹爪 = **双按键长按**：一个键按住=闭合、另一个按住=张开，两个都松=停。
