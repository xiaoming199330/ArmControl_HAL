## 1. 「feedback unreadable」在固件里到底是什么

调用链（`Core/Src/main.c`）：

```
main loop (每趟)
 ├─ 7483  cmdMultiPointService()      ← 轨迹结束那一拍内
 └─ 7562  cmdMultiPointService()      ← 之后每趟主循环都调（同一趟里第二遍）
             └─ cmdMultiPointTargetReached()
                   └─ SERVO_GetPositionDiagTO(j, 10ms) ×6 + 失败重试
       返回 2 (≥1 轴两次都读不到) 累计 25 次  -> 打印
```

判据要点：

| 返回值 | 含义 |
|---|---|
| 1 | 六轴都在 ±2.0°（`MULTI_POINT_REACHED_TOL_DEG`）内 ⇒ 到位，开始稳定窗口 |
| 0 | 至少一轴读数有效但超差 ⇒ 还没到 |
| 2 | **至少一轴连续两次读不到** ⇒ 无法判定，累计 25 次就打印 |

所以这句话的准确含义是「**QL 在等"到位"的时候，某根轴的反馈连续 25 次都读不回来**」，
不是「线缆一定坏了」。

## 2. 为什么这条消息容易把人带偏（固件缺陷 A）

`DXL_ReadDiag()`（`scs_protocol.c:155`）把**三件完全不同的事**都算成"读失败"：

| diag | 真因 | 现场处置 |
|---|---|---|
| `DXL_RD_NO_REPLY` | 一个字节都没收到 | 线缆 / 接插 / 共地 / 供电 |
| `DXL_RD_BAD_FRAME` | 帧损坏（找不到 `FF FF ID`、校验错、长度不足） | 总线噪声 / 丢字节 |
| `DXL_RD_ERROR_BITS` | **状态帧回来了，但 Error 字节非 0**（overload / over_temp / over_volt / sensor_fail …） | **查负载与散热，跟线缆无关** |

固件里**本来就有**区分三者的打印 —— `print_pose_read_fail()`（main.c:2092，`f` 走这条）：

```
  FK J3 READ FAILED: servo ALERT err=0x08 [overload ] (check load/temperature, not wiring)
  FK J3 READ FAILED: corrupt frame (bus noise/dropped byte).
  FK J3 READ FAILED: no reply (cable/connector/ground).
```

但 QL 这条路径旧版用的是丢掉原因的 `SERVO_GetPosition()`，于是统一打印成
"check bus/cable" —— 现场最容易被带去拆线，而真凶常常是**舵机顶死/过载后一直回带告警位的状态帧**。

**已修**：QL 到位判定改用 `SERVO_GetPositionDiagTO(j, 10ms, &diag, &err)`，
打印时复用同一套判据 + `SERVO_ErrorString()`：

```
  QL: J3 feedback blocked - servo ALERT err=0x08 [overload ] (check load/temperature, not wiring)
  QL: J3 feedback blocked - corrupt frame (bus noise / dropped byte)
  QL: J3 feedback blocked - no reply (cable/connector/ground)
```

顺带：旧文案的「0.5s」也不成立 —— 25 次计数 × 每拍耗时（≈读超时/轴）才是真实时长；
用旧的 100ms 超时时，一轴连续失败会让**每趟主循环被拖 100~200ms**（控制台 / 遥测 /
软件 E-STOP 一起停摆）。热路径统一 10ms（与 `SERVO_GetPositionRawTO` / `ReadTelemetry` 一致）。

## 3. 收尾斜坡的两个缺陷（指纹 A 逼出来的）

`main.c` 主循环「到位收尾降速」段。先用日志反推：

- 打印 `tick=140/137` ⇒ `traj_tick` 已经**越界**（137 是 `ttotal`）；
- `want` 被钳到 1.0 后 `v = all_servo_moving_speed + (TRAJ_APPROACH_SPEED - 1000) * 1`
  = **`TRAJ_APPROACH_SPEED`**；打印是 `1000->0` ⇒ **`TRAJ_APPROACH_SPEED`（#42）当前 = 0**；
- 而 `traj_tick` 每拍跳 `TRAJ_SEND_PERIOD_TICKS = 4`，序列是 0,4,8,…,136,140。
  第一次进入收尾区居然发生在 **140**，说明 `ttotal*(1-FRAC) > 136`
  ⇒ **#43 `traj.approach_frac` ≈ 0**（若为默认 0.05，应在 tick=132 打印 `1000->730`）。

⇒ 结论：名义上的"线性斜坡"**退化成最后一拍的一次速度阶跃**，而且这一拍把
舵机 `GOAL_SPEED` 直接写成 **0**。

### 缺陷 B：斜坡分支缺少 `#42 = 0` 守卫（与交接分支不一致）

同一个 `main.c` 里，交接分支（约 7455 行）明确把 0 当"禁用"：

```c
uint16_t hspd = (uint16_t)(TRAJ_APPROACH_SPEED + 0.5f);
if (hspd < 1U) hspd = all_servo_moving_speed;   /* #42=0(禁用) 时退回常速 */
```

斜坡分支**没有**这个守卫 ⇒ 把 0 当目标速度算出来、原样写进六轴速度寄存器。
速度寄存器 0 在 STS 里是特殊值（厂商定义＝不限速），于是最后一拍由常速
**满速冲到终点** —— 正是这段代码本来要消除的顿挫/撞停/末端过冲来源，
负载轴上还容易把舵机告警位（overload）打起来，而告警位一起来，
读位置就开始被 `DXL_RD_ERROR_BITS` 拦下 ⇒ 就是第 2 节那条"读不到"。

> 现场自检：`LP` 看 #42 / #43 的值；#42 = 0 就是本缺陷的触发条件。

### 缺陷 C：斜坡窗口可能短于一个下发节拍

`tail_start = ttotal * (1 - FRAC)`，而 `traj_tick` 每拍跳 4。只要
`ttotal - tail_start < 4`，斜坡就只会在最后一拍触发一次。这解释了
「明明是"线性斜坡"，日志里却只出现一行」。

## 4. 改法（已实施，两臂均编译通过、新增告警 0）

1. `servo_driver.c/.h`：新增 `SERVO_GetPositionDiagTO(joint, to_ms, diag, err_bits)`；
   旧 `SERVO_GetPositionDiag()` 变成它的薄壳（行为不变，仍 100ms）。
2. `main.c` 斜坡段：
   - `approach_target = (TRAJ_APPROACH_SPEED >= 1.0f) ? TRAJ_APPROACH_SPEED : 常速`
     —— 与交接分支同一条规则；
   - `tail_start` 至少提前 `2 * TRAJ_SEND_PERIOD_TICKS`，保证斜坡≥2 拍；
   - 打印追加标记 `[#42=0: ramp disabled, keeping normal speed]`。
3. `main.c` QL 到位判定 + 打印：按 diag 三分支输出真实原因（见第 2 节）。
4. 未动但记录在案：`cmdMultiPointService()` 在同一趟主循环里被调两次
   （7483 / 7562），是冗余轮询，可删前者；本次不动以缩小改动面。

## 5. 现场三步验证（建议顺序）

1. `f` —— 看是否出现 `servo ALERT err=0xXX [overload ]`。
   一刀切开「线缆 vs 舵机告警」，这是现有固件就有的能力。
2. `LP` —— 看 #42 / #43 现值。若 #42=0、#43=0：`SP 42 30` + `SP 43 0.1`，
   再跑一次 `QL` 对比日志（斜坡应出现多次、`want` 从 1000 递减到 30）。
   确认合理后 `F` 落盘（否则重启又回到 Flash 里的旧值）。
3. `tm 200 ptivl`（或 `pv` / `pf`）—— 看六轴温度 / 电流 / 负载，
   哪一轴异常（顶死、堵转、过热）就查那一轴的机械与限位，不必拆线。
