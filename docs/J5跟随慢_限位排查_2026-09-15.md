## 0. 数据判决：两臂 `zi` 实测（结论性）

两臂各自敲 `zi` 得到：

| 轴 | A 臂 `JOINT_*_RAW` | B 臂 `JOINT_*_RAW` | 同/异 |
|---|---|---|---|
| J1 | `[0, 4095]` (360.0°) | `[729, 3450]` (239.2°) | **异** |
| J2 | `[660, 3003]` (206.0°) | `[883, 3245]` (207.7°) | **异** |
| J3 | `[885, 3138]` (198.1°) | `[886, 3139]` (198.1°) | **同** |
| J4 | `[944, 3287]` (206.0°) | `[838, 3229]` (210.2°) | **异** |
| **J5** | **`[1014, 2834]` (160.0°)** | **`[1015, 2835]` (160.0°)** | **同** |
| J6 | `[0, 4095]` (360.0°) | `[1460, 2675]` (106.8°) | **异** |

`calib_zero_raw` 两臂都是 `≈[2048 ×6]`，`SERVO_OFFSET` 都是 `≈180.0°` —— **两台臂的
J5 零点与窗口都对得上**。

### 0.1 为什么"两臂一致"就否掉了旧假设

旧假设要求"一台臂走偏移分支、另一台走兜底分支"。实测：

```
A 臂: zero[4]=2047 → 2047 + (-1033) = 1014,  2047 + 787 = 2834   ✅ 偏移分支
B 臂: zero[4]=2048 → 2048 + (-1033) = 1015,  2048 + 787 = 2835   ✅ 偏移分支
```

**两臂都走偏移分支**。而 rel-home 窗口 = `(zero + offset) × 360/4095 − zero × 360/4095`
= `offset × 360/4095` —— **`zero` 被整项减掉**，所以两臂窗口**逐位相同**：

```
A 臂  zero[4]=2047 → raw[1014, 2834] → rel-home [-90.813°, +69.187°]   跨度 160.00°
B 臂  zero[4]=2048 → raw[1015, 2835] → rel-home [-90.813°, +69.187°]   跨度 160.00°
```

不是差 90.8°，是 **0.000°**。所以"主臂吐 rel-home、从臂用自己零点解释、语义差 90.8°"
这条链路**不存在**。

### 0.2 顺带更正：`J5_LIMIT_OFF_*` 其实**不是**陈旧值

`arm_config.h:126-127` 标着"待重测 (旧舵机值)"，容易让人以为它错了。用旧 epoch 的
零点一代，就能看出它是对的：

```
旧 epoch: Home raw = 3081  (main.c:1200 注释: "旧舵机 zero=3081 时代实测")
偏移分支给出的绝对窗口 = 3081 + (-1033) .. 3081 + 787
                      = raw [2048, 3868]
                      = servo 180.0° .. 340.0°        ←←← 正是 arm_config.h:118
                                                          "J5 永不让 IK 进入 77~174
                                                          机械卡区, 硬覆盖为 180~340"
```

**偏移值与旧 epoch 完全自洽**：它编码的就是设计意图的 160° 挡块带。

换舵机 / 重装盘位器之后 Home 从 raw 3081 变成 2048（整条 raw 刻度平移 −1033），
**同一块物理挡块带**随之落到 raw `[1015, 2835]`。代码 `zero + offset` 会自动跟随这个
平移 ⇒ **偏移分支在当前 epoch 下是对的**，`zi` 报的 servo 89.2~249.2° 只是"绝对舵机
刻度"的说法变了，物理位置没变。

⇒ 所以 `J5 合法 rel-home = [-90.8°, +69.2°]` 是**设计区间**（跨度 160°，与兜底分支
`[0°, +160°]` 跨度一致，只是锚点差 90.8°）。**锚点不一致只影响 `zero==0` 的未校准兜底
路径** —— 两台臂都不在那条路径上（见 §2）。

## 0.3 ◉ 实测判决（2026-09-15 15:40）：从臂 J5 撞固件下限，静默夹住

现场：从臂 `sf 1` 跟随中，加 `pv 500` 看实读角；主臂把 J5 从一端物理挡块推过全程。
以下是 36 s 抓包里的**关键三点**。

### (1) 从臂 J5 钉死在 `JOINT_MIN_RAW[4]` 上

| 序列 | 从臂 `Feedback: J5=`（servo 度） |
|---|---|
| 跟随时 | 208.35 → 197.45 → 188.92 → 187.52 → 176.70 → 165.80 → 152.18 → 141.36 → 130.46 → 119.56 → 108.75 → 97.93 → **89.76** |
| 之后 30 秒 | **89.67 → 89.67 → 89.67 → …（一直不动）** |

`89.67°` 对上限位下限：`JOINT_MIN_RAW[4] = 1015` → `1015×360/4095 = 89.23°`，**差 0.44°（5 raw）**，
在量化 + 到位误差内 ⇒ **从臂 J5 停在下限**。

### (2) 主臂读数继续走了 71.3°，从臂一动不动

| | 主臂 `#P` 第 5 个数 | rel-home | 折算坐标 |
|---|---|---|---|
| 起点 | `+791` | **+79.10°** | 主臂 raw 2946.8 / 从臂刻度 servo 259.14° |
| 终点 | `−1621` | **−162.10°** | 主臂 raw 203.1 / 从臂刻度 servo 17.94° |

从臂固件窗口只到 servo `[89.23°, 249.23°]`：

```
下限被夹掉 = 89.23 − 17.94 = 71.29°
上限被夹掉 = 259.14 − 249.23 =  9.91°
```

**两端都被夹，下端 71.3° 是主因。** 主臂是 `ma 0`（扭矩 OFF、人力拖动），
读数**不受任何限位约束**，所以能一路推过从臂的窗口边界 —— 这正是 §3 候选 1 的判据 (1)。

### (3) 窗口内跟得**非常准** ⇒ 排除舵机嫌疑（候选 2）

从 208.35 到 89.76，从臂 J5 **平滑连续、与主臂同步**，每 2 s 约 −11°（≈5.5°/s），
**没有任何滞后或爬行**。所以 `servo_driver.c` 的 `accel`/`goal_speed`/扭矩限幅**不是本因**，
候选 2 **本轮排除**。

### (4) 为什么"静默"

`cmdStreamJoints()`（main.c:1749-1753）对越限值走 `clamp_raw()`，**夹住后照常写舵机**、
成功即 `return 0U`：

```c
raw[j] = clamp_raw(deg_to_servo_raw(sd), JOINT_MIN_RAW[j], JOINT_MAX_RAW[j]);
...
if (SERVO_SetPositionsRawSync(raw) != HAL_OK) { stream_reject++; return 1U; }
...
return 0U;            /* ← 被夹住也走这里，不打印任何东西 */
```

**所以"J5 卡住"时控制台是干净的** —— 这也是前几轮一直误判成"舵机慢"的原因。

> 注意 `[#P] rejected rc=4` 里那个 `rc=4` **不是**夹住的报错：`ArmApi_StreamJoints()`
> 把 `cmdStreamJoints()` 的一切非 0 返回（跳变 / pose / SyncWrite 失败）**统一映射**
> 成 `ARM_API_ERR_LIMIT = 4`（arm_control_api.c:113）。夹住本身永不报错。

## 0.4 附带的第二个缺陷：从臂回显 `#P` ⇒ 断流 ⇒ 整帧拒绝

同一份抓包里的独立现象，**与限位无关**，但会让从臂**整体**瞬间冻结：

| 抓包里的行 | 含义 |
|---|---|
| `[从臂] > #P -573 -1029 906 77 673 -449` | 从臂控制台把**收到的每一行 `#P` 回显**回来 |
| `Stream watchdog: no cmd for 500 ms -> hold   (×5)` | **断流 500 ms**，退出流模式 |
| `Stream reject: J5 jump 160 deg (> 25)   (×2)` | 恢复后首帧跳变 160°（= 窗口全宽）⇒ 整帧拒 |
| `[#P] rejected rc=4 (limit/estop), 3457 of 9133` | 累计 **37.8%** 的帧被拒 |

**机理**：`#P` 行 ~35 B × 60 Hz ≈ **2.1 kB/s 纯回显**，在 115200 bps 的控制台 TX 上占约 18%，
且 `cprint` 是**阻塞发送**；叠加 `pv` 输出与诊断打印后，从臂主循环被拖慢 ⇒ 出现 500 ms 级断流。
断流期间主臂已走 160° ⇒ 恢复后 `stream_prev` 是旧值 ⇒ 首帧必然判跳变 ⇒ `return 1U`
（**且 `stream_prev` 不更新**，1778-1784 行），连续若干帧被拒。

**待验证**：从臂 `pv 0` 关掉实时反馈后再跑一轮，看 `watchdog` 是否消失 ——
若是，则"回显 `#P`"是可优化点（流模式下应静音控制台回显）。

## 3. 现在的主线：三条候选（按嫌疑排序）

### 候选 1 ✅ **已确诊**（2026-09-15 15:40 实测，证据见 §0.3）：固件窗口 ⊂ J5 物理可达行程 ⇒ 从臂被**静默**夹住

`J5 合法 rel-home` 只有 **160°**（`-90.8 … +69.2`，且**左右不对称**）。而
**主臂是 `ma 0`（扭矩 OFF、人力拖动）**，它的"读数"不受任何限位约束 —— 只要机械上
能推到，`#P` 第 5 个数就会超过窗口。从臂收到越界值后 `clamp_raw()` 把它夹在边界，
**且不打印任何东西**（`cmdStreamJoints()` 里 clamp 之后直接往下走，SyncWrite 成功即
`return 0`）。现场看到的就是"J5 走一段就不跟了 / 落在后面"。

`main.c:1200-1201` 的注释本身就是这条的预警：

> J5 卡区偏移 (旧舵机 zero=3081 时代实测) 暂沿用 —— **J5 若出现"物理可达却被限位拒"
> 的现象, 用同样方法重测 J5_LIMIT_OFF_\***。

**判据（10 秒，不用改固件、不用重启）**：主臂把 J5 慢慢往一个方向推到底，盯
**转发脚本的 `#P` 第 5 个数** 和 **从臂 J5 的实际位置**：

| 观察 | 结论 |
|---|---|
| `#P` 第 5 个数**一直在变**（越过 ±908 / +692），从臂 J5 **停在原地** | ✅ **候选 1 成立**：从臂被夹住，不是舵机慢 |
| `#P` 第 5 个数**自己就停在 ≈ −908 或 +692** | 主臂 J5 物理行程就到那儿 ⇒ 窗口是对的，转候选 2 |
| 两边都在动，但从臂 J5 明显滞后 | 转候选 2 |

### 候选 2 ❌ **本轮排除**：从臂 J5 舵机侧（内部 profile / 扭矩限幅残留，或机械阻力）

> 排除依据（§0.3(3)）：窗口内从臂 J5 从 208.35° 平滑跟到 89.76°，**与主臂同步、无滞后无爬行**。
> 舵机侧若有 profile 残留，窗口内就该看出来。

`servo_driver.c` 写 `accel` / `goal_speed` / `torque_limit` 走的是 `SERVO_WriteSimple()`
—— **不校验返回**；而 `stream_enter()` 重置 GOAL_SPEED 的两条 SyncWrite 连返回值都丢了：

```c
(void)DXL_SyncWrite(BUS_A, STS_ADDR_GOAL_SPEED, 2U, ids_a, z6,     3U);  /* 返回值丢弃 */
(void)DXL_SyncWrite(BUS_B, STS_ADDR_GOAL_SPEED, 2U, ids_b, z6 + 3, 3U);
```

**任何一次丢帧都会让某颗舵机把旧的低速 profile 留着**，而且它就在 BUS_B（J4/J5/J6）。
这是"单颗舵机慢"的现成通道。

**判据**：

```
从臂: sf 0            # 停跟随（或主臂 sp 0）
从臂: a 4 90          # 单关节 servo 度移动 J5 —— 快不快？
从臂: a 4 300
从臂: s               # 看 J5 的 raw / load / temp / error
```

- `a 4` 单关节也慢 ⇒ **舵机侧**（候选 2 成立）。`load` 高 + `temp` 高 ⇒ 在硬扛（机械/挡块）；
  `load` 正常但慢 ⇒ 内部 profile 残留 ⇒ 从臂 `i 4` 重下发该关节初始化参数（⚠ `i` 会走
  `INST_RESET`，见 §5 警告）。
- 单关节快、只有流模式下慢 ⇒ 回到候选 1 / 3。

### 候选 3 ❌ **本轮排除**：主臂 J5 读数被判据丢弃（整拍丢）

> 排除依据（§0.3(2)）：整段抓包转发速率稳在 **61.0 Hz**（`sp 60` 设定值），
> 且 `#P` 第 5 个数始终平滑单调 —— 主臂没有整拍丢；控制台也无 `MASTER UNSTABLE: J5`。

`read_pos_vote()` 要求 3 次采样里 2 次相差 ≤ `START_READ_TOL_DEG = 4.0f`；**任一轴不达标
就整拍 `return`**（`main.c:2625-2635`）。手腕（J5）是人手最容易快速甩动的轴。

**判据**：跑脚本时看有没有

```
MASTER UNSTABLE: J5 two samples differ > 4 deg (bus noise)
```

这行打在**主臂**控制台 —— `--echo` 就能看见。

## 4. 现场三步（本轮工具已改好，从臂诊断不再是黑盒）

```powershell
cd "C:\Users\Administrator\Desktop\ArmControl_HAL（1）"
py tools\pc_relay.py --master COM22 --slave COM11 --hz 60 --echo
```

`--echo` 现在会同时打 **`[主臂]`** 和 **`[从臂]`** 两边的非 `#P` 行；并且**从臂的
拒绝/告警类行会自动打出来**（不必带 `--echo`），关键词：`reject` / `watchdog` /
`unstable` / `Stream mode` / `fail` / `clamp`。这条改动直接补上了最大的观测盲点 ——
旧版主循环**只 `readline()` 主臂口**，从臂的 `Stream reject: J5 jump …` 永远没人看见。

**步骤**

1. **看主臂是不是在抱怨**：盯 `[主臂]` 有没有 `MASTER UNSTABLE: J5 …`（候选 3）。
2. **看从臂是不是在拒绝**：`[从臂]` 出现 `Stream reject: J5 jump N deg (> 25)` 即候选 3 的
   从臂版本；出现 `Stream mode OFF/Watchdog` 说明流被中断。
   > 想让从臂定期吐 6 轴实时角，加一条：`--slave-cmd "pv 500"`（500 ms 打一次，
   > 会经 `[从臂]` 显示出来）—— 能直接看到 J5 是不是**卡在某个固定值**。
3. **手工扫 J5 两端极限**（判候选 1）：见 §3 判据表。这一步最关键。

## 5. 候选 1 的修复（已按 §0.3 实测值算好）

### 5.1 立即验证（RAM-only，重启即恢复）

按 §0.3 实测：主臂 J5 全程需从臂覆盖 servo **`[17.94°, 259.14°]`**，
而固件窗口只有 **`[89.23°, 249.23°]`**。先在从臂上**只放宽下限**：

```
从臂: L 4 20 250
```

| 参数 | 值 | 说明 |
|---|---|---|
| 目标窗口 | servo `20 ~ 250°` | 覆盖实测所需 `[17.94, 259.14]` 的绝大部分，两端各留 ~2° |
| 当前窗口 | servo `89.23 ~ 249.23°` | `JOINT_MIN_RAW[4]=1015` / `MAX=2835` |
| 效果 | **下限放宽 69.2°** | 上限仅动 0.77°，便于观察主效应 |

**期望**：再推一次主臂 J5，从臂 `Feedback: J5=` 不再钉在 89.67，而是一路跟到 ~20 ⇒ **确诊**。
若从臂到某个更靠下的位置就停住，**那个位置就是物理挡块**，记下它的 servo 值。

> `L` 的参数是 **servo 度**（内部 `deg_to_servo_raw()` 转 raw），取值钳在 `0~360`，
> 且要求 `min < max`（main.c:3650-3666）。

⚠ **这是验证手段不是修复**：正确窗口必须**实测从臂自己的物理挡块**后写进 `J5_LIMIT_OFF_*`，
否则等于把"卡区保护"关掉。
⚠ 放宽后 J5 会向物理挡块方向多走 69°，**慢慢推、听到堵转异响立刻停**。

### 5.2 实测从臂 J5 物理行程（定最终值用）

```
从臂: sf 0          # 停跟随，从臂自锁
从臂: t 4 0         # 松 J5 扭矩（'t J 0' 是解力）
      手动把 J5 轻推顶死两端挡块
从臂: p 5           # 读 J5 实际 servo 度（两端各读一次）
```

### 5.3 根治：改 `J5_LIMIT_OFF_MIN / MAX`

`J5_LIMIT_OFF_*` 是**相对 zero 的 raw 偏移**（`JOINT_MIN_RAW[4] = zero[4] + OFF_MIN`，main.c:1248）。

| | 现值 | 按本次实测推算 | 跨度 |
|---|---|---|---|
| `J5_LIMIT_OFF_MIN` | `−1033` | **`−1843`** | |
| `J5_LIMIT_OFF_MAX` | `+787` | **`+899`** | |
| 合计跨度 | 1820 raw = **160.0°** | 2744 raw = **241.2°** | 差 **81.2°** |

推导：主臂实测 rel-home `[−162.10°, +79.10°]`（`ma 0` 人力拖动 ⇒ 读数即物理位置）
⇒ 从臂 raw `[204, 2948]` ⇒ 减 `zero[4]=2048`。

⚠ **这两个数还只是"按主臂行程搬过来"的推算**，前提是"两臂 J5 机械一致"。**必须以 §5.2 的
从臂实测值为准**再写进 `arm_config.h`。同时按 §2 把 `else` 兜底分支一起对齐，
让两条路径给出同一区间。

⚠ **别用 `zr` 去"修"**：`zr` 复位**六轴**零点，会连带影响本来正常的 J2/J3/J4 的 IK 精度。

⚠ **`i 4` 有风险**：`i` 走 `Torque OFF → INST_RESET → servo mode`，`INST_RESET` 是舵机
**恢复出厂**指令。用它重置 J5 的 profile 之前，先确认重置后本固件会把 ID / 波特率 /
模式 / 限位全部重写回来（`SERVO_InitAll` 的既有流程），并且**只动单关节 `i 4`**。

**判据要留档**：如果重测后算出 J5 物理挡块带 ≠ `[zero−1033, zero+787]`，就按实测值改宏，
同时把 §2 的兜底分支一起对齐，让两条路径给出同一区间。

另外建议给 `cmdStreamJoints()` 的 clamp 加一条**限流打印**（例如每 64 帧报一次
`J5 clamped`），让"静默夹住"这类问题以后自己暴露。
