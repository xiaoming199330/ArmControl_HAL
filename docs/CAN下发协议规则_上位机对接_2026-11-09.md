# CAN 下发协议规则 — 上位机对接完整规范（2026-11-09）

> 适用固件：**ARM-BOTH-0924CC**（LINK=both 构建）  
> 真值来源：`Core/Inc/arm_control_protocol.h`（命令码）、`Core/Inc/arm_proto_can.h`（CAN 承载）、  
> `Core/Src/arm_control_protocol.c`（应答布局）。本文与三者逐字节核对过。  
> CAN 与串口/网口共用**同一套二进制协议**，只有承载层（分包方式）不同。

## 1. CAN 总线参数

| 项目      | 值                                                                       |          |
| ------- | ----------------------------------------------------------------------- | -------- |
| 帧类型     | CAN 2.0A **标准帧**（11 位 ID）                                               |          |
| 波特率     | 默认 **500 kbps**；可切 100/125/250/500/**1000**（`can baud K` + `can save`）  |          |
| 位时序     | 14 TQ（BS1=11 / BS2=2），采样点 85.7%，SJW=1TQ                                 |          |
| node_id | **1~15**，固件 `can node N` 配置并掉电保存；默认 1                                   |          |
| 硬件接口    | CAN1 = PB8(RX)/PB9(TX)（可运行时切 PA11/PA12）；CAN2 = PB12(RX)/PB13(TX)，\`cx 1 | 2\` 运行时切 |
| 终端电阻    | 总线两端各 120Ω                                                              |          |

## 2. 仲裁 ID 规划（11 位）

| ID             | 方向      | 用途                           |
| -------------- | ------- | ---------------------------- |
| `0x100 + node` | 上位机 → 臂 | 命令（分包通道）                     |
| `0x180 + node` | 臂 → 上位机 | 响应（ACK/NACK/数据，分包通道）         |
| `0x280 + node` | 臂 → 上位机 | 周期状态帧 / 异步事件帧（**8B 单帧，无分包**） |
| `0x7E0`        | 双向      | 链路自检帧（`ct` 对拍用，与协议层无关）       |

上位机过滤建议：只收 `0x180+node` 与 `0x280+node`；发包一律发 `0x100+node`。

## 3. 逻辑流与 CAN 分包格式

### 3.1 逻辑流（与串口帧相同，只是去掉 AA 55 帧头）

```
逻辑流 = SEQ(1B) + CMD(1B) + LEN(1B) + PAYLOAD(0~64B) + CRC16(2B, 小端)
CRC-16/CCITT-FALSE（poly 0x1021, init 0xFFFF, 非反射）
计算范围 = SEQ 起到 PAYLOAD 末（即 3+LEN 字节）
LEN 上限 64（APROTO_MAX_PAYLOAD）
SEQ：uint8 请求序号，响应回显同值，用于请求-应答配对
```

### 3.2 分包到 8 字节数据场

```
首帧: d[0] = 0x80 | 总帧数(1~15)
      d[1] = SEQ
      d[2] = CMD
      d[3] = LEN
      d[4..7] = 逻辑流第 4 字节起的 4 字节（即 PAYLOAD 前 4B；不足则 CRC 顶上）
续帧: d[0] = 帧序号(1..14)
      d[1..7] = 逻辑流剩余字节，每帧 7B
单帧: PAYLOAD+CRC ≤ 4B（即 PAYLOAD ≤ 2B）时只有首帧（总帧数=1）
```

- 容量核算：首帧装 4B + 续帧每帧 7B → 最大逻辑流 = 4 + 14×7 = 102B = 3+64+2+尾部余量 ✓
- **一整包由同一函数连续发完**，帧间无握手、不插其它帧；协议帧与 0x280 状态帧互不嵌套
- 臂→上位机方向同理（发到 0x180+node），**必须按上述规则重组**；把非协议帧塞进 0x180 会废掉正在重组的那一包

### 3.3 实例：MOVE_JOINTS 请求（逻辑流 3+16+2=21B → 3 帧）

```
→ 0x101 [83 22 10 10 58 02 00 00]   首帧: 0x83=共3帧, SEQ=0x22, CMD=0x10, LEN=0x10, PAYLOAD[0..3]=58 02 00 00
→ 0x101 [01 BB 00 86 00 00 00 00]   续帧1: PAYLOAD[4..10]
→ 0x101 [02 00 00 00 00 00 A9 1A]   续帧2: PAYLOAD[11..15] + CRC16(A9 1A)
← 0x181 [81 22 7F 02 00 A2 46]      应答: 0x81=单帧, SEQ=0x22, ACK(0x7F), orig_cmd=0x02... 见 §5
```

单帧请求实例（GET_STATUS，LEN=0）：

```
→ 0x101 [81 1E 02 00 9C F2]         0x81=单帧, SEQ, CMD=0x02, LEN=0, CRC=9C F2
← 0x181 [84 1E 82 15 0B 07 ...]     0x84=共4帧, SEQ=0x1E, RSP=0x82, LEN=0x15(21B)...
```

## 4. 定点编码（全协议通用，小端）

| 加速度 a | uint16 | 0.1 °/s²     | 80 → 800                                |

## 5. 响应规则

| 类型    | 响应 CMD                     | payload                  |
| ----- | -------------------------- | ------------------------ |
| 数据查询类 | 请求 CMD | 0x80（如 0x02→0x82） | 见 §7                     |
| 控制成功  | **0x7F ACK**               | u8 orig_cmd, u8 err(=0)  |
| 控制失败  | **0x7E NACK**              | u8 orig_cmd, u8 err(错误码) |

### 错误码表（ARM_API_ERR\_*）

| 值  | 名称        | 含义                |
| -- | --------- | ----------------- |
| 0  | OK        | 成功（运动类=已启动）       |
| 1  | PARAM     | 参数非法（长度/范围/ID）    |
| 2  | CRC       | 帧 CRC 校验失败        |
| 3  | UNREACH   | IK-CCD 不可达/不收敛    |
| 4  | LIMIT     | 解算结果超关节限位         |
| 5  | ESTOP     | E-Stop 激活，禁止运动    |
| 6  | FK_VERIFY | IK 解 FK 回代验证超差    |
| 7  | READ      | 舵机总线读取失败          |
| 8  | MAGIC     | 危险命令 magic 不符     |
| 9  | BUSY      | 轨迹/示教/回放进行中，操作不允许 |
| 10 | NOTCAL    | 未做 Home 零点校准，无法换算 |

### 6.2 文本透传（覆盖全部 144 条控制台指令的关键通道）

| CMD  | 名称         | 请求 payload                                         | 应答                                                                              |
| ---- | ---------- | -------------------------------------------------- | ------------------------------------------------------------------------------- |
| 0x0B | TEXT_EXEC  | u32 magic(0x5A5A5A5A) + ASCII 命令行 + 0x00（有效长度 ≤58） | 0x8B: u16 total, u8 flags, u16 off, u8 n, char text[n]；flags bit0=输出超 2048B 被截断 |
| 0x0C | TEXT_FETCH | u16 off, u8 n(1~58)                                | 0x8C: 同 0x8B 格式，取上一条输出后续分页                                                      |

- magic **无条件要求**（这条命令等于整个控制台，最危险）
- 执行路径与 COM11 敲同一行**完全相同**（TextGate → ProcessCommand）
- 只有 `h`（帮助表 5406B）等超长输出需要翻页；收到 total 后循环 0x0C 直到 off+n ≥ total
- ⚠ 运动类文本（`z a`/`P 0`/`fi 1` 等）在此通道**可以执行**（与串口同权）

## 8. 0x280+node 状态帧 / 事件帧（8B 单帧，无分包）

### 周期状态帧（心跳，`can hb <ms>` 开启）— 逐字节布局（arm_proto_can.c:249）

| 字节      | 含义                                                                                                  | 示例（实测 2026-11-10）     |
| ------- | --------------------------------------------------------------------------------------------------- | --------------------- |
| d[0]    | 固定 0x53 ('S')                                                                                       | 53                    |
| d[1]    | node_id                                                                                             | 01                    |
| d[2]    | flags 位图：bit0=E-Stop, bit1=轨迹中, bit2=流模式, bit3=修正中, bit4=示教录, bit5=示教回放, bit6=CAN 硬件 OK, bit7=协议层就绪 | C0 = HW_OK+RDY（健康空闲态） |
| d[3]    | **last_err**：最近一次命令返回码（ARM_API_ERR\_*）                                                              | 00 = 无错误              |
| d[4..5] | **已执行命令计数**低 16 位（uint16 LE）——主机看它在不在推进就是"臂活着"的直接证据                                                 | BC 01 → 0x01BC=444 次  |
| d[6..7] | **运行秒数**低 16 位（uint16 LE，约 18h 回绕）                                                                  | B8 00 → 184s          |

> 实测样例：`0x281 [53 01 C0 00 BC 01 B8 00]` = node1、健康、无错误、已执行 444 条命令、上电 184s。  
> d[2] 的 bit6 从驱动层实时取：bus-off 自动恢复期间会短暂为 0，主机可据此区分"臂忙"和"CAN 挂了"。

### 异步事件帧 — 逐字节布局（arm_proto_can.c:268）

| 字节      | 含义                           |
| ------- | ---------------------------- |
| d[0]    | 固定 0x45 ('E')                |
| d[1]    | node_id                      |
| d[2]    | 事件码                          |
| d[3]    | 事件参数                         |
| d[4..7] | HAL_GetTick 毫秒时间戳（uint32 LE） |

| d[2] 事件码 | 含义                 | d[3] 参数     |
| -------- | ------------------ | ----------- |
| 1        | E-Stop 触发          | 0           |
| 2        | **TRAJ_DONE 轨迹结束** | 1=正常 / 0=中止 |
| 3        | 流模式退出              | 看门狗超时值      |
| 4        | 示教缓冲写满             | —           |
| 5        | CAN 配置已落盘          | —           |

## 9. 上位机实现必须遵守的规则（踩坑总结）

1. **MOVE_JOINTS 非目标轴绝不能填 0**——先 GET_STATUS 读当前六轴，非目标轴填当前实际角，否则五轴会同时冲向对面限位（2026-11-09 现场"乱动"事故根因）。
2. **发运动前先查状态**：GET_STATUS 要求 `read_ok=1`（flags bit3）且 `traj_active=0`；read_ok=0 说明舵机总线丢读，**停发一切运动指令**。
3. **ERR_BUSY(9)**：轨迹执行中再来运动指令会被拒；收到 BUSY 先 STOP 或等 TRAJ_DONE 事件（0x280 事件码 2）。
4. **轨迹完成判定**：发 MOVE 后等 0x280 事件帧 TRAJ_DONE，或轮询 GET_STATUS flags bit1 变 0；**ACK err=0 只代表"已启动"不代表"已到位"**。
5. **0x13 STREAM_JOINTS 用"逻辑关节角"**（相对本臂 Home 的角，两端零点各自校准），与 0x10 MOVE_JOINTS 的"舵机度"**不是同一个坐标系**，不要混用；20~50Hz 连续发，不做轨迹规划。
6. **TEXT_EXEC 必须带 magic**，文本 ≤58 字节，输出 >2048B 要用 0x0C 翻页（循环到 off+n ≥ total）。
7. **SEQ 配对**：响应回显请求 SEQ；CAN 应答可能落后（舵机总线阻塞时 3~4s），上位机超时建议 ≥3s，超时后**不要盲目重发运动指令**（可能双发）。
8. **危险命令**（0x70/0x72/0x73 及 TEXT_EXEC 里的 M a/zr）务必二次确认后由用户主动触发，工具里不要做自动重试。
9. **心跳未开时没有 0x280 帧**：臂只被动应答；要主动推状态发文本 `can hb 500`。
10. **角度编码 10 倍坑**：0.1° 定点——发 90° 是 900(0x0384)，发 900 会被钳到限位走满行程。

## 10. 遥测轮询方案（不改固件，角度/温度/电流全靠轮询 + 心跳白捡）

固件在 CAN 上**没有周期角度/温度/电流推送帧**（8B 数据场装不下 6×2B 角度），0x280 心跳只带 flags/计数器。  
上位机按下面的分工拿数据：

### 10.1 各数据源与推荐频率


| 数据 | 命令 | 应答 | 单次代价 | 建议频率 |
|---|---|---|---|---|
| 六轴角度 + xyz + flags | 0x02 GET_STATUS | 0x82 | 读 6 轴舵机总线 **4~6ms**（大头，CAN 本身仅 ~1ms） | **10~20Hz**；轨迹执行中降到 5Hz |
| 温度/电流/负载/电压 | 0x04 GET_JOINT_DETAIL（joint=0xFF 全轴） | 0x84 | 同样读舵机总线，6 轴全扫 | **1Hz** 足够（变化慢） |
| 状态位/活体 | 0x0A GET_FLAGS | 0x8A | **不碰舵机总线，极轻** | 10~50Hz 随意 |
| flags/last_err/命令计数 | 0x280 心跳（免轮询） | — | 后台收线程监听即可 | `can hb 100` 开到 100ms |
| 轨迹完成 | 0x280 事件帧（免轮询） | — | 事件码 2 = TRAJ_DONE | — |

### 10.2 CAN 独有的免轮询项（先吃白饭）

1. **发文本 `can hb 100`**（TEXT_EXEC 下发即可），心跳加密到 100ms 后开后台收线程只听 `0x280+node`：flags 位图、last_err、已执行命令计数（推进 = 臂活着）**不用发任何查询就持续到手**。
2. **轨迹完成有事件帧主动推**（0x280 事件码 2），不用盯轮询 flags bit1——UDP 上才需要盯。

### 10.3 轮询代码骨架（复用 tools/can_host.py）

```python
from can_host import ArmCanHost, open_bus_with_retry, decode_status_payload
import time

bus = open_bus_with_retry("pcan", "PCAN_USBBUS1", 500000)
h = ArmCanHost(bus, node=1)

t_detail = 0.0
while True:
    now = time.monotonic()
    # 角度 10~20Hz（0x82 应答自动多帧重组）
    seq = h.send(0x02)
    res = h.wait_response(seq, 3.0)
    if res and res[0] == 0x82:
        st = decode_status_payload(res[1])   # st['joints'] 六轴 / st['read_ok'] / st['traj']
        if not st["read_ok"]:
            pass                             # 停发一切运动指令
    # 温度/电流 1Hz
    if now - t_detail >= 1.0:
        seq = h.send(0x04, b"\xFF")          # 0xFF = 全六轴, 0x84 = 62B
        res = h.wait_response(seq, 3.0)
        t_detail = now
    time.sleep(0.05)
```

### 10.4 节奏设计（防舵机总线过载）

1. **错峰**：0x02 与 0x04 别在同一拍发——舵机总线一次只能跑一个事务，叠发会互相排队加延迟。
2. **轨迹感知降速**：`traj_active=1`（0x82 flags bit1 或心跳 d[2] bit1）时把 0x02 降到 5Hz，给轨迹让路；空闲恢复 20Hz。
3. **再省总线**：0x04 一次只查一根轴（joint=0~5），每拍换轴，六拍扫全臂，单次事务减到 1/6。
4. **超时 ≥3s**（舵机总线阻塞时应答可迟 3~4s）；超时重发查询可以，**重发运动指令不可以**。
5. 遥测频率还想更高 → 走**串口并行**：COM11 恒常通，`tm 150 pti` 每 150ms 推角度/温度/电流（CAN 管控制、串口管遥测，互不干扰）。
