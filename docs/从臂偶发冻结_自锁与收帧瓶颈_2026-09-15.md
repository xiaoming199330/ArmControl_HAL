# 从臂"停住几秒 → 突然瞬间跟上" 的机理与修复（2026-09-15）

> 现象（用户原话）：*"跳动大的问题会让臂停住过一会又会瞬间跟随"*，
> 控制台伴随 `Stream reject: Jx jump ≥25 deg`、`[#P] rejected rc=4`、
> `Stream watchdog: no cmd for 500 ms -> hold`。

**结论**：这不是舵机慢，也不是主臂的问题。是**从臂控制台收帧路径被自己的
"逐字符回显 + 每拍只吃 1 个字符"拖住 → 128 B 环溢出丢字节 → 行内数字被啃坏
→ `#P` 整帧拒 → 而"拒帧"分支冻结跳变基准 ⇒ 自锁冻结**。
两个缺陷叠加，第二个（自锁）才是"停几秒"的来源。

---

## 0. 判决证据：拒帧是"连续"的，不是偶发

日志里两组计数**同步递增**（每次都是 +64，因为打印限流在 `err % 64 == 1`）：

| `[#P]` 行 | `pc_relay_rx` | `pc_relay_err` | 这一段的帧数 | 这一段的拒帧数 |
|---|---|---|---|---|
| 1 | 35066 | 2689 | 0 | 0 |
| 2 | 35130 | 2753 | 64 | **64** |
| 3 | 35194 | 2817 | 128 | **128** |
| 4 | 35258 | 2881 | 192 | **192** |
| 5 | 35322 | 2945 | 256 | **256** |
| 6 | 35386 | 3009 | 320 | **320** |
| 7 | 35450 | 3073 | 384 | **384** |

**连续 384 帧（≈5.8 s @66 Hz）全部被拒。** 这不是"偶发坏行"——偶发坏行会让
`err` 增速远低于 `rx`。这是**锁死**。

> 判据速记：`err` 与 `rx` 同速增长 ⇒ 自锁；`err` 慢于 `rx` ⇒ 偶发坏行。

## 1. 代码层机理（五步链）

### ① 从臂控制台"每拍只吃 1 个字符"

`main.c` 主循环（非急停分支）：

```c
int len = Console_TryReadLine();      /* ← 每次只取 1 个字符 */
if (len > 0) { ProcessCommand(...); }
```

`Console_TryReadLine()` 内部从环形缓冲取 **1 字节**就返回。所以收一行
`#P`（35 字符）**需要 35 拍主循环**。

### ② 每个字符都要一次**阻塞**发送（回显）

```c
console_rx[console_rx_len++] = ch;
/* Echo */
HAL_UART_Transmit(&hconsole, &ch, 1, 10);   /* ← 每字符一次阻塞发送 */
```

115200 下 1 字节 = 86.8 µs。一行 `#P` 的账：

```
35 (正文回显) + 2 (CRLF) + 2 (提示符 "> ") = 39 B ≈ 3.39 ms 阻塞发送/帧
@66 Hz ⇒ 22.4% 的主循环时间花在"把收到的字打回去"
```

实测印证：`从臂 918217 B / 408 s = 2251 B/s`，而 `主臂收到 800510 B`
⇒ **从臂的发送线 100% 是回显**，一个字的诊断信息都没有。

### ③ 环只有 128 B，且**溢出静默丢字节**

```c
#define RX_BUF_SIZE  128
...
if (next != rx_tail) { ... }        /* 满了就丢, 旧版没有任何计数 */
```

入流 66 × 37 ≈ **2430 B/s** ⇒ 128 B 只够 **53 ms** 的抖动余量。
主循环任何一拍被拖长超过 ~53 ms（总线读超时 100 ms、诊断打印、SyncWrite
突发），环立刻溢出。

### ④ 丢字节会啃坏数字

丢的若是 `\r`+`\n`，两行会粘起来（此时首个 6 数还是上一帧的旧值，**无害**）。
**真正有害的是丢在数字中间**：`-1030` 被啃成 `-030`（= −3.0°，偏 100°）、
`-1621` 被啃成 `-621`（偏 100°）。`atoi` 照收，值合法但错 100° ⇒
单帧跳变 > 25° ⇒ **整帧拒**。

> ⚠ 也因此存在一个更坏的可能：被啃坏的值**若恰好落在跳变阈值内**，
> 就会被当成合法目标下发 —— 那是一次没人要求的误动作。这是修它的第二个理由。

### ⑤ 拒帧**不更新基准** ⇒ 自锁

`cmdStreamJoints()` 的拒绝分支：

```c
if (fabsf(dj - stream_prev[j]) > STREAM_MAX_JUMP_DEG) {
    stream_reject++;
    ...
    return 1U;                 /* ← 不更新 stream_prev, 也不更新 stream_last_ms */
}
```

后果：

- `stream_prev` 冻结在"最后一次成功的下发值"，**主臂继续走，差距只增不减**
  ⇒ 后面每一帧都超阈值 ⇒ 每帧都拒；
- `stream_last_ms` 不更新 ⇒ 500 ms 后 `cmdStreamService()` 触发看门狗
  ⇒ 退出流模式 ⇒ **臂停住**（这就是"停住"）；
- 下一帧重新 `stream_enter()`，基准改读**当前实际位置**。臂没动，基准还是那个
  冻结值 ⇒ 继续拒；
- 直到主臂回到阈值内（操作者来回扫、或重启链路）才放行 ⇒ 此刻
  `stream_enter()` 已把 GOAL_SPEED 写成 `0`(=不限速) ⇒ **臂一次冲到主臂位置**
  ⇒ 这就是"过一会又瞬间跟随"。

**所以"跳动大"不是原因，是结果**：`J4 jump 207 deg` 的 207° 正是 J4 的整个
窗口跨度（206°），说明基准已经和主臂差了一个满行程 —— 基准陈旧了几秒，
不是主臂真的瞬移了。

## 2. 本次改动（只加仪表 + 开关，**不动任何判定逻辑**）

| # | 改动 | 位置 | 风险 |
|---|---|---|---|
| A | **`ec 0\|1`** 控制台回显开关，默认 ON=旧行为。`ec 0` 后不再逐字符回显收到的 `#P` | `main.c` `Console_TryReadLine` + `ProcessCommand` | 极低（纯开关） |
| B | **按需吸干**：主循环一次把环里已到的字符尽量消化掉（上限 64 拍，防饿死急停检查） | `main.c` 主循环 | 低（只影响收帧速度） |
| C | **`rx_ovf` 环溢出计数**（旧版静默丢字节） | `main.c` `USART6_IRQHandler` | 无 |
| D | **拒帧自锁计数**：`reject streak now/max`、`watchdog(total)`，并把"控制台 RX / PC relay"整段打进 `lk` | `main.c` `cmdStreamService` + `lk` | 无（只读诊断） |

新增的 `lk` 输出：

```
    console RX: ring drop 12345 B, echo OFF(quiet)
    PC relay(#P): ok 35066, reject 2689 (7.6%), bad 12
      reject streak now 384, max 1204, watchdog(500ms) 7
      (max 数十以上 = 自锁冻结, 不是偶发坏行)
```

**读数判据**

| 看到 | 结论 |
|---|---|
| `ring drop` 一直涨 | 收帧路径仍在丢字节 ⇒ 回显没关或主循环被别的东西拖住 |
| `max` 只有个位数 | 剩下的是偶发坏行（可接受） |
| `max` 几十~上千 | 自锁仍在发生 ⇒ 该上 §3 的限速方案 |
| `watchdog` 次数 > 0 | 每次 = 一次 500 ms 冻结 |

**没有改的**：跳变判据、姿态判据、clamp、看门狗阈值、`stream_prev` 语义、
机械限位 —— 一律原样。

## 3. 待你点头的第二刀（改判定语义，我没动）

即使把 A/C/D 都做上，**只要有一次真正的高速主臂动作**（手腕一甩 >
25°/帧 @66 Hz = 1650°/s），就会再触发一次自锁。想根治要把 ② 从
**整帧拒绝** 改成 **限速跟随（slew）**：

```
真值    : 目标 = 主臂值;  若 |目标 - 上帧| > 25° ⇒ 拒整帧 (并暂停 500ms)
建议    : 目标 = 上帧 + sign(Δ)·min(|Δ|, 25°)   ⇒ 每帧最多走 25°，永不冻结
```

理由：

- 安全意图（"一个坏值不能让从臂猛冲"）**仍然满足**：坏值最多让它多走 25°，
  下一帧主臂回到正常值就会往回修；
- 1650°/s 已经**超过舵机物理能力**，所以限速跟随反而比"拒帧+冻结+最后猛冲"
  更平缓、更安全 —— 现行方案是先冻 500 ms、再以 `GOAL_SPEED=0`(无限速) 猛冲，
  比限速危险得多；
- 代码注释里"钳制会造出用户没要求的姿态"针对的是 ③ **姿态检查**（那条保持
  整帧拒绝不动）。② 跳变检查用限速是遥操的标准做法。

另需注意：舵机**同总线必须一次 SyncWrite**（`sync_write_goalpos_by_bus` 的
不变量）—— 限速要逐轴算完再一起下发，不能拆成逐轴写，否则同组轴不同时起跑、
机械会歪。

## 4. 现场步骤

**第一步：先重启转发脚本。** 你贴的状态行里没有 `抖动` 一栏
（结尾是 `从臂 918217 B | 用时 408 s`），而脚本 16:02 已经改了格式 ——
说明那次运行是**改动前启动的进程**。重启后才会看到 `抖动 X.X ms`。

**第二步：烧 `outputs/link_pc/06_slave_PCrelay_ec.bin`（从臂）**
`d61b579633cb9c1706b0b1f1463e846d`，171112 B。
主臂可一并烧 `05_master_PCrelay_ec.bin`（`973a2cc9a79fcfc93b5afaba6c091faa`），
也可以先不动。

**第三步：开流前先在从臂敲 `ec 0`**（停流时敲 `ec 1` 恢复回显）：

```
从臂> ec 0
  Console echo OFF (quiet). Type `ec 1` to restore.
```

脚本侧可以直接带：

```powershell
py tools\pc_relay.py --master COM12 --slave COM11 --hz 60 --slave-cmd "ec 0"
```

**第四步：跑 1~2 分钟，停流后在从臂敲 `lk`**，对比 `ring drop` 与
`reject streak max`。预期：`ring drop` 不再增长、`max` 从几十/上千降到个位数、
`watchdog` 次数归零。

## 5. 附：延迟账（顺带回答"还能不能再降"）

| 环节 | 现状 | 关掉回显后 |
|---|---|---|
| 从臂逐字符回显 | **3.39 ms/帧 + 22.4% 主循环** | **0** |
| 从臂收帧环余量 | 53 ms | 同样 53 ms，但不再被回显挤占 |
| 从臂主循环拍预算 @66 Hz | 411 µs（需 ≥2430 拍/s） | 显著放宽 |
| 主臂口 Latency Timer | 仍是驱动默认 16 ms（注册表实测 `<unset>`） | **未动，仍需去设备管理器改 1 ms** |
| 主臂采样节拍 | `sp 60` → 16.7 ms | 可 `sp 100` → 10 ms |

⇒ 回显关掉解决的是**冻结/拒帧**（体验里最刺眼的那块）；
**常数延迟那一块仍然是主臂口的 Latency Timer（16 ms），那一步只能你在
设备管理器里改**，我没法从命令行写注册表。
