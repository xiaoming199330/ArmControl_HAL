## 0. 先回答那个问题：UDP 容易丢包吗？

**在这个场景下不容易，但"不丢"不是靠 UDP，是靠"本地直连 + 低速 + 无拥塞"。**

三条硬事实：

| 事实 | 数字 | 出处 |
|---|---|---|
| 本项目 UDP 直连实测（真机） | **p50 1.03 ms / p99 6.82 ms / 0 超时 / 0% 板侧丢包** | 本文 §2B（2026-09-24） |
| 本项目 UDP 直连实测（更早，另一台/线） | p50 1.61 ms / p99 3.4 ms / 0 超时 / 547 fps | `docs/三链路延迟基准_实测报告_2026-09-22.md` |
| UDP 压到 1200 fps 仍不丢 | **实物 1199.7 fps，板侧 Δudp_cmd 全额到齐** | 本文 §2B |
| 遥操实际用量 | **50 Hz** = 上限的 **1/40** | `RC_cfg_final` / `teleop` 默认 |
| UDP 载荷 | 一帧 12 ~ 17 字节 + 8 字节 UDP 头 | `STREAM_JOINTS` = 12 B |

以太网帧最小 64 字节，所以**每帧都在浪费带宽** —— 链路利用率不到 1%。
在这个状态下丢包概率 ≈ 网卡/交换机缓冲溢出的概率，而 50 Hz / 12 字节压不出溢出。

**那 UDP 的风险到底是什么？** 不是"容易丢"，是**丢了没人告诉你**：

| 命令类型 | 丢一帧的后果 | 严重度 |
|---|---|---|
| `PING` / `GET_STATUS` / `GET_*` 查询 | 这次读失败，重发即可 | 无 |
| `STREAM_JOINTS` 流帧 | 这一帧的位置增量丢了，**下一帧就补上了**（本来就只有增量） | 无 —— 设计如此 |
| `MOVE_JOINTS` 运动命令 | **这条命令根本没执行**，而你可能以为它执行了 | 高 |
| `PARAM_WRITE` 写参数 | 参数没写进去，回读才发现 | 中 |
| `CMD ≥ 0x80` | 固件**故意不回**（防死锁）⇒ 看不出是丢还是设计如此 | 设计如此 |

所以正确的说法是：**UDP 不是"容易丢"，是"丢了你不知道"**。
关键命令（运动 / 写参数）必须自己补 `SEQ 匹配 + 超时 + 重试`，或者干脆走 HTTP 借 TCP 的可靠性。

## 1. 但 HTTP 没法直接跑在板子上 —— 原因很简单

板子的网口栈是**手写的裸 MAC + ARP + IPv4 + ICMP + UDP**：

```
Core/Src/arm_net.c   1430 行
  ├─ eth_send()            裸帧收发（HAL_ETH）
  ├─ ip_checksum()         IPv4 头校验和
  ├─ udp_send()            逐字段写 UDP 头
  └─ ICMP echo reply       ping 应答

Core/Inc/arm_net.h    225 行
```

**没有 lwIP、没有 Middlewares 目录、没有 TCP。** 所以：

* ❌ 不能"给板子发 HTTP" —— 没有任何东西监听 80 端口，也没法三次握手。
* ❌ 想真在 MCU 上做 TCP，要自己写：滑动窗口 / 重传定时器 / 乱序重组 /
  拥塞控制（慢启动、快重传、快恢复）/ 零窗口探测。**工作量远超收益**，
  而且会碰红线 4（本工程**没有看门狗**，TCP 状态机卡住就是整机卡住）。
* ✅ 正确做法：**HTTP 放在 PC 侧做边车**。这本来就是市面上的常规架构 ——
  上位机软件从来的不会直连 UDP。

```
┌──────────┐  HTTP/1.1 (TCP keep-alive)   ┌──────────────┐  逻辑包 UDP    ┌──────┐
│  上位机  │ ───────────────────────────► │ http_bridge  │ ────────────► │ 臂   │
│ GUI/脚本 │ ◄─────────────────────────── │  (PC 侧)     │ ◄──────────── │ :5000│
└──────────┘       JSON + 头部             └──────────────┘   12 B 回包     └──────┘
             ← loopback，<1 ms →                ← 这一段才是被测链路 →
```

边车**不改协议、不加语义**，只是翻译。所以 HTTP 上看到的行为与 UDP 直连**完全一致**
（错误码、丢读哨兵、静默钳制都原样透传）。

## 2. loopback 实测（假臂 + 边车，2026-09-24）

命令：

```bash
# 一个窗口起假臂
cd sdk_package && python -m arm_sdk.mock_server --host 127.0.0.1 --port 5000
# 另一个窗口跑对照
python tools/udp_vs_http_bench.py --mode all --target-ip 127.0.0.1 \
       --n 400 --rates 50,100,200,400,800,1200 --sec 2 --burst 300
```

### 2.1 延迟（400 次 PING 往返）

| 形态 | p50 | p90 | p99 | max | 超时率 |
|---|---|---|---|---|---|
| **udp**（直连） | **2.14 ms** | 2.98 | 4.48 | 5.48 | 0.0% |
| http-close（每次新建 TCP） | 5.71 ms | 7.98 | 13.81 | 20.15 | 0.0% |
| **http-keepalive**（复用连接） | **2.80 ms** | 3.82 | 4.78 | 6.39 | 0.0% |

关键的拆解（边车在每个响应里带 `X-Arm-Rtt-Ms`，把两段分开）：

| 形态 | 链路 RTT p50 | HTTP 开销 p50 | 说明 |
|---|---|---|---|
| udp | = 端到端 2.14 ms | 0（无 HTTP） | —— |
| http-close | 2.41 ms | **+3.31 ms** | 建连（SYN/ACK）+ 头部 + JSON |
| http-keepalive | 1.83 ms | **+0.97 ms** | 只剩头部 + JSON |

> **⭐ 最大的一个数：把连接复用起来，省 2.91 ms / 次（51%）。**
> 用 Python 就一句话 —— `requests.Session()` 或 `http.client.HTTPConnection` 复用，
> 别每发一条命令 `requests.get()` 一次。C# 用 `HttpClient` 单例（默认就复用）。
> **这一条比"选 UDP 还是 HTTP"更值钱。**

### 2.2 速率阶梯（每档 2 s，绝对时间轴）

| 目标 fps | udp 实测 | http-close 实测 | http-keepalive 实测 |
|---|---|---|---|
| 50 | 49.9 | 49.9 | 49.7 |
| 100 | 99.8 | 99.5 | 99.8 |
| 200 | 199.7 | 155.5 | 199.8 |
| 400 | 353.1 | 157.9 | 188.8 |
| 800 | 472.6 | 142.2 | 256.2 |
| 1200 | 439.4 | 117.9 | 245.3 |

**超时率全程 0.0%，三种形态都是。**

⚠ **这里的 fps 天花板不是链路，是基准程序自己**（单线程 Python，客户端 + 采样 +
JSON 序列化都在一个进程里）。所以：

* **可用的结论**：HTTP-close ≈ 155 fps 就到顶、keep-alive ≈ 250 fps 才到顶
  ⇒ **HTTP 的吞吐只有 UDP 的 1/2 ~ 1/3**，而且这个比例由"每次多付 3.3 ms / 1.0 ms"决定，
  换成 C#/C++ 实现比例关系不变。
* **不可用的结论**：不能说"UDP 只能跑 470 fps" —— 真机实测已经到过 547 fps
  （而且那也不是上限，是当时压到那儿）。

### 2.3 突发（连发不等回包，只有 UDP 能做）

```
连发 300 条 → 0.391 s 发完（767 fps 瞬时）
臂侧 Δudp_cmd = 测不到（假臂无 nx）
```

这个模式是**唯一能压出臂侧收包能力**的测法：顺序发的时候 RTT 本身就是限速器
（最多 1/RTT ≈ 400~600 fps），压不到 MCU 的极限。真机上跑这个 + `nx` 前后做差，
才知道臂在 1200 fps 突发下会不会掉帧。

### 2.4 丢包：loopback 这组为什么全是"—"

假臂没有 `nx` 命令，所以**板侧计数测不到**。工具在这种情况下如实报"—"，
**不会编一个 0% 出来**。真丢包看下一节 §2B。

## 2B. ★ 真机实测（结论以这组为准）

> 采集时间：2026-09-24 18:1x ｜ 目标：`net://192.168.7.120:5000`
> 板内固件：`ARM-NET-0924J` ｜ PHY：`state RUN (phy found addr 0)`，`link UP, 100M full-duplex`
> 探针：`PING(0x01)` 只读、不动臂 ｜ 边车跑在本机 in-process

### 2B.1 延迟（500 次 PING 往返）

| 形态 | 样本 | 成功 | 超时 | p50 | p90 | p99 | max | 链路RTT p50 | **HTTP 开销 p50** |
|---|---|---|---|---|---|---|---|---|---|
| **udp 直连** | 500 | 500 | **0** | **1.03 ms** | 3.12 ms | 6.82 ms | 46.96 ms | — | — |
| http-close（每次新建 TCP） | 500 | 500 | **0** | 3.95 ms | 14.92 ms | **48.04 ms** | 164.21 ms | 0.87 ms | **+3.08 ms** |
| **http-keepalive（复用连接）** | 500 | 500 | **0** | 1.71 ms | 2.97 ms | 4.92 ms | 9.86 ms | 0.62 ms | **+1.08 ms** |

三个必须看出来的点：

1. **UDP p50 1.03 ms** —— 500 次一次没超时。对比 loopback 假臂（0.52 ms），
   真机慢一倍，这 0.5 ms 就是**真实网络 + MCU 主循环**的钱，跑不掉也不重要。
2. **`http-close` 的 p99 = 48.04 ms**，是它自己 p50 的 **12 倍**。
   因为每个 3 次握手都可能被调度/重传拖住 ⇒ **用 `requests.get()` 循环的上位机，
   卡顿会一阵一阵地来**。这就是"必须复用连接"的实证。
3. **链路段（边车→臂）只要 0.62~0.87 ms**，其余全是 HTTP/TCP/JSON 自己的开销。
   `X-Arm-Rtt-Ms` 响应头就是让你能把这笔账分开算的。

### 2B.2 速率阶梯（每档 3 s，绝对时间轴）

| 目标 | udp 实测 | http-close 实测 | http-keepalive 实测 | 超时率 | **板侧丢包** |
|---|---|---|---|---|---|
| 50 fps | **50.0** | 49.8 | **50.0** | 0.0% | **0.0%** |
| 100 fps | **100.0** | 99.9 | 99.9 | 0.0% | **0.0%** |
| 200 fps | **199.9** | 195.0 | 199.8 | 0.0% | **0.0%** |
| 400 fps | **399.8** | 280.7 | 399.6 | 0.0% | **0.0%** |
| 800 fps | **797.7** | 306.7 | 486.9 | 0.0% | **0.0%** |
| 1200 fps | **1199.7** | 315.5 | 491.6 | 0.0% | **0.0%** |

**18 档全部：超时率 0.0% + 板侧丢包 0.0%。**

- **UDP 一条都没掉队**，连 1200 fps 都精确跟上（1199.7）。而遥操只要 50 Hz ⇒ **余量 24 倍**。
- **`http-close` 在 ~315 fps 到顶**，`http-keepalive` 在 ~491 fps 到顶。
  HTTP 的限速器就是 RTT：一次一个来回，跑不出 RTT 的倒数。
- 注意 `http-close@400fps→68.1`（首轮 loopback）那种**抖动**，真机上表现为
  实测曲线在小目标时还能跟上、一过拐点就整段塌下去 —— 低速率下 HTTP 够用，
  但**拐点在哪取决于机器负载，不是常数** ⇒ 不能拿它当运动控制通道。

### 2B.3 突发（连发不等回包）

```text
连发 400 条 → 0.037 s 发完（10804.5 fps 瞬时）
臂侧 Δudp_cmd = 806 / 400  ⇒ 丢 0.0%
```

**怎么读这个 806**：Δ 是"这段时间内臂总共收了多少条 UDP 命令"的差值，
包含了同一窗口里 `nx` 自身翻页等其他命令，所以它只保证"**≥ 400 条全部到达**"，
不能反过来解读成"臂只能收 806 条"。判定规则也因此是对的：**Δ < N 才算丢**。

结论：**臂侧在 10000+ fps 的瞬时突发下都不掉**，主循环收包能力远超需要。

### 2B.4 链路本身干净吗？看 `nx` 的累计错误计数

真机 `nx` 全文（`text_exec("nx")`，**1050 B，需自动翻页**）：

```text
  ===== nx NET status =====
  state    : RUN (phy found addr 0)
  link     : UP, 100M full-duplex
  addr     : udp://192.168.7.120:5000  (MAC 02:4E:45:54:00:01)
  rx/tx    : 55210/55142 帧   udp cmd=55128  crc err=0  tx err=0
  peer     : arp=12  icmp(ping)=3
```

跑完整套基准（约 2 万条命令）之后：**`crc err=0`、`tx err=0`**。
这两个数是**累计值**，长期为 0 才叫链路真干净：

| 计数 | 涨起来说明什么 |
|---|---|
| `crc err` | 链路误码 —— 网线/接口/接地问题，不是软件问题 |
| `tx err` | 板子发不出去 —— 描述符/缓冲耗尽，再快就会丢 |
| `rx/tx` 差 | rx 含 ARP/ICMP 等非 UDP 帧，**不等于**丢包（本例 55210 vs 55142） |

### 2B.5 与 loopback 的对照（同一个工具，两种环境）

| 指标 | loopback（假臂） | **真机** | 差额说明 |
|---|---|---|---|
| udp p50 | 0.52 ms | **1.03 ms** | +0.5 ms = 真实网络 + MCU 主循环 |
| http-close 开销 | +5.39 ms | **+3.08 ms** | loopback 上进程争抢更严重 |
| http-keepalive 开销 | +1.35 ms | **+1.08 ms** | 同上 |
| UDP 吞吐 | 928.7 fps（已到顶） | **1199.7 fps（追平目标）** | 假臂的 Python 模拟反而是瓶颈 |
| 板侧丢包 | 测不到 | **0.0%** | 只有真机能测 |

**相对结论两边一致（`udp ≈ keepalive` ≪ `close`），绝对值必须看真机。**

## 3. 为什么"板侧计数"是测丢包的唯一干净办法

本协议**没有传输层 ACK**。PC 侧只能数"超时"，但超时是三种原因的并集：

```
超时 = (a) 请求包在路上丢了
     ∪ (b) 臂收到了、回包在路上丢了      ← 只影响这一次观测
     ∪ (c) 臂收下了但主循环还没处理完    ← 队列/忙
```

要把 (a)(c) 和 (b) 分开，只能问板子自己收了几条。臂的 `nx` 正好有这个（**真机实际输出**）：

```text
  rx/tx    : 55210/55142 帧   udp cmd=55128  crc err=0  tx err=0
                              ^^^^^^^^^^^^ 累计值 ⇒ 做差
```

方法：

```
PC 发出 N 条  →  臂侧 Δudp_cmd = M
单向丢包率 = (N − M) / N            ← 不掺回程丢包，最干净
```

工具已经内置（`--no-board` 可关）：

```bash
python tools/udp_vs_http_bench.py --mode sweep --target-ip 192.168.7.120
# 每档扫频前后各读一次 nx，自动算 Δudp_cmd 并打印「板侧丢包」
```

> ### ⚠⚠ 实现这个功能时踩过的坑（2026-09-24，真机）
>
> **`nx` 全文 1050~1311 B，必须走自动翻页；只取第一页会静默失效。**
>
> SDK 有两个方法，名字很像、行为完全不同：
>
> | 方法 | 行为 | 用于 |
> |---|---|---|
> | `client.text_exec(cmd)` | **自动** `TEXT_FETCH` 翻页并**按字节**拼接，最后统一 UTF-8 解码 | ★ 读长输出（`nx` / `h` / `i` / `L`） |
> | `client.text_out(cmd)` | **只取第一页**（58 字符）+ 保留分页元信息 | 只要你自己控节奏时 |
>
> 第一版 `read_nx()` 用了 `text_out("nx")`，只拿到 63 个字符：
>
> ```text
> '\r\n  ===== nx NET status =====\r\n  state    : RUN (phy found'
> ```
>
> `udp cmd=` 在第 20 页附近 ⇒ 正则**永远匹配不到** ⇒ 自动退化成
> "读不到板侧计数"，而这一步正是**唯一**能测真丢包的手段。
> 更糟的是当时 `except Exception: return None` 把原因也吞了，
> 现象看起来像"假臂没有 nx / 链路不通"，把排查方向整个带偏。
>
> **两条纪律**（已写进 `tools/udp_vs_http_bench.py`）：
> 1. 读 `nx`/`h`/`i` 这类长输出 **一律用 `text_exec`**；
> 2. 失败**必须打印原因**（哪怕只打一次），不许静默 `return None`。

**注意两个 `crc err` / `tx err` 也是指标**：`crc err` 涨 = 链路误码（线/接口问题），
`tx err` 涨 = 板子发不出去（描述符耗尽）。这两个长期为 0 才算链路真干净 ——
真机实测跑完约 2 万条命令后**两者仍为 0**（见 §2B.4）。

## 4. 选型结论

| 用途 | 选谁 | 为什么 |
|---|---|---|
| **50 Hz 遥操流**（`STREAM_JOINTS`） | **UDP 直连** | 丢帧无所谓（只有增量，下帧补上）；HTTP 每帧要等应答 ⇒ 帧率被 RTT 锁死在 ~250 fps 以下，且**卡住时你不知道卡了多久** |
| **急停 / `STOP`** | **UDP 直连** | 少一跳就少一个故障点，绝不能让 HTTP/TCP 重传挡在中间 |
| **配置 / 查询 / 写参数**（`GET_*` / `PARAM_WRITE`） | **HTTP 边车**（keep-alive） | TCP 保证送达；JSON 好调试；Postman / `requests` / `HttpClient` 直接用 |
| **上位机 GUI 的常规按钮** | **HTTP 边车** | 人手点击 ~10 Hz，多付 1 ms 完全无感，换来不用自己处理 CRC/SEQ/分页 |
| **示教文件上传下载** | **HTTP 边车** | 天然适合 HTTP 的请求-响应形态，大块数据 HTTP 更省心 |

**一句话：两个并存，不是二选一。**
遥操/急停走 UDP 拿低延迟无中间态；其余走 HTTP 拿可靠性和生态。

### 代价清单（说清楚就不可怕）

| 引入 HTTP 边车后多出来的 | 量级 | 对策 |
|---|---|---|
| 延迟 | +1 ms（keep-alive）/ +3.3 ms（每次新建） | **复用连接**（这一条解决 90%） |
| 吞吐上限 | UDP 的 1/2 ~ 1/3 | 只有遥操流在乎 ⇒ 遥操走 UDP |
| 额外进程 | 一个 Python 边车 | `systemd` 常驻（Linux）/ 计划任务（Windows） |
| 额外故障点 | 边车挂了 = 上位机失联 | 边车崩溃不影响进行中的 UDP 遥操（两条独立路径）⚠ 但**边车重启会丢当前状态**，请保证它无状态（本实现已是） |
| 安全 | HTTP 无鉴权 | 默认只绑 `127.0.0.1`；**别改成 `0.0.0.0`** |

>     --n 500 --rates 50,100,200,400,800,1200 --sec 3 --burst 400
> ```
>
> 会报 **`一元运算符"--"后面缺少表达式`** / `表达式或语句中包含意外的标记"n"`。
> 原因：**PowerShell 不支持 bash 的反斜杠 `\` 续行**（bash/POSIX 专有），
> 第二行被当成新语句，行首的 `--n` 于是被解析成"一元 `--` 运算符"。
>
> **三种正确做法，随便挑一种：**
>
> ```powershell
> # ① 就写一行（最省事）
> python tools/udp_vs_http_bench.py --mode all --target-ip 192.168.7.120 --n 500 --rates 50,100,200,400,800,1200 --sec 3 --burst 400 --with-burst
>
> # ② 用 PowerShell 自己的续行符：反引号 ` （不是 \）
> python tools/udp_vs_http_bench.py --mode all `
>     --target-ip 192.168.7.120 `
>     --n 500
>
> # ③ ★ 直接用封装好的入口（推荐，参数有默认值、退出码有解释）
> .\tools\bench.ps1                      # 默认 192.168.7.120，跑全套
> .\tools\bench.ps1 -Mode rtt -N 1000     # 只测延迟
> .\tools\bench.ps1 -SelfTest             # 离线自检，不连板子
> ```
>
> `tools\bench.bat` 是同样功能的 CMD/双击版（`bench.bat [IP] [额外参数...]`）。
> 它俩会自己设好 `PYTHONUTF8=1` 并加 `-X utf8`，避免中文/emoji 输出在
> 中文 Windows 上 `UnicodeEncodeError` 把脚本打死。

> ⚠ `--burst N` 只是设**连发条数**，要真正跑突发模式还得加 `--with-burst`。
> 只写 `--burst 400` 不会报错，但 burst 段不会执行 —— 别对着空结果找数。

**上真机前的纪律**（照 `docs/工程红线速查_2026-09-17.md`）：

* 探针只用 `PING(0x01)` —— 只读、必有应答、**不动任何东西**（工具已固定）。
* 网口要先 `link net` → `link save` → **按 RESET**（链路不热切换，红线 69）。
* ⚠ 如果顺手要动臂：先串口 `m 180 180 180 180 180 180 15` 回中位；
  **绝对不要用 `M a`**（那是标定，会废掉量纲基准）。
* 烧录/复位必丢力矩、臂会下沉（实测 J2 曾掉到距下限仅 1.3°）。
* ⚠ **`TEXT_EXEC` 只能发"只读"文本命令**。顺手发别的会踩雷：
  `i` = 初始化舵机（**Torque ON 抱闸**，现场实测误发过一次）、
  `zr` = 零位复位、`M a` = 标定。要看状态用 `nx` / `s` / `L` / `h`。

**预测 vs 实测**（§2B 已采，留此表供换线/换板后对照）：

| 指标 | 当初预期 | **真机实测** | 差在哪 |
|---|---|---|---|
| UDP p50 | ~1.6 ms | **1.03 ms** | 比预期还好 |
| UDP p99 | ~3.4 ms | **6.82 ms** | 略差，但 500 次 0 超时 |
| UDP 零超时速率上限 | ≥ 547 fps | **≥ 1199.7 fps** | 预期太保守 |
| HTTP keep-alive 额外开销 | 1 ~ 2 ms | **1.08 ms** | 落在区间内 ✔ |
| HTTP 吞吐上限 | 200 ~ 400 fps | **keepalive 491 / close 315** | keepalive 超预期 |

**如果真机上 HTTP 的额外开销远大于 2 ms**，第一嫌疑是**上位机没复用连接**
（每次 SYN/ACK = 一个额外 RTT）—— 先查这一条，别去怀疑链路。

## 7. 一句话总括

> **UDP 不容易丢包，容易让人不知道丢了。**
>
> 真机实测（§2B）：UDP **p50 1.03 ms**，压到 **1199.7 fps** 时
> **超时 0.0% + 板侧丢包 0.0%**，`crc err` / `tx err` 累计仍为 0。
> 而遥操只要 50 Hz ⇒ 余量 **24 倍**。
>
> 板子没有 TCP ⇒ HTTP 只能做在 PC 侧边车；边车把延迟多付 **1.08 ms（连接复用后）**，
> 把吞吐砍到 **1/2.4**。
>
> 所以：**遥操/急停走 UDP，配置/查询/写参数走 HTTP 边车**，两条路并存。
> 而且无论走哪条，**HTTP 客户端一定复用连接** —— 真机实测这一条省 **2.25 ms/次（57%）**，
> 比"选 UDP 还是 HTTP"更值钱。
